# Задания: задание кластера

## Задание кластера (`cluster_task`, `clusters/NN.md`)

- «Данные» — из ядра (`prompt_builder_service`) с `normalize_evidence=False`: ID и время в
  логе сохраняются. Каждый кусок данных идёт под своим id (`source_ids=True`): `S1` —
  сообщение, `S2` — трейс, дальше блоки отобранного лога, например
  `--- [S3 · лог app.log · строки 120–134 · тест createOrder] ---` (пометка строк из
  `core-logs.md` уходит в заголовок). Пометки отбора (пропуски, «не вошло», пояснение и итог
  обрезки) остаются в данных без id.
- Лог операции (ядро — `core-logs.md`, «Операция теста»): у каждого теста строка «Операция
  теста: operUID=…» (его `correlation_hint`, без id куска, не цитируется; прежнего раздела
  «Корреляция запроса» кластера нет). Лог другого участника — только отдельным примером «с
  логом приложения» со своим сообщением и операцией, в том числе когда пример у кластера
  один: под сообщением представителя чужой лог выглядел бы логом его операции. У теста был
  общий лог (`operation_logs`), а записей сервиса нет (`has_service_log`: секции «файл»
  или «журнал»; HTTP-ответ лог не заменяет — ревью Codex) — после лога пометка
  `[лог операции не найден: …]` (`log_note_for`; id неизвестен — так и сказано). В задании
  нет кусков «лог»/«журнал» ни у одного примера (`_quotes_service_log`) — флаг
  `log_not_found` и вариант задания «лог операции не найден» (`build_task_text(
  log_not_found=True)`, `_LOG_NOT_FOUND_MISSING`). Вариант задания выбирается по кускам
  записей сервиса (`has_log = _quotes_service_log`), HTTP-ответ — симптом (`_has_symptom`,
  и рядом с записями сервиса — тогда «симптом + лог»): иначе при одном HTTP-ответе задание
  велело разбирать «лог приложения» (ревью Codex). В
  записи кластера `log_not_found: true`, и
  `validate_analysis(log_not_found=True)` не примет «НЕ ХВАТАЕТ» без слова «лог»
  (`LOG_NOT_FOUND_ERROR`).
- Примеры (шаг 4): больше одного примера у кластера (`example_tests`; ни у одного нет лога, а
  у участника есть — он добавляется примером «с логом приложения») — данные идут блоками
  «### Пример N — <роль> · тест …» (`build_cluster_examples_prompt`), id кусков общие.
  «Данные остальных тестов группы в задание не вошли» — только если в группе есть тесты вне
  примеров (иначе это неправда, и модель переносила её в «НЕ ХВАТАЕТ»).
  Лимиты сообщения, трейса и лога делятся: первому (типичному) половина, остальным поровну
  (`example_shares`); лог каждого отбирается `focus_log` под свою долю. Трейс, не влезающий
  в долю, заменяется сжатым (`cluster_task.short_trace`: сообщение исключения целиком — все
  строки до первого кадра, expected/actual у AssertJ бывают на следующих строках, — затем
  `Caused by` и кадры проекта; у Python сообщение после последнего кадра). Кадров берётся
  столько, сколько влезает в долю рядом с сообщением: обрезка с начала оставляла кадры JUnit
  без кадра теста, а у Python отрезала сообщение в конце. «Кадры стека из кода проекта» — только по трейсу представителя: кадры каждого
  примера уже в его сжатом трейсе, отдельный раздел дублировал бы их. Сообщение и трейс,
  совпадающие с первым примером, заменяются строкой «такое же, как в примере 1». Один
  пример — прежний вид задания (данные представителя и источника лога). В записи кластера
  `examples` (чьи данные видела модель — по ним эталон считает видимость) и
  `example_blocks`; при `example_blocks > 1` в разборе обязательна «СОГЛАСОВАННОСТЬ: одна
  причина | разные проблемы — <чем отличаются> | недостаточно данных» (`consistency_errors`).
  Выбор однозначный: два варианта в тексте (перечисление, скопированный шаблон) или
  незаполненный заполнитель шаблона (`TEMPLATE_PLACEHOLDERS` — все `<…>` из шаблонов
  разбора, например `<чем отличаются примеры>`) — ошибка, иначе шаблон открывал бы общую
  правку для смешанной группы. Значения из данных в `<…>` (`<200>`, `<Подтверждено>`)
  допустимы.
- Бюджет: тест назван один раз («Данные теста: …» или шапка примера), в заголовке куска — только
  если кусок от другого теста; имена в заголовках — до 60 символов. Лог отбирается `fit_log`:
  `focus_log` под бюджет минус заголовки кусков (`log_header_overhead`), иначе сотня коротких
  ошибок с длинными именами раздувала задание в десятки раз.
- Реестр источников — `evidence/NN.sources.json` (`sources.py`): id → вид, тест (id и имя),
  секция и вложение (имя, id из `log_attachments`), строки и **ровно тот текст**, что видела
  модель. `evidence/NN.txt` не меняется: на нём держатся `match_cluster` и проверка
  признака. Плюс список тестов (без ссылок TestOps и без повторов шага),
  корреляция, кадры стека, подсказки по коду (`code_hints`). Раздел «Где искать код
  автотеста» печатается всегда: без подсказок — «исходник не удалось сопоставить» (подсказок
  нет и при нераспознанном или неоднозначном имени теста, так что «файлов нет» было бы
  неправдой) и «файлы из кадров стека — тоже»: подсказок нет, значит, кадры не сопоставились
  (`hints_for_cluster` пробует и их), открывать нечего. Отсылки «открой файлы из кадров» нет:
  модель угадывала путь и делала glob (стенд E07, E08). `RULES` разрешают открывать только
  файлы этого раздела и запрещают искать код (glob, grep_search, shell): поиск начинался и
  при готовой подсказке (E10 glob по `src/`, A01 `grep | sed` — искали классы приложения из
  лога). Строки стека без файловой позиции («Caused by», «Unknown Source», «Native Method»)
  идут разделом «Строки стек-трейса без файлов» (`has_frame_files`): в длинном трейсе
  фреймворка это бывает единственное указание на причину.

- Повторы (шаг 5, `retries.py`): после списка тестов — раздел «--- Повторы в TestOps ---»,
  если хоть у одного теста кластера были попытки (`FailedTestSummary.attempts`, считаются
  все участники, не только показанные в списке). Факты: у скольких тестов были повторы и
  сколько неудачных попыток; у каждого теста одна группа, по старшинству — «есть попытка с
  другой ошибкой» (до двух разных текстов, по 200 символов), «одна из попыток прошла»,
  «ошибка попыток неизвестна», «есть попытка со статусом skipped/unknown», «все попытки
  упали с той же ошибкой» (только если каждая разобранная попытка failed/broken с той же
  ошибкой). У одного теста — «Тест запускался
  повторно», без «у N тестов»; число попыток у группы — «всего по группе». Есть
  `attempts_omitted` (ядро хранит последние 5 попыток) — число и «все попытки упали с той же
  ошибкой» говорят о «разобранных», в заголовке — «более ранних попыток не разобрано: M». После пустой
  строки — правило (`TASK_NOTE`) с подписью «Правило скилла (не данные TestOps)», иначе оно
  читается как продолжение данных под `UNTRUSTED_NOTE`: повторы говорят о
  воспроизводимости, ни один факт раздела (в том числе прошедшая попытка) не довод за
  категорию; в СОГЛАСОВАННОСТЬ ошибки попыток не входят; раздел не цитировать (он есть и в
  списках нецитируемого — `_OBSERVATIONS_NOTE`, `analysis-format.md`). Есть попытка с другой
  ошибкой — ещё `TASK_NOTE_DIFFERENT`: по ней категорию не выбирать (ConnectionRefused
  попытки тянул бы к «окружению»), в ПРИЧИНУ и КАК ИСПРАВИТЬ не переносить, упомянуть не
  больше чем фразой в ЧТО СЛОМАЛОСЬ. Правило — в разделе, а не в `RULES`: директива
  показывается только там, где есть повторы. Формат разбора не меняется.
  Группа одного теста — `retry_group` (им же считает `retry_facts`; отбор кандидатов
  перезапуска — `skill-rerun-candidates.md`).
- «Правила» и «Задание» (`RULES`, `build_task_text`) принадлежат скиллу. Каждая директива
  сказана один раз; варианты задания — симптом + лог / только лог / только симптом / мало
  данных / есть записи базы знаний; есть категория «неизвестно».
- «Только симптом» значит, что фрагмента лога в задании нет, а был ли лог — неизвестно:
  задание запрещает писать «лог пуст / без ошибок» (модель выдавала это за факт, когда
  вложений не было вовсе) и не велит говорить, что лога нет: обязательное начало «лога
  приложения в данных нет, анализ построен …» (и «лог операции не найден, …») убрано — в
  проектах без логов оно стояло у каждой проблемы (решение пользователя: отсутствие логов не
  повод не делать выводов). «Лог не обязателен»: однозначная ошибка в сообщении, трейсе или
  HTTP-ответе — вывод по ней.
- Правило «пиши простым языком»: тексты разборов попадают в отчёт как есть.

- Наличие контрактных директив проверяет `tests/test_skill_prompts.py`: сокращая текст,
  не теряйте их. Поведение модели проверяется отдельно через `skill-evaluation`.
