# Память скилла: обратная связь и история

## Обратная связь (`feedback`)

Отказы `remember` (`STATUS: fix`) считаются подряд по проблеме в `state.json`
(`refusals`, `feedback.MAX_REFUSALS` = 3): ответ начинается с «Попытка N из 3», третий отказ —
`STATUS: error` без «Затем выполни» (показать замечания пользователю и не повторять), счёт
после него и после успешного `remember` начинается заново. Лимита попыток, как у `next`, у
`remember` раньше не было, и модель могла повторять его бесконечно.

Успешный remember из feedback оставляет `state.accepted_feedback[file_id]`: SHA256 точного
текста, run_uid, запись и папку базы знаний, хеш категории/причины/шагов/признака записи.
Отметку пишет только успешное сохранение; отказ её не создаёт. Общий источник состояния
по ней принимает исправление инженера в отчёте и снимке. Правка feedback, смена смысловых
полей записи, удаление/отказ/переназначение записи отменяют действие отметки; даты,
посторонние подтверждения тестов и другие метаданные — нет. Сохранение из другого
источника снимает отметку и записывает точный хеш старого feedback в ignored_feedback,
чтобы он не блокировал новый диагноз; редактирование этого файла снова делает его входом
для remember. Сам файл инженера не удаляется.

**Вопрос после отчёта** (решение пользователя 2026-10-26): `done` просит спросить, какие
разборы верны (`cli._kb_question`), — первым пунктом «После отчёта», до правок и перезапуска:
за цепочкой «правка → проверка перезапуском» он терялся (ревью исполнителя). Команда — с
местом для номеров (`remember N1 N2 … --from-analysis`) и «верны все» — списком: готовая со
всеми номерами при правиле «команды — как есть» сохраняла бы и разбор, названный неверным.
Повторно о тех же номерах не спрашивается. Номера —
`cli._kb_offer`: принятые разборы агента с категорией, кроме `auto`, разобранных по базе знаний,
неоднородных, по отвергнутой записи или с другой категорией, чем у её записи
(`known.mismatched`), с подтверждённым выводом расширения и тех, что запись уже узнаёт точно
(`current_kb_matches` → `exact`: сохранённое второй раз не спрашиваем) — кроме узнанных точно
с логом, которого запись не видела, если разбор назвал эту запись (`_new_log_of`):
подтверждение добавит отпечаток, и в следующий раз проблема разберётся без модели. Группы «одна причина»
(объединил агент) — отдельно: их пользователь видел общей причиной, сохраняются по
`feedback.md` «Порядок», не `--from-analysis`. Проблемы с правкой агента (`separate`) отчёт
не объединяет — у каждой своя команда `apply`, и вопрос называет их отдельными номерами
(ревью Codex: иначе вопрос называл пункт «Проблема 1 и 2», которого в отчёте нет). Молчание — не согласие: без ответа ничего не
пишется (вариант «сохранять всё, что не отвергли» пользователь отклонил — догадки модели стали
бы подтверждёнными и повторялись бы без агента).

`remember N N… --from-analysis` (`feedback.remember_many`; несколько номеров — только с
`--from-analysis` и без `--entry`): каждый номер — общим путём `_remember`, отказ одного не
мешает остальным; ответ `saved` перечисляет сохранённое, «Не сохранены проблемы …» — суть
каждого отказа строкой (`_refusal_reason`), **без** его команд и формата (у «уже
подтверждали» и «запись уже есть» — и без команды обновления записи после `_UPDATE_PREFIX`:
оговорка «обновляй, только если…» стоит строкой ниже и в пакет не попадает, ревью Codex): их «Затем
выполни» модель выполнила бы подряд или написала бы файл обратной связи из своего разбора;
сохранить такие номера — только со слов пользователя. `next` — одной строкой в конце. Не
сохранилось ничего: один номер — ответ как у одной проблемы, несколько — `error` со
списком. «Уже подтверждали в записи R» (не у `--from-extension`) — ещё и строка: обновлять R,
только если пользователь уточняет её рецепт, другая причина — сначала `reject` (иначе
`--entry R` переписал бы запись для всех проблем, которые она узнаёт). Просьба `next` после
`reject`/`remember` (`_report_refresh`) называет и `analyze`.
`--from-analysis` у разбора со ссылкой `БАЗА ЗНАНИЙ: R` (и без `--entry` или `--entry R`)
**подтверждает R**: `record.confirm(signature, tests)`, текст записи (слова инженера) не
меняется, проверки текста не нужны; категория разбора не та, что у R, — отказ (`fix`:
спросить пользователя). Раньше создавалась запись-дубль из слов разбора: `owner` искался
только среди точных, а R узнавала по признаку.

`remember`/`reject` берут данные из `feedback/NN.md` (или подтверждённого разбора, см.
`--from-analysis` в `skill-protocol.md`); признак проверяется по `evidence/NN.txt`, секреты не
пишутся. Отчёт они не пересобирают; если изменённую запись называет хоть один разбор прогона
(`БАЗА ЗНАНИЙ:` того же `kb_dir`), вывод просит выполнить `next` (`_report_refresh`) — так
группа известной проблемы распадается после `reject`.

Третий источник `remember` — `--from-extension <имя>` (взаимоисключающий с
`--from-analysis`): последний `extensions/<имя>/*-NN.finding.json` (`confirmed.find_finding`),
проверка формы, `format_ok`, категории и секретов — `confirmed.check_finding`; признак —
признак кластера. Отказы здесь — `error` без «Попытки N из 3»: вывод расширения модель не
перепишет. `kb_fields` вывода — своё поле записи `<имя>` (`KBRecord.extra`, с `confirmed` и
`launch_id`), `confirmed/NN.json` — для отчёта (`skill-analysis-confirmed.md`), поэтому ответ всегда
просит `next`. Общий путь трёх источников — `feedback._Input`. Подтверждение снимается
(`confirmed.drop_confirmed`, ответ просит `next`): `remember` без `--from-extension` по той
же проблеме — пользователь поправил причину, а прежний `confirmed/NN.json` показывал бы
старую как подтверждённую (ревью Codex); `reject` записи, в которую подтверждение сохранено
(`kb_entry`).

## История (`history`)

- `alla-reports/history.jsonl` (локально). Повторы — по точной сигнатуре или записи базы
  знаний из другого `launch_id` **того же модуля** (`module` в записи истории; корень —
  `""`). Строки прежних версий (без `run`, `file_id` или `module`) при чтении пропускаются.
- В задание идёт только число повторов и дата; прошлые выводы модели не подаются — они
  анкерят её на непроверенной догадке.
- История только дописывается: каждый `done` сравнивает полные записи и пишет лишь
  изменённые/отсутствующие. `load_history` оставляет последнюю физическую строку
  `(run, file_id)` до фильтрации повторов. Это обновляет `kb_entry` независимо от хэша
  сводки.
- Даты исходные; число повторов считается по разным `launch_id`.
- `kb_entry` в записи — только подтверждённая ссылка (`known_issues.refs`): отвергнутая после
  разбора запись повторы не считает; после `reject` и `next` строка прогона перезаписывается.
