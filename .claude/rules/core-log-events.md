# Ядро: события лога

- Текстовый лог делится на события (`utils/log_events.py`): запись начинается строкой со
  временем (ISO, `dd.MM.yyyy`, `yyyy/MM/dd`, `HH:mm:ss.SSS`, Serilog `[HH:mm:ss ERR]` без долей секунды, syslog, JUL, в `[]`), logfmt
  `time=`, заголовком klog/glog `E1003 10:00:00.123456 12 file.go:42]` (уровень — первая
  буква: `I`/`W`/`E`/`F` → INFO/WARNING/ERROR/FATAL), Ruby `Logger` (Rails)
  `E, [2026-10-04T11:00:00.126776 #52] ERROR -- : …` (уровень — слово после `]`), .NET
  SimpleConsole `fail: Category[1]` строкой (`fail` → ERROR, `crit` → CRITICAL; без суффикса
  `[id]` и с текстом в той же строке — не запись; сообщение и исключение ниже с отступом —
  продолжение), Go `panic: …` и `fatal error: …` с
  колонки 0 (уровни `PANIC`, `FATAL`; `[signal …]`, дамп goroutine, кадры
  `\tfile.go:42 +0x…`, пустые строки и вложенный `\tpanic:` — продолжение до следующей
  записи), Java `Exception in thread "…" класс` (событие-исключение без времени), Python
  `ERROR:root:`, `Traceback` или строкой исключения перед кадрами `at`; остальные строки —
  продолжение. Уровень — только в позиции уровня (первые 6 мест после времени, в скобках
  регистр любой; группа `[…]` из нескольких слов — MDC, поток с пробелами — одно место, её
  первое слово проверяется: `[INFO ]`) или самостоятельное поле logfmt `level=`/`lvl=`/
  `severity=` (значения в кавычках читаются целиком: `msg="… level=info …"` уровнем не
  считается): `ERROR` в тексте INFO не ошибка, WARN не ошибка. Уровни ошибки —
  `log_events.ERROR_LEVELS`, включая `PANIC`/`DPANIC` (logrus, zap, zerolog). JUL «дата класс метод» + `SEVERE:` — одно событие
  (`LogEvent.level_line` = 1: уровень и причина во второй строке); Traceback кончается строкой
  исключения. `ErrorBlocksHandler` берёт события-ошибки, Traceback и исключения, и
  записи с полями ошибки ответа. Для лога
  `<ISO-время> [ERROR] …` извлечение побайтово прежнее (эталон старой функции —
  `test_core_log_events.py`).
- **Поля ошибки ответа** (`log_events.has_error_fields`) делают ошибкой событие любого уровня
  (`LogEvent.reports_error`, по нему фильтрует `error_events`): бизнес-ошибку сервисы пишут на
  INFO — `[INFO] … {"errorCode":6, "errorMessage":"счет закрыт"}`; раньше её отбрасывал отбор по
  уровню, в том числе до отбора по операции. Поле — JSON (`"key":`),
  `key=`/`key:` или XML (`<ns:key>…</`), имя — любой префикс + `error|err|fault` + `_?` +
  `code|message|msg|text|description|desc|string` (`bizErrorCode`, `error_message`, `faultString`;
  регистр любой; `errorCount` и `"error":` — нет). Ответ внутри строкового поля JSON-записи
  (`"message":"Response {\"errorCode\":6}"`) — тоже поле (ревью Codex: иначе INFO-запись
  отбрасывалась): вложенный уровень (до 3) читается в содержимом строкового значения с
  экранированием, где снят ровно один уровень (`\"` → `"`, `\\` → `\`). Не все кавычки текста
  сразу — иначе `"errMsg":"\"account\" not found"` читалось пустым значением; и не весь текст
  заново — иначе прочитанное поле (`"errorCode":"RULE\"6"`) читалось второй раз, обрезанным
  (`errorcode=rule` у кодов 6 и 12 — общий ключ держал разные ошибки в одной проблеме). Значение
  в кавычках — с одним снятым уровнем экранирования (ревью Codex). Значение «успеха» ошибкой не делает: пусто,
  `null`/`none`/`nil`, `ok`/`success`, `false`, одни нули; объект и список — тоже нет.
  `is_error` прежний: продолжение стека (строка исключения после ошибки) решает только уровень,
  и INFO с полями ошибки следующее исключение не поглощает. `log_focus` даёт таким блокам тот
  же бонус и якоря, что ERROR-блокам. Разные бизнес-ошибки при одном сообщении разделяет
  gate по логу по кодам ошибки ответа (`error_field_codes`, `core-clustering.md`, «Кластеризация», п. 3).
- JSON-запись строкой (NDJSON: zap, zerolog, slog, logrus, logstash-logback-encoder, ECS,
  Log4j2 JsonTemplateLayout) — тоже начало записи, и в текстовом логе, и во вложении,
  определённом как json (`ErrorBlocksHandler` берёт `text` и `json`): строка с `{` (отступ из
  пробелов и табов допустим, показ — исходная строка), объект с
  полем уровня `level`/`lvl`/`severity`/`log.level` или `{"log": {"level": …}}`. Уровень —
  строка из уровней `log_events` в любом регистре; целое под `level` — шкала zerolog
  (−1…5: 3 — ERROR, 4 — FATAL, 5 — PANIC; 2 — WARN) или pino (10…60: 50 — ERROR, 60 — FATAL,
  40 — WARN); иное значение — уровень неизвестен,
  но запись отдельная. JSON без поля уровня (тело ответа после ERROR, ответ API во
  вложении) — как раньше: продолжение, событий-ошибок нет. Показ ошибки
  (`LogEvent.rendered`/`shown`): без многострочного стека — строка дословно; со стеком
  (многострочное поле на любой глубине, последняя часть имени — `stack_trace`,
  `stacktrace`, `stack`, `exception`, `extendedStackTrace`: `error.stack_trace`,
  `exception.stacktrace`) — заголовок `json.dumps` записи без этих полей и их строки ниже
  без пустых; пометка — строка записи. Многострочное сообщение (`msg`, `message`…) остаётся
  в заголовке с `\n`: строки под записью сигнатура берёт, только если в них есть признак
  ошибки, и `warehouse closed\nretry later` с `credentials revoked\nretry later` давали бы
  одну сигнатуру. Отрендеренный блок
  разбирается обратно в то же событие (сигнатура читает лог через `iter_events`).
  `HttpSignalsHandler` по-прежнему идёт после: поле `error` JSON-лога бывает и в секции
  `HTTP`, как у текстовых логов. Ошибка страницы браузера `{"type": "pageerror", …}`
  (Playwright, Puppeteer) — запись уровня ERROR. JSON-массив записей одним документом
  (`page-errors.json`, выгрузка браузерного лога Selenium `{"level": "SEVERE", …}`) —
  `ErrorBlocksHandler` разворачивает его в строки (`log_events.json_array_lines`), если
  **каждый** элемент — объект с полем уровня или `pageerror`: массив-ответ API логом не
  становится; номер строки в пометке — номер записи в массиве. Для отбора по операции такой
  массив — тоже лог (`log_operation_ids`, `HttpSignalsHandler` читают записи строками,
  `_log_text`): иначе его id попадали в свои, и ошибки чужих операций шли без отбора (ревью
  Codex). `iter_events` массив не
  разбирает (весь документ — одна строка или pretty JSON). Причина: в эталоне dev
  `one_problem_resources` ошибка скрипта страницы была только в таком массиве, и четыре теста
  с разными локаторами давали четыре проблемы. Не распознаются: многострочный pretty JSON
  отдельных записей (Log4j2 JsonLayout `compact=false`), zap console с epoch-временем и
  уровнем строчными, logrus TTY `ERRO[0001]`.
- **Префикс сборщика логов контейнера** (`log_events._collector_prefixes`): `docker logs -t`,
  `kubectl logs --timestamps`, файл CRI `/var/log/containers` ставят время RFC3339 перед
  **каждой** строкой вывода (CRI — ещё `stdout|stderr F|P`), и раньше каждая строка стека
  становилась записью без уровня: отбор ошибок выбрасывал исключение, кадры и `Caused by`, в
  задание шла одна строка `ERROR … failed` (dev `collector_prefixed_logs`: потеря
  доказательств 4/4 → 0/4). Вывод сборщика — префикс у ≥ 90 % непустых строк и у половины из
  них 7–9 знаков долей: сборщик пишет наносекунды (kubectl — без хвостовых нулей), а лог
  приложения со своим ISO-временем (`2026-…T…:…:….123Z ERROR`, Spring Boot 3 в UTC с `  INFO`)
  — миллисекунды или микросекунды, и стек у него без времени, — его не трогаем. Тело строки —
  без префикса; признаки начала записи, уровень, JSON, Traceback, исключение со стеком
  ищутся в нём. Если хоть одно тело начинает запись (у приложения своё время, уровень,
  JSON), лог разбирается и **показывается** по телам, как без сборщика: блоки, пометки строк
  (номера прежние) и всё после извлечения те же — все форматы `FORMAT_LOGS` под тремя
  сборщиками дают побайтово те же блоки. Исключение — строка с уровнем в позиции уровня
  (`[ERROR] …`, `[worker-1] ERROR …` соседнего процесса без своего времени, `Caused by: … ERROR:
  …` после WARN): у неё время сборщика, и она начинает запись (с префиксом в показе), как до
  сборщика, а не пристаёт к соседней INFO — иначе одна JSON-запись приложения переключала
  весь файл, и такая ошибка пропадала (ревью Codex, два прохода). Инвариант: строка с уровнем
  ошибки не теряет его из-за сборщика; не запись она только как продолжение стека идущей
  ошибки (`_continues` при ошибке без `closed`) и как вторая строка JUL `SEVERE: …`. Своих записей нет (`printStackTrace`,
  `console.log`) — запись начинает каждая строка вывода (уровень — первые слова тела), кроме
  продолжений (`_continues`: пустая, с отступом без уровня первым словом, `Caused by:`/
  `Suppressed:`, `... N more`, строка исключения, Traceback), и строки показываются с
  префиксом: другого времени у них нет. Цена второго случая: кадры с префиксом gate по логу
  кадрами не узнаёт (`_STACK_FRAME_RE` — с начала строки). Части длинной строки CRI (`P`) не
  склеиваются.
- Текст, начинающийся с `[`, считается JSON, только если за скобкой JSON-значение:
  `[2026-10-04 …]` и `[main] …` — текстовые логи.
