# Ядро `alla_core`

`scripts/alla_core/` — доступ к TestOps и анализ падений, на нём стоит `alla_skill_lib`.

- Состав: клиент TestOps, триаж, логи, кластеризация, сборка блока «Данные» для заданий
  (`services/prompt_builder_service.py`). Правил и «Задания» для модели в ядре нет — они в
  `alla_skill_lib` (см. `skill-analysis.md`); сигнатура проблемы — тоже там
  (`signature.py`, см. `skill-memory.md`).
- Происхождение: вендорено из серверного `src/alla` (коммит `e100909`), теперь обычный
  рукописный код: генератора, пометок GENERATED и drift-теста нет, правится напрямую, с
  тестами.
- Унаследованное от сервера, что скиллу может быть не нужно (поля под PostgreSQL, модели
  LLM), удалять осознанно: сверяться с импортами `alla_skill_lib` и тестами. Модели базы
  знаний и обратной связи сервера (`knowledge/`) уже удалены.
- Клиент TestOps только читает: методы записи сервера (комментарии, ссылки запуска) удалены,
  новые запросы — только `GET` (`POST` — лишь обмен токена в `auth.py`).

## Сбор данных

`TriageService` → `LogExtractionService` → `ClusteringService`, склеены в
`alla_skill_lib/pipeline.py`.

- `TriageReport.launch_created_ms` — `createdDate` прогона (`GET /api/launch/{id}`); `prepare`
  пишет его в `run.json` как `launch_created` (ISO 8601, UTC). Нужен расширениям: `sut-code`
  по нему выбирает ревизию приложения, если инженер её не назвал.

- **Полнота выгрузки** (`TriageReport.fetch`, `FetchInfo`; в `run.json` внутри `triage`,
  только числа). Результаты без повторов id (`_unique_results`: страницы идущего прогона
  сдвигаются); `results_reported` — `totalElements` последней страницы
  (`AllureTestOpsClient.last_total_elements`, у фейковых провайдеров нет — `None`);
  `execution_failed`/`detail_failed` — активные падения, чьё дерево шагов или запасной
  `GET /api/testresult/{id}` не получены после повторов (у них может не быть сообщения и
  шага — тест уйдёт не в ту проблему). `launch_closed` — поле `closed` прогона, `None` —
  TestOps его не прислал (тогда прогон идущим не считается). `fetch_warnings` — предупреждения
  прогона (`run.json` `warnings`, вывод `prepare`, отчёт) с командой `prepare <id> --fresh`:
  прогон не закрыт, получено меньше `totalElements`, данные тестов не получены. Лимит
  страниц (`max_pages`) проверяется по первой странице: `PaginationLimitError` с
  `pages_needed`, подсказка `errors.py` называет нужное значение `ALLURE_MAX_PAGES`.
- `hidden` results исключаются из статистики и анализа как retry/non-final, но до фильтрации
  связываются с финальными (`services/retry_linking.py`, шаг 5). Ключ — свой у каждой
  попытки (`attempt_key`), первое поле, значение которого у неё есть: `historyId`, затем
  `historyKey`, иначе `testCaseId` + `parameters` + `environment`; финальный ищется по тому же
  полю (финальные проиндексированы по каждому), на следующее поле попытка не переходит —
  другой `historyId` при том же `historyKey` — другое выполнение. Раньше ключ был один на
  прогон, и попытка без `historyId` в прогоне, где он есть у других, не связывалась (dev
  `retries_more`: 11 → 13 из 15). `RetryInfo.linked_by` — использованные поля через запятую.
  Контекст — `testCaseId` + `parameters` + `environment` (только если есть `testCaseId` и оба поля —
  список или словарь, пустой тоже; нет поля или `null` — контекст неизвестен, а не пуст;
  пары «имя=значение» отсортированы, `excluded: true` пропускаются), иначе не
  связываются. Один `testCaseId` — не ключ (смешал бы параметризованные тесты); смена
  окружения или параметров — другой ключ. Финальных с одним ключом несколько — попытки не
  связываются. Порядок попыток — `createdDate`, затем id. Итог — `TriageReport.retries`
  (`RetryInfo`: поле связи и числа, в `run.json` внутри `triage`); предупреждения прогона
  (`retry_warnings`) — только если что-то не связалось или ошибки попыток известны не все.
- Попытки активного падения — `FailedTestSummary.attempts` (`AttemptSummary`: id, статус,
  первая строка ошибки до 300 символов, `same_as_final`), последние 5; более ранние —
  число в `attempts_omitted`. Ошибка — из `statusDetails` списка (message, затем trace,
  затем верхний `trace`), иначе `GET /api/testresult/{id}` с параллелизмом
  `ALLURE_DETAIL_CONCURRENCY` и потолком `ALLURE_RETRY_MAX_DETAIL_REQUESTS` на прогон (по
  порядку падений; не запрошенные — `errors_capped`). «Та же ошибка» — `repeat_key` первых
  строк целиком, до обрезки до 300 символов (код ошибки бывает в конце длинной строки; как
  свёртка повторов лога: без времени, UUID, длинных чисел и имён потоков, но с кодами ошибок);
  `None` — у попытки или финального результата ошибки нет. Сбой запроса — ошибка
  неизвестна. Финальный `passed` с неудачными попытками — `RetryInfo.passed_after_retry`
  (ошибка только из списка, без запросов). Попытки не участвуют в сигнатуре и кластеризации.
- muted failed/broken считаются отдельно и в активные кластеры не попадают.
- Ошибка берётся из execution tree, затем из `statusDetails`, затем fallback
  `GET /api/testresult/{id}`.
- Логи — из processable attachments: text, JSON, XML, NDJSON и unknown text-like. Binary
  пропускаются.
- Изображения (`services/image_attachments.py`) не скачиваются при извлечении логов:
  `enrich_with_logs` записывает их метаданные в `FailedTestSummary.image_attachments`
  (`ImageAttachmentRef`, `exclude=True`, в `run.json` не пишутся). Изображение — MIME
  `image/png|jpeg|gif|webp`, без MIME — расширение; SVG — нет (текст, может нести скрипт).
  Шаг — по дереву исполнения: вложение шага с тем же id; по имени — только вложения дерева
  без id, и если имя однозначно с обеих сторон: одно среди них и одно среди вложений списка,
  не сопоставленных по id (иначе шаг неизвестен) (одноимённый `screenshot.png` после теста вне дерева
  иначе получал шаг упавшего и вытеснял его скриншот — ревью Codex); `failed_step` — шаг или любой его предок failed/broken (через сколько угодно passed-шагов). Скачивает и показывает модели
  скилл (`skill-analysis.md`, «Скриншоты»). Из вложений для логов изображения исключены и
  без MIME (`is_image_attachment` по расширению): иначе фильтр MIME пропускал
  `screenshot.png` без типа, и картинки всех падений скачивались как логи — даже при
  `ALLURE_IMAGES_PER_PROBLEM=0`.
- **Операция теста.** Свои id теста (`operation_ids`, `key=value`; ключи — реестр
  `_CANONICAL_CORRELATION_KEYS`: operUID, rqUID, requestId, correlationId, traceId, и ключи
  проекта `ALLURE_OPERATION_ID_KEYS` — `Settings.operation_keys` →
  `LogExtractionConfig.operation_id_keys` → `AttachmentContext.operation_keys`; регекспы —
  `log_utils._operation_regexes`, показ ключа — как в настройке; реальный прогон: `ufsBusinessId`
  не из реестра, записи своей операции не находились) — **все**
  значения (`log_utils.operation_ids`) из сообщения и трейса и из вложений, которые не лог
  (`attachment_handlers.log_operation_ids` → `None`: запрос и ответ HTTP, JSON, XML, HTML).
  Лог — журнал `StructuredErrorLogHandler` или текст, где `iter_events` распознаёт хоть одно
  событие не `plain` (`log_events.is_log_text`): запись со временем или уровнем, а также
  Traceback и исключение со стеком — вывод stderr без времени тоже лог (ревью Codex: иначе
  его id попадали в свои, а ошибки — без отбора). Лог **с id операций** (общий лог сервиса) в первом
  проходе откладывается (байты не держим), во втором скачивается заново и отбирается по своим
  id (`AttachmentContext.operation_ids`): события-ошибки (`ErrorBlocksHandler`, отбор **до**
  свёртки повторов — `repeat_key` не различает id, и первым вхождением осталась бы чужая
  ошибка), записи журнала, HTTP-сигналы (только из записей своей операции любого уровня).
  Запись без id в таком логе — не своя. Своих id нет — из такого лога ничего. Ключи проекта —
  только для id операции: строки `Корреляция:` секции HTTP и `extract_correlation_pairs_*` —
  по реестру, свои id и так попадают в `correlation_hint` (`format_operation_ids`). Лог **без id**
  операций — как раньше: сверить не с чем. Итог: `operation_logs` (подписи отобранных логов),
  `foreign_log_events` (отброшено записей других операций), `correlation_hint` — свои id
  (`format_operation_ids`), а не первый id любого вложения. Причина (ревью): общий лог давал
  цитаты из чужих операций и одинаковые логи разным падениям — log override склеивал их
  (эталон `shared_service_log`: до правки 5 тестов трёх групп в одном кластере).
- Корреляция кластера (`example_correlation`) — только представителя: операция другого
  участника под сообщением представителя была бы чужой.
- Текстовый лог делится на события (`utils/log_events.py`): запись начинается строкой со
  временем (ISO, `dd.MM.yyyy`, `yyyy/MM/dd`, `HH:mm:ss.SSS`, syslog, JUL, в `[]`), logfmt
  `time=`, заголовком klog/glog `E1003 10:00:00.123456 12 file.go:42]` (уровень — первая
  буква: `I`/`W`/`E`/`F` → INFO/WARNING/ERROR/FATAL), Ruby `Logger` (Rails)
  `E, [2026-10-04T11:00:00.126776 #52] ERROR -- : …` (уровень — слово после `]`), .NET
  SimpleConsole `fail: Category[1]` строкой (`fail` → ERROR, `crit` → CRITICAL; без суффикса
  `[id]` и с текстом в той же строке — не запись; сообщение и исключение ниже с отступом —
  продолжение), Go `panic: …` и `fatal error: …` с
  колонки 0 (уровни `PANIC`, `FATAL`; `[signal …]`, дамп goroutine, кадры
  `\tfile.go:42 +0x…`, пустые строки и вложенный `\tpanic:` — продолжение до следующей
  записи), Java `Exception in thread "…" класс` (событие-исключение без времени), Python
  `ERROR:root:`, `Traceback` или строкой исключения перед кадрами `at`; остальные строки —
  продолжение. Уровень — только в позиции уровня (первые 6 мест после времени, в скобках
  регистр любой; группа `[…]` из нескольких слов — MDC, поток с пробелами — одно место, её
  первое слово проверяется: `[INFO ]`) или самостоятельное поле logfmt `level=`/`lvl=`/
  `severity=` (значения в кавычках читаются целиком: `msg="… level=info …"` уровнем не
  считается): `ERROR` в тексте INFO не ошибка, WARN не ошибка. Уровни ошибки —
  `log_events.ERROR_LEVELS`, включая `PANIC`/`DPANIC` (logrus, zap, zerolog). JUL «дата класс метод» + `SEVERE:` — одно событие
  (`LogEvent.level_line` = 1: уровень и причина во второй строке); Traceback кончается строкой
  исключения. `ErrorBlocksHandler` берёт события-ошибки, Traceback и исключения, и
  записи с полями ошибки ответа. Для лога
  `<ISO-время> [ERROR] …` извлечение побайтово прежнее (эталон старой функции —
  `test_core_log_events.py`).
- **Поля ошибки ответа** (`log_events.has_error_fields`) делают ошибкой событие любого уровня
  (`LogEvent.reports_error`, по нему фильтрует `error_events`): бизнес-ошибку сервисы пишут на
  INFO — `[INFO] … {"errorCode":6, "errorMessage":"счет закрыт"}`; раньше её отбрасывал отбор по
  уровню, в том числе до отбора по операции (реальный прогон). Поле — JSON (`"key":`),
  `key=`/`key:` или XML (`<ns:key>…</`), имя — любой префикс + `error|err|fault` + `_?` +
  `code|message|msg|text|description|desc|string` (`ufsErrorCode`, `error_message`, `faultString`;
  регистр любой; `errorCount` и `"error":` — нет). Ответ внутри строкового поля JSON-записи
  (`"message":"Response {\"errorCode\":6}"`) — тоже поле (ревью Codex: иначе INFO-запись
  отбрасывалась): вложенный уровень (до 3) читается в содержимом строкового значения с
  экранированием, где снят ровно один уровень (`\"` → `"`, `\\` → `\`). Не все кавычки текста
  сразу — иначе `"errMsg":"\"account\" not found"` читалось пустым значением; и не весь текст
  заново — иначе прочитанное поле (`"errorCode":"RULE\"6"`) читалось второй раз, обрезанным
  (`errorcode=rule` у кодов 6 и 12 — общий ключ держал разные ошибки в одной проблеме). Значение
  в кавычках — с одним снятым уровнем экранирования (ревью Codex). Значение «успеха» ошибкой не делает: пусто,
  `null`/`none`/`nil`, `ok`/`success`, `false`, одни нули; объект и список — тоже нет.
  `is_error` прежний: продолжение стека (строка исключения после ошибки) решает только уровень,
  и INFO с полями ошибки следующее исключение не поглощает. `log_focus` даёт таким блокам тот
  же бонус и якоря, что ERROR-блокам. Разные бизнес-ошибки при одном сообщении разделяет
  gate по логу по кодам ошибки ответа (`error_field_codes`, «Кластеризация», п. 3).
- JSON-запись строкой (NDJSON: zap, zerolog, slog, logrus, logstash-logback-encoder, ECS,
  Log4j2 JsonTemplateLayout) — тоже начало записи, и в текстовом логе, и во вложении,
  определённом как json (`ErrorBlocksHandler` берёт `text` и `json`): строка с `{` (отступ из
  пробелов и табов допустим, показ — исходная строка), объект с
  полем уровня `level`/`lvl`/`severity`/`log.level` или `{"log": {"level": …}}`. Уровень —
  строка из уровней `log_events` в любом регистре; целое под `level` от −1 до 5 — шкала
  zerolog (3 — ERROR, 4 — FATAL, 5 — PANIC; 2 — WARN); иное значение — уровень неизвестен,
  но запись отдельная. JSON без поля уровня (тело ответа после ERROR, ответ API во
  вложении) — как раньше: продолжение, событий-ошибок нет. Показ ошибки
  (`LogEvent.rendered`/`shown`): без многострочного стека — строка дословно; со стеком
  (многострочное поле на любой глубине, последняя часть имени — `stack_trace`,
  `stacktrace`, `stack`, `exception`, `extendedStackTrace`: `error.stack_trace`,
  `exception.stacktrace`) — заголовок `json.dumps` записи без этих полей и их строки ниже
  без пустых; пометка — строка записи. Многострочное сообщение (`msg`, `message`…) остаётся
  в заголовке с `\n`: строки под записью сигнатура берёт, только если в них есть признак
  ошибки, и `warehouse closed\nretry later` с `credentials revoked\nretry later` давали бы
  одну сигнатуру. Отрендеренный блок
  разбирается обратно в то же событие (сигнатура читает лог через `iter_events`).
  `HttpSignalsHandler` по-прежнему идёт после: поле `error` JSON-лога бывает и в секции
  `HTTP`, как у текстовых логов. Ошибка страницы браузера `{"type": "pageerror", …}`
  (Playwright, Puppeteer) — запись уровня ERROR. JSON-массив записей одним документом
  (`page-errors.json`, выгрузка браузерного лога Selenium `{"level": "SEVERE", …}`) —
  `ErrorBlocksHandler` разворачивает его в строки (`log_events.json_array_lines`), если
  **каждый** элемент — объект с полем уровня или `pageerror`: массив-ответ API логом не
  становится; номер строки в пометке — номер записи в массиве. Для отбора по операции такой
  массив — тоже лог (`log_operation_ids`, `HttpSignalsHandler` читают записи строками,
  `_log_text`): иначе его id попадали в свои, и ошибки чужих операций шли без отбора (ревью
  Codex). `iter_events` массив не
  разбирает (весь документ — одна строка или pretty JSON). Причина: в эталоне dev
  `one_problem_resources` ошибка скрипта страницы была только в таком массиве, и четыре теста
  с разными локаторами давали четыре проблемы. Не распознаются: многострочный pretty JSON
  отдельных записей (Log4j2 JsonLayout `compact=false`), zap console с epoch-временем и
  уровнем строчными, logrus TTY `ERRO[0001]`.
- **Префикс сборщика логов контейнера** (`log_events._collector_prefixes`): `docker logs -t`,
  `kubectl logs --timestamps`, файл CRI `/var/log/containers` ставят время RFC3339 перед
  **каждой** строкой вывода (CRI — ещё `stdout|stderr F|P`), и раньше каждая строка стека
  становилась записью без уровня: отбор ошибок выбрасывал исключение, кадры и `Caused by`, в
  задание шла одна строка `ERROR … failed` (dev `collector_prefixed_logs`: потеря
  доказательств 4/4 → 0/4). Вывод сборщика — префикс у ≥ 90 % непустых строк и у половины из
  них 7–9 знаков долей: сборщик пишет наносекунды (kubectl — без хвостовых нулей), а лог
  приложения со своим ISO-временем (`2026-…T…:…:….123Z ERROR`, Spring Boot 3 в UTC с `  INFO`)
  — миллисекунды или микросекунды, и стек у него без времени, — его не трогаем. Тело строки —
  без префикса; признаки начала записи, уровень, JSON, Traceback, исключение со стеком
  ищутся в нём. Если хоть одно тело начинает запись (у приложения своё время, уровень,
  JSON), лог разбирается и **показывается** по телам, как без сборщика: блоки, пометки строк
  (номера прежние) и всё после извлечения те же — все форматы `FORMAT_LOGS` под тремя
  сборщиками дают побайтово те же блоки. Своих записей нет (`printStackTrace`,
  `console.log`) — запись начинает каждая строка вывода (уровень — первые слова тела), кроме
  продолжений (`_continues`: пустая, с отступом без уровня первым словом, `Caused by:`/
  `Suppressed:`, `... N more`, строка исключения, Traceback), и строки показываются с
  префиксом: другого времени у них нет. Цена второго случая: кадры с префиксом gate по логу
  кадрами не узнаёт (`_STACK_FRAME_RE` — с начала строки). Части длинной строки CRI (`P`) не
  склеиваются.
- Текст, начинающийся с `[`, считается JSON, только если за скобкой JSON-значение:
  `[2026-10-04 …]` и `[main] …` — текстовые логи.
- Происхождение: каждый абзац события-ошибки (отбор делит блоки по пустым строкам)
  начинается пометкой строк источника `[строки 120–134]` (номера с 1 по `splitlines`); имя
  вложения — в заголовке секции, id — `FailedTestSummary.log_attachments` (transient, в
  `run.json` не пишется). Точные повторы — равные после `normalize_text` (время, UUID,
  длинные числа) и без имён потоков (`replace_thread_names` и обрезки Spring Boot
  `[nio-8080-exec-1]` — только в `repeat_key`, сигнатуру не меняют) **и** с теми же кодами ошибок (`numeric_codes`: `error_code=10001`,
  JSON `"error_code":"10001"`, со знаком `-10001`, `ORA-01017`; `thread-1234`, имена потоков вроде `http-nio-8080-exec-7` и id операции — не код, см. ниже) — свёрнуты в первое вхождение:
  `[строки 3–5 · повторялось 7 раз: 3–5, 9–11, … и ещё 2]`. Подписи вложений теста в
  заголовках уникальны (`_unique_labels`): одинаковые имена получают id (`app.log #100`), а
  если такая подпись занята настоящим именем другого вложения — ещё и номер
  (`app.log #100-2`). По подписи реестр источников находит id вложения.
- **Id операции — не код и не текст ошибки.** `numeric_codes` не берёт совпадение, которое
  продолжает токен через дефис (`op-tr-3001` — id, а не код `tr-3001`; цена — составной код
  `cust-err-4001` тоже не код), и значения полей id операции. `normalize_text` (не
  `normalize_text_for_llm`: модели id нужен для сверки) заменяет значение поля id операции
  на `<ID>` первым шагом: `[operUID=op-tr-3001]` → `[operUID=<ID>]` — у скобки число
  защищено как значение ассерта и иначе оставалось. Поля — `operUID=…`/`rqUID: "…"`/
  `<traceId>…</traceId>` с ключами реестра `_CANONICAL_CORRELATION_KEYS`
  (`log_utils.CORRELATION_KEYS`), без ключей проекта: сигнатура от настроек не зависит.
  Значение с плейсхолдерами (`op-tr-<NUM>` из сохранённого признака базы знаний) тоже
  заменяется — старый признак узнаётся. Причина: id операции у каждого теста свой, и код
  `tr-3001`/`tr-3002` давал ключи gate по логу, «отличающийся» пример кластера и сигнатуру,
  меняющуюся с логом участника (dev `info_business_error`: задание 9265 → 7751 символов,
  ложный второй пример ушёл; `signature_log_unstable` 2 → 1; номер счёта в кавычках
  `"account":"4081…0301"` `_LONG_NUMBER_RE` защищает, и сигнатура стирает его сама — в
  строках лога, `skill-memory.md`, «Строки лога — свой мягкий вид»).
- Пометка — первая строка блока и переживает `StreamingLogSelector` и `focus_log`: при
  сокращении блока она сохраняется целиком или убирается полностью (`_with_mark`), но не
  обрезается — обрезанная перестала бы распознаваться. Из материала сигнатуры, признака
  базы знаний (`evidence/NN.txt`) и лог-канала кластеризации пометки вырезаются
  (`strip_source_marks`); заголовки секций там остаются, как раньше.
- `utils/log_focus.py` отбирает блоки лога по связи с ошибкой — и при выгрузке, и под лимит
  задания (общий для ядра и скилла).

### Отбор логов (`LogExtractionService`)

- До первого переполнения сохраняются буквальные секции; затем `StreamingLogSelector`
  переоценивает сохранённые и текущую и оставляет ограниченный набор фрагментов. Все
  следующие вложения обрабатываются; память `O(лимит + текущее вложение)`, исходники больших
  кандидатов не удерживаются.
- Header каждого фрагмента точный, включая HTTP: headerless fragment ядро не выдаёт. Итоговый
  лимит включает headers, пропуски и единственный footer.
- Отбор на лету детерминирован, но не обязан совпадать с offline greedy или заполнять весь
  бюджет. При нормальном лимите (от 1000) контекст значимых строк сохраняется; короткая
  склейка побайтово прежняя.
- `log_selection_error` замораживает сообщение, первые 20 строк трейса и известную до обхода
  вложений корреляцию; задание использует контекст фактического источника лога.
- `log_selection_truncated` разрешает очистку служебных строк для сигнатуры и кластеризации.
  Задание закрепляет только последний footer и только при этом флаге; отдельные пропуски
  объединяет с новыми. Marker-like строки приложения при `false` — обычные данные.
- Tiny fallback задания сохраняет полезный текст, а не одни пометки (headerless допустим
  только здесь, вне расчёта сигнатуры).
- Связь с сигнатурой и `run.json` — в `skill-memory.md`.

## Кластеризация (design notes)

1. Message-first: низкая message similarity обычно блокирует merge, но log override может
   объединить падения с одинаковой явной ошибкой в логе.
2. **Step path — hard gate**: если у обоих падений есть `failed_step_path` и step similarity
   ниже `clustering_step_strict_threshold`, пара не сливается. Gate применяется до
   message/log, log override его не обходит.
3. **Лог — gate по ошибкам** (`_LogErrorGate`): пара не сливается, если ошибки логов явно
   разные. Лог — блоки событий-ошибок секций `файл` (там только они; `HTTP` и `журнал` — весь
   JSON-массив с INFO — не входят) без пометок строк, кадров стека (Java `at …`, `... N more`,
   Python `File "…", line N`, Go — файл `\t/app/x.go:42 +0x1c` или ассемблерный рантайма
   `\t…/asm_amd64.s:1650 +0x1` и функция строкой выше, заголовок `goroutine N [running]:`;
   общие кадры net/http и `runtime.goexit` держали вместе разные паники),
   времени, ID, имён потоков и цифр; ключи блока — корневой класс (последний `…Exception|Error|Throwable`, то есть самый
   глубокий `Caused by`; обёртки вроде `ServletException` не ключ), `numeric_codes` и коды
   ошибки ответа (`log_events.error_field_codes`: поля ошибки на `code` — `errorCode`,
   `error_code`, `ufsErrorCode`, `faultCode` — без «успеха»; `"errorCode":6` → `errorcode=6`,
   имя без регистра и `_`, значение без регистра, короткие коды тоже).
   «Явно разные» — у логов нет ни одного общего блока, ни общего ключа, а TF-IDF похожесть
   ниже `clustering_log_split_threshold` (0.30); или общих блока и ключа нет, а коды ошибки
   ответа есть у обоих — тогда похожесть не решает. TF-IDF — по блокам (вектор лога — сумма
   счётчиков его блоков, idf по логам прогона), без обрезки словаря: иначе одинаковые
   документы, чьи слова выпали из `max_features`, дали бы 0.
   - **Любая общая ошибка держит пару.** Общий фон (health-check, Kafka) и общая ошибка
     падения по паре неотличимы («пул + Redis / NPE + Redis» против «NPE + Redis / NPE +
     Kafka»), а по прогону «фоном» выглядит и причина с несколькими симптомами (та же NPE за
     ассертом и за исключением клиента). Обе попытки сокращать общие блоки (все общие; общие,
     которые есть и у другого симптома) дробили настоящую проблему — ревью нашло контрпример
     к каждой. Цена: одинаковая фоновая ошибка в обоих логах выключает gate для пары, и
     различает модель по примерам. Группы всё же расходятся, если хотя бы одна пара между
     ними чистая (complete linkage): NPE без фона не даёт пулу БД с фоном попасть к NPE с
     фоном (эталон `background_log_errors`).
   - Общий ключ — та же ошибка: посторонние ошибки вокруг неё пару не режут; цена — два
     разных NPE за одним ассертом остаются одной проблемой (`same_assertion_two_npes`).
     Общая обёртка с разной причиной похожа на 0.49 — решают прежние веса.
   - **Коды ответа.** Бизнес-ошибку сервис пишет одним шаблоном с разными полями:
     `Response {"status":"REJECTED","errorCode":6,"errorMessage":"счет закрыт"}` и
     `…"errorCode":12,"errorMessage":"недостаточно средств…"` — 0.45 (общие `Response`,
     `status`, `REJECTED`, имена полей), между порогами gate и override, и одинаковое
     сообщение ассерта склеивало их (эталон `info_business_error`, precision 0.5). Разный
     код ответа — другая ошибка, сколько бы ни совпадало слов (та же строка с другим кодом —
     1.0). Ключ — только код, не `errorMessage`: в тексте бывают номера счетов и заказов, а
     общее сообщение без кода решает похожесть. Код только у одного лога — сравнивать нечем,
     правило прежнее. Общий ключ или блок (тот же код, фон) по-прежнему держит пару; в
     `held_by_shared` остатки с кодами у обоих тоже «разделил бы». `numeric_codes` короткий
     код без имени поля не берёт и `errorcode` как метку не знает — он общий с сигнатурой,
     поэтому коды ответа — отдельная функция, а сигнатура прежняя.
   - Число: пары, которые решает похожесть (без общего ключа), у разных ошибок корпуса — не
     выше 0.16; одна ошибка с шумом (потоки, строки, ID, четыре посторонние ошибки) — от
     0.46, nginx с разными путями и клиентами — от 0.75. 0.30 — половина порога «логи
     одинаковые» (log override, 0.60): ниже лог разделяет, от 0.60 объединяет, между —
     решают веса.
   - Лог только у части тестов — gate не применяется к паре без лога; complete linkage не
     сводит две разные ошибки через тест без лога. Gate после step-gate, до message/log.
4. **Ресурсы сообщения** (`utils/message_resources.py`): хосты отказа соединения, пула Python
   requests (`HTTPConnectionPool(host='h', port=p)`) и URL, локаторы
   Selenide/Selenium/Playwright/Cypress/Puppeteer/WebdriverIO (`element ("…") still not
   displayed`). Если ресурсы одного вида у двух сообщений
   не пересекаются, сообщения разные (message gate, `pair_sim = 0`), сколько бы ни совпадало
   остальное: одно слово в длинном сообщении TF-IDF почти не замечает (Playwright-пара
   `ui_and_network` стояла ровно на 0.600). Log override работает: разные элементы при одной ошибке скрипта в
   логе — одна проблема. Ресурсы — только из известного контекста (`ru.company.X`,
   `Foo.java:40` и значения в кавычках — не ресурсы); IP — `<ip>`, цифры имени и локатора —
   `#` (реплики `orders-1/2`, `:nth-child(2)`). Порт остаётся, и в виде `host/IP:port`
   (OkHttp): в TF-IDF сообщения четырёхзначные порты сливаются в `<NUM>`, разделить
   `localhost:8080` и `:5432` может только ресурс. Регистр хоста не важен, локатора — важен
   (`#Login` и `#login` — разные id, а TF-IDF приводит текст к нижнему регистру). Локатор
   Puppeteer закрывает та же кавычка, что открыла (`'[data-test="submit"]'`). Ошибка разрешения имени
   (`UnknownHostException`, `ENOTFOUND`, Go `dial tcp: lookup h on …: server misbehaving` /
   `no such host`…) хостов не даёт: сбой DNS бьёт по всем хостам сразу,
   отказывает общий резолвер (иначе сбой DNS дал бы по проблеме на хост; dev
   `ui_and_network`: `net-pricing + net-geo` поэтому остаётся склейкой). По той же причине
   message-документ для похожести у сбоя DNS — без имён хостов
   (`without_resolved_hosts`: `EAI_AGAIN h`, `lookup h on`, `UnknownHostException: h`,
   `Could not resolve host: h`, URL): в коротком `getaddrinfo EAI_AGAIN <fqdn>` имя — половина
   слов, и похожесть одной проблемы была 0.57 (dev `one_problem_resources`, dns-node).
   Примеры кластера сравнивают сообщения с хостами. Шаблоны расширяются, только если эталон
   это показывает. Выключатель — `clustering_resource_gate`.
5. При `logs_clustering_weight=0` log matrix не создаётся, лог не уменьшает мягкий штраф за
   разные шаги и gate по ошибкам лога выключен; остальные формулы и перераспределение весов
   сохраняются.
6. Итоговые distances пишутся сразу в condensed float64 — без `final_sim`, `dist_matrix` и
   второго цикла; канальные dense-матрицы остаются. Полностью непустые документы возвращают
   cosine subset без копии; диагональ принудительно единичная даже у строки без токенов.
   Статистика похожести — только DEBUG.
7. **Счётчики gates** (`ClusteringReport.gates`, `ClusteringGateStats`) — только числа, чтобы
   команда могла показать, как часто gates срабатывают на её прогонах (эталон, сводка
   `run_eval.py --cassette`; в `run.json` — `clustering.gates`). Пары — среди падений с
   текстом; пару засчитывает **первый** gate, который её решил (assertion → шаг → лог →
   сообщение), поэтому разрезанные шагом пары в счётчики лога не попадают. Поведение
   кластеризации счётчики не меняют: `_LogErrorGate.verdict` даёт `SPLIT` ровно там, где
   раньше `differ`, и похожесть gate считается в прежнем порядке операций.
   - `log_held_by_key` — общего блока нет, общий ключ держит пару с похожестью ниже порога
     (`same_assertion_two_npes`).
   - `log_held_by_block` — общий блок есть, и без общих блоков gate разделил бы пару: у обоих
     логов остаются свои ошибки, их ключи не пересекаются, похожесть остатков (тот же TF-IDF
     и idf) ниже порога. Буквальное «общий блок и похожесть ниже порога» не годится: общий
     фон сам поднимает похожесть (пул + Redis / NPE + Redis — 0.52), и такое определение
     давало 0 на `background_log_errors` (контрфактическое — 16). По паре не отличить «общий
     фон + разные ошибки» от «общая ошибка + разный фон», поэтому это верхняя граница; цена —
     `log_held_merged` (из удержанных в одном кластере) и сверка с разметкой в эталоне.
   - Остатки считаются после цикла и только для пар `SHARED` (`held_by_shared`): одна
     матрица уникальных остатков, одинаковые пары остатков — один раз (общий фон и повторы
     ошибок дают их квадратично), произведения строк — пакетами по `PAIR_BATCH` (256), чтобы
     память не росла с числом пар. У `big_launch` пар `SHARED` нет, `cluster_failures`
     0.675 → 0.689 с.
   - Пары id тестов удержанных пар и пар log override — `held_test_pairs`/
     `override_test_pairs`, `exclude=True`: для сверки с разметкой, в `run.json` не пишутся.
8. **Близкие пары** (`ClusteringReport.near_pairs`, `NearPair`, до `MAX_NEAR_PAIRS` = 50, в
   порядке кластеров): два кластера, между которыми есть пара падений с похожестью
   сообщений не ниже `similarity_threshold`, — текст ошибки почти тот же. `reason` — чаще
   всего решавший код среди пар между ними с расстоянием выше порога (complete linkage:
   хватило бы одной): gate из `NEAR_REASONS` или `score` (gate не сработал, не хватило
   похожести); ничья — меньший код. Код пишется в том же цикле, что счётчики (`int8`
   condensed), кластеры и счётчики не меняются. Названия кодов — в `models/clustering.py`:
   `review` берёт их оттуда, не загружая sklearn. Числа по причинам — в `pilot-summary.md`
   («Кластеризация»), в эталоне — `near_pairs`/`near_pairs_same` (README, «Близкие пары»).
   Dev: из 15 близких пар одна проблема только у `step_split_one_cause` (`step`) — поэтому
   gates не ослабляются, а лишнее дробление помечается после разбора.

- Примеры кластера (`FailureCluster.examples`, `select_examples`), до трёх, детерминированно
  (ничья — меньший id): `typical` — медоид по итоговым попарным расстояниям (condensed-вектор
  кластеризации, `_Distances`); `different` — самый далёкий от типичного среди тех, чьё
  сообщение, шаг или лог отличаются после нормализации (по расстоянию отличие бывает не видно:
  сбой DNS сравнивается без хостов) (логи — когда есть у обоих, и без
  цифр: номер строки кадра или потока — не другая проблема; но с кодами ошибок из исходного
  лога — `numeric_codes` и HTTP-статусы `_HTTP_STATUS_RE`: «HTTP 401», «HTTP статус: 401» (вывод
  самого извлекателя), `status="401"`, `"status":401`, `statusCode`, `response_code`, «-> 401»; число с буквенным или дробным хвостом — `401ms`,
  `401.5s` — длительность, не статус); `informative` — больше всего
  событий-ошибок (пометок строк) среди остальных, чей лог отличается от выбранных (повторы
  исключаются до выбора, а не после).
  Нет различий — один пример. `representative_test_id` (самое длинное сообщение) не
  меняется: на нём сигнатура и база знаний.
- Метка кластера — текст ошибки, иначе первая строка трейса, иначе категория, иначе
  `Тест: <имя теста>` (ID результата — только без имени). Метка только для показа (отчёт,
  задания, сводка), в сигнатуру не входит; «Тест: 301» модель переносила в сводку.

## Клиент TestOps

- API-модели принимают неизвестные поля (`extra="allow"`) и оба стиля имён
  (`populate_by_name=True`): payloads TestOps плавают.
- `_request()` должен корректно обрабатывать пустые тела PATCH/DELETE; `_request_raw()` — для
  бинарных attachments.
- **Повторы при временных сбоях.** GET (JSON и stream) повторяется до `http_retries` раз при
  `RETRY_STATUSES` (429, 502, 503, 504) и `httpx.RequestError` (сеть, таймаут): пауза —
  `Retry-After` в секундах, иначе 1, 2, 4… с, не больше 30 с (`clients/retry.py`); каждая
  попытка — со своим повтором при 401. 500 не повторяется (ошибка TestOps на запрос обычно
  воспроизводится), не-GET — тоже. Последний ответ отдаётся как раньше: 5xx — `AllureApiError`
  со статусом, сеть — `AllureApiError(0, …)`. Обмен токена (`AllureAuthManager`,
  `retries=settings.http_retries`) повторяется так же (POST обмена идемпотентен; 401 — нет).
  Причина: один 502 балансировщика при пагинации обрывал весь `prepare`. Тесты подменяют
  `_sleep` клиента и менеджера.
- `get_attachment_content(id, max_bytes=None)` — потолок по умолчанию
  `logs_max_attachment_bytes`; скриншоты скилл качает со своим (`images_max_bytes` + 1 байт:
  длиннее потолка — обрезан, пропускается). Протокол `AttachmentProvider` параметра не
  требует: фейковые провайдеры логов его не знают.

## Настройки (`config.py`)

`Settings` читает `<skill>/.env` и переменные окружения `ALLURE_*` (окружение важнее файла),
чужие ключи игнорирует. Границы значений — `BOUNDS` (ge/le). `load(require_testops=False)` — для
команд без TestOps (`rerun`): адрес и токен не обязательны, остальное проверяется.

| Переменная | Обязательная | По умолчанию | Описание |
|---|:---:|---|---|
| `ALLURE_ENDPOINT` | да | — | URL Allure TestOps без `/api` |
| `ALLURE_TOKEN` | да | `""` | API token |
| `ALLURE_REQUEST_TIMEOUT` | нет | `30` | HTTP timeout к TestOps |
| `ALLURE_HTTP_RETRIES` | нет | `3` | Повторы GET при 429/502/503/504 и сбоях сети (0–10) |
| `ALLURE_PAGE_SIZE` | нет | `100` | Размер страницы TestOps API |
| `ALLURE_MAX_PAGES` | нет | `200` | Защита пагинации; больше страниц — `PaginationLimitError` сразу после первой страницы |
| `ALLURE_DETAIL_CONCURRENCY` | нет | `10` | Параллелизм details/comments |
| `ALLURE_SSL_VERIFY` | нет | `true` | Проверка TLS |
| `ALLURE_LOGS_CONCURRENCY` | нет | `5` | Параллелизм скачивания attachments |
| `ALLURE_LOGS_MAX_ATTACHMENT_BYTES` | нет | `10485760` | Максимум байт из одного вложения (stream-чтение с обрезкой) |
| `ALLURE_LOGS_MAX_SNIPPET_CHARS` | нет | `65536` | Максимум символов финального `log_snippet` одного теста |
| `ALLURE_CLUSTERING_THRESHOLD` | нет | `0.60` | Порог similarity; ниже — агрессивнее объединение |
| `ALLURE_CLUSTERING_STEP_STRICT_THRESHOLD` | нет | `0.95` | Hard gate по step path (см. выше); `0.0` отключает, `1.0` режет при любом отличии |
| `ALLURE_LOGS_CLUSTERING_WEIGHT` | нет | `0.15` | Вес log channel в кластеризации |
| `ALLURE_CLUSTERING_LOG_SPLIT_THRESHOLD` | нет | `0.30` | Gate по ошибкам лога (см. «Кластеризация»); `0.0` отключает |
| `ALLURE_CLUSTERING_RESOURCE_GATE` | нет | `true` | Gate по хостам и локаторам сообщения (см. «Кластеризация») |
| `ALLURE_LLM_PROMPT_MESSAGE_MAX_CHARS` | нет | `2000` | Лимит message в задании |
| `ALLURE_LLM_PROMPT_TRACE_MAX_CHARS` | нет | `400` | Лимит trace в задании |
| `ALLURE_LLM_PROMPT_LOG_MAX_CHARS` | нет | `8000` | Лимит log в задании |
| `ALLURE_RETRY_MAX_DETAIL_REQUESTS` | нет | `200` | Потолок `GET /api/testresult/{id}` за ошибками попыток на прогон; `0` — не запрашивать |
| `ALLURE_IMAGES_PER_PROBLEM` | нет | `3` | Скриншотов на проблему в задании (0–3); `0` — не скачивать |
| `ALLURE_IMAGES_MAX_BYTES` | нет | `5242880` | Потолок одного скриншота (64 КБ – 20 МБ) |
| `ALLURE_RERUN_ATTEMPTS` | нет | `3` | Перезапуск тестов (`skill-rerun.md`): запусков до первого успеха (1–5) |
| `ALLURE_RERUN_MAX_TESTS` | нет | `20` | Тестов за раз (0–100); `0` выключает перезапуск |
| `ALLURE_RERUN_TIMEOUT` | нет | `1800` | Общий потолок времени перезапуска, с (60–14400) |
| `ALLURE_RERUN_MAVEN_ARGS` | нет | `""` | Свои аргументы Maven (`shlex`), значения не печатаются |
| `ALLURE_OPERATION_ID_KEYS` | нет | `""` | Ключи id операции проекта через запятую (`ufsBusinessId`), к реестру; имя — `[A-Za-z][A-Za-z0-9_.-]{0,63}`, иначе `ConfigurationError` |

## Тесты ядра

`test_core_*.py` (кластеризация, gates по шагу, логу и ресурсам, извлечение логов и вложений,
декодирование, триаж, клиент TestOps, auth, `log_utils`) перенесены из серверных тестов
`e100909` с импортами `alla_core`. libmagic в окружении нет: ветку с `magic` проверяют через
фейковый модуль (`_fake_magic`).
