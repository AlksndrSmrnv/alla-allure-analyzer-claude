# Ядро `alla_core`

`scripts/alla_core/` — доступ к TestOps и анализ падений, на нём стоит `alla_skill_lib`.

- Состав: клиент TestOps, триаж, логи, кластеризация, сборка блока «Данные» для заданий
  (`services/prompt_builder_service.py`). Правил и «Задания» для модели в ядре нет — они в
  `alla_skill_lib` (см. `skill-analysis.md`); сигнатура проблемы — тоже там
  (`signature.py`, см. `skill-memory.md`).
- Происхождение: вендорено из серверного `src/alla` (коммит `e100909`), теперь обычный
  рукописный код: генератора, пометок GENERATED и drift-теста нет, правится напрямую, с
  тестами.
- Унаследованное от сервера, что скиллу может быть не нужно (поля под PostgreSQL, модели
  LLM), удалять осознанно: сверяться с импортами `alla_skill_lib` и тестами. Модели базы
  знаний и обратной связи сервера (`knowledge/`) уже удалены.

## Сбор данных

`TriageService` → `LogExtractionService` → `ClusteringService`, склеены в
`alla_skill_lib/pipeline.py`.

- `hidden` results исключаются из статистики и анализа как retry/non-final, но до фильтрации
  связываются с финальными (`services/retry_linking.py`, шаг 5). Ключ один на прогон:
  `historyId`, затем `historyKey` (есть значение хотя бы у одной hidden-попытки), иначе
  `testCaseId` + `parameters` + `environment` (только если есть `testCaseId` и оба поля —
  список или словарь, пустой тоже; нет поля или `null` — контекст неизвестен, а не пуст;
  пары «имя=значение» отсортированы, `excluded: true` пропускаются), иначе не
  связываются. Один `testCaseId` — не ключ (смешал бы параметризованные тесты); смена
  окружения или параметров — другой ключ. Финальных с одним ключом несколько — попытки не
  связываются. Порядок попыток — `createdDate`, затем id. Итог — `TriageReport.retries`
  (`RetryInfo`: поле связи и числа, в `run.json` внутри `triage`); предупреждения прогона
  (`retry_warnings`) — только если что-то не связалось или ошибки попыток известны не все.
- Попытки активного падения — `FailedTestSummary.attempts` (`AttemptSummary`: id, статус,
  первая строка ошибки до 300 символов, `same_as_final`), последние 5; более ранние —
  число в `attempts_omitted`. Ошибка — из `statusDetails` списка (message, затем trace,
  затем верхний `trace`), иначе `GET /api/testresult/{id}` с параллелизмом
  `ALLURE_DETAIL_CONCURRENCY` и потолком `ALLURE_RETRY_MAX_DETAIL_REQUESTS` на прогон (по
  порядку падений; не запрошенные — `errors_capped`). «Та же ошибка» — `repeat_key` первых
  строк целиком, до обрезки до 300 символов (код ошибки бывает в конце длинной строки; как
  свёртка повторов лога: без времени, UUID, длинных чисел и имён потоков, но с кодами ошибок);
  `None` — у попытки или финального результата ошибки нет. Сбой запроса — ошибка
  неизвестна. Финальный `passed` с неудачными попытками — `RetryInfo.passed_after_retry`
  (ошибка только из списка, без запросов). Попытки не участвуют в сигнатуре и кластеризации.
- muted failed/broken считаются отдельно и в активные кластеры не попадают.
- Ошибка берётся из execution tree, затем из `statusDetails`, затем fallback
  `GET /api/testresult/{id}`.
- Логи — из processable attachments: text, JSON, XML, NDJSON и unknown text-like. Binary
  пропускаются.
- Текстовый лог делится на события (`utils/log_events.py`): запись начинается строкой со
  временем (ISO, `dd.MM.yyyy`, `yyyy/MM/dd`, `HH:mm:ss.SSS`, syslog, JUL, в `[]`), logfmt
  `time=`, Python `ERROR:root:`, `Traceback` или строкой исключения перед кадрами `at`;
  остальные строки — продолжение. Уровень — только в позиции уровня (первые слова после
  времени, в скобках регистр любой) или самостоятельное поле logfmt `level=`/`lvl=`/
  `severity=` (значения в кавычках читаются целиком: `msg="… level=info …"` уровнем не
  считается): `ERROR` в тексте INFO не ошибка, WARN не ошибка. JUL «дата класс метод» + `SEVERE:` — одно событие
  (`LogEvent.level_line` = 1: уровень и причина во второй строке); Traceback кончается строкой
  исключения. `ErrorBlocksHandler` берёт события-ошибки, Traceback и исключения. Для лога
  `<ISO-время> [ERROR] …` извлечение побайтово прежнее (эталон старой функции —
  `test_core_log_events.py`).
- Текст, начинающийся с `[`, считается JSON, только если за скобкой JSON-значение:
  `[2026-10-04 …]` и `[main] …` — текстовые логи.
- Происхождение: каждый абзац события-ошибки (отбор делит блоки по пустым строкам)
  начинается пометкой строк источника `[строки 120–134]` (номера с 1 по `splitlines`); имя
  вложения — в заголовке секции, id — `FailedTestSummary.log_attachments` (transient, в
  `run.json` не пишется). Точные повторы — равные после `normalize_text` (время, UUID,
  длинные числа) и без имён потоков (`replace_thread_names` и обрезки Spring Boot
  `[nio-8080-exec-1]` — только в `repeat_key`, сигнатуру не меняют) **и** с теми же кодами ошибок (`numeric_codes`: `error_code=10001`,
  JSON `"error_code":"10001"`, со знаком `-10001`, `ORA-01017`; `thread-1234` и имена потоков вроде `http-nio-8080-exec-7` — не код) — свёрнуты в первое вхождение:
  `[строки 3–5 · повторялось 7 раз: 3–5, 9–11, … и ещё 2]`. Подписи вложений теста в
  заголовках уникальны (`_unique_labels`): одинаковые имена получают id (`app.log #100`), а
  если такая подпись занята настоящим именем другого вложения — ещё и номер
  (`app.log #100-2`). По подписи реестр источников находит id вложения.
- Пометка — первая строка блока и переживает `StreamingLogSelector` и `focus_log`: при
  сокращении блока она сохраняется целиком или убирается полностью (`_with_mark`), но не
  обрезается — обрезанная перестала бы распознаваться. Из материала сигнатуры, признака
  базы знаний (`evidence/NN.txt`) и лог-канала кластеризации пометки вырезаются
  (`strip_source_marks`); заголовки секций там остаются, как раньше.
- `utils/log_focus.py` отбирает блоки лога по связи с ошибкой — и при выгрузке, и под лимит
  задания (общий для ядра и скилла).

### Отбор логов (`LogExtractionService`)

- До первого переполнения сохраняются буквальные секции; затем `StreamingLogSelector`
  переоценивает сохранённые и текущую и оставляет ограниченный набор фрагментов. Все
  следующие вложения обрабатываются; память `O(лимит + текущее вложение)`, исходники больших
  кандидатов не удерживаются.
- Header каждого фрагмента точный, включая HTTP: headerless fragment ядро не выдаёт. Итоговый
  лимит включает headers, пропуски и единственный footer.
- Отбор на лету детерминирован, но не обязан совпадать с offline greedy или заполнять весь
  бюджет. При нормальном лимите (от 1000) контекст значимых строк сохраняется; короткая
  склейка побайтово прежняя.
- `log_selection_error` замораживает сообщение, первые 20 строк трейса и известную до обхода
  вложений корреляцию; задание использует контекст фактического источника лога.
- `log_selection_truncated` разрешает очистку служебных строк для сигнатуры и кластеризации.
  Задание закрепляет только последний footer и только при этом флаге; отдельные пропуски
  объединяет с новыми. Marker-like строки приложения при `false` — обычные данные.
- Tiny fallback задания сохраняет полезный текст, а не одни пометки (headerless допустим
  только здесь, вне расчёта сигнатуры).
- Связь с сигнатурой и `run.json` — в `skill-memory.md`.

## Кластеризация (design notes)

1. Message-first: низкая message similarity обычно блокирует merge, но log override может
   объединить падения с одинаковой явной ошибкой в логе.
2. **Step path — hard gate**: если у обоих падений есть `failed_step_path` и step similarity
   ниже `clustering_step_strict_threshold`, пара не сливается. Gate применяется до
   message/log, log override его не обходит.
3. **Лог — gate по ошибкам** (`_LogErrorGate`): пара не сливается, если ошибки логов явно
   разные. Лог — блоки событий-ошибок секций `файл` (там только они; `HTTP` и `журнал` — весь
   JSON-массив с INFO — не входят) без пометок строк, кадров стека, времени, ID, имён потоков
   и цифр; ключи блока — корневой класс (последний `…Exception|Error|Throwable`, то есть самый
   глубокий `Caused by`; обёртки вроде `ServletException` не ключ) и `numeric_codes`.
   «Явно разные» — у логов нет ни одного общего блока, ни общего ключа, а TF-IDF похожесть
   ниже `clustering_log_split_threshold` (0.30). TF-IDF — по блокам (вектор лога — сумма
   счётчиков его блоков, idf по логам прогона), без обрезки словаря: иначе одинаковые
   документы, чьи слова выпали из `max_features`, дали бы 0.
   - **Любая общая ошибка держит пару.** Общий фон (health-check, Kafka) и общая ошибка
     падения по паре неотличимы («пул + Redis / NPE + Redis» против «NPE + Redis / NPE +
     Kafka»), а по прогону «фоном» выглядит и причина с несколькими симптомами (та же NPE за
     ассертом и за исключением клиента). Обе попытки сокращать общие блоки (все общие; общие,
     которые есть и у другого симптома) дробили настоящую проблему — ревью нашло контрпример
     к каждой. Цена: одинаковая фоновая ошибка в обоих логах выключает gate для пары, и
     различает модель по примерам. Группы всё же расходятся, если хотя бы одна пара между
     ними чистая (complete linkage): NPE без фона не даёт пулу БД с фоном попасть к NPE с
     фоном (эталон `background_log_errors`).
   - Общий ключ — та же ошибка: посторонние ошибки вокруг неё пару не режут; цена — два
     разных NPE за одним ассертом остаются одной проблемой (`same_assertion_two_npes`).
     Общая обёртка с разной причиной похожа на 0.49 — решают прежние веса.
   - Число: пары, которые решает похожесть (без общего ключа), у разных ошибок корпуса — не
     выше 0.16; одна ошибка с шумом (потоки, строки, ID, четыре посторонние ошибки) — от
     0.46, nginx с разными путями и клиентами — от 0.75. 0.30 — половина порога «логи
     одинаковые» (log override, 0.60): ниже лог разделяет, от 0.60 объединяет, между —
     решают веса.
   - Лог только у части тестов — gate не применяется к паре без лога; complete linkage не
     сводит две разные ошибки через тест без лога. Gate после step-gate, до message/log.
4. **Ресурсы сообщения** (`utils/message_resources.py`): хосты отказа соединения и URL, локаторы
   Selenide/Selenium/Playwright/Cypress/Puppeteer. Если ресурсы одного вида у двух сообщений
   не пересекаются, сообщения разные (message gate, `pair_sim = 0`), сколько бы ни совпадало
   остальное: одно слово в длинном сообщении TF-IDF почти не замечает (Playwright-пара holdout
   стояла ровно на 0.600). Log override работает: разные элементы при одной ошибке скрипта в
   логе — одна проблема. Ресурсы — только из известного контекста (`ru.company.X`,
   `Foo.java:40` и значения в кавычках — не ресурсы); IP — `<ip>`, цифры имени и локатора —
   `#` (реплики `orders-1/2`, `:nth-child(2)`). Порт остаётся, и в виде `host/IP:port`
   (OkHttp): в TF-IDF сообщения четырёхзначные порты сливаются в `<NUM>`, разделить
   `localhost:8080` и `:5432` может только ресурс. Регистр хоста не важен, локатора — важен
   (`#Login` и `#login` — разные id, а TF-IDF приводит текст к нижнему регистру). Локатор
   Puppeteer закрывает та же кавычка, что открыла (`'[data-test="submit"]'`). Ошибка разрешения имени
   (`UnknownHostException`, `ENOTFOUND`…) хостов не даёт: сбой DNS бьёт по всем хостам сразу,
   отказывает общий резолвер (иначе сбой DNS дал бы по проблеме на хост; holdout
   `net-pricing + net-geo` поэтому остаётся склейкой). Шаблоны расширяются, только если эталон
   это показывает. Выключатель — `clustering_resource_gate`.
5. При `logs_clustering_weight=0` log matrix не создаётся, лог не уменьшает мягкий штраф за
   разные шаги и gate по ошибкам лога выключен; остальные формулы и перераспределение весов
   сохраняются.
6. Итоговые distances пишутся сразу в condensed float64 — без `final_sim`, `dist_matrix` и
   второго цикла; канальные dense-матрицы остаются. Полностью непустые документы возвращают
   cosine subset без копии; диагональ принудительно единичная даже у строки без токенов.
   Статистика похожести — только DEBUG.
7. **Счётчики gates** (`ClusteringReport.gates`, `ClusteringGateStats`) — только числа, чтобы
   команда могла показать, как часто gates срабатывают на её прогонах (эталон, сводка
   `run_eval.py --cassette`; в `run.json` — `clustering.gates`). Пары — среди падений с
   текстом; пару засчитывает **первый** gate, который её решил (assertion → шаг → лог →
   сообщение), поэтому разрезанные шагом пары в счётчики лога не попадают. Поведение
   кластеризации счётчики не меняют: `_LogErrorGate.verdict` даёт `SPLIT` ровно там, где
   раньше `differ`, и похожесть gate считается в прежнем порядке операций.
   - `log_held_by_key` — общего блока нет, общий ключ держит пару с похожестью ниже порога
     (`same_assertion_two_npes`).
   - `log_held_by_block` — общий блок есть, и без общих блоков gate разделил бы пару: у обоих
     логов остаются свои ошибки, их ключи не пересекаются, похожесть остатков (тот же TF-IDF
     и idf) ниже порога. Буквальное «общий блок и похожесть ниже порога» не годится: общий
     фон сам поднимает похожесть (пул + Redis / NPE + Redis — 0.52), и такое определение
     давало 0 на `background_log_errors` (контрфактическое — 16). По паре не отличить «общий
     фон + разные ошибки» от «общая ошибка + разный фон», поэтому это верхняя граница; цена —
     `log_held_merged` (из удержанных в одном кластере) и сверка с разметкой в эталоне.
   - Остатки считаются после цикла и только для пар `SHARED` (`held_by_shared`): одна
     матрица уникальных остатков, одинаковые пары остатков — один раз (общий фон и повторы
     ошибок дают их квадратично), произведения строк — пакетами по `PAIR_BATCH` (256), чтобы
     память не росла с числом пар. У `big_launch` пар `SHARED` нет, `cluster_failures`
     0.675 → 0.689 с.
   - Пары id тестов удержанных пар и пар log override — `held_test_pairs`/
     `override_test_pairs`, `exclude=True`: для сверки с разметкой, в `run.json` не пишутся.

- Примеры кластера (`FailureCluster.examples`, `select_examples`), до трёх, детерминированно
  (ничья — меньший id): `typical` — медоид по итоговым попарным расстояниям (condensed-вектор
  кластеризации, `_Distances`); `different` — самый далёкий от типичного, если его
  сообщение, шаг или лог отличаются после нормализации (логи — когда есть у обоих, и без
  цифр: номер строки кадра или потока — не другая проблема; но с кодами ошибок из исходного
  лога — `numeric_codes` и HTTP-статусы `_HTTP_STATUS_RE`: «HTTP 401», «HTTP статус: 401» (вывод
  самого извлекателя), `status="401"`, `"status":401`, `statusCode`, `response_code`, «-> 401»; число с буквенным или дробным хвостом — `401ms`,
  `401.5s` — длительность, не статус); `informative` — больше всего
  событий-ошибок (пометок строк) среди остальных, чей лог отличается от выбранных (повторы
  исключаются до выбора, а не после).
  Нет различий — один пример. `representative_test_id` (самое длинное сообщение) не
  меняется: на нём сигнатура и база знаний.
- Метка кластера — текст ошибки, иначе первая строка трейса, иначе категория, иначе
  `Тест: <имя теста>` (ID результата — только без имени). Метка только для показа (отчёт,
  задания, сводка), в сигнатуру не входит; «Тест: 301» модель переносила в сводку.

## Клиент TestOps

- API-модели принимают неизвестные поля (`extra="allow"`) и оба стиля имён
  (`populate_by_name=True`): payloads TestOps плавают.
- `_request()` должен корректно обрабатывать пустые тела PATCH/DELETE; `_request_raw()` — для
  бинарных attachments.

## Настройки (`config.py`)

`Settings` читает `<skill>/.env` и переменные окружения `ALLURE_*` (окружение важнее файла),
чужие ключи игнорирует. Границы значений — `BOUNDS` (ge/le).

| Переменная | Обязательная | По умолчанию | Описание |
|---|:---:|---|---|
| `ALLURE_ENDPOINT` | да | — | URL Allure TestOps без `/api` |
| `ALLURE_TOKEN` | да | `""` | API token |
| `ALLURE_REQUEST_TIMEOUT` | нет | `30` | HTTP timeout к TestOps |
| `ALLURE_PAGE_SIZE` | нет | `100` | Размер страницы TestOps API |
| `ALLURE_MAX_PAGES` | нет | `50` | Защита пагинации |
| `ALLURE_DETAIL_CONCURRENCY` | нет | `10` | Параллелизм details/comments |
| `ALLURE_SSL_VERIFY` | нет | `true` | Проверка TLS |
| `ALLURE_LOGS_CONCURRENCY` | нет | `5` | Параллелизм скачивания attachments |
| `ALLURE_LOGS_MAX_ATTACHMENT_BYTES` | нет | `10485760` | Максимум байт из одного вложения (stream-чтение с обрезкой) |
| `ALLURE_LOGS_MAX_SNIPPET_CHARS` | нет | `65536` | Максимум символов финального `log_snippet` одного теста |
| `ALLURE_CLUSTERING_THRESHOLD` | нет | `0.60` | Порог similarity; ниже — агрессивнее объединение |
