# Память скилла: база знаний, модули, обратная связь, история

База знаний проектная: `alla-kb/` в репозитории автотестов, наполняется обратной связью
пользователя.

## База знаний (`kb`)

- Где лежит: `alla-kb/<id>.json` в корне git; в многомодульном Java/Kotlin-проекте
  (Gradle/Maven) — `<модуль>/alla-kb/` (`kb_dir_for`, см. «Модули»).
- Узнавание: точно по сигнатуре `v<версия>:<hash>` (`confirmed_signatures` /
  `rejected_signatures`) или по короткому признаку `error_example` — все его строки есть в
  данных кластера, без учёта чисел/ID/времени/e-mail; хранится нормализованным.
- Правило «запись подходит кластеру» одно — `record_matches` (отвергнута — `record_rejected`
  → нет; подтверждённая сигнатура → `exact`; тест кластера в `confirmed_tests` и признак
  совпал → `exact`; все строки признака в данных → `fingerprint`): им пользуются
  `match_cluster` в `prepare` и проверка известных проблем при сборке отчёта
  (`known_issues`, см. `skill-analysis.md`). Тесты кластера — `cluster_tests` в `prepare`,
  `entry_tests` по `run.json` потом.
- **Смена версии сигнатуры.** Тесты записи действуют, только когда у неё есть сигнатуры
  того же вида и все — прежних версий (`_migrating`): подтверждение — тест в
  `confirmed_tests`, отказ — тест в `rejected_tests`; в обоих случаях нужен совпавший
  признак (тест падает и по другим причинам). Пустой список сигнатур — не смена версии
  (последнюю переназначили другой записи или правили руками). Подтверждённая сигнатура
  кластера сильнее старого отказа по тесту — внутри `record_rejected`, чтобы `prepare` и
  отчёт (`known_issues` спрашивает отказ отдельно) решали одинаково (ревью Codex).
  `prepare` в `alla-kb/` не пишет: новая сигнатура попадёт в запись со следующим
  `remember`. Поэтому версию можно поднимать: точное узнавание и отказы переживают её
  у записей с тестами (записи до 2026-10-18 тестов не имеют — только признак).
- Тесты записи — `confirmed_tests`/`rejected_tests` (`key_of_test`: `full_name` без `[...]`
  параметров в конце, иначе `testcase:<testCaseId>`; имя, похожее на секрет (`secret_lines`),
  не сохраняется — ревью Codex): `remember` и `reject` пишут тесты кластера
  (`entry_tests` по `run.json`, `prepare` — `cluster_tests` по моделям) зеркально
  сигнатурам — `confirm` снимает тесты с отказа, `reject` с подтверждения; у других записей
  тесты не трогаются (тест падает и по нескольким известным причинам), кроме записи, которая
  уже точно узнаёт эту ошибку (`record_matches` → `exact`: по сигнатуре или, после смены
  версии, по тесту): `remember` новой записи отвечает «уже подтверждали в записи …», а
  `remember --entry` другой записи снимает с прежней сигнатуру и тесты кластера (ревью Codex). Не больше
  `MAX_RECORD_TESTS` (50), новые важнее старых. Зачем — узнавание после смены версии
  сигнатуры (план `docs/plans/2026-10-18-kb-test-binding.md`).
- Свои поля записи (`jira`, `owner`…) сохраняются при перезаписи. Запись атомарная, LF.
- Сканер секретов отклоняет пароли, токены, ключи AWS/GitHub, пароль в URL, PEM.

### Разбор точно узнанной проблемы без модели (`known_issues`)

Решение пользователя (2026-10-26): проблему, которую база знаний узнаёт **точно** (сигнатуру
или, после смены версии, тест подтвердил инженер), разбирает скрипт по записи — модель её не
читает. Совпал только признак — разбирает модель с подсказкой, как раньше: 1–3 строки признака
совпадают и у чужой причины (стенд E10: каталог получал запись пула).

- Решение — в `prepare` (`cli._write_run` → `auto_resolution`): ровно одна запись с
  `origin == "exact"`; у записи есть шаги рецепта; **лог тот же, что видел инженер**:
  отпечаток строк-ошибок лога кластера (`entry["log_digest"]`, `signature.log_errors_digest`
  от `cluster_log_errors` — лог, который берёт сигнатура; `none` — ошибок в логе нет) есть в
  `confirmed_logs` записи. Строки-ошибки (`_diagnostic_lines`) — якорь лога и строки секций
  HTTP без корреляции (id запроса свой у каждого прогона): секцию HTTP сигнатура не берёт, и
  «счёт закрыт» с «не хватает средств» в ответе SOAP за одним ассертом кода получали одну
  сигнатуру и отпечаток `none` (ревью Codex; dev `same_assert_http_causes`, `kb_auto_wrong` 1
  → 0; ответ JSON ядро кладёт и в секцию лога — его различает сигнатура). Отпечаток в
  запись пишет каждый `remember` (и подтверждение R). Сигнатура ошибки, которая сама называет
  причину, лог не берёт: запись пула БД узнавала «точно» и NPE
  за тем же исключением клиента в другом прогоне (ревью Codex; dev
  `same_exception_split_log_causes`: без отпечатка `kb_auto_wrong` 1). Цена — фон: другая
  фоновая ошибка в логе — другой отпечаток, разбирает модель, а подтверждение в вопросе после
  отчёта добавит и его. Записи без `confirmed_logs` (до 2026-10-26) без модели не
  разбираются; **каждый тест группы**, и представитель тоже (не только примеры
  задания: их до трёх, и тест другой проблемы в них может не попасть; представитель — по
  своему тесту: после смены версии кластер узнаётся и по тесту другого участника, ревью
  Codex), узнаётся записью точно, как если бы был представителем (`signature.as_representatives`:
  своя сигнатура, свои данные и тест; в кластере — только тест и участники, чьи логи он берёт:
  свой лог, а без него — первый и самый содержательный лог группы, найденные один раз; иначе
  логи всех очищались для каждого теста — ревью Codex, 600 тестов — 3 с на кластер), и
  строки-ошибки его собственного лога (`signature.log_error_lines`) те же, что у лога кластера, если свой лог у теста есть (тест
  без лога ничего не опровергает; представитель без лога — лог кластера у участника): сигнатура
  ошибки, которая сама называет причину, лог не берёт, и пул БД с NPE за одним исключением
  клиента получали одну сигнатуру (dev `same_exception_two_log_causes`, `kb_auto_wrong` 1 →
  0). Фон или причина — по паре не отличить, поэтому любое различие отдаёт группу модели.
  Иначе однородность проверяет модель; нашлась цитата — строка куска реестра, где есть строка признака после
  `normalize_fp`, иначе первая строка `message`/`trace` (≥ `MIN_QUOTE_CHARS`), «ёлочки» → `"`
  (закрыли бы цитату раньше), до `KB_AUTO_QUOTE_CHARS` по границе слова. Итог —
  `entry["kb_auto"] = {"id", "quote", "fingerprint", "members"}` (`members` — «сигнатура, ключ
  теста, есть ли признак записи в его данных» каждого теста группы, `fingerprint` — признак
  записи, с которым это проверено: `next` сверяет каждый тест с текущей записью и **своим**
  тестом — `kb.matches_with_hits`, то же правило, что `record_matches`, но с готовым ответом о
  признаке. Отказ или переназначение любого после разбора другой проблемы снимает разбор всей
  группы; с общим списком тестов тест второго участника «подтверждал» и первого после смены
  версии, ревью Codex. Признак записи с тех пор правили — в данных тестов его не сверить (у
  `next` — только данные представителя), и узнавание по тесту после смены версии больше не в
  счёт, по подтверждённой сигнатуре — да: признак из кадра стека одного теста иначе
  подтверждал бы всю группу, ревью Codex). Текст разбора проверяется уже в `prepare` (`known_auto_valid`): не прошёл — запись
  остаётся в задании, иначе `next` снял бы разбор, а модель разбирала бы без подсказки; при
  `log_not_found` «НЕ ХВАТАЕТ» называет лог операции. Задание строится **без этой записи** (куски данных те
  же): после `reject` оно — запасной путь и не должно называть её «ТОЧНОЕ»; `entry["kb"]` её
  хранит — по нему проверяются `БАЗА ЗНАНИЙ:`, категория (`exact_kb`), `known_issues`, история.
- `prepare` разбор не пишет и в `alla-kb/` по-прежнему не пишет. Разбор пишет `next`
  (`sync_known_auto`, до подсчёта неразобранных) по текущему файлу записи: она точно узнаёт
  кластер — разбор из её текста (`known_issue_analysis`: обычный формат, «СОГЛАСОВАННОСТЬ:
  одна причина» при нескольких примерах, проходит `check_entry_analysis`), хэш — в
  `state.json` (`KB_AUTO_STATE`); после `remember --entry` рецепт в разборе обновится.
  Перестала (`reject`, запись удалена, ошибку переназначили другой) — свой файл (хэш совпал
  или файла нет) удаляется, и `next` отвечает `analyze`. Файл с другим хэшем — разбор модели
  после отката или правка руками — не трогается и считается разбором модели. Текст скрипта
  не прошёл проверку — удаляется, замечание `KB_AUTO_INVALID_NOTE`, разбирает модель: `fix`
  по файлу, который модель не писала, не даём.
- Правка автотеста (`propose`) для таких не просится (`KB_AUTO_NOT_PROPOSED`: рецепт — в
  записи), сравнения `relate` нет (проблема в `known.refs`), пакеты и счётчики `next`, `review`
  их не считают разборами модели. Отчёт и сводка — `skill-analysis.md`.
- `RUN_SCHEMA` не поднимался: поле `kb_auto` новое и читается через `.get`, старая папка
  разбирается как раньше.

### Сигнатура

- `alla_skill_lib/signature.py`, версия `v12` (`SIGNATURE_VERSION`). Golden-тест
  (`test_signature_is_stable_across_runs_and_pinned`) фиксирует хэш: материал меняется только
  осознанно и с новой версией — префикс не даёт старому хэшу совпасть с новым. Чтения и учёта
  старых версий нет: хэши с другим префиксом не совпадают; запись с тестами узнаётся точно
  по тесту и признаку (см. «Смена версии сигнатуры» выше), без тестов — только по
  `error_example`; история повторов с другим префиксом не совпадает. `v9` — ядро распознаёт логи Go и Java, которые раньше не
  доходили до материала (klog, `panic:`/`fatal error:`, `Exception in thread`, уровни
  `PANIC`/`DPANIC`, длинный MDC, JSON-записи), см. `core.md`, «Сбор данных». `v10` — ошибка
  статуса HTTP-клиента стала симптомом (лог входит в материал, см. ниже). `v11` — слова в
  строке лога любого алфавита (`_has_signal_words`, `_WORD_RE`): «два латинских слова»
  отбрасывали русскую строку ERROR (`Пул соединений базы данных исчерпан`), и две проблемы,
  разведённые gate по логу, получали одну сигнатуру — запись базы знаний одной точно
  предлагалась другой (ревью Codex). Версию подняли, а не оставили, как у `v9`: прежний хэш
  такой пары — ложно общий и остался бы точным совпадением. `v12` — у симптома в материал
  входят и строки HTTP-ответа (`http`, см. ниже), а ошибки статуса Spring стали симптомами:
  ответ SOAP «счёт закрыт» и «не хватает средств» за одним `expected 200 but was 500` и пул
  БД с NPE за одним `HttpServerErrorException$InternalServerError` давали одну сигнатуру, и
  запись одной проблемы подсказывалась другой как точная (dev `same_assert_http_causes`,
  `same_exception_split_log_causes`, `spring_client_error_log_causes` — 404 клиента Spring:
  `signature_shared_wrong` 3 → 0, `kb_offers_wrong` 3 → 0; `kb_offers_found`, `kb_exact_kept`,
  `kb_auto` не упали, `signature_log_unstable` 22 → 23 — смешанный кластер
  `same_exception_two_log_causes`).
- Материал — то, что называет причину, и то, что различают gates кластеризации
  (`signature_material`: основа `message+trace+resources+log`… и нормализованные части):
  - трейс есть, ошибка называет причину (исключение не-ассерт или `Caused by`) — сообщение и
    якорь трейса (первая строка ошибки и строки причин основной цепочки, без кадров и веток
    `Suppressed`), лог не входит: точное узнавание не должно зависеть от шума лога;
  - трейс есть, ошибка — **симптом** (`log_names_cause`: общий ассерт без `Caused by` или
    корневое исключение-симптом, см. ниже) — ещё и строки-ошибки лога
    (исключения, `Caused by`, `Traceback`; строки события с уровнем из
    `log_events.ERROR_LEVELS` до последней строки заголовка включительно —
    `LogEvent.level_line`: у JUL это вторая строка `ALERT: …` под заголовком, у .NET
    SimpleConsole — сообщение под `fail: Category[1]`; у события любого уровня — его строки с
    полями ошибки ответа, `log_events.has_error_fields`: `"errorMessage":"счет закрыт"` в INFO,
    и без проверки «два слова» (`_has_signal_words`) — строка `"errorCode": 6` тела
    многострочного ответа одна называет ошибку, иначе коды 6 и 12 давали одну сигнатуру, а
    общий ассерт терял лог (ревью Codex); у ERROR-записи тело ответа тоже бывает строкой ниже
    заголовка (ревью Codex, `v10`);
    слова error/fatal/severe/critical/failed — всё со смыслом).
    Уровень читает разбор событий `iter_events`, как при извлечении лога: по позиции, в
    любом регистре (`[alert]`, `[err]`, `level=crit`); «alert» в тексте INFO — не уровень.
    Лог из одних обычных строк (INFO) не добавляется. Иначе `expected: <200> but was: <500>`
    у пула БД и у NPE давал одну сигнатуру, и запись базы знаний предлагалась чужой проблеме
    точно. И строки секций HTTP того же лога (`_http_lines`: статус, поля ошибки и сообщения
    ответа в мягком виде строки лога, без строки `Корреляция:` — id запроса свой у каждого
    прогона): ответ SOAP (XML ядро как лог не читает, у теста только секция HTTP) один
    называет причину (`v12`). Gate кластеризации HTTP не берёт — такие кластеры разводит шаг;
  - трейса нет — сообщение, якорь лога (без ошибок — первые обычные строки) и строки HTTP;
  - лог для обеих частей — один (`_signature_log`: представителя; без него — самый
    содержательный у участников по якорю, без строк якоря у всех — первый); его же берут
    отпечаток лога (`cluster_log_errors`) и проверка тестов группы (`as_representatives`);
  - всегда — **ресурсы** сообщения (`resources`: `host:…`, `locator:…` из
    `alla_core.utils.message_resources`) в том же виде, по которому режет gate по ресурсам
    (`core.md`): что разделяет он, разделяет и сигнатура. Без этой части длинное сообщение с
    разным портом (`_soft` → `<NUM>`) и локаторы `#Login`/`#login` (`_collapse` → нижний
    регистр) давали одну сигнатуру двум кластерам. IP у gate — `<ip>`, цифры — `#`, поэтому
    лишнего дробления нет.
- Общий ассерт — `is_generic_assertion`: признаки в одной константе `GENERIC_ASSERTION_RE`
  (`java.lang.`/`kotlin.AssertionError`, Python `AssertionError`, `AssertionFailedError`
  opentest4j/junit3, `ComparisonFailure`, `org.assertj.…`, pytest `assert …`, Hamcrest
  `Expected: …`/`but: was`, `expected … but was|found`) по строкам сообщения и трейса без
  кадров и префикса pytest `E `; строка с классом исключения не из списка признак отменяет.
  Решает класс, а не текст: `AssertionError: Order not found` — тоже общий (текст проверки
  описывает симптом). Список расширяется, только если эталон это показывает
  (`kb_offers_wrong` падает, `kb_offers_found` нет).
- Исключение-симптом — `is_symptom_exception`: **корневое** исключение трейса (последняя
  строка исключения основной цепочки: самый глубокий `Caused by` у Java, последнее
  исключение у Python) из `SYMPTOM_EXCEPTION_RE` — `java.net.SocketTimeoutException`,
  `java.net.SocketException` (reset, broken pipe), `java.net.http.HttpTimeoutException`,
  `java.util.concurrent.TimeoutException`; `requests.exceptions`/`httpx`
  `ReadTimeout|ConnectTimeout|Timeout`, `urllib3` `ReadTimeoutError|ConnectTimeoutError`,
  `socket.timeout`, `TimeoutError`, `ConnectionResetError`; ошибка статуса HTTP-клиента
  `httpx.HTTPStatusError`, `requests.exceptions.HTTPError` (`v10`: 500 от `raise_for_status`
  — тот же симптом, что `expected 200 but was 500`; dev `same_symptom_log_causes` — три
  проблемы за одним `HTTPStatusError` получали одну сигнатуру, `signature_shared_wrong` 3 → 0);
  у Spring (`v12`) — `org.springframework.web.client` `HttpServerErrorException`,
  `HttpClientErrorException`, `HttpStatusCodeException`, `UnknownHttpStatusCodeException`,
  `RestClientResponseException` (с вложенным классом статуса `$InternalServerError`,
  `$NotFound`…) и `WebClientResponseException` реактивного клиента: текст ответа в сообщении
  (`"order submit failed"`) у разных причин бывает один (dev `same_exception_split_log_causes`).
  Таймаут и обрыв причину не
  называют — её называет лог (`timeouts_two_causes`: nginx и медленный запрос за одним
  `Read timed out`); `ResourceAccessException … Caused by: SocketTimeoutException` — тоже
  симптом, а таймаут, обёрнутый `Caused by: IOException: No space left`, — нет. Не симптомы:
  `ConnectException` (называет хост), UI-ожидания (Selenium `TimeoutException`, Selenide) —
  их различает локатор. Решает класс корня, а не текст.
- Основная цепочка — `_main_chain`: без кадров и без веток `Suppressed` (JVM печатает
  `Suppressed:` с отступом, кадры и `Caused by` ветки — внутри, `Caused by` основной
  цепочки — левее). Иначе `Caused by: IOException` подавленного исключения становился
  корнем таймаута, а у общего ассерта отменял его. Без отступов ветку не отличить: всё после
  `Suppressed:` в цепочку не входит. По ней же `is_generic_assertion` ищет `Caused by` и
  чужие классы, а `_trace_part` строит якорь трейса: ошибка закрытия ресурса при той же
  основной цепочке сигнатуру не меняет, и её строки не вытесняют причину из якоря (до 4
  строк). Список расширяется, только если
  эталон это показывает (растёт `signature_shared_wrong`, README эталона, «Сигнатуры»).
- Почему не «лог всегда» и не «по решениям кластеризации». Всегда — точное узнавание
  ошибки теста, которая сама называет причину (NPE, `IllegalStateException`), зависело бы от
  фона лога приложения. По решениям кластеризации — сигнатура зависела бы от соседей по
  прогону: в прогоне без «соседа» ложное точное совпадение вернулось бы.
- Цена лога в сигнатуре — фон: ошибка, которая есть в одном прогоне и нет в другом, меняет
  сигнатуру (точное узнавание пропадает, `error_example` остаётся). Общий фон двух логов с
  разными своими ошибками сигнатуры не сравнивает. Эталон меряет цену числом
  `signature_log_unstable` (только информирует).
- Границы. Gate по шагу в сигнатуру не входит: одна причина на разных шагах (упавший пул)
  должна узнаваться точно. Кластеры, разделённые gate по логу, совпадут по сигнатуре, если их
  свои ошибки не попали в первые 6 строк якоря или отличаются только строками продолжения
  без признаков ошибки (их берёт gate, но не якорь), или ошибка теста считается называющей
  причину, а различает их только лог (так было с `httpx.HTTPStatusError` до `v10`); их ловит
  `signature_shared_wrong`.
- Разделение склеенного кластера (gate кластеризации) сигнатуру не пересчитывает задним
  числом: кластер, которому достался прежний представитель, сохраняет её, отделившийся
  получает свою — точное совпадение записи, подтверждённой для склейки, у него пропадает
  (раньше оно было ложным).
- Лог — представителя; нет его лога — самый содержательный у участников (с причинами, с
  ошибками). Строки якоря уникальны и упорядочены по своему виду в сигнатуре (`_unique`):
  повторы, различающиеся ID или временем, не вытесняют другие строки, число повторов на
  сигнатуру не влияет. До 6 строк-ошибок, до 3 обычных.
- Секция-журнал (`StructuredErrorLogHandler`: JSON с отступами, поле на строке) читается по
  записям (`_json_records`): строка якоря — `[уровень] сообщение ошибка код=…` одной записи
  (`level`/`logLevel`/`severity`…; `message`/`msg`/`error`…; коды `errorCode`/`code`/`status`
  — с именем поля, `error_code=10001`, иначе число ушло бы в `<NUM>`), иначе уровень и
  сообщение разошлись бы по строкам и журнал выпал бы из сигнатуры общего ассерта. Записи
  разделяются не скобками (отбор лога оставляет окна вокруг ошибок и срезает `{`), а
  строками полей: поле записи — на наименьшем отступе; запись кончается строкой короче
  (скобка, пропуск) или повтором поля. Запись с уровнем из `ERROR_LEVELS` или с полями ошибки
  ответа (`has_error_fields`) — ошибка, остальные — обычные; прочие поля (`rqUID`, время) не входят. Журналом считается только
  секция `журнал` (или лог без заголовков) и только с полями на строке: JSON-записи строкой
  в секции файла (NDJSON, `core.md`) — события `iter_events`, их заголовок и строки стека
  входят как у текстового лога (иначе компактная строка давала ноль записей и лог выпадал
  из материала).
- Нормализация: строки трейса и лога и длинное сообщение — мягкая (`normalize_text`: время,
  UUID, IP, длинные числа, значения полей id операции; в строке лога — ещё номер процесса в
  заголовке записи сразу после времени, `_LOG_PID_RE`: Ruby `E, [<TS> #54321]`, журнал
  PostgreSQL `<TS> UTC [2231]` — скобки защитили бы его как значение, а после перезапуска
  сервиса он другой, ревью Codex; слово перед скобкой — пояс из 3–4 букв, а не уровень
  `log_events.LEVELS`: `ERROR [12]`, `FINE [12]` — значение после уровня, не PID), коды ошибок — отдельным отпечатком; короткое сообщение (до 10
  слов и 120 символов) — строгая, числа остаются. Везде имена потоков заменяются на
  `<THREAD>` (`replace_thread_names`: `http-nio-8080-exec-7`, `pool-3-thread-1`,
  `ForkJoinPool.commonPool-worker-5`, `ForkJoinPool-1-worker-7`, `Thread-42`): одна ошибка на
  разных потоках даёт одну сигнатуру.
- Числовой отпечаток (`code=…`, `ORA-…`) — `text_normalization.numeric_codes`, общий со
  свёрткой повторов лога; имена потоков и id операции (`op-tr-3001`, значение `operUID=…`)
  кодами не считаются, а в мягком виде значение поля id операции — `<ID>` (`core.md`, «Id
  операции»). Версию `v9` это не подняло: материал меняется только у логов с такими id, а их
  сигнатура и так была своей у каждого теста и между прогонами не совпадала. Признак базы
  знаний (`normalize_fp` → `normalize_text`) с сохранённым `operUID=op-tr-<NUM>` узнаётся:
  значение с плейсхолдерами тоже становится `<ID>`.
- **Строки лога — свой мягкий вид** (`_soft_log`, только якорь лога; сообщение и трейс —
  `_soft`). `normalize_text` оставляет длинное число у кавычки или скобки — защита значений
  ассерта (`expected:<10001>`, `"-1001"`). В строке лога кавычки — синтаксис JSON и
  `key="…"`: `"account":"40817810000000000301"` — такой же ID, как `account=4081…`, и
  становится `<NUM>` (`_LOG_QUOTED_NUMBER_RE`); у скобки (`[10001]`, `<10001>`) число и в
  логе остаётся. Код в кавычках (`"errorCode":"10001"`) так тоже стирается, а `numeric_codes`
  имени `errorcode` не знает — поэтому к отпечатку добавляются числовые коды полей ошибки
  ответа, где есть число из 4+ цифр (`log_events.error_field_codes`: `errorcode=10001`,
  `faultcode=…`), и составные: `"10001.1"` и `"10002.1"` иначе оба давали `<num>.1` (ревью Codex).
  Короткий код (`"errorCode":6`) остаётся в тексте и в отпечаток не идёт: хэш таких строк
  прежний. Кластеризация, признак базы знаний и свёртка повторов защиту сохраняют. Без этого
  dev `info_business_error`: сигнатура кластера «счёт закрыт» менялась с логом участника
  (номер счёта получателя у каждого теста свой). Версию `v9` это не подняло (как id
  операции и поля ошибки ответа): меняются только строки лога с длинным числом в кавычках
  или с числовым кодом поля ошибки ответа из 4+ цифр; такой материал (`"<num>"`, код
  `errorcode=`) прежняя версия дать не могла, поэтому ложного точного совпадения нет, а у
  остальных хэш прежний. Цена: константа в кавычках (`"amount":"5000"`) больше не различает
  сигнатуры, как и без кавычек; раньше незаметный `errorCode=10001` без кавычек (был `<NUM>`
  без отпечатка) теперь различает.
- Пометки строк источника (`[строки a–b]`) в материал не входят: `_log_evidence` их
  вырезает (`strip_source_marks`), поэтому их нет и в `evidence/NN.txt` (`cluster_sources` —
  сообщение, трейс и лог представителя для признака базы знаний, через `kb.cluster_evidence`).
- Считается в `prepare` на enriched моделях и сохраняется в `entry.signature`;
  `remember`/`reject` используют её.
- Реальный `run.json` исключает `log_snippet`, `status_trace`, `execution_steps` и transient
  `log_selection_*`. `load_models` восстанавливает сокращённые данные отчёта; пересчёт
  сигнатуры из них не является контрактом. Полный model roundtrip с логом сохраняет
  сигнатуру необрезанного лога.
- Поля ошибки ответа (`core.md`) версию `v9` не подняли: материал меняется только у логов, где
  есть записи не уровня ошибки с такими полями (их событий раньше не было в секции `файл`, а
  в журнале они были обычными строками); у остальных хэш прежний, точное узнавание
  сохраняется.
- Новый отбор ранее обрезавшихся логов может изменить точные `confirmed_signatures`/повторы;
  узнавание по `error_example` остаётся.

### Отметки «нестабильный тест» (`flaky.py`, `skill-rerun.md`)

- `<kb_dir>/flaky/<Класс>_<метод>_<sha1(ключ)[:10]>.json` — одна отметка на тест (общий

- Пишет только `rerun --remember --result <job>` после «да» (`flaky.remember_plan`): отметить

## Модули (`modules`)

Задача: базы разных модулей не должны пересекаться.

- Модуль теста — ближайшая папка выше его исходника с `build.gradle` / `build.gradle.kts` /
  `pom.xml`. Исходник ищется по `full_name` через `ProjectIndex`, не по кадрам стека: стек
  ведёт в общие модули. Корень проекта и не-JVM файлы — модуль `""` (общая база в корне git,
  как в одномодульном проекте).
- Разделение включается, только если JVM-исходники (не `.kts`, не `buildSrc`/`build-logic`)
  лежат минимум в двух модулях (`ModuleResolver.is_multimodule`). Один проект во вложенной
  папке (`autotests/pom.xml`) остаётся одномодульным — иначе его прежняя база в корне и
  история повторов потерялись бы.
- Копия кода приложения расширения `sut-code` (`.alla-sut/`) — в `code_hints.SKIP_DIRS`:
  `os.walk` её `.gitignore` не читает, и `pom.xml` копии включал многомодульный режим (база
  уезжала из корня), а исходники приложения вытесняли автотесты из индекса (50 000 файлов) —
  ревью Codex.
- Совпадение `full_name` с исходником должно быть однозначным (`ProjectIndex.best_matches`):
  одинаковый класс в двух модулях модуль не определяет, а выбор «первого найденного»
  отправил бы `remember` в чужую базу.
- Модуль кластера — самый частый среди тестов с однозначным исходником (до 50; ничья — у
  представителя). Кластер без такого берёт модуль прогона (`resolve_run_modules`: все
  определившиеся кластеры из одного модуля; для неоднозначного — только если он среди
  кандидатов), иначе `""`.
- `cli._write_run` пишет в запись кластера `module` и `kb_dir`. Подбор записей,
  `remember`/`reject` (`feedback.project_kb(run, entry)`) и повторы работают только с базой
  своего модуля.
- Проект сборки для перезапуска тестов (`rerun`, `skill-rerun.md`) — другое понятие:
  `build_dir` — ближайшая папка с файлом сборки **включая корень проекта** (модуль базы
  знаний корень не считает), `build_tool` — `maven` по `pom.xml`, `gradle` по
  `build.gradle(.kts)` (оба — `maven`), `maven_reactor` — самая верхняя папка подряд с
  `pom.xml` над модулем (`<modules>` не разбирается). Класс и метод теста —
  `code_hints.jvm_test_of`: один JVM-исходник, класс с пакетом из `full_name` (папки не обязаны
  повторять пакет), метод сразу после класса; иначе — причина словами. Папки совсем не
  похожи на пакет (`src/test/kotlin/OrderTest.kt`) — единственный файл с именем класса и тем же
  `package` (`_match_by_package`, ревью Codex); подсказки по коду этот путь не используют.

## Обратная связь (`feedback`)

Отказы `remember` (`STATUS: fix`) считаются подряд по проблеме в `state.json`
(`refusals`, `feedback.MAX_REFUSALS` = 3): ответ начинается с «Попытка N из 3», третий отказ —
`STATUS: error` без «Затем выполни» (показать замечания пользователю и не повторять), счёт
после него и после успешного `remember` начинается заново. Лимита попыток, как у `next`, у
`remember` раньше не было, и модель могла повторять его бесконечно.

**Вопрос после отчёта** (решение пользователя 2026-10-26): `done` просит спросить, какие
разборы верны (`cli._kb_question`), — первым пунктом «После отчёта», до правок и перезапуска:
за цепочкой «правка → проверка перезапуском» он терялся (ревью исполнителя). Команда — с
местом для номеров (`remember N1 N2 … --from-analysis`) и «верны все» — списком: готовая со
всеми номерами при правиле «команды — как есть» сохраняла бы и разбор, названный неверным.
Повторно о тех же номерах не спрашивается. Номера —
`cli._kb_offer`: принятые разборы агента с категорией, кроме `auto`, разобранных по базе знаний,
неоднородных, по отвергнутой записи или с другой категорией, чем у её записи
(`known.mismatched`), с подтверждённым выводом расширения и тех, что запись уже узнаёт точно
(`current_kb_matches` → `exact`: сохранённое второй раз не спрашиваем) — кроме узнанных точно
с логом, которого запись не видела, если разбор назвал эту запись (`_new_log_of`):
подтверждение добавит отпечаток, и в следующий раз проблема разберётся без модели. Группы «одна причина»
(объединил агент) — отдельно: их пользователь видел общей причиной, сохраняются по
`feedback.md` «Порядок», не `--from-analysis`. Проблемы с правкой агента (`separate`) отчёт
не объединяет — у каждой своя команда `apply`, и вопрос называет их отдельными номерами
(ревью Codex: иначе вопрос называл пункт «Проблема 1 и 2», которого в отчёте нет). Молчание — не согласие: без ответа ничего не
пишется (вариант «сохранять всё, что не отвергли» пользователь отклонил — догадки модели стали
бы подтверждёнными и повторялись бы без агента).

`remember N N… --from-analysis` (`feedback.remember_many`; несколько номеров — только с
`--from-analysis` и без `--entry`): каждый номер — общим путём `_remember`, отказ одного не
мешает остальным; ответ `saved` перечисляет сохранённое, «Не сохранены проблемы …» — суть
каждого отказа строкой (`_refusal_reason`), **без** его команд и формата (у «уже
подтверждали» и «запись уже есть» — и без команды обновления записи после `_UPDATE_PREFIX`:
оговорка «обновляй, только если…» стоит строкой ниже и в пакет не попадает, ревью Codex): их «Затем
выполни» модель выполнила бы подряд или написала бы файл обратной связи из своего разбора;
сохранить такие номера — только со слов пользователя. `next` — одной строкой в конце. Не
сохранилось ничего: один номер — ответ как у одной проблемы, несколько — `error` со
списком. «Уже подтверждали в записи R» (не у `--from-extension`) — ещё и строка: обновлять R,
только если пользователь уточняет её рецепт, другая причина — сначала `reject` (иначе
`--entry R` переписал бы запись для всех проблем, которые она узнаёт). Просьба `next` после
`reject`/`remember` (`_report_refresh`) называет и `analyze`.
`--from-analysis` у разбора со ссылкой `БАЗА ЗНАНИЙ: R` (и без `--entry` или `--entry R`)
**подтверждает R**: `record.confirm(signature, tests)`, текст записи (слова инженера) не
меняется, проверки текста не нужны; категория разбора не та, что у R, — отказ (`fix`:
спросить пользователя). Раньше создавалась запись-дубль из слов разбора: `owner` искался
только среди точных, а R узнавала по признаку.

`remember`/`reject` берут данные из `feedback/NN.md` (или подтверждённого разбора, см.
`--from-analysis` в `skill-protocol.md`); признак проверяется по `evidence/NN.txt`, секреты не
пишутся. Отчёт они не пересобирают; если изменённую запись называет хоть один разбор прогона
(`БАЗА ЗНАНИЙ:` того же `kb_dir`), вывод просит выполнить `next` (`_report_refresh`) — так
группа известной проблемы распадается после `reject`.

Третий источник `remember` — `--from-extension <имя>` (взаимоисключающий с
`--from-analysis`): последний `extensions/<имя>/*-NN.finding.json` (`confirmed.find_finding`),
проверка формы, `format_ok`, категории и секретов — `confirmed.check_finding`; признак —
признак кластера. Отказы здесь — `error` без «Попытки N из 3»: вывод расширения модель не
перепишет. `kb_fields` вывода — своё поле записи `<имя>` (`KBRecord.extra`, с `confirmed` и
`launch_id`), `confirmed/NN.json` — для отчёта (`skill-analysis.md`), поэтому ответ всегда
просит `next`. Общий путь трёх источников — `feedback._Input`. Подтверждение снимается
(`confirmed.drop_confirmed`, ответ просит `next`): `remember` без `--from-extension` по той
же проблеме — пользователь поправил причину, а прежний `confirmed/NN.json` показывал бы
старую как подтверждённую (ревью Codex); `reject` записи, в которую подтверждение сохранено
(`kb_entry`).

## История (`history`)

- `alla-reports/history.jsonl` (локально). Повторы — по точной сигнатуре или записи базы
  знаний из другого `launch_id` **того же модуля** (`module` в записи истории; корень —
  `""`). Строки прежних версий (без `run`, `file_id` или `module`) при чтении пропускаются.
- В задание идёт только число повторов и дата; прошлые выводы модели не подаются — они
  анкерят её на непроверенной догадке.
- История только дописывается: каждый `done` сравнивает полные записи и пишет лишь
  изменённые/отсутствующие. `load_history` оставляет последнюю физическую строку
  `(run, file_id)` до фильтрации повторов. Это обновляет `kb_entry` независимо от хэша
  сводки.
- Даты исходные; число повторов считается по разным `launch_id`.
- `kb_entry` в записи — только подтверждённая ссылка (`known_issues.refs`): отвергнутая после
  разбора запись повторы не считает; после `reject` и `next` строка прогона перезаписывается.
