# База знаний: сигнатура

## Сигнатура

- `alla_skill_lib/signature.py`, версия `v12` (`SIGNATURE_VERSION`). Golden-тест
  (`test_signature_is_stable_across_runs_and_pinned`) фиксирует хэш: материал меняется только
  осознанно и с новой версией — префикс не даёт старому хэшу совпасть с новым. Чтения и учёта
  старых версий нет: хэши с другим префиксом не совпадают; запись с тестами узнаётся точно
  по тесту и признаку (см. `skill-memory.md`, «Смена версии сигнатуры»), без тестов — только по
  `error_example`; история повторов с другим префиксом не совпадает. `v9` — ядро распознаёт логи Go и Java, которые раньше не
  доходили до материала (klog, `panic:`/`fatal error:`, `Exception in thread`, уровни
  `PANIC`/`DPANIC`, длинный MDC, JSON-записи), см. `core-log-events.md`. `v10` — ошибка
  статуса HTTP-клиента стала симптомом (лог входит в материал, см. ниже). `v11` — слова в
  строке лога любого алфавита (`_has_signal_words`, `_WORD_RE`): «два латинских слова»
  отбрасывали русскую строку ERROR (`Пул соединений базы данных исчерпан`), и две проблемы,
  разведённые gate по логу, получали одну сигнатуру — запись базы знаний одной точно
  предлагалась другой (ревью Codex). Версию подняли, а не оставили, как у `v9`: прежний хэш
  такой пары — ложно общий и остался бы точным совпадением. `v12` — у симптома в материал
  входят и строки HTTP-ответа (`http`, см. ниже), а ошибки статуса Spring стали симптомами:
  ответ SOAP «счёт закрыт» и «не хватает средств» за одним `expected 200 but was 500` и пул
  БД с NPE за одним `HttpServerErrorException$InternalServerError` давали одну сигнатуру, и
  запись одной проблемы подсказывалась другой как точная (dev `same_assert_http_causes`,
  `same_exception_split_log_causes`, `spring_client_error_log_causes` — 404 клиента Spring:
  `signature_shared_wrong` 3 → 0, `kb_offers_wrong` 3 → 0; `kb_offers_found`, `kb_exact_kept`,
  `kb_auto` не упали, `signature_log_unstable` 22 → 23 — смешанный кластер
  `same_exception_two_log_causes`).
- Материал — то, что называет причину, и то, что различают gates кластеризации
  (`signature_material`: основа `message+trace+resources+log`… и нормализованные части):
  - трейс есть, ошибка называет причину (исключение не-ассерт или `Caused by`) — сообщение и
    якорь трейса (первая строка ошибки и строки причин основной цепочки, без кадров и веток
    `Suppressed`), лог не входит: точное узнавание не должно зависеть от шума лога;
  - трейс есть, ошибка — **симптом** (`log_names_cause`: общий ассерт без `Caused by` или
    корневое исключение-симптом, см. ниже) — ещё и строки-ошибки лога
    (исключения, `Caused by`, `Traceback`; строки события с уровнем из
    `log_events.ERROR_LEVELS` до последней строки заголовка включительно —
    `LogEvent.level_line`: у JUL это вторая строка `ALERT: …` под заголовком, у .NET
    SimpleConsole — сообщение под `fail: Category[1]`; у события любого уровня — его строки с
    полями ошибки ответа, `log_events.has_error_fields`: `"errorMessage":"счет закрыт"` в INFO,
    и без проверки «два слова» (`_has_signal_words`) — строка `"errorCode": 6` тела
    многострочного ответа одна называет ошибку, иначе коды 6 и 12 давали одну сигнатуру, а
    общий ассерт терял лог (ревью Codex); у ERROR-записи тело ответа тоже бывает строкой ниже
    заголовка (ревью Codex, `v10`);
    слова error/fatal/severe/critical/failed — всё со смыслом).
    Уровень читает разбор событий `iter_events`, как при извлечении лога: по позиции, в
    любом регистре (`[alert]`, `[err]`, `level=crit`); «alert» в тексте INFO — не уровень.
    Лог из одних обычных строк (INFO) не добавляется. Иначе `expected: <200> but was: <500>`
    у пула БД и у NPE давал одну сигнатуру, и запись базы знаний предлагалась чужой проблеме
    точно. И строки секций HTTP того же лога (`_http_lines`: статус, поля ошибки и сообщения
    ответа в мягком виде строки лога, без строки `Корреляция:` — id запроса свой у каждого
    прогона): ответ SOAP (XML ядро как лог не читает, у теста только секция HTTP) один
    называет причину (`v12`). Gate кластеризации HTTP не берёт — такие кластеры разводит шаг;
  - трейса нет — сообщение, якорь лога (без ошибок — первые обычные строки) и строки HTTP;
  - лог для обеих частей — один (`_signature_log`: представителя; без него — самый
    содержательный у участников по якорю, без строк якоря у всех — первый); его же берут
    отпечаток лога (`cluster_log_errors`) и проверка тестов группы (`as_representatives`);
  - всегда — **ресурсы** сообщения (`resources`: `host:…`, `locator:…` из
    `alla_core.utils.message_resources`) в том же виде, по которому режет gate по ресурсам
    (`core-clustering.md`): что разделяет он, разделяет и сигнатура. Без этой части длинное сообщение с
    разным портом (`_soft` → `<NUM>`) и локаторы `#Login`/`#login` (`_collapse` → нижний
    регистр) давали одну сигнатуру двум кластерам. IP у gate — `<ip>`, цифры — `#`, поэтому
    лишнего дробления нет.
- Общий ассерт — `is_generic_assertion`: признаки в одной константе `GENERIC_ASSERTION_RE`
  (`java.lang.`/`kotlin.AssertionError`, Python `AssertionError`, `AssertionFailedError`
  opentest4j/junit3, `ComparisonFailure`, `org.assertj.…`, pytest `assert …`, Hamcrest
  `Expected: …`/`but: was`, `expected … but was|found`) по строкам сообщения и трейса без
  кадров и префикса pytest `E `; строка с классом исключения не из списка признак отменяет.
  Решает класс, а не текст: `AssertionError: Order not found` — тоже общий (текст проверки
  описывает симптом). Список расширяется, только если эталон это показывает
  (`kb_offers_wrong` падает, `kb_offers_found` нет).
- Исключение-симптом — `is_symptom_exception`: **корневое** исключение трейса (последняя
  строка исключения основной цепочки: самый глубокий `Caused by` у Java, последнее
  исключение у Python) из `SYMPTOM_EXCEPTION_RE` — `java.net.SocketTimeoutException`,
  `java.net.SocketException` (reset, broken pipe), `java.net.http.HttpTimeoutException`,
  `java.util.concurrent.TimeoutException`; `requests.exceptions`/`httpx`
  `ReadTimeout|ConnectTimeout|Timeout`, `urllib3` `ReadTimeoutError|ConnectTimeoutError`,
  `socket.timeout`, `TimeoutError`, `ConnectionResetError`; ошибка статуса HTTP-клиента
  `httpx.HTTPStatusError`, `requests.exceptions.HTTPError` (`v10`: 500 от `raise_for_status`
  — тот же симптом, что `expected 200 but was 500`; dev `same_symptom_log_causes` — три
  проблемы за одним `HTTPStatusError` получали одну сигнатуру, `signature_shared_wrong` 3 → 0);
  у Spring (`v12`) — `org.springframework.web.client` `HttpServerErrorException`,
  `HttpClientErrorException`, `HttpStatusCodeException`, `UnknownHttpStatusCodeException`,
  `RestClientResponseException` (с вложенным классом статуса `$InternalServerError`,
  `$NotFound`…) и `WebClientResponseException` реактивного клиента: текст ответа в сообщении
  (`"order submit failed"`) у разных причин бывает один (dev `same_exception_split_log_causes`).
  Таймаут и обрыв причину не
  называют — её называет лог (`timeouts_two_causes`: nginx и медленный запрос за одним
  `Read timed out`); `ResourceAccessException … Caused by: SocketTimeoutException` — тоже
  симптом, а таймаут, обёрнутый `Caused by: IOException: No space left`, — нет. Не симптомы:
  `ConnectException` (называет хост), UI-ожидания (Selenium `TimeoutException`, Selenide) —
  их различает локатор. Решает класс корня, а не текст.
- Основная цепочка — `_main_chain`: без кадров и без веток `Suppressed` (JVM печатает
  `Suppressed:` с отступом, кадры и `Caused by` ветки — внутри, `Caused by` основной
  цепочки — левее). Иначе `Caused by: IOException` подавленного исключения становился
  корнем таймаута, а у общего ассерта отменял его. Без отступов ветку не отличить: всё после
  `Suppressed:` в цепочку не входит. По ней же `is_generic_assertion` ищет `Caused by` и
  чужие классы, а `_trace_part` строит якорь трейса: ошибка закрытия ресурса при той же
  основной цепочке сигнатуру не меняет, и её строки не вытесняют причину из якоря (до 4
  строк). Список расширяется, только если
  эталон это показывает (растёт `signature_shared_wrong`, README эталона, «Сигнатуры»).
- Почему не «лог всегда» и не «по решениям кластеризации». Всегда — точное узнавание
  ошибки теста, которая сама называет причину (NPE, `IllegalStateException`), зависело бы от
  фона лога приложения. По решениям кластеризации — сигнатура зависела бы от соседей по
  прогону: в прогоне без «соседа» ложное точное совпадение вернулось бы.
- Цена лога в сигнатуре — фон: ошибка, которая есть в одном прогоне и нет в другом, меняет
  сигнатуру (точное узнавание пропадает, `error_example` остаётся). Общий фон двух логов с
  разными своими ошибками сигнатуры не сравнивает. Эталон меряет цену числом
  `signature_log_unstable` (только информирует).
- Границы. Gate по шагу в сигнатуру не входит: одна причина на разных шагах (упавший пул)
  должна узнаваться точно. Кластеры, разделённые gate по логу, совпадут по сигнатуре, если их
  свои ошибки не попали в первые 6 строк якоря или отличаются только строками продолжения
  без признаков ошибки (их берёт gate, но не якорь), или ошибка теста считается называющей
  причину, а различает их только лог (так было с `httpx.HTTPStatusError` до `v10`); их ловит
  `signature_shared_wrong`.
- Разделение склеенного кластера (gate кластеризации) сигнатуру не пересчитывает задним
  числом: кластер, которому достался прежний представитель, сохраняет её, отделившийся
  получает свою — точное совпадение записи, подтверждённой для склейки, у него пропадает
  (раньше оно было ложным).
- Лог — представителя; нет его лога — самый содержательный у участников (с причинами, с
  ошибками). Строки якоря уникальны и упорядочены по своему виду в сигнатуре (`_unique`):
  повторы, различающиеся ID или временем, не вытесняют другие строки, число повторов на
  сигнатуру не влияет. До 6 строк-ошибок, до 3 обычных.
- Секция-журнал (`StructuredErrorLogHandler`: JSON с отступами, поле на строке) читается по
  записям (`_json_records`): строка якоря — `[уровень] сообщение ошибка код=…` одной записи
  (`level`/`logLevel`/`severity`…; `message`/`msg`/`error`…; коды `errorCode`/`code`/`status`
  — с именем поля, `error_code=10001`, иначе число ушло бы в `<NUM>`), иначе уровень и
  сообщение разошлись бы по строкам и журнал выпал бы из сигнатуры общего ассерта. Записи
  разделяются не скобками (отбор лога оставляет окна вокруг ошибок и срезает `{`), а
  строками полей: поле записи — на наименьшем отступе; запись кончается строкой короче
  (скобка, пропуск) или повтором поля. Запись с уровнем из `ERROR_LEVELS` или с полями ошибки
  ответа (`has_error_fields`) — ошибка, остальные — обычные; прочие поля (`rqUID`, время) не входят. Журналом считается только
  секция `журнал` (или лог без заголовков) и только с полями на строке: JSON-записи строкой
  в секции файла (NDJSON, `core-log-events.md`) — события `iter_events`, их заголовок и строки стека
  входят как у текстового лога (иначе компактная строка давала ноль записей и лог выпадал
  из материала).
- Нормализация: строки трейса и лога и длинное сообщение — мягкая (`normalize_text`: время,
  UUID, IP, длинные числа, значения полей id операции; в строке лога — ещё номер процесса в
  заголовке записи сразу после времени, `_LOG_PID_RE`: Ruby `E, [<TS> #54321]`, журнал
  PostgreSQL `<TS> UTC [2231]` — скобки защитили бы его как значение, а после перезапуска
  сервиса он другой, ревью Codex; слово перед скобкой — пояс из 3–4 букв, а не уровень
  `log_events.LEVELS`: `ERROR [12]`, `FINE [12]` — значение после уровня, не PID), коды ошибок — отдельным отпечатком; короткое сообщение (до 10
  слов и 120 символов) — строгая, числа остаются. Везде имена потоков заменяются на
  `<THREAD>` (`replace_thread_names`: `http-nio-8080-exec-7`, `pool-3-thread-1`,
  `ForkJoinPool.commonPool-worker-5`, `ForkJoinPool-1-worker-7`, `Thread-42`): одна ошибка на
  разных потоках даёт одну сигнатуру.
- Числовой отпечаток (`code=…`, `ORA-…`) — `text_normalization.numeric_codes`, общий со
  свёрткой повторов лога; имена потоков и id операции (`op-tr-3001`, значение `operUID=…`)
  кодами не считаются, а в мягком виде значение поля id операции — `<ID>` (`core-logs.md`, «Id
  операции»). Версию `v9` это не подняло: материал меняется только у логов с такими id, а их
  сигнатура и так была своей у каждого теста и между прогонами не совпадала. Признак базы
  знаний (`normalize_fp` → `normalize_text`) с сохранённым `operUID=op-tr-<NUM>` узнаётся:
  значение с плейсхолдерами тоже становится `<ID>`.
- **Строки лога — свой мягкий вид** (`_soft_log`, только якорь лога; сообщение и трейс —
  `_soft`). `normalize_text` оставляет длинное число у кавычки или скобки — защита значений
  ассерта (`expected:<10001>`, `"-1001"`). В строке лога кавычки — синтаксис JSON и
  `key="…"`: `"account":"40817810000000000301"` — такой же ID, как `account=4081…`, и
  становится `<NUM>` (`_LOG_QUOTED_NUMBER_RE`); у скобки (`[10001]`, `<10001>`) число и в
  логе остаётся. Код в кавычках (`"errorCode":"10001"`) так тоже стирается, а `numeric_codes`
  имени `errorcode` не знает — поэтому к отпечатку добавляются числовые коды полей ошибки
  ответа, где есть число из 4+ цифр (`log_events.error_field_codes`: `errorcode=10001`,
  `faultcode=…`), и составные: `"10001.1"` и `"10002.1"` иначе оба давали `<num>.1` (ревью Codex).
  Короткий код (`"errorCode":6`) остаётся в тексте и в отпечаток не идёт: хэш таких строк
  прежний. Кластеризация, признак базы знаний и свёртка повторов защиту сохраняют. Без этого
  dev `info_business_error`: сигнатура кластера «счёт закрыт» менялась с логом участника
  (номер счёта получателя у каждого теста свой). Версию `v9` это не подняло (как id
  операции и поля ошибки ответа): меняются только строки лога с длинным числом в кавычках
  или с числовым кодом поля ошибки ответа из 4+ цифр; такой материал (`"<num>"`, код
  `errorcode=`) прежняя версия дать не могла, поэтому ложного точного совпадения нет, а у
  остальных хэш прежний. Цена: константа в кавычках (`"amount":"5000"`) больше не различает
  сигнатуры, как и без кавычек; раньше незаметный `errorCode=10001` без кавычек (был `<NUM>`
  без отпечатка) теперь различает.
- Пометки строк источника (`[строки a–b]`) в материал не входят: `_log_evidence` их
  вырезает (`strip_source_marks`), поэтому их нет и в `evidence/NN.txt` (`cluster_sources` —
  сообщение, трейс и лог представителя для признака базы знаний, через `kb.cluster_evidence`).
- Считается в `prepare` на enriched моделях и сохраняется в `entry.signature`;
  `remember`/`reject` используют её.
- Реальный `run.json` исключает `log_snippet`, `status_trace`, `execution_steps` и transient
  `log_selection_*`. `load_models` восстанавливает сокращённые данные отчёта; пересчёт
  сигнатуры из них не является контрактом. Полный model roundtrip с логом сохраняет
  сигнатуру необрезанного лога.
- Поля ошибки ответа (`core-log-events.md`) версию `v9` не подняли: материал меняется только у логов, где
  есть записи не уровня ошибки с такими полями (их событий раньше не было в секции `файл`, а
  в журнале они были обычными строками); у остальных хэш прежний, точное узнавание
  сохраняется.
- Новый отбор ранее обрезавшихся логов может изменить точные `confirmed_signatures`/повторы;
  узнавание по `error_example` остаётся.
