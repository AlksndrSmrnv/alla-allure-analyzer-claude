# Расширения скилла (`extensions.py`, `extensions/`)

Зачем: команды добавляют свои функции (git, задачи, чат) без форка скилла; включение —
одной командой. Руководство автора — `extensions/README.md` (контракт целиком), инструкция
агенту-автору — `extensions/AUTHORING.md` (порядок, неочевидные ограничения из кода, проверка;
меняя поведение `extensions.py` или `session_rules.WRITABLE_RE`, сверь её), для
пользователя — `references/setup.md`, «Расширения»; для модели — `SKILL.md`, «7. Расширения».

## Устройство

- Расширение — папка с `extension.toml`: встроенные `<скилл>/extensions/<имя>/` (выключены),
  свои `<проект>/alla-extensions/<имя>/`; своё с тем же именем заменяет встроенное
  (`overrides_bundled`). Включение — `enabled = [...]` в `<проект>/alla-extensions/config.toml`
  (общее для команды, в git); `enable`/`disable` переписывают только эту строку и только в корне
  (до первой таблицы: в `[<имя>]` может быть своя настройка `enabled`); многострочный
  список — отказ; новый текст перед записью разбирается `tomllib` и должен отличаться только
  корневым `enabled`, иначе файл не пишется (`_check_rewrite`), настройки `[<имя>]` переопределяют `[settings]` манифеста того же типа,
  неизвестный ключ — ошибка.
- Контракт `api = 1`. Скилл не импортирует код расширения: скрипты — отдельный процесс
  `sys.executable`, cwd — корень проекта, данные — JSON-контекст (`ALLA_CONTEXT`). Поля
  контекста и переменные шаблона задания — в `extensions/README.md`; их меняют только вместе
  с ним, несовместимо — только с новым `api`.
- События: `after_apply` (`_apply`, только `result.changed`), `after_revert` (`_revert`,
  отметка читается до отката), `after_report` (`next_step` при `done`, один раз на хэш
  `report.md` для каждого расширения: `state.json["extension_reports"]`). Там же, один раз на
  отчёт и набор ошибок (`state.json["extension_problems"]`), — строки о неисправных включённых
  расширениях: сломанное исключено из активных, и его хук иначе молча не сработал бы.
  Отметки пишутся и при пустом выводе хуков: молчаливый хук отчёта тоже не повторяется. Повтор —
  `extensions run <имя> [N]`: `after_apply` только для правки в состоянии `applied`.
- `on_request` (`REQUEST_EVENT`) — функция по просьбе пользователя: если у расширения есть
  этот хук, `extensions run <имя> N [N…] --run DIR [--param k=v…]` (`cli._extensions_request`)
  стреляет им по разу на каждую названную проблему (дубли номеров убираются, номер обязателен,
  правка и `done` не нужны), `confirm` не спрашивается. Без хука `run` — прежний повтор, а
  `--param` и несколько N — ошибка. `parse_params`: ключ `[a-z][a-z0-9_]*`, значение — одна
  строка до 500 символов; в контексте `params` — ключ → список значений, в шаблоне
  `$param_<ключ>` через запятую.
- Контекст проблемы (`problem_context(paths, entry, record, run)`) несёт `tests` (до 20,
  представитель первым) и `sources` — куски «Данных» из реестра `evidence/NN.sources.json`
  (до `MAX_SOURCES_CHARS`); общий контекст — `launch_created` из `run.json` и `params`.
- Хук `task` — задание субагенту `alla-<имя>` (файл агента расширения, проверяется как
  `alla-batch`): контекст `<папка разбора>/extensions/<имя>/<stem>.json`, задание `<stem>.md`,
  в ответ команды — блок «Расширения:» (`ext.block`) с вызовом `agent` и запасным путём без
  `subagent_type`; `confirm = true` — сначала вопрос пользователю. Хук `script` — скилл
  запускает сам, вывод (≤ `OUTPUT_LIMIT`) — пользователю.
- **Время скриптов** — под лимит Qwen на команду shell (120 с): скрипты хуков одной команды
  скилла делят `HOOK_BUDGET_S` (60 с; `fire(deadline=…)`, `hook_deadline()`; `on_request` по
  нескольким проблемам — один срок на все), каждому `min(timeout манифеста, остаток)`, без
  остатка — «не запущено»; действие — не дольше `ACTION_LIMIT_S` (110 с). Проверка манифеста
  (1–600) прежняя. Отметка `extension_reports` пишется **до** запуска хуков `after_report`.
  Причина: при `timeout` 120 зависший хук отчёта убивал `next` до отметки, и каждый следующий
  `next` запускал его снова — отчёт не выводился никогда.
- Действие — `extensions action <имя> <действие> [--context FILE | --run DIR] [-- аргументы]`:
  только включённое расширение; при --context файл только из
  `<папка отчётов>/<разбор>/extensions/<имя>/*.json`. --run строит свежий контекст по папке
  разбора. Без обоих нужен явный --reports-dir; скилл собирает общий контекст без run_dir.
  Первая строка вывода скрипта
  `STATUS: ok|error`, иначе `error`.
- Ошибка расширения (битый манифест, нечитаемый файл агента, упавший или зависший скрипт,
  неверные настройки) — строка блока «Расширения:», статус команды скилла не меняется:
  `discover` ловит `OSError`/`ValueError` манифеста, `active` — любой сбой обхода папок (его
  зовут `prepare`, `next`, `apply`), `fire` — сбой хука. `apply` после записи файла обязан
  ответить `applied`.
- Неисправная своя замена встроенного расширения выключает его: встроенное вместо неё не
  запускается (у команды могли быть свои ограничения — remote, `confirm`). В
  `alla-extensions/` расширение — любая папка (кроме `.`/`_`), без `extension.toml` — тоже
  неисправная: удалённый манифест не возвращает встроенное.
- Хук `task` — не больше одного на событие: задание пишется в `<событие>-NN.md`, второе
  затёрло бы первое. Хуков `script` на событие может быть несколько.
- Агенты включённых расширений ставит `enable` и каждый `prepare`
  (`qwen_files.install_extension_agent`); `disable` убирает файл, только если он совпадает с
  нашим.
- Слэш-команды расширения — `commands = ["commands/<имя>.md"]` в манифесте
  (`_commands`/`_check_command`: `.md`, имя по `NAME_RE`, `description`,
  `disable-model-invocation: true`, не пустой текст). Имена команд скилла заняты
  (`skill_command_names` — из папки рядом с модулем, не из `ws.SKILL_DIR`), одна команда у двух
  включённых расширений — второе в `Active.problems`. Ставятся тем же путём, что агенты:
  `enable`/`prepare` → `.qwen/commands/alla/<имя>.md`, `disable` — убрать, если файл наш.
  Цикл по командам в `_extensions_toggle` — своей переменной (`command`): `name` там — имя
  расширения, по нему подсказка называет таблицу настроек `[<имя>]`.
  `enable` поверх занятой команды отказывает (`command_conflict`) до записи `config.toml` и
  файлов: включённое ставится последним, `active` отдаёт команду первому, и второе затёрло бы
  чужой файл, оставшись неактивным (ревью Codex).
- Модель работу расширения не делает: субагент запускает только команду скилла из задания
  (правило «из shell только команды скилла» не ослаблено). `session_rules.WRITABLE_RE`
  разрешает субагенту только `extensions/<имя>/*.txt` (сообщение коммита).
- Имя `batch` занято (`RESERVED_NAMES`): субагент `alla-batch` расширения затёр бы
  субагента пакетов.

## git-publish

- `scripts/publish.py` не меняет рабочую копию, индекс и HEAD: временный индекс
  (`GIT_INDEX_FILE`) от `base`; если версия файла в базе == `sha_before` — блоб = текущий файл
  байт в байт (`hash-object --stdin`, без фильтров), иначе `git apply --cached` показанного
  патча (`--directory`, если проект — подпапка репозитория), не ложится — отказ.
- Файл ≠ `sha_after` — отказ (ушли бы чужие правки). Ветка `<branch_prefix><прогон>-problem-<N>`,
  занята локально или на remote — `-2`…; `git branch` без checkout; `push -u` с
  `GIT_TERMINAL_PROMPT=0`; ссылка на MR — из строк `remote:`. Результат — `<stem>.result.json`:
  повтор после push — «уже выгружена», после неудачного push — та же локальная ветка.
- `after_revert.py` только напоминает о ветке на сервере, ничего не удаляет.
- Тесты — на настоящем git (`test_ext_git_publish.py`, изолированный `GIT_CONFIG_GLOBAL`);
  поведение модели — сценарий стенда `X01` (фикстура `test_bug`, bare-remote внутри проекта).

## sut-code

Разбор проблемы по коду тестируемого приложения по просьбе пользователя (`/alla:code N
[ревизия] [ссылка]`, хук `on_request`, субагент `alla-sut-code`). Подсказка после отчёта —
`scripts/hint.py` (`after_report`, проблемы «приложение»/«неизвестно» без `confirmed`).

- Копия — `<проект>/.alla-sut/` со своим `.gitignore` (`*`): `<имя>-<sha1(url)[:6]>/repo.git` —
  bare partial clone (`--filter=blob:none`, ветки в `refs/heads/*`), `trees/<sha12>` — `git
  worktree --detach` (+ `<sha12>.ready`), `lock` — `fcntl` на fetch/worktree. Первый клон и
  дерево ревизии — фоновая работа (`sutlib.py job`, `start_new_session`, `jobs/<имя>/done|failed`):
  скрипт ждёт её `WAIT_BUDGET` (70 с), иначе `SutPending` — «повтори через пару минут»; клон
  идёт во временную папку и переименовывается при успехе. Очистка (`cleanup_trees`,
  `keep_trees`) не трогает деревья запроса и те, чей `.ready` моложе `TREE_BUSY_SECONDS` (час):
  каждое действие отмечает дерево (`load_state`), его может читать субагент другого запроса.
  Дерева запроса нет — `load_state` просит повторить `prepare` (`switch` — `need_trees=False`,
  он создаёт дерево сам). Дерево — `worktree add` с `-c core.symlinks=false`: символическая
  ссылка из репозитория приложения (`Service.java → ../../.env`) становится файлом с текстом
  ссылки, иначе субагент своим чтением файлов и окно кода `prepare` открыли бы файл вне
  ревизии (ревью Codex); `window` к тому же не читает путь, разрешённый за папку ревизии.
  Формат распаковки — вторая строка `.ready` (`TREE_FORMAT`, `tree_ready`): дерево без неё
  распаковано до этого правила и не готово — `ensure_tree` распаковывает заново,
  `load_state` просит повторить `prepare`, `cleanup_trees` удаляет его, даже свежее и в
  пределах `keep_trees` (кроме дерева текущего запроса). Тот же формат — в `spec.json`
  фоновой работы (`Job.format`, `job_format`): работу прежней версии, пережившую таймаут,
  `ensure_tree` не подхватывает — идущую дожидается (`SutPending`), затем удаляет и
  распаковывает заново (ревью Codex). Меняя способ распаковки, меняйте `TREE_FORMAT`. `timeout = 110` в манифесте: Qwen
  обрывает команду на 120 с (`SHELL_COMMAND_TIMEOUT_MS`, исходники Qwen Code 0.25).
- Ссылки (`check_url`): https/http/ssh и `git@host:path`; без пароля в URL, без `::`, без
  ведущего «-»; локальный путь — только `allow_local` (тесты, стенд). git — с
  `protocol.ext.allow=never`, `GIT_TERMINAL_PROMPT=0`, ssh `BatchMode=yes`, если у инженера нет
  своего `GIT_SSH_COMMAND`/`core.sshCommand`.
- Ревизия (`prepare.choose_revision`): `--param ref=X` (или `имя=X` для одного репозитория) →
  ветка, тег `X`/`vX`, коммит; иначе приблизительно — `rev-list -1 --before=<launch_created>`
  основной ветки (`default_branch` или HEAD bare-копии). Версию из TestOps пока не читаем
  (решение отложено, план `docs/plans/2026-10-15-sut-code-extension.md`).
- `prepare` пишет `<stem>.sut.md` (ревизии и папки, места кадров стека всех языков с окнами
  кода, `git grep -F` постоянных кусков текстов ошибок, куски `[S…]`) и `<stem>.sut-state` (не
  `.json`: `extensions action` принимает контекстом любой `.json` папки расширения).
- Поиск — действия `search` (`git grep -F -i`) и `files`: `grep_search`/`glob` Qwen копию не
  видят. `switch` пересобирает данные на другой ревизии, `history` — `git log -L`/по файлу от
  ревизии назад, `compare` — коммиты основной ветки после ревизии по файлу.
- `check` (`RESULT_FORMAT`, повторён в `task.md` и README расширения): место и цитаты кода — в
  файле ревизии ±3 строки, `[S…]` — в куске данных, коммиты ИСТОРИИ — в репозитории; попытки —
  `<stem>.check-attempts`, третья принимается с `format_ok = false`. Итог — `result.json`
  (вход будущего расширения дефектов), `report.md`, `finding.json` (контракт выводов, см.
  ниже).
- Тесты — `test_ext_sut_code.py` на настоящем git (репозиторий с тегом, веткой релиза,
  коммитом с NPE и исправлением после даты прогона).

## tickets и публичный снимок

- `on_request_many` — один контекст с `selected_numbers`, уникальный stem на вызов.
  Нельзя одновременно объявить `on_request`. Новое событие тоже не спрашивает общий
  confirm; создание тикета имеет отдельный просмотр.
- `snapshot = true`: скилл перед каждым хуком и действием с контекстом разбора строит
  актуальный снимок в extension_data и передаёт snapshot_path. Обратного запуска скилла
  из расширения нет. Диагнозы, принятие, подтверждения и группы — из общей функции текущего
  состояния, используемой next/отчётом. Нет правил отбора тикетов в ядре; расширение
  сравнивает значимую проекцию. schema снимка в контракте api: новые необязательные поля
  совместимы; смена смысла/типа, удаление/переименование или новое обязательное поле требуют
  новых schema и api.
  Созданные на время действия контекст и снимок удаляются после процесса, включая ошибку;
  исходный контекст хука и его снимок остаются для задания. Лимит передаётся как budget_s —
  оставшиеся секунды, без зависимости от начала монотонных часов другого процесса.
- `--text-file KEY PATH` — обычный .txt внутри out_dir, UTF-8 до 16000 символов, без NUL;
  CRLF, отступы и окончание файла сохраняются. Поле text_params, не подстановка в шаблон.
- `state_dir` — actual reports_dir/.extensions/<имя>/<хеш project_root>/; переживает clean.
  Действие без --context/--run с явным --reports-dir получает только общий контекст проекта и
  настройки. Ядро не читает записи расширения; их формат, UUID и принадлежность проекту
  проверяет сам обработчик. Run-bound граница --context не ослабляется.
- MCP трекера: встроенный `extensions/tickets/adapters/mcp.py` — обычный адаптер `api = 1`
  (ядро и скрипты tickets не знают про MCP; решение — `docs/plans/2026-10-28-tracker-mcp.md`).
  Клиент stdio на stdlib, формат — `mcp-tracker.toml` (пример рядом). `prepare` чистый и сервер
  не запускает; метка `alla-request: UUID` в `{body}` обязательна, это ключ `lookup`
  (`[lookup]`/`[lookup_link]`; `absent` не возвращается никогда, `authoritative_absence`
  всегда false). Мутации сначала ищут метку (повторная доставка не плодит тикеты) и шлют
  `tool`/`arguments` из payload без пересборки. Сервер — `Popen(close_fds=False)`, без
  отсоединения: он наследует дескриптор блокировки; stderr сервера и его тексты ошибок не
  выводятся; `PATH` сервера безопасный, остальное окружение — из `adapter_env`. Только stdio.
  Тесты: `test_ticket_mcp_adapter.py`, сквозные — в конце `test_ext_tickets.py`, фейковый
  сервер — `tests/fake_mcp_server.py`, общий конфиг — `tests/mcp_tracker_config.py`.
- tickets: полный алгоритм и протокол адаптера в extensions/tickets/README.md. Модель
  ничего не отправляет из задания подготовки. Родитель по references/tickets.md показывает
  полный review-файл и после отдельного ответа собирает submit с --run по точному шаблону
  справочника; искать JSON контекста подготовки ему не требуется.
  show возвращает только путь, request_id и хеш, без команды отправки; хеш — целостность,
  а не доказательство согласия.
  Проверка байтов/проекции — Python, фактический показ и пауза — сценарии Qwen.
- Постоянный журнал блокирует пересекающиеся проблемы одного run_uid при sending/unknown.
  Только lookup, найдено/достоверно отсутствует/неизвестно; absent требует capability и
  совпадения устойчивого scope. Reconcile сам не вызывает create/link/submit.
- tickets не проверяет секреты (решение пользователя 2026-10-28: секреты в логах и разборе
  — не проблема): цитаты, тикет, нагрузка адаптера и поиск идут как есть. Сканер секретов
  базы знаний (`alla-kb/`, в git) — отдельный и остаётся.
- Повторный draft по отправленному составу: та же операция и цель — «Уже выполнено ранее» и
  прежний результат, другая — `TicketError`; пересечение с sending/unknown — `TicketError`.
- Скрипты tickets делят общий срок 100 с от запуска, с резервом 2 с; перед мутацией нужен
  остаток на полный timeout адаптера. Блокировка LOCK_NB ограничена 3 с и остаётся у живого
  адаптера. Все переходы состояний проверяет единая таблица; show разрешён только ready.
