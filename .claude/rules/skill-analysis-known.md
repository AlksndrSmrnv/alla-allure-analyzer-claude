# Отчёт: известные проблемы

## Известные проблемы (шаг 6, `known_issues`)

- Считаются при каждой сборке отчёта (`next`) по текущим файлам базы знаний и нигде не
  хранятся. Проблема входит в группу записи R, если разбор принят, в нём `БАЗА ЗНАНИЙ: R`,
  R подходит кластеру **сейчас** (`kb.record_matches`: не в `rejected_signatures`, точная
  сигнатура или `error_example` в `evidence/NN.txt`; без `evidence` — только точная),
  категория разбора равна категории записи и нет «СОГЛАСОВАННОСТЬ: разные проблемы». Ключ —
  `(kb_dir, id)` (`kb_dir` записи кластера), группа — от двух проблем.
- Поэтому после `reject` проблема выходит из группы и теряет метку «известная проблема»; сама
  метка (`known.refs`) — только у подтверждённой ссылки. Неоднородная — метка без группы.
  Категория не совпала с записью — `known.mismatched`: метка «расходится с базой знаний: id»
  в брифе и строка «Разбор ссылается на известную проблему …» в `report.md`.
- Запись есть, но сигнатура кластера в её `rejected_signatures` (пользователь сделал `reject`
  после разбора) — `known.rejected`: разбор по-прежнему называет эту причину, поэтому метка
  «разбор опирался на отвергнутую запись базы знаний» в брифе, строка «причина не
  подтверждена» в `report.md`, мнение агента в прошедшем времени («Агент считал:»), шаги
  разбора — «Разбор предлагал:» в `report.md` и без «Что делать» в брифе (не совет по
  неподтверждённой причине), и пометка у сжатого разбора в данных сводки
  (`REJECTED_SUMMARY_NOTE`, хэш меняется — сводка пишется заново).
- Папки `kb_dir` нет (разбор открыт не там) — ссылки как в разборе (снимок `entry["kb"]`,
  `verified=False`), групп нет, замечание «База знаний … недоступна». Битый файл записи —
  не подтверждается, замечание «не читается».
- `report.md`: после «Коротко» — «### Известные проблемы из базы знаний (K)» (название, id,
  категория, номера, тесты, причина и первый шаг записи; модуль — если записи из нескольких
  папок); у проблемы группы — «Известная проблема: id — «название», вместе с проблемами …» (не больше
  `MAX_REPORT_GROUP_NUMBERS` номеров, дальше «и ещё N»: полный список — в разделе, иначе
  отчёт рос бы квадратично с группой).
  Разделы, номера, счётчики шапки, правки и команды не меняются: группа — способ показа.
- Бриф: проблемы одной группы в разделе сворачиваются в один пункт на месте первой
  (`_brief_units`, `_brief_known`, поверх пунктов `_units`): «**Проблема 1 и 3 и 4** · K тестов ·
  [известная проблема: id]» (`_merged_title`; в `report.md` и данных сводки — список «проблемы
  1, 3, 4»: он бывает длинным), «Одна известная проблема: «название»», «База знаний: [КАТЕГОРИЯ] описание записи»,
  «Что делать:» (первый шаг записи), «Например:». Номеров — до 5. Раздел «Агент может
  поправить сам» не сворачивается (у каждой своя правка). Свёрнутый пункт — один из
  `MAX_BRIEF_ITEMS`, хвост и счётчики считают его проблемы по отдельности (в отличие от
  объединённых агентом).
- Сводка: блок «--- Известные проблемы из базы знаний (подтверждены пользователем) ---» в
  `build_summary_data` (до `MAX_SUMMARY_GROUPS` строк с первым шагом рецепта, остальное одной
  строкой «Кроме них, ещё N известных проблем … (у каждой своя причина)»; номера в строке —
  до `MAX_SUMMARY_GROUP_NUMBERS`, дальше «и ещё N»: размер задания не растёт с группой),
  директива в `SUMMARY_TASK` и `summary-format.md`. Хэш меняется вместе с группами: после
  `reject`, распавшего группу, `next` просит новую сводку.
- Отвергнутая запись у проблемы за пределами `MAX_SUMMARY_LISTED` считается в строке
  «--- Ещё N проблем поменьше …» («у K из них разбор опирался на запись…»): иначе `reject`
  маленькой проблемы не менял бы хэш и сводка осталась бы прежней.
- `render_report`/`build_summary_data` без `known` (старые вызовы, тесты) показывают ссылку
  разбора как есть, без групп.
- Разобранные скриптом по записи (`KnownIssues.auto`, только из `refs`; решение —
  `skill-memory-kb-auto.md`, «Разбор точно узнанной проблемы без модели»): подпись «База знаний:»
  вместо «Агент считает:» (`_opinion_label`), метка «разобрано по базе знаний» (`KB_AUTO_TAG`;
  у свёрнутой известной проблемы — если у всех её проблем), строка шапки «По базе знаний без
  агента: K …» (бриф — перед «TestOps:», `report.md` — после «В разборе»), в `report.md` —
  «**Разобрано по базе знаний**: … (запись `id`, дата `created`)» и что сказать агенту, если
  причина другая; в данных сводки — пометка `KB_AUTO_SUMMARY_NOTE` (хэш меняется вместе с
  набором), у проблем хвоста (после `MAX_SUMMARY_LISTED`) — их число в строке «Ещё N проблем
  поменьше», а хэш сводки (`cli`) берёт и весь набор `known.auto`: сводку прогона, где все
  проблемы известны, пишет скрипт по нему, и `reject` маленькой проблемы, которую модель потом
  разобрала с той же категорией, иначе её не менял (ревью Codex). Все проблемы с данными —
  `auto` или такие: `summary.md` пишет скрипт (`report.known_summary`: записи от крупнейшей,
  причина и первый шаг) при каждом `next`, из текущих записей, а не по хэшу: рецепт записи вне
  первых групп в данные сводки не входит, и правку его первого шага хэш бы не заметил (ревью
  Codex); хэш — `summary_data_hash`, `summary_task.md` удаляется, и `prepare` сразу отвечает
  `done`; иначе сводку пишет модель.
