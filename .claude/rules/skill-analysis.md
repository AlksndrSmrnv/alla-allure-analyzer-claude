# Задания, разборы и отчёт

Публичный снимок расширений (`extension_data.py`) использует те же настоящие проверки
разбора и related, а не парсит report.md. Подтверждённый вывод и успешно сохранённая
обратная связь учитываются при каждом запросе; отвергнутые основания непригодны.
Все участники тестов экспортируются без лимита старого problem-контекста (20).
Для tickets исходный снимок отделён от проекции конкретной версии; изменение посторонней
проблемы не отменяет её само по себе. Подробности — skill-extensions.md.
Принятые группы related также сохраняют собственный отпечаток диагнозов и актуальных
подсказок базы знаний (`state.related_scopes`). Снимок может использовать неизменённую
группу при изменении глобального задания других групп. Подтверждённые расширением,
неоднородные, отвергнутые и уже известные проблемы из этого основания исключены;
новое принятое решение related заменяет прежний набор отпечатков.

## Задание кластера (`cluster_task`, `clusters/NN.md`)

- «Данные» — из ядра (`prompt_builder_service`) с `normalize_evidence=False`: ID и время в
  логе сохраняются. Каждый кусок данных идёт под своим id (`source_ids=True`): `S1` —
  сообщение, `S2` — трейс, дальше блоки отобранного лога, например
  `--- [S3 · лог app.log · строки 120–134 · тест createOrder] ---` (пометка строк из
  `core.md` уходит в заголовок). Пометки отбора (пропуски, «не вошло», пояснение и итог
  обрезки) остаются в данных без id.
- Лог операции (ядро — `core.md`, «Операция теста»): у каждого теста строка «Операция
  теста: operUID=…» (его `correlation_hint`, без id куска, не цитируется; прежнего раздела
  «Корреляция запроса» кластера нет). Лог другого участника — только отдельным примером «с
  логом приложения» со своим сообщением и операцией, в том числе когда пример у кластера
  один: под сообщением представителя чужой лог выглядел бы логом его операции. У теста был
  общий лог (`operation_logs`), а записей сервиса нет (`has_service_log`: секции «файл»
  или «журнал»; HTTP-ответ лог не заменяет — ревью Codex) — после лога пометка
  `[лог операции не найден: …]` (`log_note_for`; id неизвестен — так и сказано). В задании
  нет кусков «лог»/«журнал» ни у одного примера (`_quotes_service_log`) — флаг
  `log_not_found` и вариант задания «лог операции не найден» (`build_task_text(
  log_not_found=True)`, `_LOG_NOT_FOUND_MISSING`). Вариант задания выбирается по кускам
  записей сервиса (`has_log = _quotes_service_log`), HTTP-ответ — симптом (`_has_symptom`,
  и рядом с записями сервиса — тогда «симптом + лог»): иначе при одном HTTP-ответе задание
  велело разбирать «лог приложения» (ревью Codex). В
  записи кластера `log_not_found: true`, и
  `validate_analysis(log_not_found=True)` не примет «НЕ ХВАТАЕТ» без слова «лог»
  (`LOG_NOT_FOUND_ERROR`).
- Примеры (шаг 4): больше одного примера у кластера (`example_tests`; ни у одного нет лога, а
  у участника есть — он добавляется примером «с логом приложения») — данные идут блоками
  «### Пример N — <роль> · тест …» (`build_cluster_examples_prompt`), id кусков общие.
  «Данные остальных тестов группы в задание не вошли» — только если в группе есть тесты вне
  примеров (иначе это неправда, и модель переносила её в «НЕ ХВАТАЕТ»).
  Лимиты сообщения, трейса и лога делятся: первому (типичному) половина, остальным поровну
  (`example_shares`); лог каждого отбирается `focus_log` под свою долю. Трейс, не влезающий
  в долю, заменяется сжатым (`cluster_task.short_trace`: сообщение исключения целиком — все
  строки до первого кадра, expected/actual у AssertJ бывают на следующих строках, — затем
  `Caused by` и кадры проекта; у Python сообщение после последнего кадра). Кадров берётся
  столько, сколько влезает в долю рядом с сообщением: обрезка с начала оставляла кадры JUnit
  без кадра теста, а у Python отрезала сообщение в конце. «Кадры стека из кода проекта» — только по трейсу представителя: кадры каждого
  примера уже в его сжатом трейсе, отдельный раздел дублировал бы их. Сообщение и трейс,
  совпадающие с первым примером, заменяются строкой «такое же, как в примере 1». Один
  пример — прежний вид задания (данные представителя и источника лога). В записи кластера
  `examples` (чьи данные видела модель — по ним эталон считает видимость) и
  `example_blocks`; при `example_blocks > 1` в разборе обязательна «СОГЛАСОВАННОСТЬ: одна
  причина | разные проблемы — <чем отличаются> | недостаточно данных» (`consistency_errors`).
  Выбор однозначный: два варианта в тексте (перечисление, скопированный шаблон) или
  незаполненный заполнитель шаблона (`TEMPLATE_PLACEHOLDERS` — все `<…>` из шаблонов
  разбора, например `<чем отличаются примеры>`) — ошибка, иначе шаблон открывал бы общую
  правку для смешанной группы. Значения из данных в `<…>` (`<200>`, `<Подтверждено>`)
  допустимы.
- Бюджет: тест назван один раз («Данные теста: …» или шапка примера), в заголовке куска — только
  если кусок от другого теста; имена в заголовках — до 60 символов. Лог отбирается `fit_log`:
  `focus_log` под бюджет минус заголовки кусков (`log_header_overhead`), иначе сотня коротких
  ошибок с длинными именами раздувала задание в десятки раз.
- Реестр источников — `evidence/NN.sources.json` (`sources.py`): id → вид, тест (id и имя),
  секция и вложение (имя, id из `log_attachments`), строки и **ровно тот текст**, что видела
  модель. `evidence/NN.txt` не меняется: на нём держатся `match_cluster` и проверка
  признака. Плюс список тестов (без ссылок TestOps и без повторов шага),
  корреляция, кадры стека, подсказки по коду (`code_hints`). Раздел «Где искать код
  автотеста» печатается всегда: без подсказок — «исходник не удалось сопоставить» (подсказок
  нет и при нераспознанном или неоднозначном имени теста, так что «файлов нет» было бы
  неправдой) и «файлы из кадров стека — тоже»: подсказок нет, значит, кадры не сопоставились
  (`hints_for_cluster` пробует и их), открывать нечего. Отсылки «открой файлы из кадров» нет:
  модель угадывала путь и делала glob (стенд E07, E08). `RULES` разрешают открывать только
  файлы этого раздела и запрещают искать код (glob, grep_search, shell): поиск начинался и
  при готовой подсказке (E10 glob по `src/`, A01 `grep | sed` — искали классы приложения из
  лога). Строки стека без файловой позиции («Caused by», «Unknown Source», «Native Method»)
  идут разделом «Строки стек-трейса без файлов» (`has_frame_files`): в длинном трейсе
  фреймворка это бывает единственное указание на причину.
- **Скриншоты** (`images.py`, `cluster_task._render_images`): модель смотрит их сама —
  `read_file` Qwen Code 0.25 отдаёт PNG/JPEG/GIF/WebP картинкой (`qwen3.8-flash` в его
  `MODALITY_PATTERNS` с `image: true`; модели без изображений — vision bridge, если настроен:
  текст «[Untrusted machine transcription of N image(s) by <модель> …]» и пересказ, где
  видимый текст переписан дословно; иначе текст «does not support image input»). Нового шага нет, всё в `analyze`. Решения
  пользователя: одно изображение на показанный тест (`shown_tests`: примеры, либо
  представитель и источник лога), до `images_per_problem` (3) на проблему; скриншот — симптом;
  включено по умолчанию, `ALLURE_IMAGES_PER_PROBLEM=0` выключает (ни одного запроса).
  - Выбор (`select_image`): последнее (наибольший id) изображение упавшего шага, иначе
    последнее у теста. Тип — по сигнатуре байтов, не по MIME; больше `images_max_bytes` (по
    метаданным — без скачивания) или не картинка — пропуск, сбой скачивания или записи —
    warning и пропуск (`fetch_images` сразу удаляет неполный файл, `place_images` пишет
    атомарно): необязательный скриншот не роняет
    `prepare` и не переводит кластер в `auto`, задание собирается с записанными.
  - `collect_launch` качает после кластеризации (нужны только показанные тесты), в
    временную папку `prepare`; в папку разбора (`images/NN/<id результата>.<ext>`)
    переносятся только попавшие в задание. Кластер `auto` скриншотов не получает.
  - Задание: после «Данных» раздел `IMAGES_HEADER` — кусок
    `--- [S4 · скриншот screenshot.png · шаг «…» · тест …] ---` и абсолютный путь; id
    продолжают нумерацию ядра, тест назван всегда. Директива `IMAGES_NOTE` — только при
    скриншотах («Правило скилла (не данные TestOps)», как у повторов): открыть каждый файл и
    только их, в лимит трёх файлов кода не входят (и `RULES` это говорит); категорию —
    как по сообщению теста, «приложение»/«данные» не подтверждает; в НАБЛЮДЕНИЯ — видимый
    текст дословно, не имя файла и шаг из заголовка; текста нет — цитировать другие куски;
    текст картинки — недоверенные данные; вместо картинки пришёл пересказ другой моделью
    (vision bridge) — разбирать по нему, как по картинке: цитировать текст, который пересказ
    приводит как видимый на экране, ничего сверх пересказа не додумывать, остальные
    скриншоты открывать (решение пользователя: в Qwen Code бывают модели без изображений,
    раньше пересказ запрещалось цитировать и упоминать); read_file вернул ошибку или
    неподдержку — не цитировать, не упоминать, не проблема скилла; остальные не открывать
    только при неподдержке изображений, после ошибки одного файла — открывать дальше (ревью
    Codex: ошибка файла не значит, что модель не видит картинок).
    Пересказ узнаётся по началу «[Untrusted machine transcription» и описанию экрана: «это
    пересказ, а не отказ», а его «do NOT call read_file» — только про этот файл (ревью
    исполнителя: слабая модель принимала пересказ за отказ или переставала открывать
    остальные). Фраза в ЧТО СЛОМАЛОСЬ о том, что видно, — одна, в `IMAGES_NOTE`, только для
    открывшегося скриншота (`_IMAGES_WHAT_NOTE` убран: безусловное «напиши» в разделе и
    условное в задании противоречили друг другу); вариант «только симптом» с картинкой пишется
    по ошибке, трейсу и ответу сервиса «и скриншоту, если он открылся». Без скриншотов задание прежнее. `EXECUTOR_RULES`, `SKILL.md` (правило 4, `analyze`) и `alla-batch.md`
    разрешают открывать `images/` только по путям из задания.
  - Реестр: `kind == "image"`, `text` пуст, `file` (от папки разбора), `step`,
    `attachment_id` — id скачанного вложения (`StagedImage` → `TaskImage` →
    `registry(attachment_ids=…)`), не поиск по имени: `screenshot.png` бывает у нескольких шагов
    (ревью Codex). В записи кластера `run.json` — `images`
    (`RUN_SCHEMA` 6). Цитата image не сверяется (`observation_errors`: id и 8 букв — да),
    `category_errors`: одни цитаты скриншота «приложение»/«данные» не подтверждают,
    `unconfirmed_by_log` — как сообщение.
  - Отчёт: `describe` — «скриншот …, шаг «…», тест …»; в `report.md` у цитаты
    `IMAGE_QUOTE_NOTE` и ссылка на файл. Бриф, сводка, `relate`, сигнатура, база знаний и
    кластеризация скриншоты не видят.
- Повторы (шаг 5, `retries.py`): после списка тестов — раздел «--- Повторы в TestOps ---»,
  если хоть у одного теста кластера были попытки (`FailedTestSummary.attempts`, считаются
  все участники, не только показанные в списке). Факты: у скольких тестов были повторы и
  сколько неудачных попыток; у каждого теста одна группа, по старшинству — «есть попытка с
  другой ошибкой» (до двух разных текстов, по 200 символов), «одна из попыток прошла»,
  «ошибка попыток неизвестна», «есть попытка со статусом skipped/unknown», «все попытки
  упали с той же ошибкой» (только если каждая разобранная попытка failed/broken с той же
  ошибкой). У одного теста — «Тест запускался
  повторно», без «у N тестов»; число попыток у группы — «всего по группе». Есть
  `attempts_omitted` (ядро хранит последние 5 попыток) — число и «все попытки упали с той же
  ошибкой» говорят о «разобранных», в заголовке — «более ранних попыток не разобрано: M». После пустой
  строки — правило (`TASK_NOTE`) с подписью «Правило скилла (не данные TestOps)», иначе оно
  читается как продолжение данных под `UNTRUSTED_NOTE`: повторы говорят о
  воспроизводимости, ни один факт раздела (в том числе прошедшая попытка) не довод за
  категорию; в СОГЛАСОВАННОСТЬ ошибки попыток не входят; раздел не цитировать (он есть и в
  списках нецитируемого — `_OBSERVATIONS_NOTE`, `analysis-format.md`). Есть попытка с другой
  ошибкой — ещё `TASK_NOTE_DIFFERENT`: по ней категорию не выбирать (ConnectionRefused
  попытки тянул бы к «окружению»), в ПРИЧИНУ и КАК ИСПРАВИТЬ не переносить, упомянуть не
  больше чем фразой в ЧТО СЛОМАЛОСЬ. Правило — в разделе, а не в `RULES`: директива
  показывается только там, где есть повторы. Формат разбора не меняется.
  Группа одного теста — `retry_group` (им же считает `retry_facts`; отбор кандидатов
  перезапуска — `skill-rerun.md`).
- «Правила» и «Задание» (`RULES`, `build_task_text`) принадлежат скиллу. Каждая директива
  сказана один раз; варианты задания — симптом + лог / только лог / только симптом / мало
  данных / есть записи базы знаний; есть категория «неизвестно».
- «Только симптом» значит, что фрагмента лога в задании нет, а был ли лог — неизвестно:
  задание запрещает писать «лог пуст / без ошибок» (модель выдавала это за факт, когда
  вложений не было вовсе) и не велит говорить, что лога нет: обязательное начало «лога
  приложения в данных нет, анализ построен …» (и «лог операции не найден, …») убрано — в
  проектах без логов оно стояло у каждой проблемы (решение пользователя: отсутствие логов не
  повод не делать выводов). «Лог не обязателен»: однозначная ошибка в сообщении, трейсе или
  HTTP-ответе — вывод по ней.
- Правило «пиши простым языком»: тексты разборов попадают в отчёт как есть.
- Цитаты идут в «НАБЛЮДЕНИЯ» (`_OBSERVATIONS_NOTE`): id куска (из заголовка) и строка
  именно из него, одной строкой; первой — та, на которой держится причина (при логе — из
  лога, при записи базы знаний — совпавшая с признаком). Цитировать можно только куски с
  заголовком `--- [S… · …] ---`: кадры стека, шаг, база знаний, список тестов и пометки
  отбора — нет (трейс в данных обрезан, кадр из «Кадров стека» в S2 может отсутствовать).
  «ЧТО СЛОМАЛОСЬ» описывает отказ словами; «чего не хватает» — только в «НЕ ХВАТАЕТ».
  «приложение» и «данные» — когда сбой сервиса однозначно показывает цитата: строка лога
  операции теста или текст ошибки самого сервиса в сообщении, трейсе или HTTP-ответе
  (исключение сервиса, ответ валидации, «не найдено»), — или ссылка `БАЗА ЗНАНИЙ:` на точную
  запись той же категории; голый код ответа, расхождение ожидаемого и полученного и скриншот
  этого не показывают — «неизвестно». Директива — `_CONFIRMED_CATEGORY_NOTE` в строке ПРИЧИНА
  каждого варианта (про базу знаний — только при записях). Скрипт
  (`analysis_format.category_errors`, `quotes_checked_source`, `exact_kb` из `entry["kb"]` с
  `origin == "exact"`) отклоняет (`fix`, `CATEGORY_UNCONFIRMED_ERROR`) только разбор, где все
  цитаты — со скриншота (их он не сверяет): однозначна ли сверенная цитата, решает модель по
  заданию. Раньше требовалась цитата из лога (ревью: категорию ставили по правдоподобной
  версии), но в проектах без логов это запрещало выводы даже по исключению сервиса в теле
  ответа (решение пользователя); защита от голого 500 теперь только в тексте задания —
  стенд N01. Потерянный реестр (`sources is None`) проверку не включает. Код 500 и другие 5xx
  без текста ошибки сервиса — «неизвестно», 502/503/504 — «окружение»: сервис недоступен или
  не ответил (E09: 503 «приложением» расходился с эталоном). Кто отдал ответ — сервис или
  прокси — по коду не видно, задание запрещает это утверждать (503 отдаёт и сам сервер, RFC
  9110). Лог сервиса (и балансировщика) — в «НЕ ХВАТАЕТ», только если без него причину не
  подтвердить. «НЕ ХВАТАЕТ» (`_MISSING_NOTE`) — каких данных нет и какая проверка различит
  версии; при «неизвестно» обязателен.
- Цитата причины и детали первого шага из лога нужны лишь при подтверждённой ошибке. Только
  INFO без симптома и без подтверждённой причины в точной записи базы знаний — «неизвестно».
- Наличие контрактных директив проверяет `tests/test_skill_prompts.py`: сокращая текст,
  не теряйте их. Поведение модели проверяется отдельно через `skill-evaluation`.

## Разбор модели (`analysis_format`)

Прощающий парсер разделов ЧТО СЛОМАЛОСЬ / ПРИЧИНА / НАБЛЮДЕНИЯ / НЕ ХВАТАЕТ / КАК ИСПРАВИТЬ /
КОД:

- Формат один (`EXPECTED_FORMAT`): наблюдения обязательны, кроме категории «неизвестно», а
  при ней обязателен содержательный «НЕ ХВАТАЕТ». Без наблюдений проверяются только разборы
  `auto`-кластеров — их пишет код (нет данных, сбой подготовки): `sources.observed`,
  `validate_analysis(observed=…)`.
- Наблюдение — `- [S3] «цитата»` (маркер, скобки, жирный и вид кавычек прощаются). Граница
  цитаты — внешняя пара кавычек (`_closing_quote`): у « » и “ ” учитывается вложенность, у
  одинаковых " ' ` — чётность внутренних (апостроф внутри слова — `can't` — и экранированная
  `\"` не считаются); закрывающая стоит перед концом строки или
  пояснением (« — …», « (…)»). Поэтому `«key "id" — missing»` и
  `«…» (поле «customer»)` разбираются верно. Строки «нет»/«-» в разделе — «наблюдений нет» (так пишут при
  «неизвестно»), а не ошибка формата. Цитата ищется **в названном** куске реестра: регистр, пробелы и
  вид кавычек не важны, `…`/`...` делит её на части, идущие по порядку, края частей без
  `.,;:`; минимум 8 букв и цифр. Найдена только в другом куске — ошибка «есть в S2, а не в
  S3 — укажи [S2]». Реестр не найден или повреждён (`load_registry` проверяет
  форму) — это неполадка скилла, а не разбора: модель её не исправит, поэтому разбор
  принимается без сверки цитат (`ClusterAnalysis.sources_lost`). Отчёт показывает такие
  цитаты с пометкой `SOURCES_LOST_NOTE`, в «Замечаниях» — номера проблем, `review` — причина
  `sources_lost`. Раньше это была ошибка `fix`, и модель тратила попытки до «формат нарушен». Совпадение
  цитаты подтверждает наблюдение, а не причинную связь.
- Одна проверка для `next`, `verify` и `remember --from-analysis`:
  `sources.check_entry_analysis` (прикрепляет реестр к разбору — для отчёта). Готовые
  разборы кода (`no_evidence`, `failed_prepare`, `skipped`) содержат «НЕ ХВАТАЕТ».

- принимает `1.`-нумерацию и «—» после заголовка; каждый заголовок — один раз;
- пункт списка `- Код: …` внутри шагов — текст, а не раздел;
- категория — первое слово из пяти, без «или»/«/»;
- файл и номер строки в КОД проверяются; имя файла без пути принимается, если оно
  однозначно; пути с пробелами — в кавычках/backticks либо существующий начальный путь,
  затем прежний поиск ссылки среди текста; принадлежность проекту проверяется после
  окончательного разрешения файла;
- `БАЗА ЗНАНИЙ: <id>` — только id из предложенных записей, любая фраза = «нет»;
- `parse_summary` показывает модели, что распознано.

## Отчёт (`report`)

Читаемый отчёт простым языком; слово «кластер» в тексте для человека не пишем — «проблема».
Проблемы по разделам раскладывает код, а не модель:

- «Требуют вашего внимания» — приложение, неизвестно, «формат нарушен»; ошибки приложения
  первыми.
- «Агент может поправить сам» — принятая правка `is_fix` в состоянии `applied`/`not_applied`.
- «Автотест сломан, но править вручную» — категория «тест» без правки или правка в состоянии
  `unknown`, плюс причина: агент решил не трогать / нет `КОД:` / лимит / отброшено проверкой /
  файл менялся после apply. Причина есть и в `report.md` у каждой проблемы; `unknown`-правку
  модели в «После отчёта» не предлагают.
- «Стенд и тестовые данные».

### Подтверждённый вывод расширения (`confirmed.py`)

- `confirmed/NN.json` пишет `remember --from-extension` (`skill-memory.md`); `next` читает их
  (`load_confirmed`, битые пропускаются) и передаёт в `build_summary_data` и `render_report`.
- Категория подтверждённого вывода важнее разбора модели: раздел (`приложение` → внимание,
  `тест` → вручную, остальное → стенд и данные; правка агента по-прежнему первой), `label` и
  `tag` проблемы. В `report.md` — строка «**Подтверждено инженером** (разбор по коду
  приложения, дата): категория — причина», детали (`details`) и «Как исправить
  (подтверждено)»; разбор модели остаётся рядом. В брифе — метка «подтверждено по коду»,
  строка «Подтверждено: [КАТЕГОРИЯ] причина» вместо «Агент считает» и первый шаг вывода —
  число строк проблемы не растёт.
- Проблема с подтверждённым выводом не сравнивается с другими (`candidate_groups(confirmed=…)`,
  `next` загружает выводы до шага `relate`): её причину назвал инженер, а объединённый пункт
  (`_merged_item`, `_brief_merged`) показывает только общую причину агента и разбор самой
  большой проблемы — подтверждение терялось (ревью Codex). Исключать надо до задания: запись
  базы знаний от `remember` меняет хэш данных сравнения, и `next` иначе снова просил
  сравнить и подтверждённую (второе ревью). Остальные проблемы её группы сравниваются заново,
  если их хоть две.
- Данные сводки: у проблемы из списка — строка «(подтверждено инженером по коду приложения:
  категория — причина)» (`_confirmed_summary`): хэш меняется, и `next` после подтверждения
  просит сводку заново. В `after_report` у проблемы `confirmed: true`, категория и причина —
  из вывода (подсказка `sut-code` её больше не предлагает).

### Наблюдения в отчёте

- У проблемы с реестром источников (все, кроме `auto`): «Наблюдения» — цитаты с источником
  для человека (`sources.describe`: «лог app.log, строки 2–4, тест createOrder»), «Не
  хватает» (без «нет»). «Агент считает» остаётся предполагаемой причиной.
- Пометки «причина не подтверждена логом» в отчёте, брифе и сводке нет: в проектах без
  логов она стояла у каждой проблемы (решение пользователя), а чего не хватает, разбор пишет
  в «Не хватает». `ClusterAnalysis.unconfirmed_by_log` (не «тест»/«неизвестно», все цитаты —
  сообщение, трейс или скриншот) остался только для статистики `review`.
- Разбор `auto` (реестра нет): цитат нет.

### Неоднородная группа

- «СОГЛАСОВАННОСТЬ: разные проблемы — …» → раздел «Требуют вашего внимания» при любой
  категории, пометка «В группе, похоже, несколько проблем: <отличия>» в `report.md`, метка
  в брифе, строка в сжатом разборе сводки. «недостаточно данных» — пометка «Однородность
  группы не проверена». Автоматического разделения кластеров нет.
- Задание (`_CONSISTENCY_NOTE`, `analysis-format.md`): при «разные проблемы» ПРИЧИНА называет
  причину каждого примера, категория — общая или по первому примеру, в КАК ИСПРАВИТЬ — шаг на
  каждую причину. Раньше задание велело «ПРИЧИНУ пиши по первому примеру», и в E08 причина
  группы свелась к NPE, хотя «СОГЛАСОВАННОСТЬ» называла и пул БД. Задание сводки
  (`SUMMARY_TASK`, `summary-format.md`) не даёт назвать такую проблему одной проблемой или
  одной причиной (E08: «это одна проблема»).

### Известные проблемы (шаг 6, `known_issues`)

- Считаются при каждой сборке отчёта (`next`) по текущим файлам базы знаний и нигде не
  хранятся. Проблема входит в группу записи R, если разбор принят, в нём `БАЗА ЗНАНИЙ: R`,
  R подходит кластеру **сейчас** (`kb.record_matches`: не в `rejected_signatures`, точная
  сигнатура или `error_example` в `evidence/NN.txt`; без `evidence` — только точная),
  категория разбора равна категории записи и нет «СОГЛАСОВАННОСТЬ: разные проблемы». Ключ —
  `(kb_dir, id)` (`kb_dir` записи кластера), группа — от двух проблем.
- Поэтому после `reject` проблема выходит из группы и теряет метку «известная проблема»; сама
  метка (`known.refs`) — только у подтверждённой ссылки. Неоднородная — метка без группы.
  Категория не совпала с записью — `known.mismatched`: метка «расходится с базой знаний: id»
  в брифе и строка «Разбор ссылается на известную проблему …» в `report.md`.
- Запись есть, но сигнатура кластера в её `rejected_signatures` (пользователь сделал `reject`
  после разбора) — `known.rejected`: разбор по-прежнему называет эту причину, поэтому метка
  «разбор опирался на отвергнутую запись базы знаний» в брифе, строка «причина не
  подтверждена» в `report.md`, мнение агента в прошедшем времени («Агент считал:»), шаги
  разбора — «Разбор предлагал:» в `report.md` и без «Что делать» в брифе (не совет по
  неподтверждённой причине), и пометка у сжатого разбора в данных сводки
  (`REJECTED_SUMMARY_NOTE`, хэш меняется — сводка пишется заново).
- Папки `kb_dir` нет (разбор открыт не там) — ссылки как в разборе (снимок `entry["kb"]`,
  `verified=False`), групп нет, замечание «База знаний … недоступна». Битый файл записи —
  не подтверждается, замечание «не читается».
- `report.md`: после «Коротко» — «### Известные проблемы из базы знаний (K)» (название, id,
  категория, номера, тесты, причина и первый шаг записи; модуль — если записи из нескольких
  папок); у проблемы группы — «Известная проблема: id — «название», вместе с проблемами …» (не больше
  `MAX_REPORT_GROUP_NUMBERS` номеров, дальше «и ещё N»: полный список — в разделе, иначе
  отчёт рос бы квадратично с группой).
  Разделы, номера, счётчики шапки, правки и команды не меняются: группа — способ показа.
- Бриф: проблемы одной группы в разделе сворачиваются в один пункт на месте первой
  (`_brief_units`, `_brief_known`, поверх пунктов `_units`): «**Проблема 1 и 3 и 4** · K тестов ·
  [известная проблема: id]» (`_merged_title`; в `report.md` и данных сводки — список «проблемы
  1, 3, 4»: он бывает длинным), «Одна известная проблема: «название»», «База знаний: [КАТЕГОРИЯ] описание записи»,
  «Что делать:» (первый шаг записи), «Например:». Номеров — до 5. Раздел «Агент может
  поправить сам» не сворачивается (у каждой своя правка). Свёрнутый пункт — один из
  `MAX_BRIEF_ITEMS`, хвост и счётчики считают его проблемы по отдельности (в отличие от
  объединённых агентом).
- Сводка: блок «--- Известные проблемы из базы знаний (подтверждены пользователем) ---» в
  `build_summary_data` (до `MAX_SUMMARY_GROUPS` строк с первым шагом рецепта, остальное одной
  строкой «Кроме них, ещё N известных проблем … (у каждой своя причина)»; номера в строке —
  до `MAX_SUMMARY_GROUP_NUMBERS`, дальше «и ещё N»: размер задания не растёт с группой),
  директива в `SUMMARY_TASK` и `summary-format.md`. Хэш меняется вместе с группами: после
  `reject`, распавшего группу, `next` просит новую сводку.
- Отвергнутая запись у проблемы за пределами `MAX_SUMMARY_LISTED` считается в строке
  «--- Ещё N проблем поменьше …» («у K из них разбор опирался на запись…»): иначе `reject`
  маленькой проблемы не менял бы хэш и сводка осталась бы прежней.
- `render_report`/`build_summary_data` без `known` (старые вызовы, тесты) показывают ссылку
  разбора как есть, без групп.
- Разобранные скриптом по записи (`KnownIssues.auto`, только из `refs`; решение —
  `skill-memory.md`, «Разбор точно узнанной проблемы без модели»): подпись «База знаний:»
  вместо «Агент считает:» (`_opinion_label`), метка «разобрано по базе знаний» (`KB_AUTO_TAG`;
  у свёрнутой известной проблемы — если у всех её проблем), строка шапки «По базе знаний без
  агента: K …» (бриф — перед «TestOps:», `report.md` — после «В разборе»), в `report.md` —
  «**Разобрано по базе знаний**: … (запись `id`, дата `created`)» и что сказать агенту, если
  причина другая; в данных сводки — пометка `KB_AUTO_SUMMARY_NOTE` (хэш меняется вместе с
  набором), у проблем хвоста (после `MAX_SUMMARY_LISTED`) — их число в строке «Ещё N проблем
  поменьше», а хэш сводки (`cli`) берёт и весь набор `known.auto`: сводку прогона, где все
  проблемы известны, пишет скрипт по нему, и `reject` маленькой проблемы, которую модель потом
  разобрала с той же категорией, иначе её не менял (ревью Codex). Все проблемы с данными —
  `auto` или такие: `summary.md` пишет скрипт (`report.known_summary`: записи от крупнейшей,
  причина и первый шаг) при каждом `next`, из текущих записей, а не по хэшу: рецепт записи вне
  первых групп в данные сводки не входит, и правку его первого шага хэш бы не заметил (ревью
  Codex); хэш — `summary_data_hash`, `summary_task.md` удаляется, и `prepare` сразу отвечает
  `done`; иначе сводку пишет модель.

### Похожие проблемы (`related.py`, шаг `relate`)

Кластеризация разводит почти одинаковые ошибки намеренно (`core.md`, «Близкие пары»: на dev
из 15 близких пар одна проблема только у `step_split_one_cause`), поэтому лишнее дробление
закрывается после разбора, а не ослаблением gates. Решение модели объединяет проблемы в
отчёте (решение пользователя): одна проблема «Проблема 4 и 5 и 8», номера и разборы каждой
остаются — по ним работают `apply`/`remember`/`reject`.

- Кандидаты (`candidate_groups`): принятые разборы модели — не `auto`, не «формат нарушен»,
  не «СОГЛАСОВАННОСТЬ: разные проблемы», не `known.rejected` (причина не подтверждена), не
  `known.refs` (причина известна и показана блоком известных проблем; иначе одна проблема
  попала бы в оба блока сводки), не с подтверждённым выводом расширения (`confirmed`) — одной
  категории.
  Связи по старшинству: `near` — близкая пара из `run.json` (`clustering.near_pairs`), с
  причиной разделения словами (`NEAR_WHY`: «в логах разные ошибки» — довод за разные);
  `code` — тот же файл в «КОД» и строки не дальше `LINE_WINDOW` (`code_locations` в
  `analysis_format`, имя без пути — только однозначное); `text` — взвешенный Жаккар слов
  причины и первого шага (idf по разборам прогона, длиннее 3 букв, без служебных слов) не
  ниже `TEXT_SIMILARITY` и не меньше `MIN_SHARED_WORDS` общих слов. Между `code` и `text` —
  `kb`: обеим проблемам подходит одна запись базы знаний **сейчас**
  (`known_issues.current_kb_matches` — `match_cluster` по текущим файлам, как в `prepare`:
  запись, отвергнутая `reject` после разбора, выпадает, даже если разбор на неё не
  ссылался; снимок `entry["kb"]` устаревает); запись — пара `kb_dir` + id (`_kb_key`): у
  модулей свои базы с одинаковыми id (ревью Codex). Запись узнаёт ошибку по данным, а не
  по словам разбора. У «неизвестно» —
  только `near` и `kb`: такие причины пишутся одними словами. Без sklearn: `next` зовут
  десятки раз.
- База знаний в задании (ревью: шаг сравнения её не учитывал): у каждой проблемы строки
  «БАЗА ЗНАНИЙ: id «название» (категория; точное совпадение | признак найден в данных)», до
  трёх, с причиной записи; записи из разных папок в группе подписаны папкой
  (`orders/alla-kb`). `RELATE_TASK` — общая запись — довод за `ОДНА ПРИЧИНА`, если разборы
  не называют разных причин, только разные записи — за `РАЗНЫЕ`. Строки входят в хэш
  задания: `reject` записи меняет его, и решение спрашивается заново.
- Группа — компонента связности: до `MAX_RELATE_GROUP` крупнейших проблем (без связей внутри
  оставшихся — выпадает), групп — до `MAX_RELATE_GROUPS`, крупные первыми.
- Задание (`RELATE_RULES`, `RELATE_TASK`, `EXECUTOR_RULES`): одна причина — одно исправление
  уберёт все: ломается тот же объект (запрос, поле, метод, элемент, конкретное значение
  данных, а не вид записи), чинится в одном месте; объект — по ПРИЧИНЕ, ЧТО СЛОМАЛОСЬ и КОД
  (названий шагов в `relate_data` нет — ревью исполнителя); похожий текст ошибки — не довод;
  один класс причины у разных объектов (уникальность, таймаут, права) — `РАЗНЫЕ`, у одного
  объекта (NPE на том же поле, E11) — одна причина; первый шаг с конкретным полем и местом в
  коде — довод за одну, общий шаг вроде «очистить данные перед прогоном» или «уникальные
  значения» — нет; общая причина с перечислением объектов или обобщением («сущность»,
  «запись») — `РАЗНЫЕ`. Повод — прогон пользователя: ссылка и папка, отклонённые проверкой
  уникальности на разных шагах, были объединены по классу причины и общему шагу очистки
  (стенд E12, корпус `unique_conflict_two_objects`, группа 3 примера `related-format.md`).
  Разные ошибки лога, хосты, элементы — довод за `РАЗНЫЕ`; разные шаги — ни за, ни против;
  предложенная правка решению не мешает (отчёт сам оставит проблему отдельной); номера — проблем, не групп (ревью исполнителя:
  «Группа 1» и «Проблема 1» в одном задании); сомнение — `РАЗНЫЕ`; новых фактов нет, код и
  логи не открывать. Запасной путь `fix` (`related_mismatch_note`) — сначала исправить по
  замечаниям, сброс в `РАЗНЫЕ` только при отклонённом верном файле. Директивы охраняет `test_relate_task_keeps_its_directives`.
- Формат `related.md` (`RELATED_FORMAT`): строки `ОДНА ПРИЧИНА: N, M — причина` и
  `РАЗНЫЕ: N — чем отличаются`; парсер прощает жирный, маркеры, ограды, «и»/«;» между номерами.
  Проверка: каждый номер групп ровно один раз, `ОДНА ПРИЧИНА` — от двух номеров одной группы и
  с причиной.
- Показ (`report._units`): проблемы одной группы в одном разделе — один пункт на месте
  первой по `_sort_key` и **одна проблема в счётчиках** (шапка «-> M проблем (N до
  объединения похожих)», числа разделов, хвост брифа). В «Агент может поправить сам» не
  объединяются (у каждой правки своя команда `apply`); там у проблемы метка «та же причина у
  проблем …(объединил агент)», а у пункта в другом разделе — «та же причина у проблемы N».
  Других расхождений разделов у группы нет: кандидаты одной категории, без «формат нарушен» и
  «разные проблемы».
- Бриф (`_brief_merged`): «**Проблема 4 и 5 и 8** · K тестов · [объединил агент]» (оговорка:
  вывод агента; номеров до `MAX_BRIEF_GROUP_NUMBERS`), метки участников без повторов
  («повторяется» — по самой частой), «что случилось», шаг, «Почему не сам» и тест — самой
  большой проблемы (`_largest`), «Общая причина: [КАТЕГОРИЯ] <причина из related.md>».
- `report.md` (`_merged_item`): тот же заголовок, «Общая причина», «Что случилось» и все шаги
  самой большой с подписью «(по разбору проблемы N)» (стенд E11: «Три теста…» в пункте из
  шести), «Где в коде» всех без повторов, тесты всех, «Разбор каждой проблемы — в
  подробностях ниже». Подробности — по одной проблеме, со строкой «Агент счёл одной причиной
  с проблемами …: причина». Отдельного раздела групп нет.
- Сводка: блок «--- Объединённые проблемы (агент счёл одной причиной, сравнив разборы;
  пользователь не подтверждал) ---» со строкой «Проблем после объединения: M» (`merged_count`;
  проблемы с правкой агента — `separate`, их `cli` считает до сводки, — не объединяются) и
  строками «проблема 4 и 5 — причина — K тестов» (K — тесты пункта; номера с правкой —
  «та же причина у проблемы N (ещё M тестов), у них своя правка агента»; объединённых меньше
  двух — «проблемы … — в отчёте они отдельно: своя правка агента у проблем …», правка только
  у тех, у кого она есть); входит в хэш. Директива в `SUMMARY_TASK` и
  `summary-format.md`: одна проблема с номерами, не известная; число проблем — из этой строки,
  не из шапки ядра; хвостовую строку «Кроме них…» не объединять.
- Ошибочное объединение прячет сбой: `RELATE_TASK` и `related-format.md` говорят об этом,
  «сомневаешься — РАЗНЫЕ» остаётся.

### Краткий разбор в терминале

Модель повторяет его дословно и получает при каждом `next`.

- Оформление — эмодзи + ASCII (решение Cens): эмодзи только у разделов (`BRIEF_SECTIONS`:
  🔴 внимание, 🟢 агент поправит, 🟡 вручную, 🔵 стенд и данные), без селектора U+FE0F —
  с ним в части терминалов съезжает ширина. Остальное ASCII. `report.md` — без эмодзи
  (`test_report_uses_plain_words`). Qwen Code рисует Markdown построчно (заголовки `##`/`###`
  одинаково жирным, `---` — линией); строки, начинающиеся с `|` или `>`, он принял бы за
  таблицу и цитату — в брифе их нет.
- Шапка (`_brief_header`, своя, у `report.md` — `_header`): полоска прошедших
  `[####------]` (`_pass_bar`: пустая и полная — только при 0% и 100%), счётчики без нулей,
  «N упавших тестов -> M проблем:» и обзор непустых разделов с числом проблем и тестов,
  ссылка TestOps, предупреждения с префиксом `(!) `.
- Затем «Коротко», `---` и разделы. Текст «Коротко» (и в `report.md`) проходит
  `_plain_text`: строки-ограды (```text) выпадают, у остальных строк снимается блочная
  разметка, лишние пустые строки схлопываются — незакрытая ограда модели иначе сделала бы
  кодом весь остаток отчёта. Разделы `### <значок> <название> (N)`. Проблема — блок через
  пустую строку (`_brief_item`): «**Проблема N** · K тестов · [метка]…» (метки
  «повторяется: …», «известная проблема: id», «в группе, похоже,
  несколько проблем»), строка «что случилось» (≤160; без подписи, поэтому блочная разметка
  модели в её начале — ```, ~~~, #, >, |, маркеры списка, линии (и с пробелами: `_ _ _`) —
  снимается `_plain_line`
  до выбора первого предложения: строка-ограда открыла бы у Qwen блок кода до конца
  ответа вместе со ссылкой на report.md), затем подписи в колонку
  (`_brief_field`, ширина 15): «Агент считает: [КАТЕГОРИЯ] <причина>» (≤200; `CATEGORY_TAGS`,
  у разбора с нарушенным форматом — `[ФОРМАТ НАРУШЕН]`), «Что делать:» (первый шаг, ≤140),
  «Например:» / «Тест:» — один тест проблемы, имя целиком (одной строкой; обрезка до 60
  символов мешала узнать тест, а строк с именем не больше `MAX_BRIEF_ITEMS` на раздел).
- У правки вместо шага — «Правка: `файл:строка` — статус» и одна строка «Проверьте»; у
  «править вручную» ещё «Почему не сам:» (≤160).
- Не больше 5 проблем на раздел, хвост — «… и ещё N проблем (K тестов)» без номеров.
  Предупреждения и замечания — не больше 5, по ≤300 символов.
- Размер брифа ограничен константами и не растёт с числом проблем (охраняет
  `tests/test_skill_report.py`). В конце — `---`, приглашение к обратной связи и ссылка
  `file://` на `report.md`. Строки с обычным путём нет: модель выбрасывала её как повтор
  ссылки, и `report_verbatim` падал (стенд E03, V01, 2026-10-17).
- Модель выводит бриф дословно, «значки, пустые строки и отступы сохрани» (SKILL.md, `done`);
  проверка стенда `report_verbatim` сравнивает без учёта пробелов, но эмодзи — посимвольно.

### Повторы в отчёте

- Прошедшие после повтора (`run.triage.retries.passed_after_retry`) в активные проблемы не
  входят: в брифе — строка «Прошли после повтора: N (список в полном разборе)» под
  счётчиками, в `report.md` — строка в шапке и раздел «### Прошли после повтора (N)» после
  разделов проблем (до 20 тестов со ссылкой, числом неудачных попыток и ошибкой, дальше
  «… и ещё N»); тот же раздел — в отчёте зелёного прогона.
- В подробностях проблемы `report.md` — строка «**Повторы:**» с теми же фактами, что в
  задании. В брифе и в данных сводки (`build_summary_data`, хэш сводки) повторов нет.

### Перезапуск локально в отчёте

- Итог законченного перезапуска тестов (`rerun.RerunView`, `skill-rerun.md`): строка в шапке
  брифа и `report.md`, метка «прошёл при перезапуске: k из m», строка «Перезапуск локально:
  …» в пункте `report.md` и раздел «### Перезапуск локально (N)» после «Прошли после
  повтора». Разделы и счётчики не меняются; в данные сводки не входит.

### `report.md`

В контекст не попадает и не сокращается: те же разделы со всеми пунктами (без обзора из
номеров проблем), полные «Что случилось» / «Агент считает» / шаги / «Где в коде» / причины,
ниже «Подробности по проблемам» со списком тестов (до 200, дальше ссылка на запуск в
TestOps).

### Сводка «Коротко» (`SUMMARY_RULES`, `SUMMARY_TASK`)

- Проблема с причиной «неизвестно» в сводке остаётся неизвестной: задание велит назвать,
  каких данных не хватает, и не придумывать версий (на стенде Qwen модель приписывала
  такие падения окружению и сборке). Охраняет `test_summary_task_keeps_unknown_causes_unknown`.
- «Что упало» в сводке — не больше, чем в разборе: название шага не выдаётся за результат
  (E07: «Выгрузить месячный отчёт» превратилось в «не выгрузился месячный отчёт» при голом
  assertion).
- Сжатый разбор (`compact`) несёт причину, суть,
  «НЕ ХВАТАЕТ» (без «нет») и первый шаг: смена любого из них меняет хэш и сводку.
- Пишет модель по заданию сводки из сжатых разборов: 10 самых больших проблем подробно,
  следующие до `MAX_SUMMARY_LISTED` (40) — одной строкой причины с номером из отчёта
  (`problem_numbers`), остальные — одной сводной строкой по причинам. Размер задания не
  растёт с числом проблем.
- `build_summary_data` собирает общий блок данных задания и SHA-256 для
  `state.summary_data_hash`. При изменении данных `next` удаляет старую сводку и запрашивает
  новую; `skip` удаляет сводку сразу.
- В хэш не входят пути, команды и внешние правила; изменения сжатия, его лимитов или формата
  данных меняют хэш намеренно.
- Сводка без отметки хэша в `state.json` (файл пуст или сброшен) пишется заново.
