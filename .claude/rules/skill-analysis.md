# Задания, разборы и отчёт

## Задание кластера (`cluster_task`, `clusters/NN.md`)

- «Данные» — из ядра (`prompt_builder_service`) с `normalize_evidence=False`: ID и время в
  логе сохраняются. Плюс список тестов (без ссылок TestOps и без повторов шага),
  корреляция, кадры стека, подсказки по коду (`code_hints`). Раздел «Где искать код
  автотеста» печатается всегда: без подсказок — «не найден» с запретом искать код самому
  (иначе субагенты искали его через ls/find).
- «Правила» и «Задание» (`RULES`, `build_task_text`) принадлежат скиллу. Каждая директива
  сказана один раз; варианты задания — симптом + лог / только лог / только симптом / мало
  данных / есть записи базы знаний; есть категория «неизвестно».
- «Только симптом» значит, что фрагмента лога в задании нет, а был ли лог — неизвестно:
  задание велит писать «лога приложения в данных нет», не «лог пуст / без ошибок» (модель
  выдавала это за факт, когда вложений не было вовсе).
- Правило «пиши простым языком»: тексты разборов попадают в отчёт как есть.
- Цитата причины и детали первого шага из лога нужны лишь при подтверждённой ошибке. Только
  INFO без симптома и без подтверждённой причины в точной записи базы знаний — «неизвестно».
- Наличие контрактных директив проверяет `tests/test_skill_prompts.py`: сокращая текст,
  не теряйте их. Поведение модели проверяется отдельно через `skill-evaluation`.

## Разбор модели (`analysis_format`)

Прощающий парсер разделов ЧТО СЛОМАЛОСЬ / ПРИЧИНА / КАК ИСПРАВИТЬ / КОД:

- принимает `1.`-нумерацию и «—» после заголовка; каждый заголовок — один раз;
- пункт списка `- Код: …` внутри шагов — текст, а не раздел;
- категория — первое слово из пяти, без «или»/«/»;
- файл и номер строки в КОД проверяются; имя файла без пути принимается, если оно
  однозначно; пути с пробелами — в кавычках/backticks либо существующий начальный путь,
  затем прежний поиск ссылки среди текста; принадлежность проекту проверяется после
  окончательного разрешения файла;
- `БАЗА ЗНАНИЙ: <id>` — только id из предложенных записей, любая фраза = «нет»;
- `parse_summary` показывает модели, что распознано.

## Отчёт (`report`)

Читаемый отчёт простым языком; слово «кластер» в тексте для человека не пишем — «проблема».
Проблемы по разделам раскладывает код, а не модель:

- «Требуют вашего внимания» — приложение, неизвестно, «формат нарушен»; ошибки приложения
  первыми.
- «Агент может поправить сам» — принятая правка `is_fix` в состоянии `applied`/`not_applied`.
- «Автотест сломан, но править вручную» — категория «тест» без правки или правка в состоянии
  `unknown`, плюс причина: агент решил не трогать / нет `КОД:` / лимит / отброшено проверкой /
  файл менялся после apply. Причина есть и в `report.md` у каждой проблемы; `unknown`-правку
  модели в «После отчёта» не предлагают.
- «Стенд и тестовые данные».

### Краткий разбор в терминале

Модель повторяет его дословно и получает при каждом `next`.

- Шапка, «Коротко», затем у каждой проблемы (`report._brief_item`): «что случилось» (≤160
  символов, число тестов и один пример теста, метки «повторяется»/«известная проблема»),
  «Агент считает: <категория> — <причина>» (≤200), «Что делать:» (первый шаг, ≤140).
- У правки вместо шага — «Правка: файл:строка (статус)» и одна строка «Проверьте»; у «править
  вручную» ещё «Почему агент не правил сам» (≤160).
- Не больше 5 проблем на раздел, хвост — «… и ещё N проблем (K тестов)» без номеров.
  Предупреждения и замечания — не больше 5, по ≤300 символов.
- Размер брифа ограничен константами и не растёт с числом проблем (охраняет
  `tests/test_skill_report.py`). В конце — ссылка `file://` на `report.md` и обычный путь.

### `report.md`

В контекст не попадает и не сокращается: те же разделы со всеми пунктами (без обзора из
номеров проблем), полные «Что случилось» / «Агент считает» / шаги / «Где в коде» / причины,
ниже «Подробности по проблемам» со списком тестов (до 200, дальше ссылка на запуск в
TestOps).

### Сводка «Коротко» (`SUMMARY_RULES`, `SUMMARY_TASK`)

- Пишет модель по заданию сводки из сжатых разборов: 10 самых больших проблем подробно,
  следующие до `MAX_SUMMARY_LISTED` (40) — одной строкой причины с номером из отчёта
  (`problem_numbers`), остальные — одной сводной строкой по причинам. Размер задания не
  растёт с числом проблем.
- `build_summary_data` собирает общий блок данных задания и SHA-256 для
  `state.summary_data_hash`. При изменении данных `next` удаляет старую сводку и запрашивает
  новую; `skip` удаляет сводку сразу.
- В хэш не входят пути, команды и внешние правила; изменения сжатия, его лимитов или формата
  данных меняют хэш намеренно.
- Непустая legacy-сводка без хэша молча привязывается к текущим данным; без сводки идёт
  обычное задание.
