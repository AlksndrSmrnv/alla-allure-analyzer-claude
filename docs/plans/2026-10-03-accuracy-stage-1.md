## Зачем

Скилл готовится к промышленному внедрению. Первая очередь улучшает то, на чём держится
каждый разбор: какие данные доходят до модели, насколько её выводы проверяемы и видно ли,
что в одной группе спрятано несколько проблем. Вторая очередь (история TestOps,
структурное сравнение стеков, сравнение с успешным выполнением) — после этой и в этот
план не входит.

## Ограничения и принятые решения

- **Реальных данных нет и не будет.** Пользователь не может передать ни прогонов, ни
  логов, ни примеров ответов TestOps. Всё проверяется на синтетике, построенной по
  публичным форматам логов и по тому, как TestOps отвечает в `tests/skill_fake_testops.py`.
  Инструменты записи и оценки должны работать у команды локально, без передачи данных
  разработчику; наружу — только сводные цифры, и то по желанию команды.
- **Версии форматов можно повышать** (сигнатура базы знаний, формат задания): инструмент
  пока не используется постоянно. Два подпункта ниже (старые папки и `DEFAULT_VERSION`)
  устарели: с 2026-10-08 совместимости со старыми папками, историей и отметками применения
  нет (`RUN_SCHEMA = 3`), сигнатура — `signature.SIGNATURE_VERSION = 7`. Исходно было так:
  - старые папки разборов (`alla-reports/run-*`, свежий незавершённый разбор после
    обновления скилла) должны открываться, их принятые разборы — оставаться принятыми;
  - записи базы знаний продолжают читаться, подтверждения не удаляются;
  - сигнатуру повышать (`FeedbackIssueSignature.DEFAULT_VERSION`, сейчас 5) только если
    тест покажет, что у логов старого формата меняется материал сигнатуры. Если меняется
    только у логов, где раньше ошибок не находилось, — версию не трогать и описать
    последствие в `CLAUDE.md` (так уже сделано при прошлом изменении отбора логов).
- **Не делать в этой очереди:** числовую «уверенность»; объединение по совпадению `КОД:`
  (общий helper обслуживает разные ошибки); автоматическое разделение кластеров;
  Drain3; эмбеддинги/HDBSCAN; дополнительные раунды модели; запросы истории TestOps.
- Совпадение цитаты подтверждает наблюдение, а не причинную связь. Число одинаковых
  повторов — факт о воспроизводимости, не диагноз.
- Формат заданий, валидатор (`analysis_format.py`), справочники `references/*.md`,
  `SKILL.md` и `CLAUDE.md` меняются в одном коммите с кодом. Примеры из справочников
  прогоняются через настоящие парсеры (`tests/test_skill_docs.py`), смысл формулировок
  заданий охраняет `tests/test_skill_prompts.py`, размер краткого разбора —
  `tests/test_skill_report.py`.

## Шаг 1. Эталон и фиксация текущего результата

Цель: прогоны воспроизводятся без сети, у них есть разметка, считаются ошибочные
объединения, дробление и потеря доказательств; результат текущей версии записан до
любых изменений алгоритмов.

### 1.1 Формат сохранённого прогона и загрузчик

- Каталог прогона («кассета»): `launch.json`, `results.json` (все результаты, включая
  `hidden`), `executions/<result_id>.json`, `details/<result_id>.json`,
  `attachments/<result_id>.json` (метаданные), `contents/<attachment_id>` (байты).
  Поля соответствуют `LaunchFixture` из `tests/skill_fake_testops.py`.
- `load_cassette(dir) -> LaunchFixture` и обратное `save_cassette`. Воспроизведение —
  через существующий `FakeTestOps` (сеть не используется, `httpx.MockTransport`).
- Расположение: `qwen-skill/alla-launch/tests/eval/` (папка скилла остаётся
  самодостаточной; `tests/` уже в `testpaths`). Модули без `test_` в имени.

### 1.2 Запись реального прогона (для команды, локально)

- `tests/eval/record.py <launch_id> <out_dir>`: обычный сбор `pipeline.collect_launch`
  через записывающий httpx-транспорт, настройки — `Settings` скилла (`.env`).
- Не сохранять: заголовки запросов, тело запроса токена, ответ `/api/uaa/oauth/token`
  (JWT). Тест на фейковом TestOps проверяет, что ни токен, ни JWT не попали на диск.
- Короткая инструкция в `tests/eval/README.md`: данные остаются на машине команды,
  каталог вне git.

### 1.3 Синтетический корпус с разметкой

Генераторы на Python (детерминированные, без случайности или с фиксированным seed),
а не сохранённые байты: так корпус легко расширять. Разметка задаётся при построении.

Разметка прогона (`labels.json`; JSON, а не YAML — PyYAML в зависимостях скилла нет):

```json
{"groups": [
  {"id": "pay-500-db", "cause": "payment-db-pool", "category": "приложение",
   "tests": [101, 102, 103],
   "evidence": ["HikariPool-1 - Connection is not available, request timed out"]},
  {"id": "silent-108", "cause": null, "tests": [108]}
]}
```

- `groups` — группы симптомов, эталон для кластеров.
- `cause` — подтверждённая причина; у разных групп симптомов может совпадать.
  `null` — причина неизвестна: такие группы не объединяются друг с другом.
- `evidence` — ключевые строки, которые обязаны дойти до задания модели.

Что должно быть в корпусе (dev):

- **Форматы логов**, по которым сейчас теряются ошибки (`_extract_error_blocks` в
  `scripts/alla_core/services/log_extraction_service.py` видит только строку, которая
  начинается с даты ISO, и с `[ERROR]` в скобках):
  - Spring Boot 3: `2026-10-03T10:00:00.123+03:00 ERROR 12345 --- [app] [nio-8080-exec-1] c.e.PaymentService : …`
  - logback по умолчанию: `10:00:00.123 [main] ERROR c.e.PaymentService - …`
  - log4j2: `2026-10-03 10:00:00,123 ERROR [main] c.e.PaymentService: …`
  - JUL, две строки: `Oct 03, 2026 10:00:00 AM com.example.Svc method` + `SEVERE: …`
  - Python: `ERROR:root:…`, `2026-10-03 10:00:00,123 - svc - ERROR - …`, `Traceback (most recent call last):`
  - logfmt: `time=… level=error msg="…"`; nginx: `2026/10/03 10:00:00 [error] 123#0: *1 connect() failed …`
  - текущий формат `2026-… [ERROR] …` — результат не должен измениться;
  - `Caused by:` цепочки, `... 42 more`, исключение без уровня перед кадрами `at`.
- **Ловушки:** `INFO Processed 0 errors`, `INFO ErrorController registered`,
  INFO-строка сразу после стека исключения, слово `ERROR` в тексте сообщения уровня INFO.
- **Сценарии падений:**
  - одинаковый assertion `expected: <200> but was: <500>` при разных серверных ошибках
    в логе (пул БД / NPE) — две группы, которые нынешний алгоритм, вероятно, склеит
    (меряет шаг 4);
  - 401 и 403 с похожим текстом; таймауты с разными причинами;
  - Selenide/Selenium `ElementNotFound` на разных страницах; `ConnectException` к разным
    сервисам; ошибки валидации данных; тесты без данных;
  - разные симптомы одной причины (502 + Timeout + «элемент не найден» при падении
    авторизации) — допустимо остаются разными группами;
  - ретраи (для шага 5): прошёл после повтора; все попытки с одной ошибкой; попытки с
    разными ошибками; параметризованный тест — один `testCaseId`, разные параметры;
    смена окружения между попытками;
- **Большой прогон** (≥ 300 падений, длинные логи) — для проверки лимитов памяти,
  размера заданий и времени `prepare`.

Отложенный набор (holdout): отдельный модуль генераторов с другими сервисами, текстами и
сочетаниями форматов. Правило: пороги и веса подбираются только по dev; holdout
смотрится после, и его базовая линия обновляется отдельным коммитом с объяснением.

### 1.4 Метрики и отчёт качества

`tests/eval/metrics.py` + `tests/eval/run_eval.py` (прогоняет `prepare` офлайн на
кассете или синтетике, читает `run.json` и `clusters/NN.md`):

- **Ошибочные объединения** — B-Cubed precision. Пара тестов в одном кластере верна,
  если они из одной группы симптомов или их группы имеют одну известную `cause`.
  Группы с `cause: null` между собой всегда «разные».
- **Дробление** — B-Cubed recall по группам симптомов. Разнесение разных симптомов
  одной причины не штрафуется.
- **Скрытые проблемы** — группы, ни один тест которых не показан модели (не
  представитель и, после шага 4, не пример ни одного кластера). Отдельный показатель:
  именно они дают неверный диагноз для части группы.
- **Потеря доказательств** — доля строк `evidence`, которых нет в тексте задания
  кластера, где группа видима (сравнение с нормализацией пробелов).
- Списки, а не только цифры: какие группы склеены, какие раздроблены, какие скрыты,
  какие строки потеряны.
- Вывод: таблица в stdout и JSON. Режим для команды: `run_eval.py --cassette DIR
  --labels FILE` печатает только сводку.
- Диагнозы автоматически не оцениваются: правильность причины требует человеческой
  оценки. `run_eval.py --analyses RUN_DIR` формирует чек-лист «эталонная причина /
  категория ↔ разбор модели» для ручной проверки.

## Шаг 2. Полное извлечение ошибок из текстовых логов

### 2.1 Распознавание событий и их границ

- Новый `scripts/alla_core/utils/log_events.py`: `parse_events(text) -> list[LogEvent]`,
  у события — номера первой и последней строки (1-based), уровень, вид
  (`level` / `traceback` / `exception`), строки.
- **Начало события:** время в начале строки (ISO с `T` или пробелом и с зоной;
  `dd.MM.yyyy`; `yyyy/MM/dd`; только `HH:mm:ss[.,]SSS`; syslog `Oct 03 10:00:00`;
  время в `[]`); строка вида `LEVEL:` в начале (`ERROR:root:`, `SEVERE:`);
  `Traceback (most recent call last):`; строка исключения
  (`^[\w.$]+(Exception|Error|Throwable)(: .*)?$`), за которой идут кадры.
- **Уровень ошибки:** `ERROR`, `FATAL`, `SEVERE`, `CRITICAL` (в `[]`, в `|…|` или без
  скобок), `level=error|fatal|critical` (logfmt), `[error]`/`[crit]`/`[alert]`/`[emerg]`
  (nginx). Учитывается только в позиции уровня: после времени/потока/скобок в начале
  записи или как ключ `level=`. Заглавное `ERROR` внутри текста сообщения уровня INFO —
  не ошибка. WARN — не ошибка.
- **Продолжение события:** кадры (`at …`, `\tat …`, `File "…", line N`), `Caused by:`,
  `... N more`, строки с отступом, строки без признаков начала события. Строка с
  признаком начала (в том числе INFO с временем) завершает текущее событие —
  соседний INFO не поглощается исключением.
- **Склейка:** JUL — строка «дата + класс + метод» и следующая `SEVERE: …` в одно
  событие; Python Traceback — до строки исключения включительно.
- Сигналы из `scripts/alla_core/utils/log_focus.py` (шаблон
  `ERROR|FATAL|SEVERE|CRITICAL|…Exception|Caused by|Traceback`) используются как есть
  для отбора; границы событий задаёт только `log_events`.
- `ErrorBlocksHandler` (`scripts/alla_core/services/attachment_handlers.py`) берёт из
  `parse_events` события с уровнем ошибки, Traceback и исключения. Для логов старого
  формата результат побайтово прежний (тест на существующих фикстурах
  `test_core_log_extraction.py`).
- Лимиты не меняются: `ALLURE_LOGS_MAX_ATTACHMENT_BYTES`, потоковый
  `StreamingLogSelector`, память `O(лимит + текущее вложение)`.

### 2.2 Происхождение фрагментов и повторы

- Каждый фрагмент знает: результат теста, вложение (id и имя), диапазон исходных строк.
  Источник отмечается при извлечении, **до** сокращения логов, и переживает отбор
  `StreamingLogSelector`/`focus_log`. Заголовки секций (`--- [файл: app.log] ---`) уже
  сохраняются отбором точными — диапазон строк можно нести в них
  (`--- [файл: app.log · строки 120–134] ---`) или отдельной структурой; выбрать при
  реализации, но выполнить условия:
  - источник не попадает в материал сигнатуры (`feedback_signature._extract_log_anchor`
    берёт тела секций, заголовки не берёт — проверить тестом);
  - не попадает в лог-канал кластеризации (`clustering_service._build_log_document`
    сейчас нормализует весь сниппет вместе с заголовками — убрать из него метаданные
    источника) и в сопоставление `error_example` базы знаний;
  - `parse_log_sections` и `log_focus` продолжают понимать заголовки.
- **Точные повторы** (одинаковые после замены чисел, времени, UUID средствами
  `text_normalization`) сворачиваются в первое вхождение с пометкой
  «повторялось N раз, строки a–b, c–d, …» (первые 5 мест + число остальных).
- В `FailedTestSummary` (`scripts/alla_core/models/testops.py`) — поле со списком
  источников (`exclude=True`, как `log_selection_*`, если его не нужно хранить в
  `run.json`; иначе компактно). Решение о хранении принять в 3.1.

### 2.3 Сигнатуры

- Тест: для логов старого формата материал сигнатуры и хэш не меняются. Golden-тест
  сигнатуры остаётся зелёным.
- Тест: для новых форматов сигнатура строится по найденным строкам ошибки.
- Если первый тест не проходит из-за неизбежного изменения — поднять
  `DEFAULT_VERSION` до 6, обновить golden-тест, `CLAUDE.md` (раздел «Память скилла» —
  про версию сигнатуры) и тесты, где зашита `v5:`. Старые `confirmed_signatures`
  остаются в записях, узнавание по `error_example` продолжает работать.

Приёмка шага 2: все форматы из корпуса распознаются; соседний INFO не поглощается;
`ERROR` внутри сообщения не становится ошибкой; лимиты памяти и размера задания
сохранены; влияние на сигнатуры проверено отдельным тестом; на эталоне потеря
доказательств снизилась, объединения/дробление не ухудшились (или ухудшение объяснено).

### 3.2 Новый формат разбора (только для `task_format ≥ 2`)

```
ЧТО СЛОМАЛОСЬ: <наблюдаемый отказ, 1–2 предложения>
ПРИЧИНА: <тест|приложение|окружение|данные|неизвестно> — <предполагаемая причина>
НАБЛЮДЕНИЯ:
- [S3] «дословная цитата из этого источника»
- [S1] «expected: <200> but was: <500>»
НЕ ХВАТАЕТ: <каких данных нет и какая проверка различит гипотезы> | нет
КАК ИСПРАВИТЬ:
1. <шаг>
КОД: <путь>:<строка> — <что там>   (необязательно)
БАЗА ЗНАНИЙ: <id> | нет            (если задание предлагало записи)
```

- Парсер (`scripts/alla_skill_lib/analysis_format.py`): разделы `НАБЛЮДЕНИЯ`,
  `НЕ ХВАТАЕТ` — тем же прощающим разбором, что остальные.
- Проверка (`validate_analysis`, нужен доступ к реестру и `task_format` записи):
  - хотя бы одно наблюдение; исключение — категория «неизвестно», тогда обязателен
    содержательный `НЕ ХВАТАЕТ`;
  - id источника существует в реестре кластера;
  - цитата найдена **в этом** источнике (нормализация пробелов и кавычек; `…` делит
    цитату на части, каждая ищется по порядку; минимум 8 значимых символов). Цитата,
    найденная только в другом источнике, — ошибка с подсказкой «эта строка есть в S2,
    а не в S3»;
  - сообщения `fix` называют конкретную цитату; лимит попыток прежний, предупреждение на
    предпоследней попытке — прежнее.
- Числовой уверенности нет. Полнота доказательств — только как факты в отчёте.
- `feedback/NN.md`: новые разделы необязательны; `remember --from-analysis` и проверка в
  `feedback.py:95` учитывают `task_format`.
- Пакетный разбор: `batches/N.md` и `verify` используют ту же проверку (через
  `_check_analysis` в `cli.py`).

### 3.3 Отчёт и сводка

- `report.md` у проблемы: «Наблюдения» (цитаты с понятным источником: тест, вложение,
  строки), «Предполагаемая причина», «Не хватает». Если категория не «тест» и не
  «неизвестно», а наблюдения есть только из сообщения/трейса теста, — пометка «причина
  не подтверждена логом».
- Краткий разбор в терминале: не больше одной короткой метки, лимиты брифа прежние.
- `build_summary_data`: в сжатые разборы идёт причина с пометкой, если она не

Приёмка шага 3: выдуманные цитаты и ссылки на чужой источник отклоняются; разборы

## Шаг 5. Ретраи

### 5.1 Связь попыток и реестр всех результатов

- По документации TestOps попытки одного выполнения связаны «идентичностью контекста
  выполнения» (`historyId`): тест + параметры + окружение; при смене параметров или
  окружения повтор становится отдельным результатом. Реальных ответов нет, поэтому:
  - ключ связи: `historyId` (и вариант `historyKey`), если поле есть в ответе
    (модели TestOps принимают неизвестные поля, `extra="allow"`); иначе
    `(testCaseId, нормализованные parameters, environment)`, если эти поля есть;
    иначе попытки не связываются, и это явно отмечается;
  - тесты: параметризованный тест с одним `testCaseId` и разными параметрами не
    смешивается; смена окружения не смешивается; ответы без полей связи не ломают триаж.
- `TriageService.analyze_launch` (`scripts/alla_core/services/triage_service.py:56`)
  сейчас отбрасывает `hidden` до подсчёта. Сохранить компактный реестр всех результатов
  до фильтрации (id, статус, hidden, ключ связи, `testCaseId`); статистика и активные
  падения считаются как раньше.
- Диагностика без данных: в предупреждения прогона — по какому полю связаны попытки и
  сколько не удалось связать (только числа и имена полей).

### 5.2 Ошибки попыток

- Для участников активных кластеров догружать ошибки связанных попыток: из списка
  результатов, если там есть `statusDetails`; иначе `get_test_result_detail`
  (`GET /api/testresult/{id}`), параллелизм `ALLURE_DETAIL_CONCURRENCY`, не больше
  5 попыток на тест и общий потолок запросов. Неполная загрузка обозначается
  («ошибки загружены для 120 из 200 попыток»).
- У `FailedTestSummary` — список попыток: статус, короткое сообщение, совпадает ли
  ошибка с финальной (сравнение по нормализованному сообщению).

### 5.3 Задание и отчёт

- В задании кластера — факты: «у 5 из 7 тестов были повторы: у 4 все попытки упали с
  той же ошибкой, у 1 первая попытка упала иначе: «…»». Правило в `RULES`: повторы
  говорят о воспроизводимости, причину не устанавливают.
- Финальные успешные тесты после неудачного повтора — отдельная сводка в отчёте
  («прошли после повтора: N», список в `report.md`), в активные кластеры не входят.
- Попытки не участвуют в сигнатуре и кластеризации. `load_models` (`report.py:168`)
  работает с `run.json` без нового поля.

Приёмка шага 5: видны переходы «упал → прошёл», одинаковые и разные ошибки попыток;
разные параметры и окружения не смешиваются; неполная загрузка обозначена; число
одинаковых повторов не превращается в диагноз.

## Шаг 6. Группировка подтверждённых известных проблем в отчёте

- Группы представления вычисляются при сборке отчёта (`scripts/alla_skill_lib/report.py`)
  из текущих разборов и базы знаний, поэтому пересчитываются после `remember`/`reject`:
  - ключ — `(module, id записи)`, где запись принята в разборе (`БАЗА ЗНАНИЙ:` из
    предложенных) и её совпадение подтверждено (точная сигнатура или `error_example`);
  - не группируются: разные модули; разные категории у разборов одной записи
    (противоречие — отдельно, с пометкой); группы с «разные проблемы» (шаг 4);
    разборы «формат нарушен».
- Отчёт: блок «Одна известная проблема: <запись> — проблемы 3, 7, 12 (N тестов)».
  Исходные номера, отдельные разборы, предложения правок и команды (`apply N`,
  `remember N` …) сохраняются. Тесты не теряются и не считаются дважды.
- Та же группировка — в `build_summary_data` (изменение хэша сводки ожидаемое) и в
  кратком разборе (лимиты брифа прежние).
- Совпадение места `КОД:` для объединения не используется.

## Шаг 7. Итоговая проверка очереди

- Полный сценарий на фейковом TestOps: `prepare` → `analyze` → пакетный разбор

  (совместимость со старыми форматами снята 2026-10-08).
- База знаний: `remember`/`reject` на разборах текущего формата.
- Эталон: сравнить dev и holdout с базовой линией шага 1; в итоговом коммите — таблица
  изменений.
- Качество диагнозов: ручной прогон скилла с моделью на синтетическом корпусе и
  сверка по чек-листу `run_eval.py --analyses`. Проверки цитат для оценки
  правильности причины недостаточно.
- `python -m pytest` из корня репозитория, ruff/mypy по конфигу `pyproject.toml`;
  `CLAUDE.md` описывает новое поведение (извлечение событий, реестр источников,
