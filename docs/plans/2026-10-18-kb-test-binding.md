# План: записи базы знаний переживают смену версии сигнатуры

Дата: 2026-10-18. Статус: согласован пользователем 2026-10-18.

## Зачем

Точное узнавание записи базы знаний держится на сигнатуре кластера `v<версия>:<хэш>`
(`signature.py`, сейчас `v9`). Запись хранит только хэши (`confirmed_signatures`,
`rejected_signatures`) и признак `error_example`. Как только меняется версия или материал
сигнатуры, хэши в записях больше не совпадают. Тогда:

- точное узнавание всех накопленных записей пропадает, остаётся только признак
  («сильный кандидат, проверь» вместо «ТОЧНОЕ… основная причина»). Категории «приложение» и
  «данные» по точной записи модель тоже больше не ставит;
- **отказы `reject` перестают действовать**: отвергнутая для проблемы запись снова
  предлагается ей по признаку. Это прямой вред: инженер уже сказал «не то».

С v7 по v9 версия менялась за неделю, и ошибки эталона (общие сигнатуры у разных проблем,
форматы логов) требуют менять материал и дальше. В эксплуатации каждая такая правка
обнуляла бы базы знаний команд.

### Почему не заморозка и не пересчёт

- **Заморозить `v9`** — не защищает. Хэш зависит и от ядра: отбор и нормализация логов
  (`alla_core`) меняют материал без смены номера версии (`skill-memory.md`: «новый отбор
  ранее обрезавшихся логов может изменить точные `confirmed_signatures`»). Плюс заморозка
  блокирует исправление ошибок узнавания.
- **Пересчитать записи** — нечем. В записи хэш, а не материал. Исходные данные лежат в
  папках разборов: их удаляет `clean` через 14 дней, а `run.json` хранит прогон без
  `log_snippet`. Хранить логи в `alla-kb/` нельзя: папка коммитится в репозиторий
  автотестов.

### Что предлагается

Запись запоминает ещё и **тесты**, на которых её подтвердили или отвергли. Имя теста от
версии сигнатуры не зависит. Если у записи нет ни одной сигнатуры текущей версии, а признак
совпал и тест кластера среди её тестов, узнавание считается точным (для отказа — запись не
предлагается). Это переходное правило: как только инженер подтвердит запись на новой
версии, снова работает обычная сигнатура.

Тесты нужно собирать с первого дня эксплуатации. Записи, созданные до этой правки,
мигрировать будет не по чему.

## Решения

1. **Ключ теста** — `full_name` (класс и метод: читается в git, его видно в коде); нет
   `full_name` — `testcase:<testCaseId>`. Параметризованный тест — один ключ: параметры
   проблему не меняют.
2. **Поля записи** — `confirmed_tests` и `rejected_tests`: отсортированные списки, не больше
   `MAX_RECORD_TESTS` (50), merge-friendly, как и сигнатуры. Переполнение — оставляем
   последние подтверждённые (новые важнее старых).
3. **Зеркально сигнатурам.** `confirm` добавляет тесты кластера в `confirmed_tests` и
   убирает их из `rejected_tests`, `reject` — наоборот. У других записей тесты не
   трогаем: один тест может падать по нескольким известным причинам (с сигнатурой так
   нельзя — она одна на причину).
4. **Правило совпадения** (`kb.record_matches`, одно для `prepare`, сборки отчёта и
   известных проблем):
   1. сигнатура в `rejected_signatures` → нет;
   2. **нет отвергнутой сигнатуры текущей версии**, тест кластера в `rejected_tests` и
      признак совпал → нет;
   3. сигнатура в `confirmed_signatures` → `exact`;
   4. **нет подтверждённой сигнатуры текущей версии**, тест кластера в `confirmed_tests` и
      признак совпал → `exact`;
   5. признак совпал → `fingerprint`.

   Условие «нет сигнатуры текущей версии» ограничивает правило переходом. Пока запись
   подтверждена на текущей версии, всё работает как сейчас, и разные проблемы одного теста
   не склеиваются. Без совпадения признака тесты ничего не решают: тест может упасть и
   по другой причине.
5. **`prepare` в `alla-kb/` не пишет.** Новая сигнатура попадёт в запись, когда инженер
   подтвердит её (`remember`). Иначе разбор давал бы изменения в git без действия человека.
6. **`RUN_SCHEMA` не меняется.** Тесты кластера берутся из `run.json`
   (`clustering.clusters[].member_test_ids` → `triage.failed_tests[]`), как в `report._Tests`.
7. **История повторов** (`history.jsonl`) — не в этом плане. Она локальная, а после смены
   версии лишь сбрасывает метку «повтор». Можно сделать тем же способом позже.

## Шаги (каждый — коммит с тестами)

1. `feat(kb): remember tests a knowledge base record was confirmed or rejected on`.
   - `kb.py`: `KBRecord.confirmed_tests` и `rejected_tests` (`_KNOWN_FIELDS`, `from_json` —
     список строк, иначе `ValueError`, `to_json`); `confirm(signature, tests)` и
     `reject(signature, tests)`; `test_keys(tests)` — ключи из словарей `failed_tests`
     или моделей `FailedTestSummary`; `README` папки — поля можно править руками.
   - `feedback.py`: `remember` и `reject` передают тесты кластера (helper по
     `run.json`).
   - Тесты (`test_skill_memory.py`): поля пишутся и читаются, лимит, зеркальность, чужие
     поля записи сохраняются, старая запись без полей читается.
2. `feat(kb): recognise records across signature versions by their tests`.
   - `record_matches(record, signature, haystack, tests)` — правило из решения 4;
     `match_cluster` и `known_issues` (`_matches`, `current_kb_matches`, проверка отказа в
     `known_issues`) передают тесты кластера. Версия — префикс `v{SIGNATURE_VERSION}:`.
   - Тесты: запись с сигнатурой `v8:` и тестом кластера — `exact`, без совпадения признака
     — нет, с сигнатурой `v9:` другой проблемы того же теста — `fingerprint`; отказ на `v8:`
     и тот же тест — запись не предлагается (в задании и в отчёте); сквозной сценарий:
     `remember` → подмена версии в записи → `prepare` → «ТОЧНОЕ» в задании.
3. `test(eval): knowledge base offers after a signature version change`.
   - `run_eval.py`: вторая прогонка метрики записей базы знаний, где подтверждённые
     сигнатуры заменены чужой версией. Новые счётчики — доля своих точных предложений и
     чужих. `--write-baseline --set dev`, цифры — в сообщении коммита. Holdout не открывать.
4. `docs`: `.claude/rules/skill-memory.md` (поля записи, правило перехода, когда менять
   версию), `references/feedback.md` (если там описан формат записи), `RELEASE_NOTES.md`
   («записи базы знаний переживают обновления скилла»).

Модель новых текстов не видит: «ТОЧНОЕ» в задании прежнее. Стенд Qwen не нужен; по желанию
— E10 один раз.

## Проверка

`pytest`, `ruff`, `mypy`; `run_eval.py --details` (dev) — прежние метрики не меняются,
новые записаны в базовую линию.
