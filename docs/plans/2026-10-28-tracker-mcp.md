# Задача: легко подключить MCP трекера к tickets

Дата: 2026-10-28. Статус: выполнено 2026-10-29 (встроенный адаптер `adapters/mcp.py`).

Было: трекер подключался только своим адаптером (`adapter_command`), контракт —
`qwen-skill/alla-launch/extensions/tickets/README.md`. Цель: инженер включает уже
существующий MCP трекера, и tickets создаёт и связывает тикеты через него, без реализации
API в каждом проекте.

## Выбранный путь

Встроенный универсальный адаптер `extensions/tickets/adapters/mcp.py` — MCP-клиент по
stdio, говорящий по протоколу адаптера `api = 1`. Ядро, скрипты tickets и контракт не
менялись. Решения:

- **Модель MCP-инструменты не вызывает.** Иначе пропадают гарантии байтов, состояний
  `sending/unknown` и просмотра перед отправкой.
- **Только stdio.** Без новых зависимостей; удалённый HTTP/OAuth MCP — через локальный
  мост на стороне инженера.
- **Сопоставление — файл `alla-extensions/mcp-tracker.toml`** (имена инструментов, шаблоны
  аргументов, пути в ответах, проекты команд). Вложенные таблицы допустимы: это файл
  адаптера, а не `[tickets]` с плоскими типами контракта расширений.
- **Защита от дубля — метка `alla-request: UUID` в тексте** тикета и `lookup` по ней.
  У MCP нет гарантии «не выполнится позже», поэтому `absent` не возвращается никогда.

## Кто что делает

Инженер: ставит и настраивает MCP-сервер трекера (токен — через `adapter_env`), пишет
`mcp-tracker.toml` по документации сервера (пример — `adapters/mcp-tracker.example.toml`),
проверяет на тестовом проекте трекера. Программа-адаптер (`mcp.py`): запускает сервер,
рендерит шаблоны, держит контракт (чистый `prepare`, байты, метка, `lookup`, блокировка).
Свой адаптер на API нужен только трекеру без MCP или с логикой вне шаблонов.

## Что осталось

Настоящий MCP трекера на реальных данных не проверялся: контракт доказан на фейковом
сервере (`tests/fake_mcp_server.py`). Дальше — пилот на тестовом проекте трекера; по его
итогам, вероятно, понадобятся рецепты `mcp-tracker.toml` для конкретных трекеров.
