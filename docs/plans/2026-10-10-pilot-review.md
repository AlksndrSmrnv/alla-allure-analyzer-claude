## Зачем

Пилот на настоящем TestOps проводит пользователь (Linux, Qwen Code, модель
`qwen/qwen3.8-flash` внутри закрытого периметра). Реальные прогоны и логи разработчику не
передаются. Нужно понять по каждому разбору: дошёл ли он до конца, были ли проблемы у скилла,
соблюдала ли модель правила и насколько хороши диагнозы. Отсюда отдельная сводка без данных
прогона, которую можно принести разработчику.

## Решения (согласованы с пользователем)

- **Отдельная команда, по умолчанию выключена.** `review [--run DIR]` запускается после
  `done`: пользователь вызывает его сам из терминала или просит Qwen («проверь разбор»). Пока
  разбор идёт, модели о проверке ничего не сообщается: ни в заданиях, ни в ответах `next`,
  ни в правилах исполнителя. В `SKILL.md` — одна строка в конце: «только по прямой просьбе».
  Из терминала проверка не касается сеанса разбора вовсе.
- **Две части оценки:**
  1. скрипт — факты из папки разбора и журнала сеанса Qwen;
  2. модель с чистым контекстом — оценка диагнозов. Это отдельный процесс `qwen`,
     который запускает сам скрипт: без инструментов, со схемой ответа (`--json-schema`),
     с новым `--session-id`, без переменных `QWEN_CODE_*` родителя. Файла агента в
     `.qwen/agents/` нет, поэтому модель разбора о проверяющем не узнаёт.
- **Сводка для разработчика** — отдельный файл только из чисел и фиксированных слов: без
  сообщений, логов, имён тестов, путей, кода и названия прогона. Это охраняет тест с
  метками-маркерами.

## Откуда факты

- **Папка разбора:** `run.json`, `state.json` (попытки исправления, пропуски, пакеты,
  откат к `--serial`), разборы (категории, «неизвестно», цитаты по источникам, «причина не
  подтверждена логом», «НЕ ХВАТАЕТ», «СОГЛАСОВАННОСТЬ: разные проблемы», формат нарушен),
  предложения правок.
- **Журнал сеанса Qwen** (Qwen Code ≥ 0.25 пишет его сам):
  `<QWEN_HOME или ~/.qwen>/projects/<путь проекта, не-буквы → «-»>/chats/<сеанс>.jsonl`,
  субагенты — `…/subagents/<сеанс>/agent-*.jsonl` и `.meta.json`. Qwen передаёт
  shell-командам `QWEN_CODE_SESSION_ID` и `QWEN_CODE_PROJECT_DIR`. `prepare` и `next`
  записывают их в `state.json` (`sessions`, `qwen_project_dir`), поэтому `review` в другом
  сеансе или из терминала находит журнал разбора. Окно — от `prepare` этого прогона до
  последнего `done` с этой папкой. Нет журнала — раздел фактов о поведении помечается
  «журнал не найден», остальное считается.
- **Проверки поведения — те же, что у стенда.** Модель путей Qwen и правила
  (`shell_only_skill_commands`, `no_code_search`, `listed_code_only`, `allowed_reads`,
  `allowed_writes`, `report_verbatim`) переезжают из `tests/qwen_stand.py` в
  `alla_skill_lib/session_rules.py`. Стенд вызывает их оттуда, так что одно правило не
  разойдётся на две копии. Дополнительно по журналу: `STATUS: error`, вывод без `STATUS`
  (traceback), ошибки инструментов, блок «Проблемы скилла» и строки субагентов, время,
  токены, модель, версия Qwen.

## Оценка диагнозов

- Оцениваются до `MAX_REVIEWED` (10) крупнейших проблем по числу тестов (не `auto`). В
  отчёте указано, сколько упавших тестов они покрывают.
- В запрос проверяющему идут задание кластера и разбор. Код проекта — файлы из «Где искать
  код автотеста», не больше трёх на проблему, с обрезкой.
- Ответ по схеме, по каждой проблеме: причина (`подтверждена | частично | не подтверждена`),
  категория (`согласен | не согласен` + какая), действия (`полезны | общие | неверны`),
  замечание (одна строка). Плюс общий итог.
- Нет `qwen`, тайм-аут или невалидный ответ — отчёт строится без оценки модели, причина
  указывается. `review --no-model` — сразу без модели.

## Итог «насколько успешен и хорош»

Две оценки с явными правилами, константами в коде и описанием в справочнике:

- **Ход разбора:** `сбой` (нет `done`, traceback, `STATUS: error`) · `с замечаниями`
  (нарушение правил, «формат нарушен», проблемы скилла, исправления) · `чисто`.
- **Качество диагнозов:** доля подтверждённых причин и несогласий по категории →
  `хорошо` (≥ 80 % подтверждено, несогласий ≤ 10 %) · `средне` (≥ 50 %) · `плохо` ·
  `не оценено`.

## Файлы результата (`<папка разбора>/review/`)

`facts.json` (полные факты), `assessment.json` (ответ модели), `report.md` (для
пользователя: с примерами из разбора) и `pilot-summary.md` (для разработчика: только
числа). Вывод команды: `STATUS: reviewed`, краткий итог между `===ОТЧЁТ===`/`===КОНЕЦ===`
и пути к двум файлам.

## Порядок коммитов

1. `refactor(stand)`: правила поведения → `alla_skill_lib/session_rules.py`; стенд и его
   тесты без изменений поведения.
2. `feat(skill)`: `prepare`/`next` записывают сеанс Qwen; `session_log.py` читает журнал и
   субагентов в общую модель вызовов, выбирает окно прогона.
3. `feat(skill)`: `review` — факты, `report.md`, `pilot-summary.md`, оценки хода.
4. `feat(skill)`: проверяющая модель (`review_model.py`): запрос, схема, запуск `qwen`,
   разбор ответа, оценка качества.
5. `docs`: `references/review.md`, `setup.md` (как пилоту), строка в `SKILL.md`,
   `protocol.md`, `.claude/rules/skill-protocol.md`, `CLAUDE.md`.
6. Стенд: сценарий `R01` (разбор A01, затем «проверь разбор»). Проверить на настоящем Qwen.

## Проверка

pytest на синтетических журналах (вырезки из настоящих журналов стенда): окно прогона,
субагенты, нарушения, утечка данных в сводку, фейковый `qwen` (скрипт-заглушка) для
успеха, тайм-аута и мусора. ruff, mypy strict. Затем `R01` на настоящем Qwen.
