# План: расширение `sut-code` — разбор проблемы по коду тестируемого приложения

Дата: 2026-10-15. Ветка `docs/sut-code-extension-plan`. Статус: решения согласованы; что
отложено на потом — в разделе «Отложено».

## Зачем

Разбор прогона опирается на данные TestOps и код автотестов. Для проблем категории
`приложение` (и части `неизвестно`) он останавливается на «в логе сервиса NPE в
`OrderService.create`»: почему так вышло, Алла не видит — кода приложения у неё нет.

Нужна отдельная команда «продолжить разбор по коду приложения» для уже готового отчёта.
Инженер указывает ссылку на git-репозиторий SUT. Алла сама обновляет копию, выбирает
ревизию, ходит по веткам и истории и находит в коде место и причину ошибки. Итог —
объяснение с цитатами кода, совет по исправлению и решение «заводить дефект или нет» с
черновиком. Если инженер подтвердил вывод, он попадает в отчёт и в базу знаний. Черновик
дефекта станет входом для следующего расширения — заведения дефекта (оно не входит в этот
план, см. «Задел под заведение дефекта»).

## Решения (согласованы с пользователем 2026-10-15)

1. **Универсальность.** Приложения бывают разные: один репозиторий или несколько
   (микросервисы), любой язык, любой размер. Ничего не зашиваем под один стек:
   - `repos` — список репозиториев;
   - кадры стека разбираются для Java/Kotlin, Python, JS/TS, .NET, Go, Ruby и PHP;
   - если стека нет, поиск идёт по тексту ошибки.
2. **Версия SUT.** Сейчас её называет инженер в чате (ветка, тег или коммит). Не назвал —
   приблизительно: коммит основной ветки на момент запуска прогона, с просьбой уточнить
   версию. Как версия будет приходить из TestOps (лейбл `sut-version` или другое),
   пользователь ещё не решил: это отложено (см. «Отложено»), но выбор ревизии устроен так,
   чтобы источник версии добавлялся одним шагом.
3. **Доступ к git** — корпоративный репозиторий по ssh и по https. Работают ключи и
   credential helper инженера, секретов в настройках нет. Размер репозиториев разный, поэтому
   клон частичный, а первый клон может продолжаться после таймаута скрипта.
4. **Запуск** — и слэш-командой расширения (`/alla:code N [ревизия]`), и словами («разбери
   проблему 2 по коду приложения»). Значит, нужны слэш-команды, которые поставляет само
   расширение.
5. **Отчёт и база знаний** — обязательно, но только после того, как инженер подтвердил
   вывод. Неподтверждённый разбор лежит в папке расширения и в отчёт не попадает. Инженер
   сказал, что вывод неверный, — пока ничего не делаем.
6. **Совместимость не нужна.** Скилл ещё не используется: контракт расширений, форматы
   файлов, `run.json` и справочники меняем так, как удобнее для результата. Держаться за
   `api = 1` и за аддитивность изменений не нужно.

## Что получит пользователь

```text
/alla:run 12345                       — обычный разбор, отчёт
  «Расширения: проблемы 2 и 5 похожи на ошибку приложения — можно разобрать
   их по коду приложения: /alla:code 2»
/alla:code 2                          — или словами: «разбери проблему 2 по коду приложения»
/alla:code 2 release/1.4              — на нужной ветке, теге или коммите
/alla:code 2 ssh://git@git.corp/shop/orders.git   — разовая ссылка, если repos не настроен
```

Ответ субагента — 5–10 строк:

- на какой ревизии смотрели и как её выбрали («названа инженером», «приблизительно — по
  дате запуска»);
- место в коде (`OrderService.java:42`) и причина с цитатой кода;
- связь с логом падения;
- коммит, который это внёс, и есть ли исправление в основной ветке, — если удалось найти;
- как исправить;
- «дефект: заводить / не заводить — почему»;
- последней строкой — «Подтверди вывод, и я сохраню его в отчёт и базу знаний».

«Да, верно» → вывод сохраняется в базу знаний, отчёт пересобирается. В нём у проблемы
появляется раздел «Подтверждено по коду приложения». «Нет, не так» → ничего не
сохраняется.

## Ограничения, из которых исходит план

- **Контракт расширений** (`extensions/README.md`; менять можно, но принцип остаётся).
  Работу во внешнем мире (git
  fetch, worktree, история) делают скрипты расширения. Модель из shell запускает только
  команды скилла: `extensions action …`. Правило исполнителя «из shell — только
  `alla_skill.py`» не ослабляем.
- **Правила сеанса** (`session_rules.py`, общие для стенда и `review`). Сейчас модель читает
  только файлы проекта из «Где искать код автотеста» (`listed_code_only`), не ищет
  (`no_code_search`), ничего не читает вне проекта (`allowed_reads`) и пишет только
  `extensions/<имя>/*.txt` (`WRITABLE_RE`). Код SUT должен лежать **внутри проекта** и быть
  явно разрешённой зоной чтения.
- **Не трогать рабочую копию инженера.** Копию SUT кладём в отдельную папку с собственным
  `.gitignore` (`*`), как это сделано с `alla-reports/`. `.gitignore` проекта не меняем.
- **Время скрипта — до 600 с** (`MAX_TIMEOUT`). Первый клон большого репозитория может в
  него не уложиться: клон идёт в фоне (см. «Кэш репозиториев»).
- **Слабая модель** (`qwen3.8-flash`). Ей нужна заранее найденная точка входа: файлы и строки
  по кадрам стека, окна кода. Свободный поиск — вспомогательный и с лимитом. Её утверждения
  проверяет скрипт, как цитаты `[S…]` в обычном разборе.
- **Расширение не импортирует код скилла.** Всё нужное приходит в JSON-контексте. Если
  данных не хватает — расширяем контекст. Сейчас там нет кусков «Данных» проблемы, тестов,
  даты прогона и версии SUT.
- **Отчёт и базу знаний пишет только скилл.** Расширение их не трогает: оно публикует вывод
  в своём файле по контракту, а скилл по подтверждению пользователя переносит вывод в
  `alla-kb/` и `report.md` своими проверками (секреты, формат, модуль базы).

## Архитектура

### Кэш репозиториев

```text
<проект>/.alla-sut/
  .gitignore                    — «*»: папка не попадает в git проекта
  <repo-id>/repo.git            — bare partial clone (--filter=blob:none): коммиты и деревья без блобов
  <repo-id>/trees/<sha12>/      — git worktree --detach на нужную ревизию (блобы только этого дерева)
  <repo-id>/lock                — fcntl-блокировка: два субагента не фетчат одновременно
  <repo-id>/clone.log, clone.pid — фоновый первый клон
```

- `repo-id` — slug из URL (хост + путь), чтобы смена ссылки не смешала копии.
- **Первый клон** идёт в отдельном процессе (`start_new_session`), во временную папку, и
  переименовывается в `repo.git` только при успехе. `prepare` ждёт его до ~500 с. Если клон
  не успел, `prepare` отвечает `STATUS: error`: «Копия <repo> ещё скачивается (N МБ),
  повтори `/alla:code 2` через несколько минут». Клон при этом продолжается. Следующий
  запуск видит живой `clone.pid` и снова ждёт, а не начинает заново.
- Обычный запуск делает `git fetch --prune --tags`. Он инкрементальный и быстрый.
- Partial clone тянет только историю и деревья. `worktree add` докачивает блобы одного
  дерева одним пакетом. `git log -L` по файлу докачивает только нужные версии.
- Уборка: держим `keep_trees` (по умолчанию 3) последних деревьев на репозиторий. Старые
  удаляет `git worktree remove` при следующем `prepare`.

### Несколько репозиториев

- Настройка `repos = ["ssh://git@git.corp/shop/orders.git", "billing=https://git.corp/shop/billing.git"]`.
  Имя репозитория — `имя=` перед ссылкой или последняя часть пути без `.git`.
- Разовая ссылка из команды (`--param repo=…`) добавляется к списку на этот запрос.
  `config.toml` скилл не переписывает: постоянный список инженер задаёт там сам, инструкция
  — в `references/setup.md`.
- `prepare` обновляет все репозитории из списка, а деревья создаёт только для тех, где
  нашлись кадры стека или текст ошибки. Остальные называет в ответе как «без совпадений».
  Монорепозиторий — частный случай: один элемент списка.

### Выбор ревизии

Как именно выбрана ревизия, пишется в ответ: `РЕВИЗИЯ: orders v1.4.2 (a1b2c3d4) — названа
инженером`.

1. **От инженера**: `/alla:code 2 release/1.4` или словами «…на версии 1.4.2» →
   `--param ref=…`. Значение ищется в каждом репозитории как ветка, тег или коммит:
   `1.4.2`, затем `v1.4.2`. Форма `orders=release/1.4` — версия для одного репозитория;
   параметров `ref` может быть несколько. Такой ревизии в репозитории нет — в ответе
   сказано, какие похожие теги и ветки есть, и ревизия берётся по пункту 2.
2. **Приблизительно**: последний коммит основной ветки (`default_branch`, иначе `HEAD`
   remote) на момент запуска прогона: `rev-list -1 --before=<launch_created>`. Отмечается
   «приблизительно — по дате запуска; назови версию, если стенд был не на основной ветке».

Выбор ревизии — список источников по порядку (`revision.py`). Версия из TestOps, когда её
способ передачи будет решён, станет ещё одним источником между пунктами 1 и 2.

Модель может перейти на другую ревизию сама — действием `switch` (например, в логе видна
другая версия сервиса). Действие `compare` отвечает, менялся ли файл в основной ветке после
выбранной ревизии: «возможно, уже исправлено коммитом X».

### Поток (событие → субагент → действия)

```text
extensions run sut-code 2 --run DIR [--param ref=…] [--param repo=…]
  └─ хук on_request (task) → extensions/sut-code/on_request-02.{json,md}
     └─ блок «Расширения:» → основной агент запускает субагента alla-sut-code
        1. $action_prepare          fetch, ревизия, worktree, кадры → файлы;
                                    пишет on_request-02.sut.md (данные для модели)
        2. read_file / grep_search / glob — только внутри .alla-sut/<repo>/trees/<sha>/,
           лимит чтений из задания
        3. (по необходимости) $action_switch -- <ref>,  $action_history -- <путь>[:строка],
                              $action_compare -- <путь>
        4. write_file  on_request-02.txt — разбор по формату
        5. $action_check            проверка формата и цитат; до 2 исправлений
                                    → on_request-02.result.json, on_request-02.report.md,
                                      on_request-02.finding.json (вывод для отчёта и базы)
        6. ответ: строки после STATUS: из check + просьба подтвердить
```

### Что готовит `prepare` (`<stem>.sut.md`)

- Ревизия по каждому репозиторию и способ выбора, пути к деревьям.
- Кадры стека из кусков «Данных» проблемы → файлы в деревьях SUT. Ищем по имени файла и
  совпадению пакета или пути (как `code_hints.py`, но своим кодом). Для каждого кадра —
  окно ±30 строк с номерами. Кадры фреймворков и библиотек, которых нет в деревьях,
  пропускаются.
- Сообщения об ошибках из логов (`customer is null`) → `git grep -F` по деревьям: где этот
  текст формируется. Это частый и надёжный путь к месту ошибки, и он не зависит от языка.
- Ничего не найдено — прямо сказано, задание предлагает свой поиск по деревьям.

### Формат разбора модели (`<stem>.txt`)

```text
РЕВИЗИЯ: <репозиторий> <ref> (<sha8>)   (по строке на каждый использованный репозиторий)
ВЫВОД: <приложение|тест|окружение|данные|неизвестно> — <одна фраза>
МЕСТО: <репозиторий>:<путь>:<строка> — <что там>
КОД:
- <репозиторий>:<путь>:<строка> «<дословная строка кода>»
СВЯЗЬ С ПАДЕНИЕМ: [S<номер>] «<цитата из лога>» — <как это следует из кода>
ИСТОРИЯ: <sha8> <дата> — <что изменил> | нет данных
КАК ИСПРАВИТЬ:
1. <шаг>
ДЕФЕКТ: заводить | не заводить — <почему>
ЗАГОЛОВОК ДЕФЕКТА: <до 100 символов>   (только если «заводить»)
```

`ВЫВОД` берёт категории разбора (`references/analysis-format.md`). Пример `тест`: поведение
приложения изменили намеренно, и автотест устарел.

`check` проверяет:

- все разделы на месте;
- цитаты кода дословно есть в файле ревизии рядом с названной строкой (±3);
- `[S…]` есть в кусках проблемы;
- `sha` — коммит этого репозитория;
- «заводить» — с заголовком.

Ошибки — текстом для модели, как `STATUS: fix` у разборов. После второй неудачной попытки
результат принимается с пометкой «формат нарушен», и такой вывод сохранить в базу знаний
нельзя. Итоговые файлы:

- `result.json` — полная структура для будущего расширения дефектов;
- `report.md` — для человека;
- `finding.json` — вывод для отчёта и базы, формат по контракту ниже.

### Подтверждение: в отчёт и базу знаний

Новое в контракте расширений: **вывод расширения по проблеме**.

- Файл `<out_dir>/<stem>.finding.json`, поля:

  | Поле | Что там |
  |---|---|
  | `problem` | номер проблемы |
  | `category` | категория разбора, кроме `неизвестно` |
  | `title` | 3–8 слов |
  | `cause` | причина |
  | `fix` | список шагов |
  | `details` | до 8 строк для отчёта: ревизия, место, цитата, коммит |
  | `kb_fields` | плоский словарь строк, хранится в записи базы как своё поле `<имя расширения>` |
  | `format_ok` | прошёл ли вывод проверку формата |

  Пример `kb_fields`: `{"repo": "orders", "revision": "v1.4.2", "location": "OrderService.java:42", "commit": "a1b2c3d4"}`.
- **Подтвердил как есть** («да, верно», «запомни») →
  `remember N --run DIR --from-extension sut-code`. Скилл:
  - читает `finding.json` этой проблемы;
  - проверяет: категория не `неизвестно`, `format_ok`, длины, сканер секретов `kb`;
  - сохраняет запись в базу своего модуля обычным путём `remember`. Признак — собственный
    признак кластера (`evidence/NN.txt`), `kb_fields` — своим полем записи;
  - пишет `confirmed/NN.json` в папке разбора (вывод, расширение, время);
  - отвечает `STATUS: saved` и просит выполнить `next`.
- **Сказал, что вывод неверный** → ничего не сохраняется: ни в базу, ни в отчёт. Основной
  агент отвечает, что вывод не сохранён. Обычная обратная связь (`feedback/NN.md`,
  `remember`) по-прежнему доступна, если инженер сам назовёт причину, но с выводом
  расширения она не связана.
- **Отчёт** (`report.py`): у проблемы с `confirmed/NN.json` — раздел «Подтверждено по коду
  приложения (инженер)»: причина, `details`, как исправить. В сводных числах категорий
  проблема считается по подтверждённой категории. В кратком разборе — одна пометка
  «подтверждено по коду», без новых строк: размер брифа охраняет `test_skill_report.py`.
  `confirmed/` входит в хэш входов отчёта: `next` после `remember` пересобирает отчёт. Если
  подтверждение меняет входы сводки — `STATUS: summary`, как после обычного `remember`.
- `after_report` у `sut-code` не подсказывает уже подтверждённые проблемы.

## Изменения в скилле

Совместимость не держим: если по ходу работы контракт расширений проще сделать заново
(например, `api = 2` с событием `on_request` и выводами вместо `after_apply`-частностей) —
меняем вместе с git-publish, README, AUTHORING и тестами.

1. **Событие `on_request`** (`EVENTS`, `extensions.py`, `cli._extensions_run`).
   - Срабатывает только по `extensions run <имя> N [N…] --run DIR [--param ключ=значение…]`.
   - Если у расширения есть хук `on_request`, `run` вызывает его. Иначе работает как сейчас
     (`after_apply`/`after_report`), поэтому git-publish не меняется.
   - Для каждой N — свой `stem` (`on_request-NN`). Несколько N — несколько пунктов блока,
     субагенты по очереди.
   - Применённая правка не нужна. Нет разбора проблемы — отказ с понятной строкой.
   - `confirm` для `on_request` не спрашивается: пользователь сам попросил.
2. **Новые поля контекста** (README, `problem_context`, `_fire_hook`):
   - `problem.sources` — куски «Данных» проблемы: `id`, `title`, `text`;
   - `problem.tests` — `name`, `full_name`, `link`;
   - `launch_created` — время запуска прогона, ISO 8601;
   - `params` — словарь из `--param`; в шаблоне задания — `$param_<ключ>`.
3. **Время запуска прогона** (ядро, `core.md`). `created_date` прогона уже приходит в
   `LaunchResponse`; сохраняем его в `run.json` как `launch_created` и поднимаем
   `RUN_SCHEMA` до 5. Фейковый TestOps (`skill_fake_testops.py`, `fake_testops_server.py`)
   отдаёт дату. Версию из TestOps не читаем — это отложено.
4. **Слэш-команды расширений.** Расширение может положить `commands/<имя>.md`. `enable` и
   `prepare` ставят команду в `.qwen/commands/alla/`, как агента расширения
   (`qwen_files`), а `disable` убирает, только если файл наш. Имена встроенных команд скилла
   (`run`, `apply`…) заняты. Так `/alla:code N` принадлежит расширению; тот же механизм
   понадобится для `/alla:defect N`. Формат команды и проверки — как у `commands/alla/`
   (`test_skill_commands.py`).
5. **Вывод расширения в отчёт и базу знаний** (раздел «Подтверждение»):
   - `remember --from-extension <имя>` (`cli`, `feedback`, `kb`);
   - папка `confirmed/` (`workspace.RunPaths`);
   - раздел отчёта (`report.py`);
   - справочник `references/feedback.md`.
6. **Правила сеанса** (`session_rules.py`) — зона кода приложения `.alla-sut/`:
   - чтение (`read_file`, `read_many_files`) разрешено, как и `alla-reports/`
     (`NOT_PROJECT_CODE`);
   - `glob`/`grep_search` разрешены только с областью внутри `.alla-sut/<repo>/trees/<sha>/`.
     Поиск по всему `.alla-sut/` или выше остаётся нарушением;
   - запись туда запрещена (`WRITABLE_RE` не меняется). Shell по-прежнему только скилл.
   - Проверить оба потребителя: `test_qwen_stand.py` и `test_skill_session_log.py`.
7. **`SKILL.md` и справочники:**
   - раздел 7: «разбери проблему N по коду приложения» → `extensions run sut-code N --run DIR
     [--param ref=…] [--param repo=…]`. Основной агент код приложения сам не читает и не
     ищет;
   - раздел 5: подтверждение или правка вывода расширения → `remember --from-extension`;
   - таблица слэш-команд: команды расширений;
   - `references/protocol.md`, `references/feedback.md`.

## Расширение `extensions/sut-code/`

```text
extension.toml
agent.md            — alla-sut-code: read_file, grep_search, glob, write_file, run_shell_command
task.md             — задание on_request (запреты повторены: до перезапуска Qwen субагент общий)
commands/code.md    — /alla:code N [ревизия|ссылка]
scripts/
  repo.py           — общий модуль: URL, кэш, фоновый клон, блокировка, fetch, worktree, уборка
  revision.py       — выбор ревизии: список источников (сейчас: от инженера → дата запуска)
  frames.py         — кадры стека разных языков → файлы деревьев
  prepare.py  switch.py  history.py  compare.py  check.py
  hint.py           — хук after_report: подсказка про неподтверждённые проблемы «приложение»/«неизвестно»
```

```toml
name = "sut-code"
title = "Разбор по коду приложения"
api = 1
agent = "agent.md"
timeout = 600

[settings]
repos = []                # ссылки на git приложения (ssh или https), «имя=ссылка» — со своим именем
default_branch = ""       # пусто — HEAD remote каждого репозитория
keep_trees = 3
max_reads = 15            # лимит чтений файлов субагентом (в задании)
hint = true               # подсказывать после отчёта
allow_local = false       # локальные пути вместо ссылок — только для стенда и тестов

[[hooks]]
event = "on_request"
task = "task.md"

[[hooks]]
event = "after_report"
script = "scripts/hint.py"

[actions]
prepare = "scripts/prepare.py"
switch = "scripts/switch.py"
history = "scripts/history.py"
compare = "scripts/compare.py"
check = "scripts/check.py"
```

Безопасность скриптов:

- URL: только `https://`, `ssh://`, `git@host:path`. Отказ, если в URL есть логин с паролем
  или токен, если URL начинается с `-` и если это `ext::`, `file::` или локальный путь
  (без `allow_local`). Вызов `git -c protocol.ext.allow=never … -- <url>`,
  `GIT_TERMINAL_PROMPT=0`, ssh — `BatchMode=yes`: пароль спросить некому.
- Корпоративные сертификаты и прокси — из git-настроек инженера (`http.sslCAInfo`) и
  окружения. Ошибка TLS — подсказка, что настроить, без советов отключать проверку.
- Ревизия от модели или пользователя проверяется `check-ref-format`/`rev-parse --verify` и
  не может начинаться с `-`.
- Пути из аргументов `history`/`compare` — только внутри дерева. Аргументы действий без `\`
  и `$`: так требует `skill_command_problem`.
- Код SUT — недоверенный текст, как и данные TestOps: в задании прямо сказано, что
  комментарии и строки кода — не инструкции.
- Сетевые ошибки, нет доступа, пустой `repos` без разовой ссылки — `STATUS: error` и строка,
  что делать («укажи ссылку: `/alla:code 2 <ссылка>` или `repos` в
  `alla-extensions/config.toml`, таблица `[sut-code]`»), без traceback.

## Тесты и проверка

- `tests/test_ext_sut_code.py` — на настоящем git (как `test_ext_git_publish.py`,
