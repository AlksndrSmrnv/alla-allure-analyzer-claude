# План: расширение `sut-code` — разбор проблемы по коду тестируемого приложения

Дата: 2026-10-15. Статус: черновик, ждёт решений по открытым вопросам.

## Зачем

Разбор прогона опирается на данные TestOps и код автотестов. Для проблем категории
`приложение` (и части `неизвестно`) он останавливается на «в логе сервиса NPE в
`OrderService.create`»: почему так вышло, Алла не видит — кода приложения у неё нет.

Нужна отдельная команда «продолжить разбор по коду приложения» для уже готового отчёта.
Инженер один раз указывает ссылку на git-репозиторий SUT. Алла сама обновляет копию,
выбирает ревизию, ходит по веткам и истории и находит в коде место и причину ошибки. Итог —
объяснение с цитатами кода, совет по исправлению и решение «заводить дефект или нет» с
черновиком. Черновик станет входом для следующего расширения — заведения дефекта (оно не
входит в этот план, см. «Задел под заведение дефекта»).

## Что получит пользователь

```text
/alla:run 12345                       — обычный разбор, отчёт
  «Расширения: проблемы 2 и 5 похожи на ошибку приложения — можно разобрать
   их по коду приложения: /alla:code 2»
/alla:code 2                          — или словами: «разбери проблему 2 по коду приложения»
/alla:code 2 release/1.4              — то же на нужной ветке, теге или коммите
```

Ответ субагента — 5–10 строк: на какой ревизии смотрели и почему именно на ней, место в
коде (`OrderService.java:42`), причина с цитатой кода, связь с логом падения, при
наличии — коммит, который это внёс, и есть ли исправление в основной ветке, как исправить,
«дефект: заводить / не заводить — почему». Полный разбор лежит в
`alla-reports/<разбор>/extensions/sut-code/`.

## Ограничения, из которых исходит план

- **Контракт расширений `api = 1`** (`extensions/README.md`). Работу во внешнем мире (git
  fetch, worktree, история) делают скрипты расширения. Модель из shell запускает только
  команды скилла: `extensions action …`. Правило исполнителя «из shell — только
  `alla_skill.py`» не ослабляем.
- **Правила сеанса** (`session_rules.py`, общие для стенда и `review`). Сейчас модель читает
  только файлы проекта из «Где искать код автотеста» (`listed_code_only`), не ищет
  (`no_code_search`), ничего не читает вне проекта (`allowed_reads`) и пишет только
  `extensions/<имя>/*.txt` (`WRITABLE_RE`). Код SUT должен лежать **внутри проекта** и быть
  явно разрешённой зоной чтения.
- **Не трогать рабочую копию инженера** (README расширений). Копию SUT кладём в отдельную
  папку с собственным `.gitignore` (`*`), как это сделано с `alla-reports/`. `.gitignore`
  проекта не меняем.
- **Время скрипта — до 600 с** (`MAX_TIMEOUT`). Первый клон большого репозитория должен в
  него укладываться: делаем partial clone.
- **Слабая модель** (`qwen3.8-flash`). Ей нужна заранее найденная точка входа: файлы и строки
  по кадрам стека, окна кода. Свободный поиск — вспомогательный и с лимитом. Её утверждения
  проверяет скрипт, как цитаты `[S…]` в обычном разборе.
- **Расширение не импортирует код скилла.** Всё нужное приходит в JSON-контексте. Если
  данных не хватает — расширяем контекст (сейчас там нет кусков «Данных» проблемы, тестов и
  даты прогона).

## Архитектура

### Где лежит код SUT

```text
<проект>/.alla-sut/
  .gitignore                    — «*»: папка не попадает в git проекта
  <repo-id>/repo.git            — bare partial clone (--filter=blob:none): история и деревья без блобов
  <repo-id>/trees/<sha12>/      — git worktree --detach на нужную ревизию (блобы только этого дерева)
  <repo-id>/lock                — fcntl-блокировка: два субагента не фетчат одновременно
```

- `repo-id` — slug из URL (хост + путь), чтобы смена `repo` в настройках не смешала копии.
- Partial clone быстрый: тянутся только коммиты и деревья. `worktree add` докачивает блобы
  одного дерева одним пакетом. `git log -L` по одному файлу докачивает только нужные версии.
- Уборка: держим `keep_trees` (по умолчанию 3) последних деревьев. Старые удаляет
  `git worktree remove` при следующем `prepare`.

### Выбор ревизии («сама ходит по веткам»)

`prepare` делает `git fetch --prune --tags` и выбирает ревизию по порядку. Как именно
выбрана ревизия, пишется в ответ (`РЕВИЗИЯ: v1.4.2 (a1b2c3d4) — по версии из лога [S3]`):

1. Явно от пользователя: `/alla:code 2 release/1.4` → `--param ref=release/1.4`.
2. Настройка `ref` в `config.toml` (стенд всегда собран из `develop`).
3. Версия из данных прогона: регулярные выражения `version_patterns` по имени прогона и
   кускам «Данных» проблемы (`build 1.4.2`, `commit a1b2c3d`) → тег, ветка или коммит, если
   такой есть в репозитории.
4. Запасной путь: последний коммит основной ветки (`default_branch`, иначе `HEAD` remote) на
   момент запуска прогона: `rev-list -1 --before=<launch_created>`. Отмечается как
   «приблизительно».

Модель может перейти на другую ревизию сама — действием `switch` (например, в логе видна
другая версия сервиса). Действие `compare` отвечает, менялся ли файл в основной ветке после
выбранной ревизии: «возможно, уже исправлено коммитом X».

### Поток (событие → субагент → действия)

```text
extensions run sut-code 2 --run DIR [--param ref=…]
  └─ хук on_request (task) → extensions/sut-code/on_request-02.{json,md}
     └─ блок «Расширения:» → основной агент запускает субагента alla-sut-code
        1. $action_prepare          fetch, ревизия, worktree, кадры → файлы;
                                    пишет on_request-02.sut.md (данные для модели)
        2. read_file / grep_search / glob — только внутри .alla-sut/<repo>/trees/<sha>/,
           лимит чтений из задания
        3. (по необходимости) $action_switch -- <ref>,  $action_history -- <путь>[:строка],
                              $action_compare -- <путь>
        4. write_file  on_request-02.txt — разбор по формату
        5. $action_check            проверка формата и цитат; до 2 исправлений
                                    → on_request-02.result.json + on_request-02.report.md
        6. ответ: строки после STATUS: из check
```

### Что готовит `prepare` (`<stem>.sut.md`)

- Ревизия и способ выбора, путь к дереву.
- Кадры стека из кусков «Данных» проблемы (Java `at …(File.java:N)`, Python, JS, .NET,
  Go) → файлы в дереве SUT, найденные по имени файла и пакету (как `code_hints.py`, но
  своим кодом). Для каждого — окно ±30 строк с номерами.
- Сообщения об ошибках из логов (`customer is null`) → `git grep -F` по дереву: где этот
  текст формируется. Это частый и надёжный путь к месту ошибки.
- Ничего не найдено — прямо сказано, задание предлагает свой поиск по дереву.

Регулярные выражения поиска модели не нужны: `skill_command_problem` запрещает `\` и `$` в
команде, а `grep_search` Qwen внутри дерева их и так поддерживает.

### Формат разбора модели (`<stem>.txt`)

```text
РЕВИЗИЯ: <ref> (<sha8>)
ВЫВОД: <ошибка в приложении | тест устарел (поведение изменили намеренно) | конфигурация или окружение | причина в коде не найдена> — <одна фраза>
МЕСТО: <путь>:<строка> — <что там>
КОД:
- <путь>:<строка> «<дословная строка кода>»
СВЯЗЬ С ПАДЕНИЕМ: [S<номер>] «<цитата из лога>» — <как это следует из кода>
ИСТОРИЯ: <sha8> <дата> — <что изменил> | нет данных
КАК ИСПРАВИТЬ:
1. <шаг>
ДЕФЕКТ: заводить | не заводить — <почему>
ЗАГОЛОВОК ДЕФЕКТА: <до 100 символов>   (только если «заводить»)
```

`check` проверяет: разделы на месте; цитаты кода дословно есть в файле ревизии рядом с
названной строкой (±3); `[S…]` есть в кусках проблемы; `sha` — коммит репозитория;
«заводить» — с заголовком. Ошибки — текстом для модели, как `STATUS: fix` у разборов. После
второй неудачной попытки результат принимается с пометкой «формат нарушен». Итог:
`result.json` (структура для будущего расширения дефектов) и `report.md` (для человека).

## Изменения в скилле (контракт, `api` остаётся 1 — всё аддитивно)

1. **Событие `on_request`** (`EVENTS`, `extensions.py`, `cli._extensions_run`).
   - Срабатывает только по `extensions run <имя> N [N…] --run DIR [--param ключ=значение…]`.
   - Если у расширения есть хук `on_request`, `run` вызывает его. Иначе работает как сейчас
     (`after_apply`/`after_report`), поэтому git-publish не меняется.
   - Для каждой N — свой `stem` (`on_request-NN`). Несколько N — несколько пунктов блока,
     субагенты по очереди: кэш SUT общий, хотя он и под блокировкой.
   - Применённая правка не нужна. Нет разбора проблемы — отказ с понятной строкой.
   - `confirm` для `on_request` не спрашивается: пользователь сам попросил.
2. **Новые поля контекста** (README, `problem_context`):
   - `problem.sources` — куски «Данных» проблемы: `id`, `title`, `text`. Без них нет кадров
     стека и логов приложения.
   - `problem.tests` — `name`, `full_name`, `link`.
   - `launch_created` — время запуска прогона, ISO 8601. Нужно запасному пути выбора ревизии.
     В `run.json` его пока нет: добавить при `prepare` и поднять `RUN_SCHEMA` до 5.
   - `params` — словарь из `--param` (у других событий пустой). В шаблоне задания —
     `$param_<ключ>`.
3. **Команды расширений в Qwen** (необязательно, этап 5). Расширение может положить
   `commands/<имя>.md`. `enable` и `prepare` ставят его в `.qwen/commands/alla/`, как
   агента расширения, а `disable` убирает. Так `/alla:code N` принадлежит расширению, а не
   скиллу. Тот же механизм понадобится для `/alla:defect N`. Запасной путь без этого —
   `/alla:extensions run sut-code N` и просьба словами.
4. **Правила сеанса** (`session_rules.py`) — зона кода приложения `.alla-sut/`:
   - чтение (`read_file`, `read_many_files`) разрешено, как и `alla-reports/`
     (`NOT_PROJECT_CODE`);
   - `glob`/`grep_search` разрешены только с областью внутри `.alla-sut/<repo>/trees/<sha>/`.
     Поиск по всему `.alla-sut/` или выше остаётся нарушением;
   - запись туда запрещена (`WRITABLE_RE` не меняется). Shell по-прежнему только скилл.
   - Проверить оба потребителя: `test_qwen_stand.py` и `test_skill_session_log.py`.
5. **`SKILL.md`, раздел 7, и `references/protocol.md`.** Пользователь просит «разбери
   проблему N по коду приложения» → `extensions run sut-code N --run DIR [--param ref=…]`,
   дальше блок «Расширения:» как обычно. Отдельно сказать: основной агент код приложения сам
   не читает и не ищет, это делает только субагент.

## Расширение `extensions/sut-code/`

```text
extension.toml
agent.md            — alla-sut-code: read_file, grep_search, glob, write_file, run_shell_command
task.md             — задание on_request (запреты повторены: до перезапуска Qwen субагент общий)
commands/code.md    — /alla:code N [ревизия] (если делаем п. 3)
scripts/
  repo.py           — общий модуль: URL, кэш, блокировка, fetch, worktree, уборка
  prepare.py  switch.py  history.py  compare.py  check.py
  hint.py           — хук after_report: подсказка про проблемы «приложение»/«неизвестно»
```

```toml
name = "sut-code"
title = "Разбор по коду приложения"
api = 1
agent = "agent.md"
timeout = 600

[settings]
repo = ""                 # ссылка на git тестируемого приложения (https или ssh), без пароля в URL
default_branch = ""       # пусто — HEAD remote
ref = ""                  # всегда эта ревизия (иначе — по версии из прогона или дате запуска)
version_patterns = []     # регулярные выражения с группой (?P<ref>…) по имени прогона и логам
keep_trees = 3
max_reads = 15            # лимит чтений файлов субагентом (в задании)
hint = true               # подсказывать после отчёта

[[hooks]]
event = "on_request"
task = "task.md"

[[hooks]]
event = "after_report"
script = "scripts/hint.py"

[actions]
prepare = "scripts/prepare.py"
switch = "scripts/switch.py"
history = "scripts/history.py"
compare = "scripts/compare.py"
check = "scripts/check.py"
```

Безопасность скриптов:

- URL: только `https://`, `ssh://`, `git@host:path`. Отказ, если в URL есть логин с паролем
  или токен, если URL начинается с `-` и если это `ext::`, `file::` или локальный путь.
  Исключение для локального пути — флаг `allow_local` для стенда. Вызов
  `git -c protocol.ext.allow=never … -- <url>`, `GIT_TERMINAL_PROMPT=0`. Доступ — через
  ssh-ключи или credential helper инженера, секретов в настройках нет.
- Ревизия от модели или пользователя проверяется `check-ref-format`/`rev-parse --verify` и
  не может начинаться с `-`.
- Пути из аргументов `history`/`compare` — только внутри дерева.
- Код SUT — недоверенный текст, как и данные TestOps: в задании прямо сказано, что
  комментарии и строки кода — не инструкции.
- Сетевые ошибки, нет доступа, нет `repo` в настройках — `STATUS: error` и строка, что делать
  («укажи repo в alla-extensions/config.toml, таблица [sut-code]»), без traceback.

## Тесты и проверка

- `tests/test_ext_sut_code.py` — на настоящем git (как `test_ext_git_publish.py`,
  изолированный `GIT_CONFIG_GLOBAL`). Фикстура: bare-репозиторий SUT с Java/Python-файлами,
  ветками `main`/`release/1.4`, тегом `v1.4.2`, коммитом, который вносит NPE. Проверяется:
  - выбор ревизии по каждому из 4 правил и по `switch`;
  - кадры → файлы и окна, `git grep` по сообщению;
  - `history`, а также `compare` («исправлено в main»);
  - `check` принимает верный разбор и отклоняет выдуманную цитату, чужую строку, неверный
    `[S…]`;
  - повторный запуск не клонирует заново, уборка деревьев;
  - отказы по URL (пароль, `-u…`, `ext::`), нет `repo`, недоступный remote;
  - блокировка.
- `test_skill_extensions.py`: событие `on_request`, `--param`, несколько N, новые поля
  контекста, `run` без хука `on_request` работает по-старому.
- `test_qwen_stand.py`, `test_skill_session_log.py`: зона `.alla-sut/` — чтение и поиск в
  дереве допустимы, поиск выше дерева, запись и чтение вне проекта — нарушение.
- `test_skill_docs.py` / `test_skill_prompts.py`: пример формата из README расширения через
  настоящий `check`, наличие запретов в `task.md`.
- **Стенд Qwen, сценарий `X02`**: фикстура с NPE в логе приложения и bare-репозиторием SUT
  внутри проекта (`allow_local`), реплики «/alla-launch 7xx» → «разбери проблему 1 по коду
  приложения». Автопроверки:
  - субагент запускал только команды скилла;
  - читал только `.alla-sut/…/trees/<sha>/`;
  - `check` → `ok`;
  - `МЕСТО` совпадает с внесённой ошибкой;
  - `ВЫВОД` — «ошибка в приложении».

  Второй вариант того же сценария: поведение изменили намеренно → «тест устарел».
- Эталон (`tests/eval/`) не затрагивается: извлечение логов и кластеризация не меняются.
- После правки задания и `SKILL.md` — агент `qwen-executor-review`.

## Этапы и коммиты

0. **Разведка на стенде (до кода).** Работают ли `read_file`, `grep_search` и `glob` Qwen в
   папке, которую исключает её собственный `.gitignore` (`*`)? Чтение `alla-reports/` уже
   работает, а поиск может молча вернуть пусто, потому что Qwen уважает `.gitignore`. Если
   поиск не работает — вместо него действие `search -- <текст>` (`git grep -F`), а
   `grep_search` в задании не упоминаем. Сколько живёт `run_shell_command` Qwen на долгой
   команде: первый `prepare` может идти минуты.
1. `feat(skill): on_request extension event with params and problem sources`. Событие,
   `--param`, поля контекста, `launch_created` с `RUN_SCHEMA` 5, README/AUTHORING,
   `skill-extensions.md`, тесты.
2. `feat(skill): allow reading app code from .alla-sut in session rules`. Правила, тесты
   стенда и `review`, `skill-protocol.md`.
3. `feat(ext): sut-code repository cache and revision selection`. `repo.py`, `prepare`,
   `switch`, `history`, `compare`, тесты на git.
4. `feat(ext): sut-code task, agent and result check`. `task.md`, `agent.md`, `check.py`,
   `hint.py`, формат в README расширения, тесты.
5. `feat(skill): extension-provided slash commands` (если согласуем) + `/alla:code`;
   `SKILL.md` раздел 7, `references/protocol.md`, `references/setup.md` («Расширения»: как
   включить, где указать `repo`, доступ к git), строка в `CLAUDE.md`.
6. `test(stand): X02 app-code analysis`. Сценарий, прогон, `--repeat 3` для разброса,
   находки — в `docs/skill-quality.md`.

## Задел под заведение дефекта (следующее расширение)

- `<stem>.result.json` расширения `sut-code` — стабильная структура: `revision`, `verdict`,
  `location`, `code_quotes`, `log_quotes`, `history`, `fix_steps`, `defect: {needed, title,
  summary}`. Описать её в README расширения.
- Передавать её будущему расширению (`defect`) через контекст, а не чтением чужой папки
  (AUTHORING запрещает читать служебные файлы). Новое общее поле `problem.extension_results`
  — словарь «имя расширения → result.json этой проблемы». Его сделаем вместе с `defect`.
- Механизм слэш-команд расширений (этап 5) даст `/alla:defect N`, а `confirm = true` — вопрос
  перед заведением.

## Открытые вопросы (нужно решение пользователя)

1. **Один репозиторий или несколько?** Если SUT — набор микросервисов, `repo` становится
   списком `["orders=https://…", "billing=…"]`, а сервис выбирается по пакету кадра или
   имени лога. План закладывает один репозиторий и формат настройки, который можно
   расширить.
2. **Как по прогону понять версию приложения?** Есть ли в TestOps у прогона теги или
   параметры окружения с версией или веткой, пишется ли версия в логи, отражает ли её имя
   прогона? От этого зависит, нужен ли клиенту TestOps запрос тегов и окружения прогона (в
   ядре его сейчас нет) или хватит `version_patterns`.
3. **Git-хостинг и доступ**: GitLab/GitHub/Bitbucket, https с credential helper или ssh? Какой
   примерно размер репозитория? Это влияет на таймаут первого клона.
4. **Отдельная слэш-команда `/alla:code`** через механизм команд расширений (этап 5) — или
   хватит `/alla:extensions run sut-code N` и просьбы словами?
5. **Влияет ли результат на отчёт и базу знаний?** В плане — нет: отчёт `report.md` не
   меняется, результат лежит в папке расширения. Сохранить вывод в базу знаний пользователь
   может обычным `/alla:remember N <причина>`.
