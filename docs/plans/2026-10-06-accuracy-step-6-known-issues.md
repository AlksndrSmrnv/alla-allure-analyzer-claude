с повышением версии.

## Зачем

Одна причина часто даёт разные симптомы: пул БД исчерпан — у одних тестов 502, у других
таймаут, у третьих «элемент не найден». Кластеризация по симптомам разносит их по разным
проблемам, и это правильно (дробление по симптомам эталон не штрафует). Но если причина
уже записана в базе знаний и модель в каждом разборе подтвердила эту запись, человек видит в
отчёте три независимые проблемы вместо одной известной. Шаг 6 показывает их вместе, ничего не
теряя: номера, разборы, правки и команды остаются как были.

## Что есть сейчас

- `prepare` подбирает записи базы знаний для каждого кластера (`cli.py:546`,
  `kb.match_cluster`, `kb.py:391`): точно по сигнатуре (`confirmed_signatures`, без
  `rejected_signatures`) или по признаку `error_example`; не больше трёх. Снимок записей
  лежит в `run.json` у кластера (`entry["kb"]`) и в задании.
- Модель пишет `БАЗА ЗНАНИЙ: <id> | нет`; валидатор пропускает только id из снимка
  (`analysis_format.validate_analysis`, `sources.py:120`). Результат — `ClusterAnalysis.kb_ref`.
- Отчёт показывает `kb_ref` как есть: метка «известная проблема: id» в брифе
  (`report.py:786`) и строка в `report.md` (`report.py:841`). Если пользователь потом сказал
  `reject N <id>`, метка остаётся: снимок и разбор не меняются.
- История пишет `kb_entry = analysis.kb_ref` (`history.py:115`); по нему следующий `prepare`
  считает повторы (`recurrence`).
- Отчёт и `report.md` пересобирает только `next` (`cli.py:777–803`). `remember`/`reject`
  меняют файлы `alla-kb/` и отчёт не трогают.
- Сводка: `build_summary_data` (хэш — `state.summary_data_hash`); при смене данных `next`
  удаляет `summary.md` и просит модель написать сводку заново.
- На стенде Qwen нет сценария с базой знаний; в эталоне нет ничего про записи базы знаний.

## Решения

### Кто входит в группу

Проблема входит в группу записи R, если выполнено всё:

1. Разбор принят (не «формат нарушен») и в нём `БАЗА ЗНАНИЙ: R`.
2. Совпадение R с этой проблемой **подтверждается сейчас**, по текущим файлам базы знаний:
   запись есть и читается; сигнатуры кластера нет в `rejected_signatures`; сигнатура есть в
   `confirmed_signatures` или все строки `error_example` есть в `evidence/NN.txt` (та же
   проверка, что в `match_cluster`, но для одной записи и без лимита в три).
3. Категория разбора совпадает с категорией записи (`KB_TO_CATEGORY`). Эталон — запись: её
   категорию подтвердил человек, а большинство разборов могло ошибиться вместе.
4. Не «СОГЛАСОВАННОСТЬ: разные проблемы» (шаг 4).

Ключ группы — `(папка базы знаний, id записи)`. Папка — `entry["kb_dir"]`, у старых записей
без поля — `run["kb_dir"]`; внутри одного разбора папка однозначно соответствует модулю,
поэтому это и есть «(модуль, id)» из исходного плана, но работает и для папок до модулей.
Группа — от двух проблем. Одна подтверждённая проблема — без блока, только метка, как сейчас.

Пункт 2 даёт главное свойство: после `reject` запись перестаёт подтверждаться и при следующей
сборке отчёта проблема выходит из группы, а её метка «известная проблема» пропадает (сейчас
она остаётся навсегда).

### Что не группируется и как это видно

- Разные папки базы знаний (модули) — разные группы, даже при одинаковом id.
- Категория разбора не совпала с записью — проблема остаётся отдельно, в `report.md` строка
  «Разбор ссылается на известную проблему R, но называет другую причину (окружение; в базе
  знаний — приложение) — проверьте разбор или запись», в брифе метка «расходится с базой
  знаний».
- Неоднородная группа и «формат нарушен» — отдельно; у неоднородной метка «известная
  проблема» остаётся, если совпадение подтверждено.
- Совпадение `КОД:` не используется (решение исходного плана).
- `remember N` по проблеме без `БАЗА ЗНАНИЙ:` в разборе не добавляет её в группу этого
  прогона: текст разбора в отчёте остался бы версией модели. Следующий `prepare` предложит
  запись точно, и группа сложится там.

### Когда база знаний недоступна

Папки `kb_dir` нет (разбор открыт на другой машине, проект переехал) — проверить совпадения
нельзя: групп нет, метки «известная проблема» — по разбору, как сейчас, и одно замечание
«База знаний <папка> недоступна — известные проблемы не сгруппированы». Битый файл записи —
запись не подтверждается, предупреждение того же вида, что у `ProjectKB.load`.

### Тесты не теряются и не считаются дважды

Кластеры прогона не пересекаются, у разбора не больше одного `kb_ref`, значит проблема входит
не больше чем в одну группу. Счётчики шапки и разделов (проблемы и тесты) не меняются: группа —
способ показа, а не новая проблема. Тест: сумма тестов по группам и негруппированным проблемам
равна `active_failures`.

## 6.1 Подтверждение и группы — `known_issues.py`

- Новый модуль `scripts/alla_skill_lib/known_issues.py` (чистые функции, без вывода):
  - `confirmed_ref(entry, analysis, kb, evidence) -> str | None` — пункты 1–2 выше;
  - `known_issues(run, analyses, flagged, paths) -> KnownIssues`: загружает записи каждой папки
    один раз (`ProjectKB.load`), читает `evidence/NN.txt`, строит группы и список
    «расходится с базой знаний»; порядок групп — по числу тестов, затем по наименьшему номеру.
  - У группы: ключ, снимок записи (id, название, категория, описание, первый шаг рецепта),
    номера проблем, сумма тестов. Снимок нужен отчёту и сводке, чтобы не читать файлы дважды.
- Проверку совпадения одной записи вынести из `match_cluster` в `kb.py` (`record_matches`),
  `match_cluster` вызывает её же: одно правило для `prepare` и отчёта.
- Папка без `evidence/NN.txt` (до сохранения доказательств) — подтверждение только по точной
  сигнатуре.
- Тесты `tests/test_known_issues.py` на фабриках `skill_fixtures`: три кластера с одной записью
  по признаку → одна группа; `reject` одного → группа из двух; `reject` второго → группы нет,
  у оставшегося метка есть, у отвергнутых нет; разные `kb_dir` с одним id → две записи по одной
  проблеме; категория не совпала → вне группы и в списке расхождений; «разные проблемы» и
  «формат нарушен» → вне группы; сумма тестов сходится; `legacy_run_v1` → групп нет.

## 6.2 `report.md`

- После «Коротко», перед разделами — «### Известные проблемы из базы знаний (K)», если групп
  больше нуля: «- «<название>» (`<id>`, <категория>) — проблемы 3, 7, 12 · 14 тестов» и
  строка «Рецепт: <первый шаг>». При записях из нескольких модулей — «, модуль <имя>».
- У каждой проблемы группы строка «Известная проблема» заменяется на «- Известная проблема:
  «<название>» (`<id>`) — вместе с проблемами 7, 12». Одиночная подтверждённая — прежняя
  строка. Неподтверждённая (отвергнута, запись удалена) — строки нет.
- Строка о расхождении категории — у проблемы (см. «Решения»).
- Разделы, номера, порядок, правки, «Почему агент не правил сам», «Подробности по проблемам»
  и команды `apply N`/`remember N` не меняются.
- `history.run_records`: `kb_entry` — только подтверждённый `confirmed_ref`, иначе отвергнутая
  запись продолжала бы считать повторы. История только дописывается, поэтому после `reject`
  и `next` строка прогона перезапишется с `kb_entry: null` (так уже работает
  `append_changed_run`).

## 6.3 Краткий разбор

- В разделе брифа проблемы одной группы (две и больше в этом разделе) сворачиваются в один
  блок на месте самой важной из них (`_sort_key`):

  ```
  **Проблемы 3, 7, 12** · 14 тестов · [известная проблема: payment_db_pool_1a2b3c4d]
  Одна известная проблема: «Пул соединений БД платежей исчерпан»
     База знаний:   [ПРИЛОЖЕНИЕ] <описание записи, ≤200>
     Что делать:    <первый шаг рецепта, ≤140>
     Например:      <тест самой большой проблемы>
  ```

  Номера — не больше пяти, дальше «и ещё N». Текст записи проходит `_plain_line`, как текст
  модели.
- Раздел «Агент может поправить сам» не сворачивается: у каждой проблемы своя правка и своя
  команда `apply N`. Если в разделе осталась одна проблема группы — обычный блок с меткой
  «известная проблема: id» (как сейчас).
- Свёрнутый блок считается одним пунктом в `MAX_BRIEF_ITEMS`; хвост «… и ещё N проблем
  (K тестов)» считает проблемы и тесты, как сейчас. Заголовок раздела «(N)» и обзор в шапке —
  число проблем, без изменений.
- Метки «известная проблема» и «расходится с базой знаний» — только по `KnownIssues`.
- Размер брифа: `test_skill_report.py` — свёрнутый блок не больше обычного блока плюс строка
  номеров; потолок брифа на огромном прогоне прежний (добавить вариант, где все проблемы —
  одна известная, и вариант с сотней групп).

- `build_summary_data`: после данных ядра — блок «--- Известные проблемы из базы знаний ---»:

  14 тестов», остальные одной строкой «ещё N известных проблем (M тестов)». Размер задания

- `SUMMARY_TASK`: проблемы одной известной проблемы называть одной («8 проблем, три из них —

- Хэш сводки меняется намеренно: при обновлении скилла у разборов с группами `next` попросит

## 6.5 `remember`/`reject` и протокол

- После `STATUS: saved` скрипт проверяет, упоминается ли запись в разборах этого прогона
  (`kb_ref` по `parse_analysis`, без полной проверки). Если да — строка «Запись R указана в
  разборах проблем 3, 7, 12 — выполни next, чтобы обновить отчёт». Иначе вывод прежний.
- `SKILL.md` (раздел 5) и `references/feedback.md`: после такой строки выполнить `next` и
  дальше как обычно (`summary` → `done`, бриф выводится дословно). Других шагов не добавлять.
- `.claude/rules/skill-memory.md`: подтверждение совпадения в отчёте, `record_matches`,
  `kb_entry` в истории. `.claude/rules/skill-analysis.md`: блок в `report.md`, свёртка в брифе,
  блок сводки, метки. `CLAUDE.md`: `known_issues` в таблице модулей.

## 6.6 Эталон: предложение записей

Группа складывается, только если запись предложена всем проблемам своей причины и не
предложена чужим. Это проверяется офлайн, без модели.

- Новый кейс dev `known_issue_symptoms` (`corpus_dev.py`): одна причина (пул БД платежей,
  «приложение») и три группы симптомов — 502, таймаут, «элемент не найден», — у каждой в логе
  есть строка пула. В нынешнем `auth_down_symptoms` общая строка есть только у группы 502:
  он остаётся как пример причины, которую признак не покрывает.
- `tests/eval/metrics.py`: для каждой `cause`, у которой в разметке ≥ 2 групп симптомов,
  синтетическая запись с `error_example` = первая строка `evidence` первой группы. После
  `prepare` для каждого кластера — `match_cluster` по этим записям. Метрики:
  «предложена своей причине» (доля кластеров причины, которым запись предложена) и
  «предложена чужой причине» (число кластеров другой `cause` или с `cause: null`, которым она
  предложена; ложное предложение + согласие модели = ложная группа). Списки — какие кластеры.
  Низкая доля «своей» у `auth_down_symptoms` ожидаема (признака нет в данных), это не ошибка.
- В `run_eval.py --details` и `baseline.json` (dev, вместе с новым кейсом); holdout —
  отдельным коммитом.
- Если «чужие» не нулевые — не чинить в этом шаге, а записать в «Осталось» итогового плана с
  примерами: признак — выбор пользователя, и правило признака меняется отдельно.

## 6.7 Стенд Qwen

Модель здесь решает главное: пишет ли она `БАЗА ЗНАНИЙ: <id>` в каждом из разборов.

- Новый вид `known` в `fake_testops_server.py`: прогон из кейса `known_issue_symptoms`
  (6.6) плюс посторонняя проблема с другой ошибкой в логе.
- `build_project` получает файлы `alla-kb/` для сценария: одна запись (приложение, признак —
  строка пула БД), закоммичена в проект до запуска.
- Сценарий E10 «Известная проблема у нескольких проблем», два хода: `/alla-launch <id>`, затем
  «Проблема N — не пул БД, эта запись к ней не относится». Проверки: `report_verbatim`;
  `known_issue_grouped` (после первого хода в `report.md` есть блок с ≥ 2 номерами);
  `kb_rejected` (выполнен `reject N <id>`, после `next` проблема N вне группы);
  `project_unchanged` с исключением `alla-kb/` — в нём только `rejected_signatures` записи.
  Ревью: «Evidence: модель подтвердила запись цитатой признака в каждом разборе, посторонняя
  проблема записи не получила».
- Прогон — на устройстве с Qwen: E10, плюс A01 и E08 (их бриф меняется только при группах —
  проверить, что не изменился).

## На ревью

- Категория записи как эталон (а не большинство разборов): так расхождение видно сразу, но
  если запись устарела, все разборы окажутся «расходятся». Альтернатива — группировать по
  совпадению категорий разборов между собой, а расхождение с записью только помечать.
- Новая сводка после `reject`, распавшего группу: одна лишняя запись сводки моделью против
  «Коротко», которое противоречит отчёту.
- Свёртка в брифе против одной строки в шапке («3 проблемы — одна известная»): свёртка
  экономит место, но прячет «что случилось» каждой проблемы (оно остаётся в `report.md`).
