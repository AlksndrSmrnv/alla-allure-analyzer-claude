# План: расширение `ticket` — подсказка и заведение тикета по проблеме

Дата: 2026-10-28. Статус: план, код не пишем, пока владелец не ответит на вопросы в конце
(решения ниже можно реализовывать и без ответов: вопросы помечены отдельно). Ветка
реализации — отдельная; этот коммит содержит только план.

Трекер задач владелец не называет и API не даёт. Расширение поставляет нейтральный
контракт адаптера. Пока адаптер не подключён, подтверждённый запрос инженера сохраняет
черновик и не обращается наружу.

## Зачем

После разбора часть проблем — дефекты приложения или повторяющиеся сбои стенда. Сейчас
инженер сам переносит причину, тесты, ссылку на прогон и цитаты в трекер. Скилл уже
умеет подключать такие функции расширением (`git-publish`, `sut-code`) и не должен знать
конкретный трекер.

Нужно три вещи:

1. После отчёта подсказать, по каким проблемам тикет уместен.
2. Показать черновик и завести тикет только после явной команды инженера.
3. Не завести второй тикет на ту же ошибку — ни в этом прогоне, ни в следующем, ни у
   другого инженера, который подтянул `alla-kb/`.

Задел в плане `docs/plans/2026-10-15-sut-code-extension.md` («заведение дефекта», поле
`problem.extension_results`, чтение чужого `result.json`) не реализуем. Чужую папку
расширения читать нельзя (`extensions/AUTHORING.md`). Вход для тикета — контекст, который
собирает скилл, и подтверждённый вывод (`confirmed/`), а не файл `sut-code`.

## Что уже есть и чего не хватает

Хватает без новой версии `api`:

- встроенное расширение выключено, пока его не включат; своё в `alla-extensions/ticket/`
  заменяет встроенное;
- хук `script` на `after_report` — короткая подсказка, как `sut-code/scripts/hint.py`;
- хук `script` на `on_request` — слэш-команда `/alla:ticket N` и
  `extensions run ticket N`;
- скрипт запускается отдельно, скилл его код не импортирует; ошибка скрипта не ломает
  отчёт;
- настройки — строка, число, да/нет или список строк (`extensions.py`, `_valid_setting`);
- модель из shell запускает только команды скилла; внешний вызов делает скрипт;
- запись базы знаний хранит чужие поля (`KBRecord.extra`: в комментарии уже названы
  `jira`, `owner`) и не затирает их при `remember`.

Не хватает, это и есть минимальные изменения контракта (`api` остаётся 1: старые
расширения незнакомые поля пропускают, файл `outcome.json` пишут только новые):

1. В контексте проблемы нет сигнатуры, модуля, признака, повторов, ссылки на прогон,
   проверенных цитат, фрагмента `report.md`, итога перезапуска, признака «разбор сломан»
   и уже известного тикета. Без этого скрипт либо слепой, либо полезет в `run.json` и
   `alla-kb/`, что автору расширения запрещено.
2. Скрипту некуда записать ключ тикета так, чтобы следующий прогон его увидел. Папка
   `extensions/ticket/` живёт внутри одного разбора и удаляется вместе с ним (`clean`,
   14 дней). Писать в `alla-kb/` само расширение не должно.
3. Совпадение «та же ошибка» после смены версии сигнатуры умеет только скилл
   (`record_matches`, тесты + признак). Второй раз ту же логику в расширении не копируем.

Вложенные таблицы в настройках не включаем. Маршрут категории задаётся списком строк —
этот тип настройка уже разрешает.

Новое событие не нужно. `confirm = true` тоже не подходит: на `on_request` вопрос не
задаётся (инженер уже попросил), а на `after_report` вопрос прозвучал бы до показа
черновика и слился бы с вопросами про базу знаний и перезапуск.

## Решения

1. **Имя** `ticket`, команда `/alla:ticket`. В комплекте скилла, выключено по умолчанию.
   Заголовок для человека: «Тикет по проблеме».
2. **Текст тикета собирает скрипт по шаблону**, не модель. Слабая модель переписывает
   недоверенные логи и может вызвать трекер сама. Субагента у расширения нет: оба хука —
   `script`.
3. **Два шага.** Подсказка после отчёта ничего не спрашивает и ничего не заводит: она
   называет номера и команду. `/alla:ticket N` показывает черновик. Отправка — только
   вторая просьба, «заведи тикет N» или `/alla:ticket N завести`. Голое «да» на правку,
   базу знаний или перезапуск тикетом не считается.
4. **Режим по умолчанию — черновик.** Адаптер не вызывается, наружу ничего не уходит.
   Владелец подключает свой трекер настройкой, не правкой скилла.
5. **Адаптер — отдельный процесс или класс в проекте автотестов.** Скилл его не
   импортирует. Контракт один: JSON тикета внутрь, JSON результата наружу.
6. **Ключ тикета хранит скилл** в `alla-kb/ext/ticket/` того модуля, где лежит база
   знаний проблемы. Это не запись базы (`alla-kb/<id>.json`): новую запись из-за тикета
   не создаём, иначе проблема стала бы «известной» и разобралась бы без модели.
   Существующую запись не переписываем целиком; при точном совпадении дописываем строковые
   поля `ticket` и `ticket_url` в `extra` (они и так переживают `remember`).
7. **Повторный запуск с тем же ключом идемпотентности адаптер обязан принять как «уже
   есть».** Так безопасен повтор, если процесс умер после ответа трекера, но до записи
   файла. Скилл второй раз адаптер не зовёт, когда связь уже сохранена.
8. **`RUN_SCHEMA` не поднимаем.** Новые данные живут в контексте расширения и в
   `alla-kb/ext/`, не в `run.json`. Эталон (`tests/eval/`) не трогаем: извлечение логов и
   кластеризация те же.

## Как это выглядит для инженера

Расширение выключено — блок «Расширения:» про тикеты молчит, как сейчас.

```text
/alla:run 12345
  краткий разбор, как раньше
  Расширения:
  - Тикет по проблеме (ticket): проблема 2 — приложение, уже было в 3 прогонах.
    Черновик: /alla:ticket 2
  - Тикет по проблеме (ticket): проблема 5 — окружение, третий прогон подряд
    (команда стенда). Черновик: /alla:ticket 5

/alla:ticket 2
  Заголовок: [приложение] OrderService.create падает с NPE без customer
  Куда: Bug, команда backend
  Прогон: https://testops.example/launch/12345
  Черновик: alla-reports/…/extensions/ticket/on_request-02.description.md
  Тикет ещё не создан. Завести — напиши «заведи тикет 2».

заведи тикет 2
  без адаптера:
  Черновик сохранён. Трекер не подключён, тикет никуда не отправлен.
  Связь записана в alla-kb/ext/ticket/… — закоммить вместе с базой знаний.

  с адаптером:
  Тикет DEMO-120 заведён: https://tracker.example/DEMO-120
  Связь записана в базу знаний модуля (alla-kb/ext/ticket/…).
```

Повтор «заведи тикет 2» отвечает «уже есть DEMO-120» и адаптер не вызывает.
«Не заводи тикет 2» запоминает отказ: в следующих прогонах подсказки по этой ошибке нет,
пока инженер сам не попросит `/alla:ticket 2` (черновик снова можно открыть; отправка
просит явное «всё равно заведи»).

В `report.md` у проблемы одна строка в подробностях, не в кратком разборе: «Тикет:
DEMO-120» или «Тикет: решили не заводить». Размер краткого разбора не растёт
(`test_skill_report.py`).

Словами работает то же, что команда: «покажи черновик тикета 2», «заведи тикет 2»,
«не заводи тикет 2». Несколько номеров — несколько событий `on_request`, по одному
черновику. Одной фразой «заведи все» скилл не отправляет: в просьбе нужен номер.

## Критерии подсказки

Решает скрипт `hint.py` по полям контекста, не модель. Подсказка — не создание тикета.

Проблема попадает в подсказку, когда выполнены все общие условия и одно условие
категории.

Общие:

- настройка `hint = true` (так по умолчанию);
- категория входит в `suggest_categories`;
- разбор прошёл проверку формата (не `flagged`);
- у группы нет пометки «разные проблемы» (`consistency` не `different`): один тикет на
  несколько причин не предлагаем;
- перезапуск этой проблемы не закончился прохождением всех её тестов (`rerun` не
  `passed`): невоспроизведённое падение тикетом не считаем;
- нет уже сохранённой связи со статусом `filed` или `skipped` (ни файла расширения, ни
  ручного поля записи, см. ниже).

По категории. «Повторы» — это `recurrence.launches`: число **других** прогонов с той же
сигнатурой или той же записью базы, в том же модуле (`history.recurrence`). Текущий
прогон в это число не входит.

| Категория | Когда подсказывать |
|---|---|
| `приложение` | в других прогонах уже была (`launches` ≥ `min_repeats`, по умолчанию 1) **или** в разборе есть проверенная цитата из лога **или** инженер уже подтвердил вывод расширения (`confirmed`) |
| `окружение` | `launches` ≥ `min_repeats_env`, по умолчанию 2. Один обрыв связи тикетом на команду стенда не предлагаем; третий прогон подряд — предлагаем. В скилле «стенд» — это категория `окружение` (`analysis_format.py`) |
| `данные` | в список по умолчанию не входит. Если её туда добавят — то же правило, что у `окружение` |
| `тест`, `неизвестно`, пустая категория | не подсказываем никогда, даже если их вписать в `suggest_categories` |

Отметка «нестабильный» в базе сама по себе подсказку для `приложение` не гасит: флаки с
NPE в логе как раз кандидат в тикет. Гасит только успешный перезапуск.

Явная команда шире подсказки:

- `/alla:ticket N` на проблему «тест» показывает черновик и после «заведи» отправляет,
  если для категории задан маршрут;
- «неизвестно», сломанный формат разбора, нет маршрута — черновик с предупреждением,
  отправка отказывается и объясняет, что поправить;
- «разные проблемы» в группе — отправка только с «всё равно заведи»
  (`--param force=yes`).

Так подсказка молчит на прогоне, где упали только тесты (категория «тест») и на одиночном
сбое окружения. Эти два случая — обязательные отрицательные проверки, см. «Тесты».

## Модель тикета

Скрипт пишет два файла в свою папку разбора (`out_dir`, в git не попадает):

- `<stem>.ticket.json` — полезная нагрузка адаптера;
- `<stem>.description.md` — то же описание, как его увидит человек.

Поля JSON (`api` тикета = 1, это не `api` манифеста расширения):

| Поле | Откуда |
|---|---|
| `idempotency_key` | `ticket\|<сигнатура>\|<модуль>`. При «всё равно заведи» суффикс `\|2`. Считается до вызова адаптера и одинаков при повторе |
| `title` | шаблон, одна строка, до 200 символов |
| `description_md` | шаблон Markdown |
| `description_text` | тот же текст без разметки: адаптер берёт тот вид, который принимает трекер |
| `category` | категория разбора: `тест`, `приложение`, `окружение`, `данные` |
| `fields` | плоский словарь строк из маршрута: `type`, `team`, `component`. Пустых ключей нет |
| `problem` | номер, метка, причина, шаги «как исправить», модуль, сигнатура, id записи базы или `null`, число тестов |
| `tests` | до 20 тестов: `name`, `full_name`, `link`; если тестов больше — `tests_hidden` |
| `launch` | `id`, `name`, `created`, `url` (`launch_url` из `run.json`) |
| `evidence` | до 8 цитат: `source_id` (`S1`), `kind`, `title`, `quote` до 500 символов. Только цитаты, которые скрипт скилла сверил с куском «Данных» |
| `confirmed` | если инженер подтвердил вывод расширения: имя расширения, причина, `details`, `kb_fields`. Иначе `null` |
| `recurrence` | `launches`, `first_date`, `last_date` или `null` |
| `report_excerpt` | раздел этой проблемы из `report.md`, до 4000 символов. Вырезает скилл, расширение само `report.md` не разбирает |
| `attachments` | файлы внутри `out_dir`: всегда `description.md` и фрагмент отчёта. Исходные логи — только при `attach_sources = true` (по умолчанию выключено) |
| `links` | прогон TestOps и ссылки тестов |

Вложения — пути, по которым адаптер сам решает, загружать ли их в трекер. Скилл файлы
наружу не отправляет. Путь вне `out_dir` в список не попадает.

Шаблоны лежат в `extensions/ticket/templates/title.txt` и `description.md`. Подстановка —
`$label`, `$category`, `$cause`, `$fix`, `$tests`, `$launch_url`, `$launch_id`,
`$launch_name`, `$quotes`, `$recurrence`, `$confirmed`, `$report_excerpt`, `$kb_id` (тот же
`string.Template`, что у заданий расширений). Неизвестная переменная остаётся как есть,
лишний `$` в данных экранируется. Свой текст команда кладёт в папку проекта и указывает
её настройкой `template_dir` (только внутри проекта, только эти два имени файлов). Копировать
всё расширение ради правки формулировки не нужно.

Каркас описания:

```text
Что сломалось          — метка проблемы
Почему так решили      — категория и причина
Как исправить          — шаги разбора
Повторы                — сколько других прогонов, даты; или «в прошлых прогонах не встречалась»
Тесты                  — имя и ссылка
Прогон                 — название, id, ссылка TestOps
Доказательства         — цитаты [S…]
Подтверждено инженером — блок из confirmed, либо «нет»
Фрагмент отчёта        — report_excerpt
```

Секрет в заголовке или причине — отправка отменяется, в ответе имя поля, не сам секрет.
Секрет в одной цитате — эта цитата выкидывается, в описании строка «одна цитата убрана:
похожа на секрет». Сканер тот же, что у базы знаний (`kb.secret_lines`).

## Адаптер

Настройка `adapter`:

| Значение | Поведение |
|---|---|
| `draft` | по умолчанию. «Заведи» пишет черновик и короткую связь `status: drafted`. Процесс адаптера не запускается |
| `command` | дочерний процесс без shell: список аргументов `adapter_command`. Рабочая папка — корень проекта. На stdin — один JSON тикета, кодировка UTF-8. На stdout — один JSON результата. Stderr — короткая ошибка для человека, до 500 символов, без токенов |
| `python` | скрипт расширения (не скилл) импортирует класс из проекта: `adapter_entrypoint = "пакет.модуль:Класс"`. Корень проекта добавляется в `sys.path` только этого процесса |

Результат адаптера — объект:

```json
{"status": "created", "key": "DEMO-120", "url": "https://tracker.example/DEMO-120", "message": "Заведён DEMO-120"}
{"status": "exists", "key": "DEMO-120", "url": "https://tracker.example/DEMO-120", "message": "Уже есть DEMO-120"}
{"status": "error", "message": "Нет прав на проект"}
```

`created` и `exists` — успех: связь сохраняется как `filed`. Пустой `key` — ошибка, связь
не пишем (дедуплицировать будет нечем). Не-JSON, ненулевой код, обрыв по таймауту —
ошибка, связь не пишем, черновик в папке разбора остаётся.

Класс Python, если владелец выберет этот способ:

- конструктор получает плоские настройки расширения (без секретов) и словарь переменных
  из файла секретов (только разрешённые имена);
- метод `submit(ticket: dict) -> dict` возвращает тот же объект, что команда печатает в
  stdout;
- исключение скрипт ловит сам и отвечает человеку одной строкой, без traceback. В
  `out_dir` можно писать `adapter.log` без заголовков авторизации и без значений
  секретов.

Зависимости — стандартная библиотека и то, что уже есть у скилла (`httpx`, `pydantic`).
Свой SDK трекера в `.venv` скилла не ставим: для него режим `command` и любое окружение
команды.

Порядок отправки, его же проверяет тест:

1. Собрать JSON и прогнать сканер секретов.
2. Записать `<stem>.attempt.json` с `idempotency_key` (ещё до вызова).
3. Вызвать адаптер один раз. Повторов внутри скрипта нет: повтор создал бы второй тикет,
   если адаптер не соблюдает ключ.
4. На `created` или `exists` записать `<stem>.outcome.json` и только потом строку
   результата.
5. Скилл после хука, если `outcome.json` валиден, сохраняет связь. В текст для инженера
   дописывает, куда закоммитить файл. Если сохранение не удалось — ключ тикета в ответе
   всё равно есть и есть команда повтора без нового вызова адаптера:
   `extensions outcome ticket --run <папка> --problem N`.

Таймаут адаптера — настройка `adapter_timeout` (по умолчанию 30 секунд) и в любом случае
не больше лимита действия (110 секунд). Хук подсказки в эти 30 секунд не входит: сеть
из `hint.py` запрещена, подсказка делит 60 секунд `after_report` с другими хуками и
должна уложиться в доли секунды.

### Пример заглушки (в репозиторий не кладём)

Заглушка нужна владельцу, чтобы проверить цепочку до появления настоящего трекера, и
тестам стенда. Это отдельная программа в проекте автотестов, не файл скилла.

Поведение:

1. Читает один JSON из stdin.
2. Проверяет, что на месте `idempotency_key`, `title` и `description_md`.
3. Ищет ключ в своей папке `tracker-outbox/` (файл на ключ, папка в `.gitignore` проекта).
   Нашла — печатает `status: exists` и тот же `key`, код возврата 0.
4. Не нашла — запоминает тело тикета, назначает ключ `LOCAL-<номер>` по числу файлов,
   печатает `status: created`, `url` вида `file://…/LOCAL-N.json`, код 0.
5. Битый JSON — `status: error` и код 1. Токены не читает и не печатает: ей достаточно
   тела тикета.
6. Повтор с тем же `idempotency_key` не создаёт второй файл.

Настоящий адаптер делает то же с API трекера: перед созданием ищет задачу с этим ключом
(метка, поле или свой журнал на стороне адаптера) и в этом случае возвращает `exists`.
Если трекер поиск по произвольному ключу не умеет, журнал ведёт сам адаптер — для скилла
это незаметно.

## Конфиг

Всё в `alla-extensions/config.toml`, таблица `[ticket]`. Секретов в ней нет: файл
коммитят. Пример, его же проверяет тест разбора настроек:

```toml
[ticket]
adapter = "draft"          # draft | command | python
dry_run = false
hint = true
suggest_categories = ["приложение", "окружение"]
min_repeats = 1            # приложение: сколько других прогонов достаточно само по себе
min_repeats_env = 2        # окружение и данные
attach_sources = false
adapter_timeout = 30
env_file = "alla-extensions/.env"
adapter_env = ["TRACKER_URL", "TRACKER_TOKEN", "TRACKER_REPORTER"]
existing_key_fields = ["jira", "ticket", "issue", "key"]
template_dir = ""          # пусто — шаблоны расширения
require_route = true
routes = [
  "приложение = type: Bug, team: backend",
  "окружение = type: Task, team: stand, component: environment",
  "* = type: Task, team: qa",
]
# только для adapter = command, список аргументов без shell:
# adapter_command = ["python3", "alla-extensions/tracker/adapter.py"]
# только для adapter = python:
# adapter_entrypoint = "tracker.adapter:TrackerAdapter"
```

Строка маршрута: категория или `*` , затем `=`, затем пары `ключ: значение` через
запятую. Ключи только `type`, `team`, `component`. Чужой ключ или пустое значение —
отправка отказывается, черновик всё равно показывается, в тексте сказано, какую строку
поправить. Категория без своей строки берёт `*`. Нет ни своей строки, ни `*` при
`require_route = true` — отправка отказывается. `component` в первой версии только из
этой таблицы; место в коде из подтверждённого вывода остаётся в тексте тикета, а не
становится компонентом трекера.

`extensions enable` по-прежнему проверяет только тип значения. Смысл `routes` и
`adapter` проверяет скрипт в момент черновика, чтобы ошибка настройки не выглядела как
поломка всего расширения в `extensions list`.

## Секреты, dry-run, отказы

Файл секретов — `<проект>/alla-extensions/.env` (путь переопределяется `env_file`,
последний компонент пути обязан быть `.env`). Правила сеанса уже запрещают модели читать
любой файл с таким именем (`FORBIDDEN_READ_RE`). Скилл этот файл не открывает и не
кладёт в JSON контекста.

Скрипт отправки читает его сам и передаёт дочернему адаптеру **новый** список
переменных: `PATH`, `LANG`, `LC_ALL` и только имена из `adapter_env`. Остальные строки
файла игнорируются. Окружение процесса Qwen целиком не копируется: там лежит
`ALLURE_TOKEN` из `.env` скилла. `.env` скилла по-прежнему расширениям не передаётся
(`AUTHORING.md` эту фразу сохраняет и рядом объясняет файл трекера).

Подстановка переменных внутри `.env` выключена (`KEY=$OTHER` остаётся буквальным
текстом), чтобы значение не подтянуло токен TestOps. Формат строки — `KEY=VALUE`, без
`export`.

Отказы до вызова адаптера, одной русской строкой и без traceback:

- файла нет или в нём нет `TRACKER_TOKEN` — «запишите токен в alla-extensions/.env»,
  черновик на месте, тикет не отправлен;
- файл доступен всем пользователям системы (бит «все» на чтение) — не читаем его;
- `git ls-files` показывает, что файл секретов отслеживается — не читаем его;
- `dry_run = true` или `--param dry_run=yes` — печатаем заголовок, маршрут и путь
  черновика, адаптер не вызываем, `outcome.json` не пишем (следующая подсказка не
  гаснет);
- адаптер не найден, таймаут, сеть, 4xx/5xx в сообщении адаптера — черновик сохранён,
  связь не пишем, повторить можно той же командой (ключ идемпотентности тот же);
- подсказка упала — одна строка в блоке «Расширения:», отчёт уже показан (отметка
  `after_report` пишется до хуков, как сейчас).

Модель ключ и токен не видит: их нет в контексте, в задании (задания нет), в stdout
длиннее обрезки и в файлах `alla-kb/ext/`. Тест поднимает в окружении родителя
`ALLURE_TOKEN` и `TRACKER_TOKEN` и проверяет, что заглушка получила только второй, а в
черновике и stdout нет обоих.

## Дедупликация и база знаний

Скилл после успешного хука читает `<out_dir>/<stem>.outcome.json`. Файл пишет только
скрипт расширения. Схема общая, чтобы следующее расширение положило свой идентификатор
тем же путём; в этой версии скрипт принимает `kind = ticket`.

Поля outcome, все строки, кроме списков `tests`:

- `kind`, `status` (`filed`, `drafted`, `skipped`);
- `idempotency_key`, `signature`, `module`, `fingerprint` (нормализованный признак, тот
  же вид, что `error_example`);
- `tests` — ключи `key_of_test`, не больше 50;
- `title` до 200 символов;
- плоская карта `fields`: `key`, `url`, `category`, `kb_id`, `launch_id`.

Цитат и описания в этом файле нет: его коммитят. Секрет в любой строке — файл
отклоняется целиком, адаптер при этом уже мог создать тикет, поэтому скрипт обязан
прогнать сканер **до** вызова, а outcome собирает только из проверенных полей.

Куда кладётся: `<модуль>/alla-kb/ext/ticket/<16 hex sha256 ключа идемпотентности>.json`.
Один файл на ошибку, как записи базы: при смене статуса (`drafted` → `filed`, `skipped`
→ `filed`) файл перезаписывается атомарно. `remember` и `reject` эту папку не трогают.
В README базы (`kb.README`) — абзац, что `ext/` не записи причин и руками id не меняют.

Совпадение с новой проблемой того же модуля считает скилл, одним правилом, рядом с
историей, не расширение:

1. сигнатура равна — совпало;
2. иначе, если у сохранённой сигнатуры другой префикс версии, пересеклись ключи тестов и
   признак нашёлся в данных кластера (`fingerprint_hits`) — совпало;
3. иначе не совпало.

Несколько файлов — берём `filed`, затем `skipped`, затем `drafted`; внутри статуса —
более поздний `filed_at`.

Дополнительно, если проблема точно узнана записью базы: смотрим строковые `extra` из
списка `existing_key_fields`. Значение вида ключа задачи (`ABC-123`) считаем уже
заведённым тикетом (`source: kb`), даже если папки `ext/ticket/` ещё нет. Так ручное поле
`jira`, которое базы уже предполагают, не даёт второй тикет. Чужое значение не
перезаписываем. Своего поля ещё не было — при сохранении `filed` пишем `extra["ticket"]`
и `extra["ticket_url"]` строками.

Что видит подсказка:

- `filed` — молчит; строка есть только в подробном отчёте;
- `skipped` — молчит, пока инженер сам не откроет `/alla:ticket N`;
- `drafted` — короткая строка «черновик уже есть, трекер не подключён: /alla:ticket N»,
  без повторного уговора завести;
- нет связи — обычная подсказка по критериям.

Гонка двух инженеров до коммита `alla-kb` остаётся на ключе идемпотентности адаптера:
оба пошлют один и тот же ключ, второй получит `exists`.

Общие, рядом с `launch_id`: `launch_url`.

| `member_count` | сколько тестов в проблеме; список `tests` по-прежнему обрезан 20 |

| `records` | сохранённые связи этой ошибки: `extension`, `status`, `key`, `url`, `title`, `source` |

же, как уже делает список `after_report`. Сейчас `problem_context` читает только файл

«приложение».

У элемента `problems` события `after_report` поле `tests` остаётся числом: так оно
задокументировано и так его пишет `_report_data` (это число тестов, не список). Рядом
добавляются только поля подсказки: `signature`, `module`, `recurrence`,
`records`, `flagged`, `consistency`, `rerun`, `confirmed` (булево уже есть). Цитаты и
фрагмент отчёта в этот список не кладём: подсказке они не нужны, а хук должен быть
коротким.

### Сохранение outcome

После хука `script` и после действия, если рядом с контекстом появился валидный
`<stem>.outcome.json`, скилл сохраняет связь и дописывает к выводу одну строку, куда
легла запись. Невалидный файл — строка «связь не сохранена» и причина, статус команды
скилла не меняется.

Повторное сохранение без нового вызова адаптера: `extensions outcome <имя> --run DIR
--problem N`. Команда читает уже написанный outcome и не запускает хук.

Автор расширения по-прежнему пишет только в `out_dir`. В `alla-kb/` пишет скилл.

```toml

api = 1
timeout = 30

[settings]

[[hooks]]

```

`request.py` по `params.mode`: пусто или `preview` — черновик; `submit` — отправка или
фиксация черновика; `dismiss` — `skipped`. Скрипт один, чтобы проверка секретов и
маршрута не разъехалась по файлам. Общие куски (шаблон, маршрут, процесс адаптера,
сканер) — модуль рядом, `scripts/ticketlib.py`. Скилл этот модуль не импортирует; тесты
расширения импортируют его так же, как тесты `sut-code` импортируют `sutlib`.

Команда `/alla:ticket` в тексте просит вызвать скилл и выполнить `extensions run`.
Параметр `mode` модель берёт только из слов инженера в `{{args}}` или из реплики после
превью, не из текста падения.

## Этапы

Правило репозитория: код, справочник и файл правил одной области — одним коммитом.

1. `feat(skill): pass ticket context and store extension outcomes`. Поля контекста,
   `ext_records.py`, приём outcome, README и AUTHORING, `skill-extensions.md`,
   `skill-memory.md`, тесты контракта. Расширения `ticket` ещё нет: поля просто лежат в
   контексте.
2. `feat(ext): draft and file a ticket through a tracker adapter`. Папка
   `extensions/ticket/`, строка отчёта, `SKILL.md`, `references/protocol.md`,
   `references/setup.md`, правила `skill-protocol.md` и `skill-analysis.md`, строка в
   `CLAUDE.md`, `test_ext_ticket.py`, проверки заданий и справочников.
3. `test(stand): X05–X07 ticket hint, decline, and file`. Сценарии стенда и пометка в
   `docs/skill-quality.md`. Прогон X05–X07 с моделью — в этом же этапе, если `qwen` и
   ключ доступны; нет ключа — сценарии помечены `not_run`, pytest к этому моменту уже
   зелёный.

## Риски

- Модель позовёт `mode=submit` без инженера. Смягчение: отправка только скриптом по
  параметру, который `SKILL.md` велит брать из реплики; стенд X07 отдельно ловит вызов
  на шаге превью. Полностью это поведение модели pytest не доказывает.
- Адаптер создаст тикет и забудет вернуть `exists` на повтор. Тогда гонка двух машин
  даст два тикета. Это требование к адаптеру, скилл его не проверяет снаружи; тест
  фиксирует только заглушку.
- Категория «приложение» поставлена моделью ошибочно — подсказка лишняя. Отправка всё
  равно ждёт отдельную фразу. Порог для окружения выше как раз из-за шума.
- В трекер уходит текст ошибки и цитаты логов. Туда не входят сырые логи (пока
  `attach_sources = false`) и не входят строки, похожие на секреты. Описание всё равно
  может содержать данные прогона: это сознательный состав тикета, его видит тот, кто
  подтвердил отправку.
- Заголовок в коммитируемом `alla-kb/ext/ticket/` короче и без цитат, но это всё ещё
  текст ошибки. Сканер секретов его смотрит.
- Смена версии сигнатуры без пересечения тестов и признака откроет подсказку снова.
  Так же ведёт себя точное узнавание базы; второе правило совпадения закрывает обычный
  случай, когда тесты у записи есть.
- `after_report` стреляет заново после `remember` и `reject`, потому что меняется
  `report.md`. Подсказка обязана быть дешёвой и не ходить в сеть.
- Режим `python` выполняет код проекта в процессе расширения. Это тот же доверенный
  контур, что `config.toml`, который пишет команда, а не текст TestOps. Аргументы
  `adapter_command` из текста падения не собираются.

## Открытые вопросы к владельцу

Ответы не блокируют черновик и контракт адаптера. От них зависит только таблица
`[ticket]` у команды и, может быть, один лишний метод адаптера.

1. Пороги по умолчанию: для приложения достаточно одного прошлого прогона или цитаты из
   лога, для окружения — двух прошлых прогонов. Нужны другие числа?
2. Когда тикет уже есть, скилл молчит и не дописывает комментарий «снова упало в прогоне
   N». Нужен ли такой комментарий в первой версии (метод адаптера `comment`)?
3. Можно ли коммитить `alla-kb/ext/ticket/` в репозиторий автотестов (ключ тикета,
   заголовок, сигнатура, имена тестов, без цитат)? Если нет, связь останется только на
   машине инженера, и коллега заведёт дубль, пока его не погасит сам адаптер.
4. Хватает ли текстовых вложений (описание и фрагмент отчёта)? Нужны ли в первой версии
   скриншоты и файлы surefire?
5. Кем заводить задачу: учётной записью из `TRACKER_REPORTER` или сервисной, которую
   адаптер знает сам? Скилл имя учётки в трекер не выбирает, только передаёт переменную,
   если она задана.
6. Пока адаптер не подключён, подтверждение сохраняет короткий статус «черновик» в
   `alla-kb/ext/` и полный текст только в папке разбора (её удалит `clean` через 14
   дней). Нужно ли коммитить и полный markdown?
7. Маршрут задаётся категорией целиком (`приложение` → одна команда). Привязка
   компонента к сервису из кода — не в этой версии. Хватает ли команде одного маршрута
   на категорию?
8. Подсказка включена и в режиме черновика, без трекера. Выключить её, пока `adapter`
   не станет `command` или `python`?

## В эту версию не входит

- Закрытие тикета, смена статуса, вложения-скриншоты, комментарий к повторному падению.
- Выбор компонента по пути файла из `sut-code`.
- Создание записи базы знаний ради тикета.
- Любой код конкретного трекера внутри `qwen-skill/alla-launch/`.
- Поднятие `api` расширений и `RUN_SCHEMA`.
