# Установка и настройка скилла alla-launch

## Что нужно

- Qwen Code, запущенный в корне проекта автотестов.
- Python 3.11+ для `.venv` в корне проекта автотестов (работу на 3.10 мы не проверяли). Сам
  скрипт запуска работает на любом `python3` ≥ 3.8 и перезапускает себя в этом `.venv`.
- API-токен Allure TestOps и доступ к индексу пакетов pip (PyPI или
  корпоративное зеркало).

## Установка

1. Скопируйте папку `qwen-skill/alla-launch` из репозитория alla в проект
   автотестов: `<project>/.qwen/skills/alla-launch/`.
2. Один раз поставьте зависимости скилла:

       python3 .qwen/skills/alla-launch/scripts/alla_skill.py setup

   Зависимости ставятся в `.venv` в корне проекта автотестов. Если его нет, `setup` его
   создаст; нужен конкретный интерпретатор — `... setup --python /usr/bin/python3.11`.
   Если `.venv` уже есть, `setup` поставит зависимости в него: он должен быть на Python
   3.11+, иначе `setup` ответит ошибкой и ничего не тронет — пересоздайте `.venv` сами.
   `.venv` без pip (создан с `--without-pip`) `setup` дополнит pip через `ensurepip`.
   Окружение общее с проектом: pip может обновить в нём httpx, pydantic, numpy и другие
   пакеты из `requirements.txt` скилла.
   Корпоративное зеркало или прокси для pip — аргументы после `--`:
   `... setup -- --index-url https://mirror/simple --proxy http://proxy:3128`
   (или переменные `PIP_INDEX_URL`, `PIP_CERT`, `HTTPS_PROXY`). Установка
   печатает вывод pip и занимает 1–3 минуты — не прерывайте её.
3. `setup` создаёт `.env` рядом с `SKILL.md` из `.env.example` (права 600).
   Впишите в него `ALLURE_ENDPOINT` и `ALLURE_TOKEN` — адрес сайта TestOps без
   `/api` в конце. Комментарии в конце строки со значением не поддерживаются.
   Вместо файла можно задать переменные окружения с теми же именами — они
   важнее файла. Чужие переменные в `.env` игнорируются.
4. `.env` скилла исключён его собственным `.gitignore`. Если git не игнорирует `.venv`
   проекта, `setup` допишет `/.venv` в корневой `.gitignore` (без слэша на конце — так
   прикрыт и `.venv`-симлинк) — закоммитьте эту строку.
   Папка `alla-reports/` создаётся при первом разборе со своим `.gitignore`
   (`*`), поэтому отчёты не попадают в git.

Шаги 2–3 можно поручить самому скиллу: после копирования папки вызовите в Qwen Code
`/alla-launch установи` — он выполнит `setup` и `check` и попросит вписать
`ALLURE_ENDPOINT` и `ALLURE_TOKEN` в `.env`. Зеркало pip и выбор интерпретатора — только
ручным `setup`.

Скилл вызывается командой `/alla-launch 12345` (можно вставить ссылку на
запуск) или фразой «разбери прогон 12345».

**Слэш-команды `/alla:*`.** Кроме `/alla-launch` у скилла есть короткие команды Qwen Code:
`/alla:run <номер или ссылка>`, `/alla:continue`, `/alla:apply N`, `/alla:revert N`,
`/alla:remember N <причина>`, `/alla:reject N [id]`, `/alla:rerun [N…]`, `/alla:review`,
`/alla:setup`. Каждая —
короткая просьба к модели действовать по своему разделу `SKILL.md`, поэтому правила и
подтверждения те же, что у просьбы словами. Описания команд лежат в `commands/alla/` папки
скилла; `setup` и каждый `prepare` копируют их в `<project>/.qwen/commands/alla/` (новые и
изменённые файлы, свои файлы пользователя в этой папке не трогают). Qwen Code читает команды
при старте сеанса — они появятся после перезапуска. Папку можно закоммитить. Если в Qwen Code
включено доверие к папкам (folder trust), команды проекта видны только в доверенной папке.
Модель сама эти команды не вызывает (`disable-model-invocation: true`).

**Подтверждения.** Чтобы Qwen Code не спрашивал подтверждение на каждый вызов
скрипта, разрешайте не весь `python3`, а только префикс команды скилла:
`python3 .qwen/skills/alla-launch/scripts/alla_skill.py` (общее разрешение
`python3` даёт модели запускать любой Python, а это противоречит правилу
«из shell — только скрипт скилла»). Команды, которые печатает сам скрипт, начинаются
с абсолютного пути к `alla_skill.py`, поэтому разрешите и его:
`python3 <абсолютный путь к папке скилла>/scripts/alla_skill.py`. Каждая запись разбора — это `write_file`
и тоже запрос подтверждения; разрешать их можно только для папки
`alla-reports/`. Режим «автоматически принимать правки» снимает и защиту
`apply`: модель сможет менять файлы проекта, минуя diff и «да» — держите его
выключенным.

**Параллельный разбор.** Если кластеров много (от 10 без разбора), `next`
отвечает `STATUS: analyze_batch`: кластеры режутся на пакеты по 6, и модель
раздаёт их субагентам Qwen Code (инструмент `agent`; за раз — до 4 пакетов,
то есть до 24 кластеров; прогон из 65 кластеров идёт тремя волнами). Нужна
версия Qwen Code, в которой субагенты есть. Субагент видит только свой файл
`batches/N.md`, пишет `analyses/NN.md` и проверяет их командой `verify`
(только чтение — `state.json` она не трогает). Итоговую проверку, повторы,
предложения правок и общий анализ делает основной агент через `next`. Каждый
кластер раздаётся пакетом не больше одного раза: то, что субагенты не записали,
разбирается по одному, а если волна не записала ничего (например, субагентам
не разрешена запись), пакетный режим выключается для этого разбора — включить
его снова можно командой `next --workers N`. Если Qwen Code выполняет вызовы
субагентов по очереди, результат тот же, только не быстрее. Число субагентов — `next --workers N` (1–8; по умолчанию 4), без
субагентов — `next --serial`. Подтверждения инструментов у субагентов идут
по `approvalMode` сеанса (`bubble` показывает их в основном сеансе): заранее
разрешите write_file для `alla-reports/` и тот же префикс команды скилла,
иначе разбор встанет на запросах.

Пакеты разбирает свой субагент Qwen Code `alla-batch` (`agents/alla-batch.md` в папке
скилла): узкая роль «прочитай свой пакет и делай только его» и инструменты read_file,
write_file, run_shell_command. Встроенный `general-purpose` по своей роли сначала осматривает
проект, и субагенты лезли в папки вопреки правилам скилла. `prepare` сам кладёт описание в
`<project>/.qwen/agents/alla-batch.md` (если файла нет или он устарел); файл можно
закоммитить. Qwen Code читает агентов при старте сеанса, поэтому в первом сеансе после
установки пакеты уходят встроенному субагенту — со следующего сеанса работает `alla-batch`.

**Правила исполнителя.** Агент ведёт разбор строго по сценарию: не правит файлы скилла,
не пишет своих скриптов и неполадки скилла записывает в `skill-problems.md` папки разбора, а
не в ответ (`SKILL.md`, `references/problem-report.md`); их показывает проверка разбора. Это текстовые правила: они есть в
`SKILL.md` и повторяются в каждом задании (`clusters/NN.md`, `batches/N.md`,
`relate_task.md`, `summary_task.md`), но технически ничем не подкреплены. Хотите жёсткой защиты — запретите
в настройках разрешений Qwen Code правку файлов `.qwen/skills/alla-launch/**` (точный
синтаксис зависит от версии Qwen Code) и не включайте режим автоматического принятия
правок.

Форматы файлов, которые пишет агент, описаны в справочниках `references/analysis-format.md`,
`proposal-format.md`, `related-format.md`, `summary-format.md`, `feedback.md`; статусы, лимиты и разграничение
файлов — в `references/protocol.md`. Тесты скилла сверяют примеры справочников с
парсерами, поэтому при смене формата в коде правьте и справочник.

Проверить настройки и доступ к TestOps без модели и без создания файлов:

    python3 .qwen/skills/alla-launch/scripts/alla_skill.py check

Если после `check` нужно убедиться и в самом запуске — `prepare 12345`.

## Что получается

```
alla-reports/                       локально, в git не попадает
  history.jsonl                     история разборов: по ней видны повторы
  .last_run                         путь последнего разбора (для `next` без аргументов)
  .jobs/                            служебная: фоновые выгрузки `prepare` и проверки `review`
  <launch_id>-<YYYYmmdd-HHMMSS>/
    run.json                        данные прогона (служебный файл)
    state.json                      служебный: попытки исправления, выданные пакеты
    clusters/NN.md                  задание на разбор кластера NN
    analyses/NN.md                  разбор кластера, написанный моделью
    batches/N.md                    задание субагенту на пакет кластеров (большие прогоны)
    proposals/NN.md                 решение по правке автотеста (для категории «тест»)
    proposals/NN.patch              diff, который показал apply (можно применить git apply)
    proposals/NN.orig               файл до правки: из него revert возвращает исходную версию
    proposals/NN.orig.1, .2, …      версии до прошлых apply, если правку повторяли (--repeat)
    proposals/NN.applied.json       отметка: правка применена (хэши файла до и после)
    feedback/NN.md                  обратная связь пользователя по проблеме NN
    evidence/NN.txt                 текст ошибки для проверки признаков (служебный)
    images/NN/<id результата>.png   скриншоты тестов-примеров проблемы NN: их смотрит модель
    relate_task.md, related.md      похожие проблемы: задание и решение модели, у каких одна
                                    причина (только если скрипт нашёл похожие)
    summary_task.md, summary.md     задание и общий анализ прогона
    report.md                       итоговый отчёт: краткий текст + детали
    review/                         проверка разбора (только после `review`)
      report.md                     отчёт о ходе и качестве разбора
      pilot-summary.md              сводка для разработчика: только числа
      facts.json, assessment-*.json служебные: все факты и ответ проверяющей модели
alla-kb/                            база знаний проекта, коммитится в git
  <id>.json                         запомненная причина и рецепт
<модуль>/alla-kb/                   то же, но в многомодульном Java/Kotlin-проекте
```

Выгрузка большого прогона из TestOps идёт минуты, а Qwen Code обрывает одну команду через
2 минуты. Поэтому `prepare` выгружает прогон фоновым процессом: ждёт итога до 75 секунд и,
если не дождался, отвечает `STATUS: running`. Агент повторяет ту же команду, и повтор
дожидается идущей выгрузки, а не начинает её заново. Пока выгрузка идёт, повтор (даже с
`--fresh`) присоединяется к ней; правило о неоконченном разборе ниже действует, когда она
закончилась. Так же идёт `review` с оценкой моделью. На Windows обе команды работают
по-прежнему, без фона: выгрузку очень большого прогона там лучше запускать из терминала.

`prepare` создаёт новую папку. Но если разбор этого же прогона не закончен
(нет `report.md`) и ему меньше суток, `prepare` продолжает его и не обращается
к TestOps: так повтор после таймаута или сжатия контекста не плодит дубли.
Папка с пустым или оборванным `run.json` (сбой на записи) не продолжается:
`prepare` берёт другой свежий неоконченный разбор или начинает новый, а
`next` и другие команды на такой папке отвечают `STATUS: error` с готовой
командой `prepare <ID> --fresh`. `prepare <ID> --fresh` начинает заново. `next` без аргументов работает с
последним разбором (`alla-reports/.last_run`); в каждом ответе `next` вторая
строка называет прогон и папку. Старые разборы удаляет `clean` (по умолчанию
старше 14 дней; `--dry-run` показывает, что будет удалено; `history.jsonl`
не трогается).

## База знаний проекта (`alla-kb/`)

Когда пользователь в чате называет причину проблемы и рецепт (или
подтверждает разбор), агент сохраняет это командой `remember`. Запись
ложится в `alla-kb/<id>.json` — **закоммитьте её**, чтобы рецептом пользовалась
вся команда.

**Где лежит база.** В одномодульном проекте (и везде, где нет Java/Kotlin с
Gradle/Maven) — в корне git-репозитория. В многомодульном Java/Kotlin-проекте
у каждого модуля своя база — `<модуль>/alla-kb/`, рядом с `build.gradle(.kts)`
или `pom.xml`, и проблема видит только записи своего модуля: одинаковый текст
ошибки в разных модулях — разные проблемы, повтор по истории тоже считается
внутри модуля.

Проект считается многомодульным, только если исходники (`.java`, `.kt`,
`.groovy`, `.scala`) лежат минимум в двух модулях. Единственный проект во
вложенной папке (например, `autotests/pom.xml` в репозитории, где скилл стоит
в корне) одномодульный: его база остаётся в корне. `buildSrc` и `build-logic`
модулями не считаются. Если в проекте появился второй модуль, база переезжает
в модули — перенесите прежние записи через `git mv`.

В подпапке `flaky/` базы — отметки «нестабильный тест» от перезапуска (см. «Перезапуск
тестов»); записями базы знаний они не считаются.

Модуль определяется по тестам проблемы: скилл находит исходник теста по
`full_name` и берёт ближайшую папку выше с `build.gradle`, `build.gradle.kts`
или `pom.xml` (сам корень проекта не считается, вложенные модули работают так
же). Если в проблеме тесты из нескольких модулей, выбирается тот, где их
больше (при равенстве — модуль представителя).

Исходник должен находиться однозначно. Если одноимённый класс есть в двух
модулях (`ru.company.SmokeTest`) или исходник не нашёлся (например, имена
тестов — сценарии Cucumber), тест модуль не определяет. Проблема тогда берёт
модуль прогона — когда все остальные проблемы прогона из одного модуля (для
неоднозначного класса он должен быть среди кандидатов), — иначе общую базу в
корне. Записи, созданные до этой возможности, лежат в корне и видны только
таким проблемам. Команда `check` показывает все найденные базы.

При следующих разборах скилл узнаёт проблему:
- **точно** — если эту же ошибку (по стабильной сигнатуре) уже подтверждали.
  Для общих проверок вроде `expected: <200> but was: <500>` в сигнатуру входят
  и ошибки из лога, поэтому разные причины одной проверки не путаются;
- **по признаку** — если все строки признака (`error_example`, 1–3 строки
  из текста ошибки или лога) есть в данных кластера. Числа, ID, время и
  пробелы при сравнении не учитываются.

Найденные записи попадают в задание кластера с рецептом, а в отчёте проблема
помечается «известная: <id>». Если запись к ошибке не относится, агент
выполняет `reject` — для этой ошибки запись больше не предлагается.

Записи можно править руками (`title`, `description`, `resolution_steps`,
`error_example`); поле `id` не меняйте. Свои поля (например `jira`, `owner`,
`tags`) скилл при перезаписи сохраняет. Признак `error_example` хранится
нормализованным: UUID, даты, IP и адреса почты заменены метками `<ID>`,
`<TS>`, `<IP>`, `<EMAIL>`. Файл с маркерами конфликта git скилл пропускает и
сообщает об этом в отчёте — разрешите конфликт в файле.

Строки, похожие на секреты (пароли, токены, ключи, пароль в URL, PEM), в
`alla-kb/` не записываются — скрипт просит заменить их. Правки руками эту
проверку обходят: смотрите на них при ревью.

## Правки автотестов

Если разбор относит проблему к категории «тест» и модель нашла код теста,
она решает, можно ли его исправить. Правило строгое: только конкретный дефект
автотеста. Скрипт отклоняет явное ослабление теста — удалённые или
закомментированные проверки, `@Disabled`/`Skip`/`@Retry`, пустой catch, новый
`sleep`. Смену ожидаемого значения (200 → 201) и рост таймаута он не
отклоняет, а помечает строкой «Проверь:» рядом с diff и в отчёте: решает
человек. Править можно только исходники тестов (не настройки, сборку и CI);
файл не в UTF-8 скилл не трогает.

Предложения видны в отчёте в разделе «Агент может поправить сам». Порядок:
`apply N --run DIR` показывает diff и его хэш (diff сохраняется в
`proposals/NN.patch`); после явного «да» выполняется команда из вывода с
`--yes --diff <хэш>` — записывается ровно показанный diff. Перед записью файл
сохраняется в `proposals/NN.orig`, запись атомарная, окончания строк и BOM
сохраняются. `revert N --run DIR` возвращает файл, если после `apply` его не
меняли. Если проект собирается Maven, после правки агент предлагает перезапустить тесты
проблемы (одним вопросом); на «да» они идут так же, как в «Перезапуск тестов», и итог
покажет «прошли на изменённом коде — проверка правки» или «воспроизводятся». Без Maven агент
просит запустить исправленный тест самому.

Скилл помнит, что правка применена (`proposals/NN.applied.json`), и не применяет
её повторно. Если файл потом правили, скилл говорит «применена» только при
строгом доказательстве: все изменения лежат по одну сторону от строк правки, а
сами эти строки целы. Близость файла к исходному доказательством отката не
служит: чужая правка может вернуть часть удалённого (после двух `click()`
добавили `focus(); click()`), а правка при этом остаётся в силе. Во всех
остальных случаях (правку откатили вручную вместе с другими правками, строку
правки изменили иначе, копия `NN.orig` недоступна) состояние «неизвестно»:
`apply` отвечает «не удалось определить», ничего не пишет, а отчёт помечает
проблему. Проверьте файл (`git diff`). Если правка действительно нужна заново,
`apply N --run DIR --repeat` покажет diff с предупреждением, дальше как обычно
(«да» и `--yes --diff`); прежняя резервная копия не затирается, а уходит в
`NN.orig.1`, `NN.orig.2`… (самая первая исходная версия — `NN.orig.1`;
`NN.orig` всегда последняя, её возвращает `revert`). Агент использует `--repeat` только по прямой просьбе
пользователя.

## Перезапуск тестов

Упавший в CI тест бывает нестабильным: при повторном запуске он проходит. После отчёта скилл
сам предлагает перезапустить тесты, похожие на нестабильные, а по просьбе пользователя
(`/alla:rerun N`, «перезапусти тесты проблемы 2») — тесты названной проблемы. Он
перезапускает их на этой машине и говорит, какие из них нестабильны.

Похожим на нестабильный скилл считает тест, у которого:
- повтор в TestOps прошёл или упал с другой ошибкой;
- или ошибка похожа на временный сбой (таймаут чтения или соединения, обрыв соединения,
  ответ 502/503/504, «stale element», «element click intercepted», ожидание Selenium), если
  агент не отнёс проблему к автотесту или тестовым данным.

Не предлагаются: тесты, у которых все повторы в TestOps упали одинаково; проблемы с правкой
агента (предложенной или применённой) или изменённым файлом теста; проблемы с подтверждённым
выводом расширения. Сама категория «стенд» — не признак: если стенд лежал в CI и поднялся, тест
пройдёт, но нестабильным от этого не станет. Предложение — один вопрос после отчёта; на «да»
запускается ровно предложенный набор (`rerun --run DIR --yes --plan <хэш>`). `/alla:rerun`
без номеров показывает его план, а если перезапуск уже был — его ход или итог.

Порядок для проблемы N:

1. `rerun N --run DIR` показывает план: тесты, что запустить нельзя и почему, команды Maven и
   оценку времени. Ничего не запускается.
2. После явного «да» — `rerun N --run DIR --yes --plan <хэш>` из вывода: запускается ровно
   показанный план. Maven идёт фоновым процессом (Qwen Code обрывает команду через 2
   минуты), команда ждёт итога до 75 с, дальше — `rerun --run DIR --wait`.
3. Каждый тест запускается до `ALLURE_RERUN_ATTEMPTS` раз (по умолчанию 3), до первого
   успеха. В следующий запуск идут только тесты, упавшие с той же ошибкой, что в TestOps
   (без учёта времени, ID и длинных чисел, с учётом кодов ошибок).

Итог по группам: **нестабильные** (упали в CI, при перезапуске прошли), **воспроизводятся**
(каждый раз та же ошибка), **падают локально иначе** (например, стенд недоступен с этой
машины — о нестабильности это не говорит, такой тест не повторяется), **не запустились**
(сборка не прошла, теста нет в отчётах, пропущен, вышло время). Если правка агента применена
или файл теста изменён (`git status`), прошедший запуск — проверка правки, а не
нестабильность.

Как запускается:
- Только Maven (JUnit, TestNG через surefire). Модуль теста — ближайшая папка с `pom.xml` над
  его исходником; Maven запускается из корня реактора (`-pl <модуль> -am`), а если модуля нет
  в `<modules>` — из папки модуля. Инструмент — `mvnw` проекта, иначе `mvn` из `PATH`.
- Команда: `mvn -B test -Dtest=<Класс>#<метод>+<метод> -Dsurefire.failIfNoSpecifiedTests=false
  -DfailIfNoTests=false -Dmaven.test.failure.ignore=true -DskipTests=false
  -Dmaven.test.skip=false -Dsurefire.reportNameSuffix=…` плюс
  `ALLURE_RERUN_MAVEN_ARGS` (профиль стенда, свойства: `-Pstand -Denv=ift`). Итог читается из
  `target/surefire-reports/TEST-*.xml` этого запуска.
- `-DskipTests` и `-Dmaven.test.skip` из `.mvn/maven.config` перезапуск отменяет. Пропуск,
  зашитый в `pom.xml` или профиль, — нет: тест попадёт в «не запустились» с причиной «Maven
  пропустил тесты»; нужное свойство или профиль передайте через `ALLURE_RERUN_MAVEN_ARGS`.
- Тесты идут с настройками проекта на этой машине и обращаются к тем же сервисам, что при
  обычном локальном запуске. Переменные `ALLURE_*` (токен TestOps) в окружение Maven не
  передаются.
- Одновременно в проекте идёт один перезапуск; общий потолок времени —
  `ALLURE_RERUN_TIMEOUT` (по умолчанию 1800 с), по нему Maven останавливается.
- План, ход, итог и логи Maven — в `rerun/` папки разбора. Итог попадает и в отчёт: строка
  в шапке краткого разбора, метка «прошёл при перезапуске: k из m» у проблемы и раздел
  «Перезапуск локально» в `report.md`. Общий анализ («Коротко») из-за перезапуска не
  переписывается.

**Сохранение итога.** После итога агент одним вопросом спрашивает, сохранить ли его: отметки
в базе знаний и статус passed в TestOps (что из этого есть в ответе); на «да» —
`rerun --run DIR --remember --result <id итога>`, одна команда для обоих. На «нет» или
согласие только с частью не сохраняется ничего.

**Отметки в базе знаний.** Прошедший тест отмечается
нестабильным файлом `alla-kb/flaky/<Класс>_<метод>_<хэш>.json` (в многомодульном проекте — в
базе модуля): тест, дата первой и последней отметки, прогон, на каком запуске прошёл и
признаки из CI. Отмечается только тест, у которого в CI был признак нестабильности (повтор в
TestOps, временный сбой, прежняя отметка), и только на коде как в CI: если в CI лежал стенд,
а теперь поднялся, тест пройдёт, но нестабильным не станет. Отмеченный тест, который
упал при перезапуске каждый раз с той же ошибкой, отметку теряет. Закоммитьте папку: в
следующих разборах у всех в команде отчёт пометит такую проблему «нестабильные по базе
знаний», а скилл снова предложит перезапуск, даже если в TestOps повторов не было. Снять
отметку руками — удалить файл.

**Статус в TestOps.** Каждому прошедшему тесту — и нестабильному, и проверке правки — скилл
ставит в прогоне статус passed: `POST /api/testresult/{id}/resolve` на каждый результат
отдельно (у параметризованного теста — на все его варианты из проблемы), с пометкой «alla:
тест прошёл при перезапуске на машине инженера (запуск k из N)», ошибкой из CI и, для
проверки правки, «в CI этого ещё нет». Других записей в TestOps нет. Токену нужно право
менять результаты тестов в проекте: без него TestOps отвечает 403, и скилл называет причину,
а отметки базы знаний всё равно сохраняются. Отмеченные результаты — в `rerun/resolved.json`
(каждый — сразу после ответа TestOps): повтор команды отправляет только то, что TestOps не
принял. Если TestOps отвечает медленно и за один ответ команды (75 с) ушло не всё, агент сам
сразу повторяет ту же команду — когда TestOps ничего не отклонил; при отказе повтор за вами. Успехом считается только ответ 2xx: перенаправление прокси или
страницы входа — нет. Если `ALLURE_ENDPOINT` с тех пор
указывает на другой TestOps, скилл ничего не отправляет. Отметка видна и в разделе
«Перезапуск локально» `report.md` («в TestOps — passed»). Выключает её
`ALLURE_RERUN_RESOLVE=false`.

Не поддерживаются: Gradle и pytest, вложенные классы (`Outer$Inner`), интеграционные тесты
failsafe; набор TestNG из `suiteXmlFiles` при `-Dtest` не применяется (тест с параметрами
набора упадёт локально иначе). Только macOS и Linux.

## Расширения

Тикеты команды — встроенное, выключенное по умолчанию расширение `tickets`:
`extensions enable tickets`, затем перезапуск Qwen. `/alla:ticket N [N…]` готовит
просмотр; отправка только после отдельного ответа инженера. Без адаптера доступны
локальные черновики. Трекер подключается через его MCP-сервер встроенным адаптером
(`mcp-tracker.toml`) или своим адаптером. Настройки маршрутов, подключение MCP,
демонстрационный трекер и шаблон адаптера —
[../extensions/tickets/README.md](../extensions/tickets/README.md). Поручаете подключение
MCP агенту — дайте ему
[../extensions/tickets/CONNECT-MCP.md](../extensions/tickets/CONNECT-MCP.md).

Расширение добавляет скиллу функцию без правки его кода: на событие скилла
(«правка применена», «правка откатана», «отчёт готов») или по просьбе
пользователя (своя команда `/alla:…`) оно запускает своего субагента или свой
скрипт. Встроенные расширения лежат в `extensions/` скилла
и выключены; свои команда кладёт в `alla-extensions/<имя>/` в корне проекта
(своё с тем же именем заменяет встроенное — так меняют встроенное, не трогая
скилл). Как написать своё — `extensions/README.md` скилла.

Включение общее для проекта — файл `alla-extensions/config.toml` (его стоит
закоммитить). Меняют его команды или `/alla:extensions`:

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions list
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions enable git-publish
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions disable git-publish
```

`enable` ставит субагента расширения в `.qwen/agents/` и его команды в
`.qwen/commands/alla/`; Qwen Code увидит их после перезапуска (до того задание выполняется без своего типа субагента).
Настройки расширения — таблица с его именем в том же `config.toml`. Ошибка
расширения (битый манифест, упавший скрипт) не мешает разбору: она видна в
ответе команды и в `check`.

### git-publish: выгрузка правки в git

После `apply --yes` субагент `alla-git-publish` пишет сообщение коммита по
разбору, а скрипт расширения коммитит правку в новую ветку
`alla/<прогон>-problem-<N>` и пушит её. Ответ — ветка и ссылка на merge request,
если её печатает сервер (GitLab, GitHub, Bitbucket).

- Рабочая копия не меняется: текущая ветка, индекс и файлы остаются как были,
  правка у инженера — незакоммиченной. Коммит собирается во временном индексе
  от текущего коммита (`base`), в него попадает только правка — другие
  незакоммиченные изменения, в том числе в том же файле, не попадают.
- Одна правка — одна ветка. Имя занято — `…-2`, `…-3`. Повтор не создаёт вторую
  ветку; не прошедший push повторяется в ту же локальную ветку.
- Пушит с правами git инженера (ключ SSH или сохранённый пароль): пароль
  скрипт не спрашивает. Нет remote, файл менялся после `apply`, нет имени
  автора в git — отказ с объяснением, ничего не меняется.
- `revert` правку на сервере не трогает — скилл напомнит о ветке.

```toml
enabled = ["git-publish"]

[git-publish]
remote = "origin"        # куда пушить
branch_prefix = "alla/"  # начало имени ветки
base = "HEAD"            # от какого коммита ветка, например "origin/develop"
confirm = false          # true — спрашивать перед каждой выгрузкой
```

### sut-code: разбор по коду приложения

Продолжение разбора для проблемы из отчёта — по коду тестируемого приложения
(SUT): Алла скачивает и обновляет копию репозитория, выбирает ревизию, находит
в коде место ошибки по стек-трейсу и тексту ошибки из лога, смотрит историю
изменений и основную ветку, а затем говорит, в чём причина, как исправить и
нужно ли заводить дефект.

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions enable sut-code
```

```toml
enabled = ["sut-code"]

[sut-code]
repos = ["ssh://git@git.company/shop/orders.git"]   # или https://…; несколько — списком,
                                                    # «имя=ссылка» — со своим именем
default_branch = ""   # основная ветка; пусто — ветка HEAD на сервере
```

После перезапуска Qwen Code — команда `/alla:code`:

```text
/alla:code 2                  — проблема 2; версия — основная ветка на момент запуска прогона (приблизительно)
/alla:code 2 release/1.4      — стенд был на этой ветке (тег 1.4.2 или v1.4.2, коммит — тоже можно)
/alla:code 2 ssh://git@git.company/shop/orders.git   — разовая ссылка, если repos не задан
```

То же можно попросить словами: «разбери проблему 2 по коду приложения, стенд
на 1.4.2». После отчёта скилл сам подсказывает, какие проблемы («приложение»,
«неизвестно») стоит так разобрать.

- Копия кода лежит в `.alla-sut/` в корне проекта (своим `.gitignore` она
  исключена из git проекта): частичный клон и распакованные ревизии, по
  умолчанию последние 3 (`keep_trees`; ревизии, которыми пользовались в
  последний час, не удаляются — их может читать другой разбор). Её можно
  удалить — скачается заново.
- Доступ к git — правами инженера: ssh-ключ или сохранённый пароль (credential
  helper). Пароль скрипт не спрашивает, пароль или токен в ссылке не
  принимается. Корпоративный сертификат — в настройках git (`http.sslCAInfo`).
- Первое скачивание большого репозитория идёт в фоне: если оно не успело за
  минуту, Алла попросит повторить команду через пару минут.
- Вывод не попадает в отчёт сам по себе. Ответь «да, верно» — он сохранится в
  базу знаний (с ревизией, местом в коде и коммитом) и в отчёт («Подтверждено
  инженером»); «нет» — ничего не сохраняется.
- Разбор лежит в `alla-reports/<разбор>/extensions/sut-code/`: `*.report.md` —
  для человека, `*.result.json` — для следующих расширений (например, заведения
  дефекта).

## Команды

| Команда | Что делает |
|---|---|
| `setup [--python PATH] [-- pip-аргументы]` | Ставит зависимости в `.venv` проекта (создаёт его, если нет), создаёт `.env` из образца |
| `check` | Проверяет Python, настройки (без показа токена), базу знаний и доступ к TestOps |
| `prepare <ID или ссылка> [--fresh]` | Получает прогон и готовит задания; неоконченный разбор продолжает |
| `next [папка]` (или `--run папка`) `[--workers N \| --serial]` | Следующий шаг разбора; `--workers N` (1–8) — число субагентов, `--serial` — без субагентов |
| `verify N [N…] --run DIR` | Только проверка разборов (для субагентов пакета): ничего не записывает, `STATUS: ok` или `fix` |
| `skip N --run DIR [--reason …]` | Пропускает кластер N (только по просьбе пользователя) |
| `apply N --run DIR [--yes --diff ХЭШ] [--repeat]` | Показывает diff правки автотеста; с `--yes --diff` применяет его; `--repeat` — повтор правки с неизвестным состоянием (только по явной просьбе) |
| `revert N --run DIR` | Возвращает файл, изменённый `apply`, если его не меняли |
| `rerun [N…] --run DIR [--yes --plan ХЭШ \| --wait \| --remember --result ID]` | Перезапуск тестов проблем локально (Maven), без N — похожих на нестабильные: план; с `--yes --plan` — запуск после «да»; `--wait` — ход и итог; `--remember` — сохранить итог: отметки в базе знаний и статус passed в TestOps (см. «Перезапуск тестов») |
| `remember N --run DIR [--entry ID] [--from-analysis \| --from-extension ИМЯ]` | Сохраняет причину и рецепт проблемы N в `alla-kb/` из `feedback/NN.md` (или подтверждённый разбор с `--from-analysis`, или подтверждённый вывод расширения — тогда и в отчёт) |
| `reject N <id> --run DIR` | Запись `<id>` не относится к ошибке N |
| `clean [--older-than-days N] [--dry-run]` | Удаляет старые папки разборов |
| `review [папка] (или --run папка) [--no-model]` | Проверка законченного разбора для пилота (см. «Пилот: проверка разбора»); `--no-model` — без оценки диагнозов моделью |
| `extensions [list]`, `extensions enable\|disable <имя>` | Расширения проекта: список, включить, выключить (см. «Расширения») |
| `extensions run <имя> [N…] --run DIR [--param КЛЮЧ=ЗНАЧЕНИЕ…]` | Функция расширения по просьбе для проблем N (например, `sut-code`), у остальных — повтор действия для применённой правки N (без N — для отчёта) |
| `extensions action <имя> <действие> --context FILE [-- аргументы]` | Действие расширения; команду пишет задание расширения |

Первая строка вывода любой команды — `STATUS: …` (у `setup` он печатается последним, после
вывода pip). Код возврата 0, если
напечатана инструкция для агента (`analyze`, `fix`, `done`, `setup_required`…);
ненулевой — только у `STATUS: error`.

У `apply`, `remember`, `reject`, `skip`, `revert`, `rerun` папка разбора `--run`
обязательна: после нового `prepare` «последний» разбор — уже другой прогон, и
обратная связь или правка ушли бы не туда.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ALLURE_ENDPOINT` | — | URL Allure TestOps (обязательно) |
| `ALLURE_TOKEN` | — | API-токен (обязательно) |
| `ALLURE_SSL_VERIFY` | `true` | Проверка TLS. Для корпоративного прокси лучше указать его корневой сертификат в переменной окружения `SSL_CERT_FILE`; `false` отключает проверку полностью (токен не защищён) — только временный обход |
| `ALLURE_REQUEST_TIMEOUT` | `30` | Таймаут HTTP-запроса, сек |
| `ALLURE_HTTP_RETRIES` | `3` | Сколько раз повторить запрос к TestOps, если он ответил 429, 502, 503, 504 или не ответил вовсе (пауза 1, 2, 4 с или по `Retry-After`); `0` — без повторов |
| `ALLURE_PAGE_SIZE` / `ALLURE_MAX_PAGES` | `100` / `200` | Пагинация результатов: по умолчанию до 20 000 результатов прогона вместе со скрытыми повторами |
| `ALLURE_DETAIL_CONCURRENCY` | `10` | Параллельные запросы деталей тестов |
| `ALLURE_LOGS_CONCURRENCY` | `5` | Параллельные загрузки вложений |
| `ALLURE_LOGS_MAX_ATTACHMENT_BYTES` | `10485760` | Максимум байт из одного вложения |
| `ALLURE_LOGS_MAX_SNIPPET_CHARS` | `65536` | Максимум символов лога на тест |
| `ALLURE_CLUSTERING_THRESHOLD` | `0.60` | Порог похожести; ниже — крупнее кластеры |
| `ALLURE_LOGS_CLUSTERING_WEIGHT` | `0.15` | Вес лога в кластеризации |
| `ALLURE_CLUSTERING_STEP_STRICT_THRESHOLD` | `0.95` | Жёсткое разделение по шагу теста |
| `ALLURE_LLM_PROMPT_MESSAGE_MAX_CHARS` | `2000` | Лимит сообщения об ошибке в задании |
| `ALLURE_LLM_PROMPT_TRACE_MAX_CHARS` | `400` | Лимит трейса в задании |
| `ALLURE_LLM_PROMPT_LOG_MAX_CHARS` | `8000` | Лимит лога в задании; длинный лог сокращается отбором блоков, связанных с ошибкой, пропуски помечаются |
| `ALLURE_RETRY_MAX_DETAIL_REQUESTS` | `200` | Сколько запросов на прогон можно сделать за ошибками повторов, которых нет в списке результатов; `0` — не запрашивать |
| `ALLURE_IMAGES_PER_PROBLEM` | `3` | Сколько скриншотов из вложений показать модели на проблему (0–3): по одному на тест-пример — приложенный к упавшему шагу, иначе последний; `0` — не скачивать. Выключите, если модель Qwen Code не принимает изображения и пересказ картинок другой моделью (vision bridge) не настроен |
| `ALLURE_IMAGES_MAX_BYTES` | `5242880` | Потолок размера одного скриншота (от 64 КБ до 20 МБ); больше — не показывается |
| `ALLURE_RERUN_ATTEMPTS` | `3` | Перезапуск тестов: сколько раз запускать тест до первого успеха (1–5) |
| `ALLURE_RERUN_MAX_TESTS` | `20` | Сколько тестов перезапускать за раз (0–100); `0` выключает перезапуск |
| `ALLURE_RERUN_TIMEOUT` | `1800` | Общий потолок времени перезапуска, сек (60–14400); дальше Maven останавливается |
| `ALLURE_RERUN_MAVEN_ARGS` | — | Свои аргументы Maven для перезапуска (профиль, свойства стенда), как в shell: `-Pstand -Denv=ift`. В ответах скилла значения не показываются |
| `ALLURE_RERUN_RESOLVE` | `true` | Прошедшим при перезапуске тестам после «да» пользователя ставить статус passed в прогоне TestOps; `false` — скилл TestOps только читает (см. «Перезапуск тестов») |
| `ALLURE_OPERATION_ID_KEYS` | — | Свои ключи id операции через запятую (`ufsBusinessId,ufsRqUID`) — к встроенным `operUID`, `rqUID`, `requestId`, `correlationId`, `traceId`. Общий лог сервиса, где есть такие id, отбирается по id операции теста: в разбор идут только её записи. Свой id тест должен нести в сообщении, трейсе или вложении-запросе/ответе — иначе из такого лога ничего не возьмётся |

## Пилот: проверка разбора

По умолчанию выключена и на разбор не влияет: пока разбор идёт, модель о проверке ничего не
знает (ни в заданиях, ни в ответах `next`). Запускается после `STATUS: done` одним из двух
способов:

- из терминала, в корне проекта автотестов — сеанс разбора не затрагивается вовсе:

      python3 .qwen/skills/alla-launch/scripts/alla_skill.py review

  (последний разбор; другой — `review --run alla-reports/<папка>`);
- в том же сеансе Qwen Code — фразой «проверь разбор».

Что проверяется:

- **Ход разбора** — по папке разбора и журналу сеанса Qwen Code (Qwen Code ≥ 0.25 сам пишет
  его в `~/.qwen/projects/<проект>/chats/`; `prepare` и `next` запоминают, какой сеанс шёл):
  дошёл ли разбор до отчёта, ответы `STATUS: error` и падения скрипта, разборы с пометкой
  «формат нарушен» и без разбора, исправления после проверки, откат пакетного режима, ошибки
  инструментов, проблемы скилла (`skill-problems.md` и строки субагентов) и правила исполнителя — те же, что на
  стенде разработчика: из shell только команды скилла, код проекта не искал сам и открывал
  только из «Где искать код автотеста», не читал служебные файлы, писал только свои файлы,
  вывел краткий разбор дословно и без блока проблем скилла. Плюс время, токены и ошибки API,
  наибольший контекст запроса и сжатия истории (у основного агента и у субагентов отдельно).
- **Качество диагнозов** — отдельный процесс `qwen` с чистым контекстом (временная папка,
  без контекста проекта, без инструментов) получает задание, код автотеста из задания,
  скриншоты, которые видел агент, и разбор до 10 крупнейших проблем и по каждой отвечает:
  подтверждается ли причина данными, согласен ли с категорией, полезны ли действия. Это ещё
  один запрос к той же модели, что в `~/.qwen/settings.json`, — до нескольких минут.
  Цитату со скриншота проверяющий сверяет с картинкой; если картинка до него не дошла
  (файла нет, модель не принимает изображения), цитату он не засчитывает ни за, ни против, а
  причину, которая держится только на скриншоте, оценивает как «частично».

Итог — две оценки:

| Оценка | Значения |
|---|---|
| Ход разбора | `сбой` — нет отчёта, `STATUS: error`, исключение скрипта (traceback в выводе) или команда, оборвавшаяся без строки `STATUS` (тайм-аут, прерывание); `с замечаниями` — нарушено правило, «формат нарушен», нет разбора, цитаты не сверены (потерян реестр источников), проблемы скилла, откат пакетов, ошибки инструментов; иначе `чисто` (исправления после проверки и ненайденный журнал указываются, но оценку не снижают) |
| Качество диагнозов | доли — от запрошенных проблем: оценка, которую модель не вернула, — не подтверждение. `хорошо` — причина подтверждена у ≥ 80 % и несогласий по категории ≤ 10 %, и модель оценила все запрошенные; `средне` — подтверждена у ≥ 50 %; иначе `плохо`; `не оценено` — модель не ответила (причина указана) или `--no-model` |

Результат — в `<папка разбора>/review/`: `report.md` (для вас: подробности с текстами из
разбора) и `pilot-summary.md` — **его можно передать разработчику**: в нём только числа,
коды причин и названия проверок, без сообщений об ошибках, логов, имён тестов, путей, кода и
названия прогона. Перед отправкой его стоит просмотреть.

Раздел «Кластеризация» в `pilot-summary.md` — сколько пар падений развело каждое правило
группировки (отдельной строкой — пары, которые лог удержал вместе или склеил) и сколько проблем с почти одинаковым текстом ошибки осталось раздельными, с
кодом правила, которое их развело: `step` — разные шаги теста, `log` — разные ошибки в логе,
`resource` — разные хосты или локаторы, `assertion` — разное фактическое значение в проверке,
`message` — непохожие сообщения у других тестов групп, `score` — правила не сработали, но
общей похожести не хватило. По этим числам разработчик видит, какое правило дробит ваши
прогоны. Строка «похожие после разбора» — сколько групп похожих проблем скрипт дал агенту
сравнить (связи: `near` — почти одинаковый текст ошибки, `code` — одно место в коде, `kb` — общая запись базы знаний, `text` —
похожие причина и первый шаг) и сколько из них агент счёл одной причиной.

Строка «пик контекста» — самый большой запрос к модели в токенах (вся история разговора), у
основного агента и у самого загруженного субагента; «сжатий истории» — сколько раз Qwen Code
пересказал начало разговора, потому что история подошла к пределу окна модели (в
настройках Qwen Code — доля окна, по умолчанию 85 %). После сжатия модель продолжает по
пересказу и может потерять правила скилла; сжатия больше нуля или пик у самого предела окна —
повод передать сводку разработчику. Сжатия скрипт находит по записям журнала, которые пишет
Qwen Code 0.26; в старых версиях таких записей может не быть, и строка покажет 0.

Если журнал не найден (разбор шёл не из Qwen Code, старая версия Qwen Code или журнал
удалён), правила исполнителя не проверяются — это сказано в отчёте; остальное считается.

## Ограничения

- База знаний только проектная (`alla-kb/`); нет merge rules, HTML-отчёта и
  записи комментариев или ссылок в TestOps. В TestOps скилл пишет только статус passed
  тестов, прошедших при перезапуске, и только после «да» пользователя
  (`ALLURE_RERUN_RESOLVE=false` выключает и это); остальное он только читает.
- Прогон задаётся числовым ID или ссылкой; по имени запуска скилл не ищет.
- Ошибки и логи прогона передаются модели, с которой работает Qwen Code, в
  том числе как есть, без маскирования секретов в самих заданиях. Скриншоты из
  вложений — тоже (до трёх на проблему; выключает `ALLURE_IMAGES_PER_PROBLEM=0`).
- Скриншоты модель смотрит сама (read_file в Qwen Code отдаёт PNG, JPEG, GIF и
  WebP как изображение). Модель без поддержки изображений получает вместо картинки её
  пересказ другой моделью, если в Qwen Code настроен vision bridge, и разбирает скриншот по
  пересказу: видимый текст цитирует из него. Без vision bridge такая модель получает
  только сообщение об ошибке и разбирает проблему без скриншота — тогда скриншоты лучше
  выключить. Текст со скриншота скрипт с картинкой не сверяет — отчёт так и помечает такую
  цитату; категорию «приложение» или «данные» скриншот не подтверждает. Видео не берутся.
- Код проекта может отличаться от ревизии, на которой шёл прогон.
- Перезапуск тестов — только Maven (surefire) и только на macOS и Linux; тесты идут на этой
  машине, а не на агенте CI.
- История повторов (`alla-reports/history.jsonl`) локальная: у каждого
  участника своя, и в ней только разборы, сделанные скиллом на этой машине.
  Прошлые выводы модели в задания не подаются, только число повторов.
- Пустой прогон (нет результатов) `prepare` считает ошибкой. Идущий прогон скилл
  разбирает, но предупреждает: прогон в TestOps не закрыт, результаты менялись во время
  выгрузки или TestOps не отдал данные части падений (даже после повторов) — с командой
  `prepare <id> --fresh`, чтобы разобрать его заново позже.

## Обновление

Для обновления скопируйте папку скилла заново, сохранив `.env`; `.venv` проекта при этом
не трогается. Если в папке скилла остался `.venv` от прежней версии
(`.qwen/skills/alla-launch/.venv`), его можно удалить. `.venv` привязан к пути и версии
Python: после переноса проекта или смены Python пересоздайте его и выполните `setup`. Если
изменился `requirements.txt`, скрипт сам ответит `STATUS: setup_required` — выполните `setup`.

`setup` отмечает успешную установку файлом `.alla-setup-complete` в `.venv` проекта с
хэшем `requirements.txt`. Если `pip install` оборвался, маркера нет, и любая
команда просит повторить `setup` вместо падения на импорте.
