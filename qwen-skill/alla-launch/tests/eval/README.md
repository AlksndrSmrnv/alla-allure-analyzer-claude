# Эталон точности alla

Офлайн-оценка того, какие данные доходят до модели и как падения группируются в проблемы.
Модель не вызывается: оценивается работа `prepare` (сбор, извлечение логов, кластеризация,
задания). Правильность диагнозов автоматически не оценивается.

## Кассета прогона

Сохранённый прогон TestOps, который воспроизводится без сети (`cassette.py`):

```
launch.json                      ответ GET /api/launch/{id}
results.json                     все результаты прогона, включая hidden
executions/<result_id>.json      GET /api/testresult/{id}/execution
details/<result_id>.json         GET /api/testresult/{id}
attachments/<result_id>.json     метаданные вложений результата
contents/<attachment_id>         байты вложения (не больше лимита ALLURE_LOGS_MAX_ATTACHMENT_BYTES + 1)
```

## Запись своего прогона (команде, локально)

Из корня репозитория, с настройками скилла (`<skill>/.env` или переменные `ALLURE_*`):

```bash
.venv/bin/python qwen-skill/alla-launch/tests/eval/record.py 12345 ~/alla-cassettes/run-12345
```

- Сбор — тот же, что у `prepare`; TestOps только читается. Путь за прокси
  (`ALLURE_ENDPOINT=https://host/testops`) поддерживается.
- Каталог должен быть новым или пустым: поверх старой кассеты запись не идёт, иначе
  ответы двух записей смешались бы.
- Заголовки запросов, обмен API-токена и ответ с JWT на диск не пишутся (это проверяет
  `tests/test_eval_record.py`).
- В кассете — настоящие сообщения, логи и имена тестов. Каталог держите **вне git** и
  никому не передавайте; наружу — только сводные цифры, и то по желанию команды.

## Разметка `labels.json`

```json
{"groups": [
  {"id": "pay-500-db", "cause": "payment-db-pool", "category": "приложение",
   "tests": [101, 102, 103],
   "evidence": ["HikariPool-1 - Connection is not available, request timed out"]},
  {"id": "silent-108", "cause": null, "tests": [108]}
]}
```

- `groups` — группы одинаковых симптомов: эталон для проблем (кластеров). Каждое активное
  падение (failed/broken, не muted, не hidden) — ровно в одной группе.
- `cause` — подтверждённая причина; у разных групп может совпадать (502, таймаут и «элемент
  не найден» при упавшей авторизации). `null` — причина неизвестна: такие группы между собой
  всегда считаются разными.
- `category` — `тест|приложение|окружение|данные|неизвестно`, для ручной сверки разборов.
- `evidence` — ключевые строки, которые обязаны дойти до задания модели.
- `retries` (необязательно) — повторы: `links` — финальный результат и его hidden-попытки
  по порядку с ожидаемым «та же ошибка» (`same`: `true`/`false`/`null`), пустой список —
  попыток у него быть не должно (смена окружения или параметров); `passed_after_retry` —
  финальные `passed` с неудачными попытками.

```json
{"retries": {"links": [{"final": 1007, "attempts": [{"id": 1006, "same": false}]},
                       {"final": 1013, "attempts": []}],
             "passed_after_retry": [1002]}}
```

## Метрики (`metrics.py`, `run_eval.py`)

`run_eval.py` выполняет настоящий `prepare` на прогоне без сети (временный проект и папка
скилла, настройки по умолчанию — переменные `ALLURE_*` не учитываются) и сравнивает
кластеры и задания `clusters/NN.md` с разметкой:

- **precision** (ошибочные объединения) — B-Cubed: пара тестов в одном кластере верна,
  если они из одной группы или у групп одна известная `cause`;
- **recall** (дробление) — B-Cubed по группам симптомов; разные симптомы одной причины в
  разных кластерах не штрафуются;
- **скрыто** — группы, ни один тест которых модель не видит (виден представитель кластера и
  тест, чей лог попал в задание): по ним модель даст чужой диагноз;
- **потеря док.** — строки `evidence`, которых нет (с точностью до пробелов) в заданиях
  кластеров, где группа видима; у скрытой группы потеряны все.

- **повторы** (при разметке `retries`) — попытки, связанные со своим финальным
  результатом, и лишние (смешаны параметры, окружение или чужой тест); верно ли определено
  «та же ошибка»; найденные и лишние «прошли после повтора». Печатаются строкой под
  таблицей; лишние связи и потерянные находки сверяются с базовой линией.

- **записи базы знаний** (шаг 6; у сценариев, где у одной `cause` несколько групп) — для
  такой причины строится синтетическая запись, как после `remember` по её первой группе:
  признак — первая строка `evidence` группы, подтверждённая сигнатура — сигнатура её
  кластера. После `prepare` по `evidence/NN.txt` и сигнатурам проверяется, кому она подходит
  (`match_cluster`): «своей причине» — кластерам с тестами этой причины (иначе проблемы не
  сложатся в одну известную), «чужой» — остальным (ложное предложение и согласие модели
  дали бы ложную известную проблему). Задания от записей не меняются.
  `auth_down_symptoms` — причина, общей строки которой нет у части симптомов (1/3 ожидаемо).
  `known_issue_symptoms` — строка пула есть у всех трёх симптомов (3/3), «чужой» 0:
  посторонняя проблема с тем же assertion `expected: <200> but was: <500>` (NPE каталога)
  получает другую сигнатуру — у общего ассерта в сигнатуру входят строки-ошибки лога
  (сигнатура v7). До v7 лог при трейсе не входил, и подтверждённая сигнатура совпадала с ней
  точно («чужой» 1).

`--details` печатает списки: какие группы склеены, раздроблены, скрыты, какие строки
потеряны. Диагнозы модели автоматически не оцениваются: `--analyses RUN_DIR --labels FILE`
печатает чек-лист «эталонная причина и категория ↔ разбор» для ручной сверки.

```bash
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --details
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --cassette DIR --labels labels.json
```

С кассетой печатается только сводка из чисел — её можно показать за пределами команды.
Разметка проверяется: повтор `id` группы или теста, активное падение без группы — отказ с
кодом 2; `unclustered`/`unlabeled` в сводке должны быть 0.

## Корпус: dev и holdout

`corpus_dev.py` — сценарии, по которым подбираются пороги, веса и правила; `corpus_holdout.py`
— другие сервисы, тексты и сочетания форматов. Holdout смотрится только после изменений на
dev, и его базовая линия обновляется отдельным коммитом с объяснением. `big_launch` (320
падений, логи по ~110 КБ) — лимиты памяти, размера задания и время `prepare`; запускается
только с `--heavy` или явным `--case big_launch` (и всегда при `--write-baseline` и в
`test_eval_quality.py`). Поэтому
строка «ИТОГО» dev без `--heavy` и с ним разная: precision 0.976 на 125 тестах и 0.993 на
445 (2026-10-08, после gates по логу и ресурсам). Сравнивая с базовой линией или с цифрами в
планах, называйте, какая.

Склейки, которые остаются намеренно: `same_assertion_two_npes` (два разных NPE за одним
ассертом — общий корневой класс исключения не даёт логу разделить пару, различает модель по
примерам) и holdout `net-pricing + net-geo` (ошибка разрешения имени хостов не даёт: сбой DNS
бьёт по всем хостам). Контроли против дробления — `log_noise_one_problem`,
`background_log_errors` (разный фон вокруг одной ошибки) и `resources_one_problem`.

## Базовая линия

`baseline.json` — метрики каждого сценария (без времени: оно зависит от машины; пути в
заданиях заменены метками, поэтому размер задания переносим). `tests/test_eval_quality.py`
падает, если precision/recall ниже базовой линии больше чем на 0,001 или выросло число
скрытых групп либо потерянных строк. Ухудшение — только осознанно:
`run_eval.py --write-baseline` в том же коммите и изменение цифр в его сообщении. Улучшение
тоже фиксируйте `--write-baseline`, иначе следующий откат его не заметит.
