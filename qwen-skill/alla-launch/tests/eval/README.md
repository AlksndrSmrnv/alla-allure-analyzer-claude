# Эталон точности alla

Офлайн-оценка того, какие данные доходят до модели и как падения группируются в проблемы.
Модель не вызывается: оценивается работа `prepare` (сбор, извлечение логов, кластеризация,
задания). Правильность диагнозов автоматически не оценивается.

## Кассета прогона

Сохранённый прогон TestOps, который воспроизводится без сети (`cassette.py`):

```
launch.json                      ответ GET /api/launch/{id}
results.json                     все результаты прогона, включая hidden
executions/<result_id>.json      GET /api/testresult/{id}/execution
details/<result_id>.json         GET /api/testresult/{id}
attachments/<result_id>.json     метаданные вложений результата
contents/<attachment_id>         байты вложения (не больше лимита ALLURE_LOGS_MAX_ATTACHMENT_BYTES + 1)
```

## Запись своего прогона (команде, локально)

Из корня репозитория, с настройками скилла (`<skill>/.env` или переменные `ALLURE_*`):

```bash
.venv/bin/python qwen-skill/alla-launch/tests/eval/record.py 12345 ~/alla-cassettes/run-12345
```

- Сбор — тот же, что у `prepare`; TestOps только читается. Путь за прокси
  (`ALLURE_ENDPOINT=https://host/testops`) поддерживается.
- Каталог должен быть новым или пустым: поверх старой кассеты запись не идёт, иначе
  ответы двух записей смешались бы.
- Заголовки запросов, обмен API-токена и ответ с JWT на диск не пишутся (это проверяет
  `tests/test_eval_record.py`).
- В кассете — настоящие сообщения, логи и имена тестов. Каталог держите **вне git** и
  никому не передавайте; наружу — только сводные цифры, и то по желанию команды.

### Что присылать

Сводку `run_eval.py` по кассете — JSON только из чисел (ключи фиксированы, тексты прогона в
неё не попадают; это проверяет `tests/test_eval_metrics.py`):

```bash
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --cassette ~/alla-cassettes/run-12345
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --cassette ~/alla-cassettes/run-12345 --labels labels.json
```

- Без разметки — число падений и проблем, счётчики gates, числа сигнатур (кроме
  `signature_shared_wrong`, см. «Сигнатуры»), размер задания и время. Разметка не нужна:
  это самый быстрый способ показать, как часто gates срабатывают.
- С разметкой — ещё precision/recall, скрытые группы, потери доказательств, сверка пар
  gates с разметкой (см. «Счётчики gates») и `signature_shared_wrong`.
- Без кассеты: те же счётчики пишет каждый `prepare` — `clustering.gates` в `run.json`
  папки разбора (её путь `prepare` печатает строкой «Папка разбора»). Из `run.json` наружу —
  только этот объект:

```bash
python3 -c "import json,sys; print(json.dumps(json.load(open(sys.argv[1]))['clustering']['gates'], indent=2))" alla-reports/<папка разбора>/run.json
```

## Разметка `labels.json`

```json
{"groups": [
  {"id": "pay-500-db", "cause": "payment-db-pool", "category": "приложение",
   "tests": [101, 102, 103],
   "evidence": ["HikariPool-1 - Connection is not available, request timed out"]},
  {"id": "silent-108", "cause": null, "tests": [108]}
]}
```

- `groups` — группы одинаковых симптомов: эталон для проблем (кластеров). Каждое активное
  падение (failed/broken, не muted, не hidden) — ровно в одной группе.
- `cause` — подтверждённая причина; у разных групп может совпадать (502, таймаут и «элемент
  не найден» при упавшей авторизации). `null` — причина неизвестна: такие группы между собой
  всегда считаются разными.
- `category` — `тест|приложение|окружение|данные|неизвестно`, для ручной сверки разборов.
- `evidence` — ключевые строки, которые обязаны дойти до задания модели.
- `retries` (необязательно) — повторы: `links` — финальный результат и его hidden-попытки
  по порядку с ожидаемым «та же ошибка» (`same`: `true`/`false`/`null`), пустой список —
  попыток у него быть не должно (смена окружения или параметров); `passed_after_retry` —
  финальные `passed` с неудачными попытками.

```json
{"retries": {"links": [{"final": 1007, "attempts": [{"id": 1006, "same": false}]},
                       {"final": 1013, "attempts": []}],
             "passed_after_retry": [1002]}}
```

## Метрики (`metrics.py`, `run_eval.py`)

`run_eval.py` выполняет настоящий `prepare` на прогоне без сети (временный проект и папка
скилла, настройки по умолчанию — переменные `ALLURE_*` не учитываются) и сравнивает
кластеры и задания `clusters/NN.md` с разметкой:

- **precision** (ошибочные объединения) — B-Cubed: пара тестов в одном кластере верна,
  если они из одной группы или у групп одна известная `cause`;
- **recall** (дробление) — B-Cubed по группам симптомов; разные симптомы одной причины в
  разных кластерах не штрафуются;
- **скрыто** — группы, ни один тест которых модель не видит (виден представитель кластера и
  тест, чей лог попал в задание): по ним модель даст чужой диагноз;
- **потеря док.** — строки `evidence`, которых нет (с точностью до пробелов) в заданиях
  кластеров, где группа видима; у скрытой группы потеряны все.

- **повторы** (при разметке `retries`) — попытки, связанные со своим финальным
  результатом, и лишние (смешаны параметры, окружение или чужой тест); верно ли определено
  «та же ошибка»; найденные и лишние «прошли после повтора». Печатаются строкой под
  таблицей; лишние связи и потерянные находки сверяются с базовой линией.

- **записи базы знаний** (шаг 6; у сценариев, где у одной `cause` несколько групп) — для
  такой причины строится синтетическая запись, как после `remember` по её первой группе:
  признак — первая строка `evidence` группы, подтверждённая сигнатура — сигнатура её
  кластера. После `prepare` по `evidence/NN.txt` и сигнатурам проверяется, кому она подходит
  (`match_cluster`): «своей причине» — кластерам с тестами этой причины (иначе проблемы не
  сложатся в одну известную), «чужой» — остальным (ложное предложение и согласие модели
  дали бы ложную известную проблему). Задания от записей не меняются.
  `auth_down_symptoms` — причина, общей строки которой нет у части симптомов (1/3 ожидаемо).
  `known_issue_symptoms` — строка пула есть у всех трёх симптомов (3/3), «чужой» 0:
  посторонняя проблема с тем же assertion `expected: <200> but was: <500>` (NPE каталога)
  получает другую сигнатуру — у общего ассерта в сигнатуру входят строки-ошибки лога
  (с v7). До v7 лог при трейсе не входил, и подтверждённая сигнатура совпадала с ней
  точно («чужой» 1). Метрика строится только для причин с несколькими группами; две
  разные причины с одной сигнатурой ловит `signature_shared_wrong` («Сигнатуры»).

- **сигнатуры** — у всех сценариев, см. «Сигнатуры» ниже.

`--details` печатает списки: какие группы склеены, раздроблены, скрыты, какие строки
потеряны. Диагнозы модели автоматически не оцениваются: `--analyses RUN_DIR --labels FILE`
печатает чек-лист «эталонная причина и категория ↔ разбор» для ручной сверки.

```bash
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --details   # только dev
.venv/bin/python qwen-skill/alla-launch/tests/eval/run_eval.py --cassette DIR --labels labels.json
```

С кассетой печатается только сводка из чисел — её можно показать за пределами команды;
`--labels` необязателен (без него — размеры и gates). Разметка проверяется: повтор `id` группы или теста, активное падение без группы — отказ с
кодом 2; `unclustered`/`unlabeled` в сводке должны быть 0.

## Счётчики gates

`gates` — сколько пар падений решил каждый gate кластеризации (`ClusteringGateStats`, см.
`.claude/rules/core.md`, «Кластеризация»). Пары — среди падений с текстом; пару засчитывает
**первый** gate, который её решил (assertion → шаг → лог → сообщение), поэтому пары,
разрезанные шагом, в счётчики лога не попадают.

| ключ | что значит |
|---|---|
| `pairs` / `pairs_in_one_problem` | все пары / пары в одной проблеме — масштаб |
| `assertion_split`, `step_split` | разные actual в assertion; разные шаги |
| `log_pairs` | дошли до gate по логу с ошибками в обоих логах — знаменатель для лога |
| `log_split` | ошибки логов явно разные — разделены |
| `log_held_by_key` | общих блоков нет, логи непохожи, но общий корневой класс или код держит пару |
| `log_held_by_block` | **главная цифра**: без общих блоков ошибки логов разделили бы пару |
| `log_held_merged` | из удержанных (обоих видов) — в одной проблеме |
| `message_split`, `resource_split` | сообщения непохожи; похожи, но разные хосты или локаторы |
| `log_override` (`_resources`, `_merged`) | одинаковый лог склеил разные сообщения (из них — разные ресурсы; в одной проблеме) |
| `log_held_*_problem(s)`, `log_override_*_problem(s)` | только с разметкой: пары одной / разных проблем |

Как читать:
- `log_held_by_block / log_pairs` — как часто общая ошибка выключает gate по логу. По паре
  не отличить «общий фон + разные ошибки» от «общая ошибка + разный фон», поэтому это
  верхняя граница того, что дал бы поиск фона по смыслу.
- `log_held_merged` — сколько из них действительно оказались в одной проблеме (остальные
  разделил другой канал). С разметкой `log_held_different_problems` — сколько удержанных пар
  на самом деле разные проблемы: это и есть цена фона.
- `log_override_different_problems` — сколько раз одинаковый лог склеил разное.
- Для сравнения — dev (`--details`): `background_log_errors` — `log_pairs` 16,
  `log_held_by_block` 6, в одной проблеме 2, разных проблем 3 из 6; `same_assertion_two_npes`
  — `log_held_by_key` 9, все разные проблемы (склейка намеренная); `big_launch` — 0.

Счётчики есть и в базовой линии (`gates`), но `test_eval_quality.py` их не проверяет: у них
нет направления «хуже». После `--write-baseline` diff показывает, какой gate сдвинулся.

## Сигнатуры

Сигнатура кластера (`alla_skill_lib/signature.py`) — точное узнавание записи базы знаний и
повторов в истории. Модели она не показывается, задания от неё не зависят.

| ключ | что значит |
|---|---|
| `signature_shared` | пары кластеров одного прогона с одной сигнатурой: запись, подтверждённая для одного, точно предлагается и другому |
| `signature_shared_wrong` | только с разметкой: из них пары, где ни один тест одного кластера не та же проблема, что тест другого, — ложное точное совпадение |
| `signature_log_clusters` | кластеры, у участников которых минимум два разных лога |
| `signature_log_unstable` | из них те, чья сигнатура меняется, если представителем взять лог другого участника |

- `signature_shared_wrong` — ошибка: кластеризация разделила проблемы, а сигнатура нет.
  `test_eval_quality.py` не даёт ему расти. Метрика записей базы знаний этого не видит: она
  строится только для причин с несколькими группами.
- `signature_log_unstable / signature_log_clusters` — цена лога в сигнатуре: так между
  прогонами одной проблемы меняется лог (фон, посторонние ошибки), и точное узнавание
  пропадает (остаётся `error_example`). Только информирует, направления «хуже» нет.
- Dev (`--details`): `signature_shared` 0 везде. В v7 у `timeouts_two_causes` был 1, у
  разных проблем 1: голый `SocketTimeoutException`, причины только в логах. С v8 лог входит
  и при исключении-симптоме. Меняются с логом участника `same_assertion_two_npes` 1 из 1,
  `log_noise_one_problem` 2 из 2, `background_log_errors` 2 из 2 (общий ассерт: лог в
  сигнатуре), `big_launch` 0 из 40.

## Корпус: dev и holdout

`corpus_dev.py` — сценарии, по которым подбираются пороги, веса и правила; их можно
смотреть сколько угодно. `corpus_holdout.py` — только проверка, что правило, подобранное по
dev, обобщается: другие сервисы, тексты, форматы и сочетания, написанные без знания
алгоритма. `run_eval.py` без `--set` считает только dev.

`big_launch` (320 падений, логи по ~110 КБ) — лимиты памяти, размера задания и время
`prepare`; запускается только с `--heavy` или явным `--case big_launch` (и всегда при
`--write-baseline` и в `test_eval_quality.py`). Поэтому строка «ИТОГО» dev без `--heavy` и с
ним разная: precision 0.972 на 152 тестах и 0.991 на 472 (2026-10-09, после переноса
holdout v1 в dev). Сравнивая с базовой линией или с цифрами в планах, называйте, какая.

Склейки, которые остаются намеренно: `same_assertion_two_npes` (два разных NPE за одним
ассертом — общий корневой класс исключения не даёт логу разделить пару, различает модель по
примерам) и `ui_and_network`: `net-pricing + net-geo` (ошибка разрешения имени хостов не
даёт: сбой DNS бьёт по всем хостам). Контроли против дробления — `log_noise_one_problem`,
`background_log_errors` (разный фон вокруг одной ошибки, та же ошибка за другим
симптомом) и `resources_one_problem`. Одинаковая фоновая ошибка в обоих логах gate по
логу выключает: её не отличить от общей ошибки падения.

### Правило работы с holdout

Holdout перестаёт проверять обобщение не только от прогонов, но и от чтения: агент, который
грепает строку по репозиторию, получает сценарий в контекст. Поэтому учитывается каждый
просмотр, а исчерпанный holdout заменяется.

- **Просмотр** — всё, что сверх «pytest зелёный»: вывод `run_eval.py --set holdout|all`
  (таблица, `--details`, `--json`); запись базовой линии holdout, в том числе только ради
  новой метрики; разбор упавшего `test_eval_quality` по holdout-сценарию; чтение
  `corpus_holdout.py` или раздела `holdout` в `baseline.json` при работе над алгоритмом.
  Зелёный `test_eval_quality` (он проверяет оба набора) — не просмотр.
- **Когда смотреть** — один раз на этап (PR, который меняет кластеризацию, извлечение логов,
  сигнатуру или данные заданий), когда решения по dev уже приняты. Взгляд после правки по
  его итогам — новый просмотр.
- **Нашли ошибку в holdout** — не чинить по нему: воспроизвести класс ошибки новым
  сценарием dev со своими текстами и чинить по dev. Holdout-сценарий, который её показал,
  считается использованным.
- **Журнал** — `holdout_journal.md`: запись на каждый просмотр (дата, коммит, кто, что было
  видно, зачем, повлияло ли на решение) с отпечатками корпуса и раздела `holdout` базовой
  линии (`python tests/eval/journal.py` печатает текущие, метрик не показывает).
  `test_eval_corpus.py` сверяет отпечатки последней записи с текущими: изменить сценарии
  holdout или его базовую линию без записи в журнале нельзя.
- **Базовая линия holdout — отдельным коммитом**: `run_eval.py --write-baseline --set
  holdout` пишет только holdout, `--set dev` — только dev, другой набор остаётся как был.
- **Ротация** — после 3 просмотров, не считая создания, или сразу после решения, принятого
  по результату holdout: весь holdout переносится в dev (тексты уже повлияли на решения), а
  новый пишется по `holdout_brief.md` — автор без доступа к коду кластеризации, сигнатуры,
  правилам и dev-сценариям. До первого прогона нового holdout его сценарии проверяются только
  на правила разметки (тест `evidence` в `test_eval_corpus.py` — дословно ли строка есть в
  данных группы), отпечаток корпуса записывается в журнал, и после прогона сценарии не
  правятся.
- В правилах (`.claude/rules/`), README и планах holdout-сценарии не цитируются — только
  dev.

## Базовая линия

`baseline.json` — метрики каждого сценария (без времени: оно зависит от машины; пути в
заданиях заменены метками, поэтому размер задания переносим). `tests/test_eval_quality.py`
падает, если precision/recall ниже базовой линии больше чем на 0,001 или выросло число
скрытых групп либо потерянных строк. Ухудшение — только осознанно:
`run_eval.py --write-baseline` (набор из `--set`, по умолчанию dev) в том же коммите и
изменение цифр в его сообщении. Улучшение
тоже фиксируйте `--write-baseline`, иначе следующий откат его не заметит.
