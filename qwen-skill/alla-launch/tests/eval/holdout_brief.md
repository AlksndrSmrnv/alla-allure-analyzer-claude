# Задание автору holdout

Процедура ротации holdout (README эталона, «Правило работы с holdout»). Первая часть — для
того, кто готовит и проверяет (оркестратор), вторая — задание автору сценариев целиком.

## Оркестратору

1. Перенести текущие сценарии `corpus_holdout.py` в `corpus_dev.py` без изменений, отдельным
   коммитом с базовой линией dev; запись в журнал.
2. Подготовить автору во временном каталоге (вне репозитория):
   - копию README эталона **без** абзацев с цифрами и именами сценариев корпуса: в «Метриках»
     — без примеров `auth_down_symptoms`/`known_issue_symptoms`; в «Счётчиках gates» и
     «Сигнатурах» — только таблицы ключей; без раздела «Корпус: dev и holdout»;
   - перечень запретов из `corpus_dev.py`: сервисы и домены, хосты и адреса, локаторы, классы
     исключений, форматы логов, фреймворки тестов, тексты сообщений — списком, без кода
     сценариев и без пояснений, что на чём проверяется;
   - диапазон launch id, не занятый dev (dev — `51xx`, `61xx`; следующий — `71xx`, затем
     `81xx`…).
3. Запустить автора (субагент с чистым контекстом или человек) с заданием ниже. Автор не
   видит код кластеризации, сигнатуры, правил и dev-сценариев.
4. Проверить результат только на правила разметки и запреты: `pytest
   tests/test_eval_corpus.py` (структура, детерминизм, `evidence` есть в данных группы) и
   ruff. Правка — только разметки или запретного текста, каждая — в журнал. Вопрос
   «справится ли алгоритм» не обсуждается.
5. Записать отпечаток корпуса в журнал (`python tests/eval/journal.py`) **до** первого
   прогона.
6. Первый прогон: `run_eval.py --write-baseline --set holdout` и `--set holdout --details`.
   Сценарии после этого не правятся. Коммит — сценарии, базовая линия holdout, запись
   журнала «создание»; в сообщении — найденные склейки, дробления, скрытые группы, потери
   доказательств, общие сигнатуры, проблемы повторов и записей базы знаний, как есть.

## Автору

Ты пишешь отложенный корпус (holdout) эталона точности инструмента, который группирует
упавшие автотесты из Allure TestOps в проблемы и готовит для модели задания с данными
падений. Holdout проверяет, обобщаются ли правила, подобранные на другом корпусе (dev),
поэтому он должен быть похож на настоящие прогоны разных команд, а не на то, что, по-твоему,
алгоритм умеет или не умеет. Не пытайся угадать, как он устроен, и не делай сценарии
«лёгкими» или «каверзными» под него.

**Что можно читать:** выданную копию README эталона (форматы разметки и что меряют
метрики), `tests/eval/corpus.py` (построитель `LaunchBuilder`), `tests/test_eval_corpus.py`,
перечень запретов и этот файл. **Нельзя открывать** ничего другого в репозитории — ни
`scripts/`, ни `.claude/`, ни `docs/`, ни `corpus_dev.py`, `baseline.json`, `run_eval.py`,
`metrics.py`, `journal.py`, другие тесты. Не ищи по репозиторию (grep/glob) за пределами
разрешённых файлов. **Запускать можно** только `.venv/bin/python -m pytest
qwen-skill/alla-launch/tests/test_eval_corpus.py` и `.venv/bin/ruff check
qwen-skill/alla-launch/tests/eval`. `run_eval.py` и остальные тесты не запускай: они
покажут, как алгоритм справился, а этого автору знать нельзя.

**Что написать:** `tests/eval/corpus_holdout.py` — функции-сценарии, каждая возвращает
`Case` через `LaunchBuilder(...).build(имя)`, и словарь `CASES` (имя → функция). Тексты — по
публичным форматам логов, сообщений и стеков реальных фреймворков (из твоих знаний):
разные языки и стеки тестов (pytest, Jest/Cypress/WebdriverIO, Go testify, Kotest/AssertJ,
NUnit/xUnit, RSpec…), разные серверные стеки и форматы логов. Ничего из перечня запретов.
Генераторы детерминированы, без случайности и времени выполнения.

**Сценарии** (имена можешь уточнить; на каждый — прогон со своим launch id из выданного
диапазона; в сумме примерно 90–130 активных падений):

| сценарий | что должно быть |
|---|---|
| `log_formats_more` | группа на формат лога (не меньше 7 форматов, по 2 теста), причина видна только в логе: сообщение теста её не называет |
| `log_traps_more` | настоящая ошибка в логе рядом со строками, которые похожи на ошибку, но ею не являются (слово error в URL, полях, тексте INFO; WARN с исключением; обработанное исключение на INFO/DEBUG), ANSI-цвета, CRLF, длинный лог (сотни КБ) с ошибкой в середине, у теста несколько вложений и ошибка не в первом |
| `same_symptom_log_causes` | одинаковые сообщение и шаг у тестов разных проблем, причины различаются только ошибками в логах; среди них — таймаут или обрыв соединения на клиенте при разных причинах на сервере |
| `hosts_and_locators` | один шаг и одна обёртка в стеке; проблемы различаются только хостом недоступного сервиса или локатором элемента (несколько HTTP-клиентов и UI-фреймворков) |
| `shared_assert_background` | общий ассерт (`expected … but was …` в стиле фреймворка) у разных проблем с разными ошибками в логах, вокруг которых фоновые ошибки посторонних сервисов — у части логов одинаковый фон; плюс одна проблема с одной ошибкой и разным фоном |
| `one_problem_noisy` | одна проблема: логи участников различаются id, временем, потоками, номерами строк и посторонними ошибками; та же ошибка за разными симптомами (ассерт, исключение клиента, UI-ожидание) — разные группы с общей `cause`; тест без лога |
| `one_problem_resources` | одна проблема с разными ресурсами в сообщении: реплики (поды) одного сервиса, разные тестовые данные (пользователи, номера заказов), сбой DNS стенда по разным хостам в нескольких форматах, разные элементы страницы, не загрузившейся из-за одной ошибки |
| `signatures_and_kb` | разные проблемы с очень близкими текстами (одинаковый ассерт или исключение-симптом, похожие сообщения) — каждая своя группа; одна проблема, у участников которой разные логи; причина с 2–3 симптомами и общей строкой в логе у всех; причина, у части симптомов которой общей строки нет; посторонняя проблема с тем же ассертом |
| `retries_more` | повторы (hidden-попытки): прошёл после повтора; все попытки с той же ошибкой; попытки с другой ошибкой; параметризованный тест; смена окружения между попытками; ошибка попытки только в `add_detail`; больше 5 попыток; попытки без полей связи. Связь — через поля TestOps `historyId`, `historyKey`, `testCaseId` + `parameters` + `environment` (в `extra`), в том числе без `historyId`; разметка — `expect_attempts`/`expect_passed_after_retry` |
| `sparse_data` | падения без сообщения, трейса и лога; только с шагом; только с логом; muted и hidden падения (в группы не входят); passed рядом |

**Разметка** (README, «Разметка `labels.json`»):
- группа — один симптом: одинаковое по смыслу проявление (сообщение, шаг) одной причины;
  разные симптомы одной причины — разные группы с общей `cause`; неизвестная причина —
  `cause=None`;
- `category` — `тест|приложение|окружение|данные|неизвестно`;
- `evidence` — строки, без которых модель не назовёт причину; дословно из данных теста
  группы (сообщение, трейс, лог), короткие и уникальные для причины;
- каждое активное падение — ровно в одной группе (`add_failure`); hidden, muted и passed —
  через `add_result`.

**Отчёт:** по каждому сценарию — что он проверяет, какие группы и почему размечены так;
сомнения в разметке; список всех файлов, которые ты открывал, и команд, которые запускал.
