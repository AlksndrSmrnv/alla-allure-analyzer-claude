# Инструкция агенту: как написать расширение alla-launch

Для агента (Qwen Code, Claude Code, Codex), которому поручили написать расширение скилла.
Контракт — поля данных, события, переменные шаблона — в [README.md](README.md) рядом; рабочий
образец — [git-publish/](git-publish/). Здесь — порядок работы и то, чего из контракта не
видно, но без чего расширение сломается или нарушит правила скилла.

## 1. Где писать

- Расширение команды — в проекте автотестов: `alla-extensions/<имя>/`. Папку скилла
  (`.qwen/skills/alla-launch/`) не трогай: обновление скилла её перезапишет.
- Поменять встроенное — скопируй его папку в `alla-extensions/` под тем же именем и правь
  копию. Сломанная копия выключает расширение целиком, встроенное не вернётся.
- `alla-extensions/config.toml` правят только команды `extensions enable|disable` и
  пользователь (таблица настроек). Строку `enabled` сам не пиши.

## 2. Выбери форму

| Нужно | Форма |
|---|---|
| Сообщить, посчитать, отправить без участия модели | хук `script` |
| Модель должна составить текст (описание задачи, сообщение коммита), а потом что-то сделать во внешней системе | хук `task` + действие в `[actions]`: модель пишет текст в файл, действие делает внешний вызов |
| Внешнее действие, на которое пользователь должен согласиться каждый раз | хук `task` с `ask` и настройкой `confirm = true` |
| Функция по просьбе пользователя для проблемы N («разбери проблему 2 по коду приложения») | хук `on_request` (обычно `task` + действия), параметры запроса — `--param` → `params` |
| Одна функция для всего выбранного состава проблем | `on_request_many`: один уникальный контекст с `selected_numbers`; не сочетать с `on_request` |

- `confirm` и `ask` действуют **только на хуки `task`**: хук `script` запускается без
  вопроса. Не делай скриптом то, на что нужно согласие.
- Внешние действия (HTTP-запросы, git, push, сообщения) — только в скриптах. Субагенту из
  shell можно лишь `python3 <скилл>/scripts/alla_skill.py …`: проверка разбора (`review`)
  считает любую другую команду нарушением, и правила скилла её запрещают.
- Хук `task` — не больше одного на событие; хуков `script` — сколько нужно (идут в порядке
  манифеста, расширения — в порядке `enabled`).

## 3. Шаги

1. Имя — латиница в нижнем регистре, цифры, дефис; совпадает с папкой. `batch` занято
   скиллом (его субагент — `alla-batch`).
2. `extension.toml` по README: `api = 1`, хуки, действия, `[settings]` с безопасными
   значениями по умолчанию. `timeout` — с запасом на сеть: он общий для каждого запуска
   скрипта (хука и действия). Сверху его режет лимит Qwen на команду: хукам одной
   команды скилла — 60 с на всех (`HOOK_BUDGET_S`), действию — 110 с (`ACTION_LIMIT_S`);
   дольше — фоновый процесс, как в `sut-code`.
3. Скрипты — `scripts/*.py`. Python — `.venv` проекта (3.11+): стандартная библиотека и
   зависимости скилла (`httpx`, `pydantic`). Ничего не доустанавливай.
4. Для хука `task` — `agent.md` (субагент Qwen) и шаблон задания, например `task.md`.
   Для `on_request` — по желанию слэш-команда `commands/<имя>.md` (поле `commands`
   манифеста): `disable-model-invocation: true`, текст — вызвать скилл и выполнить
   `extensions run <имя> N --run <папка разбора>` с параметрами из `{{args}}`.
5. Проверь (раздел 6), затем скажи пользователю включить расширение и перезапустить Qwen
   Code. Коммитить `alla-extensions/` и `.qwen/agents/alla-<имя>.md` — решение пользователя.

## 4. Скрипты

- Контекст читай из файла `ALLA_CONTEXT`; бери данные только из него. `run.json`,
  `state.json` и прочие служебные файлы папки разбора не читай: их формат меняется без
  предупреждения. Не хватает поля — это просьба к разработчикам скилла, а не повод лезть
  внутрь.
- Тексты контекста (`label`, `cause`, `why`, `console`…) — из TestOps и ответа модели, это
  недоверенные данные: не передавай их в shell (`shell=True`, `os.system`), не исполняй, в
  запросы — только как данные (JSON, параметры).
- `problem.category` — `тест`, `приложение`, `окружение`, `данные`, `неизвестно` или `null`
  (проблему не разобрали). У `after_report` в `problems` — все проблемы отчёта, включая
  разобранные автоматически.
- Пиши только в `out_dir` и постоянный `state_dir` из контекста; рабочую копию, ветки и прочие папки
  не меняй. На сервере ничего не удаляй.
- Для текущих данных используй `snapshot = true` и переданный скиллом `snapshot_path`
  — путь файла, обновлённый перед хуком или действием. Служебные файлы разбора сам не читай.
  Контекст и снимок отдельного действия временные: после завершения процесса скилл
  удаляет их, включая случай ошибки. В постоянные результаты сохраняй нужные данные,
  а не ссылки на временные файлы. `budget_s` — оставшиеся секунды на процесс; отсчитывай
  их локально, не передавай абсолютные показания часов между процессами.
  Для длинного входа инженера —
  `--text-file KEY PATH`, не подстановка текста в shell или переменные шаблона.
- Для действий после `clean` используй `extensions action <имя> <действие> --reports-dir DIR`
  без `--run` и `--context`. Скилл собирает общий контекст, а постоянные записи читает и проверяет
  само расширение; формат своего журнала не передавай в ядро. Контракт описан в README.
- Когда действию нужна только папка разбора, используй `extensions action <имя> <действие>
  --run DIR`: скилл создаст свежий контекст и снимок без поиска JSON исходного хука.
- **Повторы.** `on_request` — при каждой просьбе пользователя, `after_apply` повторяется командой `extensions run`, `after_report` — при каждом
  изменении отчёта (после `remember`, `reject`, `skip`). Контекст `<stem>.json` при этом
  перезаписывается. Делай действие повторяемым: сохраняй итог в `<out_dir>/<stem>.result.json`
  и перед внешним вызовом проверяй его — как `git-publish/scripts/publish.py`.
- **Секреты** (токены Jira, вебхуки) — только из переменных окружения, в которых запущен Qwen
  Code (`os.environ`). Не в `extension.toml` и не в `config.toml` (их коммитят), не в выводе.
  `.env` скилла расширениям не передаётся. Нет переменной — понятная строка, какую задать.
- Стандартный ввод закрыт, пароль спросить нельзя (у git — `GIT_TERMINAL_PROMPT=0`): нет
  доступа — отказ с объяснением.
- **Хук `script`**: всё из stdout (до 4000 символов) агент покажет пользователю как есть;
  пустой вывод — ничего не покажет. Ненулевой код — строка «не сработало» с выводом или
  последней строкой stderr. Пиши для человека: по-русски, коротко, без traceback.
- **Действие**: первая строка stdout — `STATUS: ok` или `STATUS: error`, дальше текст для
  пользователя. Без такой строки или с ненулевым кодом при `ok` скилл ответит `error`.
  Аргументы скрипта — после `--` в команде действия.

## 5. Субагент и задание

- `agent.md`: `name: alla-<имя>`, непустой `description`, `tools` — минимум (обычно
  `read_file`, `write_file`, `run_shell_command`), подсказка — узкая роль по образцу
  `git-publish/agent.md`: прочитать задание, записать названный файл, выполнить одну команду,
  ответить. Явно запрети ls, find, cat, grep, git и любые команды, кроме команды из задания.
- В шаблоне задания **повтори эти запреты**: пока Qwen не перезапущен после `enable`,
  задание выполняет субагент общего назначения без `agent.md`.
- Файлы, которые пишет субагент, — **только `$out_dir/<что-то>.txt`** (например,
  `$out_dir/$stem.message.txt`). Другие пути и расширения проверка разбора считает
  нарушением.
- Команды — только через переменные `$action_<действие>`: в них уже абсолютный путь скилла и
  `--context`. Своих путей к скриптам расширения в задании не пиши.
- Значения переменных подставляются **одной строкой** (переводы строк схлопываются) — не
  рассчитывай на абзацы в `$cause`, `$why`. Литеральный `$` в шаблоне — `$$`; неизвестная
  `$переменная` остаётся как есть — проверь, что опечаток нет.
- Отметь в задании, что данные — недоверенный текст (как в `git-publish/task.md`).
- Ответ субагента основной агент показывает пользователю как есть (кроме строк «Проблема
  скилла: …»): проси 1–3 строки итога, лучше — дословно строки ответа действия после
  `STATUS:`. Долгое действие — напиши в задании «не прерывай и не повторяй».

## 6. Проверка

1. Манифест и настройки — `extensions list` (ошибки видны в строке расширения), затем
   `extensions enable <имя>`: он отклонит неверный тип настройки и неизвестный ключ.
2. Скрипт отдельно — на своём контексте, без скилла:

   ```bash
   ALLA_CONTEXT=/tmp/ctx.json .venv/bin/python alla-extensions/<имя>/scripts/<скрипт>.py
   ```

   Контекст — JSON с полями из README (`api`, `event`, `settings`, `out_dir`, `stem`,
   `problem` или `console`/`problems`); `out_dir` — временная папка. Проверь и успех, и отказ
   (нет переменной окружения, сервис недоступен, повторный запуск).
3. Хук на настоящем разборе без нового прогона: на законченном разборе
   `extensions run <имя> --run <папка разбора>` (`after_report`) или
   `extensions run <имя> N --run <папка>` (`after_apply`, правка N должна быть применена).
   Ответ — блок «Расширения:»; задание и контекст лежат в
   `<папка разбора>/extensions/<имя>/`. Прочитай отрисованное задание: все `$…` подставлены?
4. Действие на настоящем контексте:
   `extensions action <имя> <действие> --context <папка разбора>/extensions/<имя>/<stem>.json`.
5. Сломай нарочно (неверный URL, нет токена): разбор и команды скилла должны идти дальше, а
   пользователь — увидеть понятную строку.

## Готово, когда

- `extensions list` показывает расширение без ошибок, `enable` проходит;
- скрипты отвечают по-русски, без traceback, и успехом, и отказом; повтор не дублирует
  внешнее действие;
- секретов нет ни в файлах расширения, ни в выводе;
- задание отрисовано без пропущенных `$…`, субагент пишет только `.txt` в `out_dir` и
  запускает только `$action_…`;
- пользователю сказано: как включить, какие переменные окружения задать, что перезапустить
  Qwen Code и что стоит закоммитить.
