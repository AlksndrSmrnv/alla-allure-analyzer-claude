# Тикеты команде

`tickets` предлагает задачи после разбора, готовит полный просмотр и по одобрению
инженера создаёт тикет или добавляет доказательства в существующий. Расширение выключено
по умолчанию. Название и API настоящего трекера скиллу не нужны: подключение изолировано
в отдельной программе-адаптере.

## Включение и маршруты

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions enable tickets
```

После включения перезапусти сеанс Qwen Code. Появится `/alla:ticket N [N…]`.
Настройки команды — в `alla-extensions/config.toml`:

```toml
[tickets]
team_application = "backend"
team_test = "qa"
team_environment = "platform"
team_data = "qa"
team_unknown = "qa"
adapter_command = []
adapter_env = []
adapter_timeout = 25
```

Пустой `adapter_command` означает работу с черновиками: поиск помечается неподключённым,
внешняя отправка запрещена. Пустой маршрут заполняется явным `team_N` от инженера.
Все настройки имеют обычные типы контракта расширений: строки, числа, логические значения
и списки строк. Словарь маршрутов не требуется.

## Работа инженера

После отчёта скрипт показывает подходящие проблемы. Готовая правка автотеста исключается
из автоматических предложений, но не мешает явно запросить по ней тикет.

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions run tickets 2 5 --run DIR
```

Вся команда обрабатывается одним событием `on_request_many`. Перечисление `2 5` само по себе
не означает один тикет: состав определяется сохранёнными связями разбора. Явное решение
инженера об одной причине передаётся так:

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions run tickets 2 5 --run DIR --param group=2,5
```

Неназванные проблемы не добавляются. Полные пересекающиеся основания с разными составами
вызывают отказ до фиксации версий. Например, `group=2,5` конфликтует с действующей связью
`2,5,7`; молчаливого обрезания или транзитивного объединения нет. Явная группа с
отклонённым или неназванным номером также отклоняется целиком.

Решение инженера хранит `run_uid` и проекцию диагнозов. Если диагноз изменился, старое
решение остаётся в истории, но больше не применяется; повторный `group` создаёт новое.
Подтверждение через `sut-code` не удаляет действующее самостоятельное решение. Отозвать
его можно отдельным запросом даже во время конфликта:

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions run tickets --run DIR --param revoke_group=DECISION_UUID
```

Отзыв не создаёт тикетов и не отменяет отправки с неопределённым результатом. После
автоматического отбора годные части сохранённой группы не пропадают: если от `2,5`
осталась только 2, показывается одиночный кандидат 2.

Для каждого получившегося тикета N — минимальный номер его проблем. Параметры инженера:

| Параметр | Назначение |
|---|---|
| `team_N` | Команда вместо маршрута категории |
| `kind_N` | `bug`, `task` или `investigation` |
| `operation_N` | `create` или `link` |
| `target_N` | Идентификатор существующего тикета из текущего поиска; только для `link` |
| `question_N`, `check_N` | Вопрос и следующая проверка инженера; только для исследования |

Вопрос и проверка передаются файлами, а не многострочным текстом shell. Основной агент
записывает их дословно в отдельные `.txt` внутри `DIR/extensions/tickets/`, затем передаёт
пути через `--text-file question_N PATH` и `--text-file check_N PATH`. Скилл читает UTF-8
целиком, сохраняет переводы строк и отступы; предел каждого значения — 16 000 символов,
превышение вызывает ошибку без усечения. Источником вопроса служит реплика инженера.

Подготовка выполняет `plan`, затем по одному `draft --unit N` и `show --request UUID`.
Субагент на этом заканчивает работу. Основной агент читает и передаёт инженеру **полный**
файл просмотра, включая текст длиннее 4000 символов, и останавливается до ответа.
После одобрения он выполняет возвращённую `submit --request UUID --shown HASH`.

## Зафиксированные данные и повторы

Модель не заполняет рядом с проверенным текстом альтернативные поля доказательств.
Скрипт сам берёт тесты и ссылки TestOps, проверяет цитаты по номеру проблемы и источнику,
строит фактические разделы и создаёт Markdown/JSON. Проверка подтверждает происхождение
цитаты; обоснованность диагноза оценивает инженер.

Версия хранит точные байты адаптера, состав, диагнозы и источники **своих** проблем,
основание группировки, управляющие параметры, эффективные настройки, конечного адресата,
операцию, цель и нормализованный поиск. Изменение посторонней проблемы не мешает отправке.
В поиск входят только `id`, `url`, `state`, `reason`, без времени, ранга и порядка ответа.
Ошибка поиска запрещает фиксацию. Объявленный неподдерживаемый поиск допускается для
`create` с явной пометкой, но не для `link`.

UUID запроса попадает в журнал только вместе с успешно проверенной версией. Если адаптеру
он нужен в `prepare`, предварительно используется только значение в памяти. Ошибка
адресата, поиска или цели не оставляет запроса и блокировки.

Перед `submit` заново проверяются проекция, настройки, `prepare` и поиск. Изменения требуют
нового просмотра. Скрипт гарантирует соответствие отправляемых байтов версии; сам хеш
не доказывает показ и человеческое одобрение — это отдельная проверка поведения Qwen.

Один вызов действия делает максимум один `create` или `link`; перед ним сохраняется
`sending`. Таймаут, обрыв или непонятный ответ оставляют неопределённый результат.
Повтор не создаёт второй запрос, а выполняет `lookup`. Новый состав или адресат не
обходит блокировку пересекающихся проблем того же разбора.

Журнал находится в пространстве проекта внутри фактического каталога отчётов, рядом
с папками разборов. Он сохраняет запрос, операцию, версии, состояние и ссылку трекера
после `clean`. `run_uid` — отдельный сохранённый UUID, а не имя папки или номер launch.
Сверка после удаления папки разбора:

```bash
python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions reconcile tickets --reports-dir REPORTS --request-id UUID
```

Скилл сам находит запись и строит контекст; путь к контексту здесь не принимается.
`reconcile` выполняет только `lookup` и запись итога. Найденная операция завершает запрос.
Достоверное отсутствие разрешает отдельный `submit` той же версии с тем же UUID после
проверки актуальности. Неизвестный результат сохраняет блокировку.

## Подключение своего инструмента

Скопируй `adapters/template.py` в `alla-extensions/_adapters/company_tickets.py` и реализуй
операции ниже. Папки с `_` не считаются самостоятельными расширениями.

```toml
[tickets]
adapter_command = [".venv/bin/python", "alla-extensions/_adapters/company_tickets.py"]
adapter_env = ["TRACKER_TOKEN", "HTTPS_PROXY", "SSL_CERT_FILE"]
adapter_timeout = 25
```

Первый элемент — явный путь от корня проекта к исполняемому файлу. Остальные элементы —
его аргументы; cwd — корень проекта. Shell и поиск программы по `PATH` не используются.
Адаптер получает только разрешённые переменные и `PYTHONIOENCODING=utf-8`.
Переменные `ALLURE_*`, `ALLA_*`, `QWEN_*` и `PATH` передавать нельзя. Секреты не входят в
манифест, конфигурацию, нагрузку, просмотр и ответы; аутентификацию выполняет транспорт
адаптера. Настройки частного инструмента можно передать собственными аргументами файла.

На stdin приходит один JSON-объект UTF-8, stdout содержит только один JSON-ответ.
`STATUS:` — формат скриптов расширения, не адаптера. Диагностика адаптера идёт в stderr,
без секретов. Сбой не выдаётся за пустой поиск или достоверное отсутствие.

## Протокол адаптера, `api = 1`

Каждый запрос содержит `api`, `operation` и локальный `request_id`. Адаптер не назначает
и не заменяет этот идентификатор. Ответ содержит `api = 1`; отказ — поле `error` и
ненулевой код процесса. Ошибка в мутации считается неопределённым результатом.

| Операция | Дополнительный вход | Успешный ответ |
|---|---|---|
| `prepare` | `ticket`, `action`, `target_id` | `scope`, `capabilities`, `payload` |
| `search` | `scope`, `ticket`, `action`, `target_id` | `matches` |
| `create` / `link` | `scope`, `payload` | `outcome: "found"`, `ticket: {id,url,state}` |
| `lookup` | `scope`, исходный `action` | `outcome: "found" / "absent" / "unknown"`, при `found` — `ticket` |

`ticket` — нейтральный документ: `kind`, `team`, `title`, `description`, `problems`, `tests`,
`evidence`, `launch_id`, `run_uid`; для исследования ещё `question`, `check`.
`evidence` содержит проверенные `problem`, `source_id`, `quote`, `title`.
Внешние типы тикета, обязательные поля, команды, API и формат описания преобразует адаптер.

`scope` имеет ровно два строковых поля: `site`, `project_or_queue`. Это устойчивые сайт
или экземпляр и полный проект или очередь. Сеанс, время и UUID запроса в область не входят.
Для `lookup` сравнивается эта область, а не весь новый ответ `prepare`.

`capabilities` содержит логические `search` и `authoritative_absence`. Последнее по
умолчанию считается недоступным. `payload` — base64 конечных байтов UTF-8 для просмотра
и отправки. `prepare` чистый: не создаёт и не резервирует объекты, не назначает внешние
номера. При тех же входных данных возвращает те же байты; нужные дату или nonce заранее
фиксирует вызывающий скрипт. `create` и `link` отправляют сохранённый payload без повторной
сборки и используют `request_id` для идемпотентности.

Совпадение поиска: `{ "id": "TASK-17", "url": "https://tracker/tasks/17", "state": "open",
"reason": "Та же операция и исключение в журнале" }`. Поиск ограничивается реальной
областью проекта/очереди. Результаты — кандидаты, окончательное решение принимает инженер.

`link` выполняет внешнее добавление связи с TestOps и доказательств в выбранный тикет.
Локальная отметка журнала успехом не считается. Если функция недоступна, адаптер должен
вернуть отказ; интерфейс не переходит в `linked`.

`lookup: absent` принимается только при объявленной `authoritative_absence` для той же
области. Это гарантия, что операция не выполнена и не завершится позднее. Задержка
индексации, пустой обычный поиск, недоступность сервиса или отсутствие гарантии дают
`unknown`. Даже при достоверном `absent` сама сверка ничего не отправляет.

На POSIX процесс адаптера наследует дескриптор блокировки журнала: если процесс скилла
завершится, сверка дождётся живого адаптера, включая время до первого обращения к трекеру.
Если адаптер запускает локальную программу для изменения, он должен дождаться её и
передать ей этот дескриптор, например через `close_fds=False` при синхронном subprocess.
Отсоединять изменяющую программу нельзя. Для удалённых асинхронных заданий надёжное
отсутствие обеспечивает сам инструмент; иначе capability должна оставаться false.

## Демонстрация и проверка адаптера

Демо — локальная SQLite-база без сети. Подключается только явно:

```toml
[tickets]
adapter_command = [".venv/bin/python", ".qwen/skills/alla-launch/extensions/tickets/adapters/demo.py", "--db", "alla-reports/.tickets-demo.sqlite", "--project", "DEMO"]
team_application = "backend"
team_test = "qa"
team_environment = "platform"
team_data = "qa"
team_unknown = "qa"
```

Идентификаторы `DEMO-N` и ссылки `demo://…` явно демонстрационные. `prepare` не создаёт
даже файл БД. Поиск возвращает все тикеты этой демонстрационной очереди, без оценки
сходства. `link` добавляет зафиксированное обновление к существующему тикету.

`--lose-response-once` завершает процесс с кодом 75 после первого успешного commit
каждого нового запроса, не возвращая ответ. `lookup` после этого находит результат;
повторная доставка того же UUID и байтов возвращает тот же тикет. Запись отсутствующего
запроса проверяется под той же сериализацией SQLite, что и мутации. Демо объявляет
`authoritative_absence`; незавершённая транзакция не выдаётся за отсутствие.

Контрактные проверки запускают настоящие процессы адаптера: чистоту и повторяемость
`prepare`, сохранение байтов, отсутствие без вызова, потерю ответа после commit,
идемпотентность, внешнее связывание, стабильность области и ожидание незавершённой записи.
Настоящий пользовательский адаптер нужно проверить теми же сценариями на тестовом
проекте своего трекера. Демонстрация не подтверждает работу неизвестного API.
