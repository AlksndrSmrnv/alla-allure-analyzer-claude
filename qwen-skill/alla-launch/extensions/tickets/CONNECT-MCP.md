# Инструкция агенту: подключить MCP трекера, чтобы Алла заводила дефекты и тикеты

Для агента (Qwen Code, Claude Code, Codex), которому инженер сказал «подключи наш Jira /
GitLab / YouTrack к Алле». Что делает `tickets` и как устроен контракт — в [README.md](README.md)
рядом; общая инструкция по расширениям — [../AUTHORING.md](../AUTHORING.md). Здесь — порядок
работы, вопросы инженеру, проверка и разбор ошибок.

Пути в командах даны для Qwen Code: скилл лежит в `.qwen/skills/alla-launch/`, Python — в
`.venv/bin/python` корня проекта. Скилл установлен в другом месте или проект на Windows —
подставь свои пути (`python3 <скилл>/scripts/alla_skill.py …`). Все команды запускай из
корня проекта автотестов.

## 1. Выбери путь

| У трекера | Что делать |
|---|---|
| есть MCP-сервер, который запускается командой (stdio) | встроенный `adapters/mcp.py` + файл `alla-extensions/mcp-tracker.toml` — **эта инструкция** |
| MCP только удалённый (HTTP, OAuth) | то же, а в `[server] command` — локальный мост (например `mcp-remote`); спроси инженера, как он у них запускается, и пусть он один раз войдёт вручную: адаптер интерактивно авторизоваться не умеет |
| MCP нет или нужна логика, которой нет в шаблонах (вложения файлов, значение поля, вычисляемое из нескольких, число из подстановки, не Markdown) | свой адаптер по `adapters/template.py`: раздел «Подключение своего инструмента» в [README.md](README.md) |
| нужна функция, не связанная с тикетами (чат, git, отчёт) | новое расширение по [AUTHORING.md](../AUTHORING.md) |

Не пиши своё расширение «завести дефект»: просмотр перед отправкой, защита от дублей,
состояния `sending/unknown`, группировка проблем и сверка уже есть в `tickets`. MCP-клиент в
собственных скриптах тоже не пиши — защит `tickets` у него не будет.

## 2. Железные правила

- Инструменты MCP трекера, которые **пишут** (создать, добавить комментарий), вызывает только
  `adapters/mcp.py` из скрипта `tickets`, после полного просмотра и «да» инженера. Ты, субагент и
  разбор их не вызываете ни при каких обстоятельствах, даже если у тебя самого подключён этот
  MCP и инженер сказал «подключи». Свой доступ к MCP годится только для чтения: узнать имена
  инструментов и формат ответа поиска.
- Токен и пароль — только в переменных окружения, в которых запущен Qwen Code; в
  `adapter_env` перечисляются **имена** переменных. В `mcp-tracker.toml`, `config.toml`,
  выводе и сообщениях токена нет. Команду запуска сервера можно взять из настроек MCP
  (`.qwen/settings.json`, `.mcp.json`), но только саму команду и аргументы без секретов: ключи
  вроде `--token …` и блок `env` не копируй — секреты идут через `adapter_env`.
- Код скилла и `adapters/` не правь (обновление скилла перезапишет). Не хватает возможности —
  это просьба разработчикам скилла, а не повод править `mcp.py` или читать `state.json`.
- **Ошибка при настоящей отправке необратима.** Перед записью скрипт сохраняет запрос как
  `sending`; любая ошибка адаптера после этого (неверный проект или тип, права токена,
  таймаут) переводит его в `unknown`, а адаптер `absent` не возвращает никогда. Такой запрос не
  отменить: проблемы этого разбора остаются заблокированными. Опечатки в именах инструментов
  до этого не доходят: при настроенном `[search]` их ловят `draft` и `submit` (адаптер при поиске
  сверяет с сервером имена **всех** инструментов файла, а `submit` вызывает поиск до записи
  `sending`); без `[search]` их ловит только проба `--check` раздела 6. Остальное проверяй
  пробами без записи и только потом отправляй. Ломать нарочно через `submit` нельзя.
- Пробуй только на тестовом проекте трекера. Для настоящей отправки держи **запасную проблему**
  (или новый `prepare <launch> --fresh`, если блокировка уже случилась: она действует в
  пределах одного разбора).
- `mcp-tracker.toml` — в `alla-extensions/` (общий для команды, коммитится).

## 3. Что спросить у инженера до начала

Не угадывай: любое неизвестное — вопрос.

1. Команда запуска MCP-сервера и как он ставится (`npx -y …`, `uvx …`, бинарь). Нужны ли `node`
   или `uvx` — тогда их каталоги пойдут в `extra_path`.
2. Имена переменных окружения с токеном и адресом (и нужен ли серверу `HOME`, `HTTPS_PROXY`,
   `SSL_CERT_FILE`).
3. Какие команды (`team_application`, `team_test`, `team_environment`, `team_data`,
   `team_unknown`) в какой проект или очередь трекера заводят тикеты.
4. Типы тикета: что в трекере соответствует `bug`, `task`, `investigation`.
5. Устойчивый адрес трекера (`site`) для ссылок на тикеты.
6. **Тестовый проект** трекера для проверки.
7. Инструменты сервера: создать тикет, добавить комментарий (для «добавить доказательства в
   существующий»), искать тикеты. Для каждого — имя, аргументы и **пример ответа**. Если MCP
   подключён у тебя — вызови поиск на тестовом проекте и посмотри ответ (только чтение). Нет
   доступа — попроси инженера вставить пример. Формат ответа не придумывай: от него зависят
   `id_path`, `items_path`.
8. **Готовый разбор** для проверки: запуск на тестовом наборе, где есть упавшие тесты. Нет —
   попроси инженера провести разбор (`/alla:run <запуск>`) до раздела 6.

## 4. Шаги

1. Включить расширение (в Qwen Code — `/alla:extensions enable tickets`):

   ```bash
   python3 .qwen/skills/alla-launch/scripts/alla_skill.py extensions enable tickets
   ```

2. Скопировать [adapters/mcp-tracker.example.toml](adapters/mcp-tracker.example.toml) в
   `alla-extensions/mcp-tracker.toml` и заполнить по ответам инженера. **Начни с минимума**
   (только `site`, `[server]`, `[projects]`, `[kinds]`, `[create]`), когда он заработает —
   добавляй `[link]`, `[search]`, `[lookup]`, `[lookup_link]` по одному. Для проверки добавь в
   `[projects]` временный ключ `test = "<тестовый проект>"`, а если ссылка на тикет строится от
   `site` (`url_template` с `{site}` и без `url_path`, как во втором примере раздела 5), — временно
   замени `site` и проекты на тестовые: иначе ссылка в журнале поведёт в боевой проект. После
   проверки верни прежнее (раздел 6, шаг 9).
3. Подключить адаптер в `alla-extensions/config.toml`:

   ```toml
   [tickets]
   adapter_command = [".venv/bin/python", ".qwen/skills/alla-launch/extensions/tickets/adapters/mcp.py", "--config", "alla-extensions/mcp-tracker.toml"]
   adapter_env = ["TRACKER_TOKEN", "HOME"]
   adapter_timeout = 25
   team_application = "backend"
   team_test = "qa"
   team_environment = "backend"
   team_data = "qa"
   team_unknown = "qa"
   ```

   - Значения `team_*` — ключи из `[projects]` файла `mcp-tracker.toml`. Команды, которой
     нет в `[projects]`, адаптер откажет.
   - `adapter_timeout` — от 1 до 30 секунд и **больше** `[server] timeout` (иначе скилл
     оборвёт адаптер раньше, чем тот разберётся с сервером).
   - Пути — от корня проекта; переменные `PATH`, `ALLURE_*`, `ALLA_*`, `QWEN_*` в `adapter_env`
     нельзя. Секреты в `config.toml` не пиши.
   - Файл `config.toml` правят пользователь и команды `extensions enable|disable`; строку
     `enabled` сам не меняй.
4. Сказать инженеру перезапустить Qwen Code: появится `/alla:ticket N [N…]`. Пробы раздела 6
   и `extensions run tickets …` перезапуска не требуют: он нужен только слэш-команде.

## 5. Как описать инструменты в `mcp-tracker.toml`

Подстановки в `arguments`: `{title}`, `{title_q}` (заголовок для вставки в кавычки запроса
поиска), `{body}`, `{team}`, `{project}`, `{tracker_kind}`, `{target_id}`, `{request_id}`,
`{launch_id}`, `{site}`; для `lookup` и `lookup_link` — только `{project}`, `{request_id}`,
`{site}`; в `url_template` — только `{id}` и `{site}`. Неизвестное имя — ошибка. Подстановка
всегда даёт строку, в том числе внутри списка (`labels = ["{tracker_kind}"]`); число или
булево можно писать только постоянным значением (`priority = 3`). Нужно число из подстановки
(скажем, числовой `project_id` из `[projects]`) — шаблонами это не выразить, нужен свой адаптер.

- **`{body}` обязателен** в `[create]` и `[link]`. Это текст тикета с последней строкой
  `alla-request: <UUID>`; по ней `lookup` находит тикет после обрыва связи. Положи `{body}` в
  поле описания или текста комментария целиком, не режь и не меняй.
- **Идентификатор созданного тикета**: ответ инструмента — JSON → `id_path = "key"` (путь с
  точками, число — элемент списка: `"result.0.id"`); текст вроде «Created issue #123» →
  `id_regex = 'issue #(\d+)'` (первая группа или всё совпадение). Ссылка — `url_path` из
  ответа или `url_template` с `{id}`/`{site}`.
- **`[search]`** нужен для «похожие тикеты» и выбора `target` у `link`. Ответ должен быть
  JSON-списком (`items_path` — где он; `id_path`, `state_path` внутри элемента). Если ответ —
  обычный текст, `[search]` не подключай: поиск будет «не подключён», создание останется
  доступным, а `link` — нет. Текст «ничего не найдено» вместо пустого списка —
  `empty_regex`.
- **`[lookup]` / `[lookup_link]`** — поиск тикета по метке запроса (в описании тикета и в
  тексте комментария). `verify_path` — поле найденного элемента, в котором метка должна
  быть: полнотекстовый поиск трекеров нечёткий, а индекс отстаёт, поэтому пустой ответ ничего
  не доказывает. **Поле `verify_path` должно приходить в ответе поиска** (в описании тикета
  его часто нет в кратком виде) — иначе совпадения отбрасываются, `lookup` всегда `unknown` и
  защита от дублей молча не работает; проверяет это проба 7. Без этих разделов после обрыва
  связи запрос остаётся `unknown`, и тикет ищет инженер. Адаптер `absent` не возвращает
  никогда: это не настройка, а свойство MCP.
- Язык запроса поиска (JQL, GitLab-запрос, YQL) бери из документации трекера, подставляя
  `{project}` и `{title_q}`/`{request_id}`.

Примеры ниже — иллюстрация: имена инструментов и поля ответов у каждого MCP-сервера свои.

Минимум (создание, ответ — JSON, поля вложены, как у Jira-подобных серверов):

<!-- example: mcp-tracker -->
```toml
site = "https://tracker.company"

[server]
command = ["npx", "-y", "some-tracker-mcp"]
timeout = 20

[projects]
backend = "BACK"
qa = "QA"
test = "TEST"          # временно, для проверки; перед коммитом убрать

[kinds]
bug = "Bug"
task = "Task"
investigation = "Task"

[create]
tool = "create_issue"
arguments = { fields = { project = { key = "{project}" }, issuetype = { name = "{tracker_kind}" }, summary = "{title}", description = "{body}" } }
[create.result]
id_path = "key"
url_template = "https://tracker.company/browse/{id}"
```

Сервер отвечает текстом, поиск вернуть список не может — создание без поиска и без `lookup`.
Ссылка собирается из `{id}` и `{site}` (`{project}` в `url_template` недоступен), поэтому `site`
указывает на проект, а обе команды ведут в один. Из этого следует правило проверки: ссылка в
журнале строится от `site`, и тикет, созданный в другом проекте, получил бы ссылку на боевой.
Для проверки не добавляй второй проект, а временно замени `site` и **все** проекты, включая
ключ `test`, на тестовые (команды раздела 6 используют команду `test`):

<!-- example: mcp-tracker -->
```toml
site = "https://git.company/team/autotests"

[server]
command = ["/opt/mcp/gitlab-mcp", "--stdio"]
timeout = 20

[projects]
backend = "team/autotests"
qa = "team/autotests"
test = "team/autotests"   # для проверки: тестовый проект, как и site

[create]
tool = "create_issue"
arguments = { project_path = "{project}", title = "{title}", description = "{body}", labels = "{tracker_kind}" }
[create.result]
id_regex = 'issues/(\d+)'
url_template = "{site}/-/issues/{id}"
```

Полный пример со всеми разделами —
[adapters/mcp-tracker.example.toml](adapters/mcp-tracker.example.toml).

## 6. Проверка — от безопасной к настоящей

Пробы 2, 4 и 7 запускают адаптер напрямую: он читает JSON со stdin и печатает один JSON-ответ;
при ошибке — `{"api":1,"error":"…"}` и код 1. `request_id` в пробах — любой канонический
UUID. Все пробы идут в **тестовый** проект: команда `test` из `[projects]` (раздел 4, шаг 2).

В настоящем запуске адаптер получает только переменные из `adapter_env`; повтори это в
пробах через `env -i`, иначе недостающую переменную не заметишь.

1. **`extensions list`** — расширение `tickets` включено, ошибок в строке нет.
2. **`prepare` — сервер не запускается**, видны ошибки файла и итоговый текст:

   ```bash
   printf '%s' '{"api":1,"operation":"prepare","request_id":"00000000-0000-4000-8000-000000000001","action":"create","target_id":null,"ticket":{"kind":"bug","team":"test","title":"Проба подключения","description":"Проверка настройки, не тикет.","launch_id":1}}' | env -i HOME="$HOME" PYTHONIOENCODING=utf-8 .venv/bin/python .qwen/skills/alla-launch/extensions/tickets/adapters/mcp.py --config alla-extensions/mcp-tracker.toml
   ```

   В ответе `scope` (`site` и проект) и `payload` в base64: раскодируй и проверь поля
   `tool` и `arguments` (тип, проект, описание с `alla-request:` в конце).
3. **Имена инструментов — проверка без записи.** Режим `--check` запускает сервер из
   `[server] command`, читает его список инструментов и сверяет с файлом. Он обязателен, если
   в файле нет `[search]` (иначе имена не проверит никто до настоящей отправки), и полезен
   всегда: показывает точные имена сервера для исправления:

   ```bash
   env -i HOME="$HOME" TRACKER_TOKEN="$TRACKER_TOKEN" PYTHONIOENCODING=utf-8 .venv/bin/python .qwen/skills/alla-launch/extensions/tickets/adapters/mcp.py --config alla-extensions/mcp-tracker.toml --check
   ```

   У каждого раздела должно быть «есть»; код возврата 1 и «НЕТ У СЕРВЕРА» — поправь имя по
   строке «Инструменты сервера».
4. **`search` — читающий вызов настоящего трекера**: проверяет `arguments`, язык запроса и
   `items_path`, а заодно имена всех инструментов файла. Нужен раздел `[search]`; в `scope` подставь `site` и проект из ответа шага 2:

   ```bash
   printf '%s' '{"api":1,"operation":"search","request_id":"00000000-0000-4000-8000-000000000001","action":"create","target_id":null,"scope":{"site":"https://tracker.company","project_or_queue":"TEST"},"ticket":{"kind":"bug","team":"test","title":"Проба подключения","description":"Проверка настройки, не тикет.","launch_id":1}}' | env -i HOME="$HOME" TRACKER_TOKEN="$TRACKER_TOKEN" PYTHONIOENCODING=utf-8 .venv/bin/python .qwen/skills/alla-launch/extensions/tickets/adapters/mcp.py --config alla-extensions/mcp-tracker.toml
   ```

   Успех — `{"api":1,"matches":[…]}` (пустой список тоже успех). Ошибки — по таблице раздела 7.
   Раздела `[search]` нет — пропусти. `create` и `link` в пробах **не вызывай**: они создают
   настоящие записи.
5. **Просмотр на настоящем разборе, без отправки**:
   `extensions run tickets N --run <папка разбора> --param team_N=test` (N — наименьший номер
   проблем тикета; `/alla:ticket N`, если Qwen уже перезапущен, `team_N=test` попроси передать
   словами «команда test»). Прочитай полный файл просмотра: адресат (тестовый проект), тип,
   заголовок, раздел «Все отправляемые байты UTF-8» с `tool`, `arguments` и меткой
   `alla-request`. На этом шаге отправки нет.
6. **Одна настоящая отправка в тестовый проект** — только после шагов 1–5 без ошибок и «да»
   инженера на просмотр шага 5, по шаблону `submit` из
   [references/tickets.md](../../references/tickets.md). Затем проверь тикет в трекере
   глазами инженера: заголовок, описание, тип, метка. Любой сбой здесь переводит запрос в
   `unknown` (раздел 2): для повторной проверки нужна другая проблема или новый разбор.
7. **`lookup` — проверка защиты от дублей без записи.** Если настроены `[lookup]` и
   `verify_path`, найди созданный тикет по метке; `request_id` — из ответа `show` шага 5,
   `scope` — из шага 2:

   ```bash
   printf '%s' '{"api":1,"operation":"lookup","request_id":"<request_id из show>","action":"create","scope":{"site":"https://tracker.company","project_or_queue":"TEST"}}' | env -i HOME="$HOME" TRACKER_TOKEN="$TRACKER_TOKEN" PYTHONIOENCODING=utf-8 .venv/bin/python .qwen/skills/alla-launch/extensions/tickets/adapters/mcp.py --config alla-extensions/mcp-tracker.toml
   ```

   Ждём `"outcome":"found"` и тот же тикет. `unknown` при существующем тикете — индекс ещё не
   обновился (повтори через минуту) или `verify_path`/запрос `[lookup]` не подходят: поле не
   приходит в ответе поиска, неверный язык запроса. Пока `lookup` не находит свой тикет,
   защита от дублей не работает: так и скажи инженеру.
8. **Сломай нарочно — только пробами 2–4 и 7**, не `submit`: неверный токен, несуществующий
   проект, неверное имя инструмента. Должна быть понятная строка и код 1, запись в трекере и в
   журнал не появляется.
9. **Верни боевую настройку**: убери временный ключ `test` из `[projects]` (и тестовые `site`, проекты, если менял), проверь, что в
   `config.toml` маршруты ведут в боевые проекты, а в файлах нет тестовых значений и токена.

## 7. Сообщение адаптера → что править

<!-- adapter-errors -->
| Сообщение содержит | Причина и правка |
|---|---|
| `Не удалось прочитать файл mcp-tracker.toml` | файла нет по пути из `--config` или он не TOML; путь — от корня проекта |
| `неизвестный раздел` | опечатка в имени раздела; допустимы `server`, `projects`, `kinds`, `create`, `link`, `search`, `lookup`, `lookup_link` |
| `нужна строка` | нет обязательной строки: `site` в корне или `tool` в разделе; текст ошибки называет раздел |
| `нужен раздел [server] с командой сервера` | нет `[server]` или в нём лишний ключ; допустимы `command`, `extra_path`, `timeout` |
| `command — непустой список строк` | `[server] command` не список строк, например одна строка вместо `["npx", "-y", "…"]` |
| `extra_path — список каталогов` | `[server] extra_path` не список строк |
| `timeout — число секунд от 1 до 600` | `[server] timeout` не число или вне диапазона |
| `нет раздела [create]` | без создания адаптер не работает |
| `— таблица «ключ = строка»` | `[projects]` пуст или значение не строка; то же для `[kinds]` |
| `неизвестный ключ или не таблица` | в `[….result]` опечатка в ключе; допустимы `id_path`, `id_regex`, `url_path`, `url_template`, `state_path`, `state`, `items_path`, `verify_path`, `empty_regex` |
| `нужен id_path` | `[create.result]` без `id_path` или `id_regex`; у `[search]`/`[lookup]` нужен именно `id_path` |
| `нужен url_path или url_template` | не задана ссылка на тикет |
| `неизвестная подстановка` | в `arguments` или `url_template` неизвестное имя в `{…}`; список — раздел 5 |
| `не сопоставлена с проектом в [projects]` | команда (`team_*` или `team_N`) не ключ `[projects]` |
| `должны содержать {body}` | в `arguments` создания или комментария нет `{body}`: без метки нельзя найти тикет после обрыва |
| `Область запроса не соответствует mcp-tracker.toml` | `site` или проект в `scope` пробы не совпадают с файлом: возьми `scope` из ответа `prepare`, посимвольно |
| `Область поиска не соответствует команде тикета` | `scope` пробы `search` не тот проект, что у `team` в `ticket` |
| `Поиск не настроен` | в файле нет `[search]` |
| `нужен раздел [link]` | `link` запрошен, а в файле нет `[link]` |
| `нужен target_id из поиска` | `link` без `target_id`; он берётся только из результата поиска |
| `Команда MCP-сервера не найдена` | `[server] command` не находится на безопасном `PATH`; дай путь с `/` (от корня проекта) или каталог в `extra_path` |
| `Не удалось запустить MCP-сервер` | файл не запускается: права, интерпретатор |
| `У MCP-сервера нет инструмента из mcp-tracker.toml` | неверное имя `tool`; точные имена даёт проба 3 (`--check`). Ловится в `draft`/`submit` при настроенном `[search]`; без него при настоящей отправке — **необратимая** ошибка (раздел 2) |
| `MCP-сервер не ответил вовремя` | долгий старт (`npx` скачивает пакет), нет `HOME`/токена в `adapter_env`, нет сети, мост ждёт ручного входа (OAuth); подними `[server] timeout` (меньше `adapter_timeout`) |
| `MCP-сервер завершился без ответа` | сервер упал на старте; запусти его команду вручную и посмотри его вывод |
| `MCP-сервер отклонил запрос` | сервер не принял служебный вызов (`initialize`, `tools/list`): неверная версия сервера или не MCP stdio |
| `Инструмент MCP вернул ошибку` | трекер отказал: неверный проект, тип, права токена, обязательное поле; текст ошибки сервера адаптер не показывает — смотри документацию сервера и права токена, у инженера — журнал сервера; пишущий инструмент вручную не вызывай |
| `Поиск MCP не вернул список` | `items_path` не указывает на список или ответ не JSON; сверь с настоящим ответом |
| `нет идентификатора тикета` | в элементе поиска нет `id_path` |
| `нет идентификатора созданного тикета` | в ответе создания нет `id_path`/`id_regex`; тикет **уже создан** — найди его в трекере по метке, повторно не отправляй |
| `нет ссылки на тикет` | не задан `url_template`/`url_path` или поле пусто; при создании тикет **уже создан**, повторно не отправляй |
| `найдена в нескольких тикетах` | метка встречается дважды; разбирается вручную в трекере |

Тексты ошибок сервера и его stderr адаптер наружу не выводит (в них могут быть секреты):
причину ищи по документации сервера, его журналу и правам токена. Вызывать вручную инструмент,
который пишет (создание, комментарий), нельзя: это обход просмотра и журнала запросов и
могло бы создать дубль, которого `tickets` не видит. Читающие инструменты (поиск) можно. Если ошибка
случилась уже при `submit`, запрос в `unknown`: исправь конфиг, проверь трекер по метке
`alla-request`, и для повторной проверки возьми другую проблему или новый разбор.

## 8. Ограничения

- Только stdio. Удалённый HTTP/OAuth MCP — через локальный мост в `[server] command`.
- Текст тикета — Markdown; трекеру с другой разметкой нужен свой адаптер.
- Вложения файлов, условия «если… то…» и числа из подстановок в шаблонах не выражаются: свой
  адаптер. Вложенные таблицы и списки в `arguments` (`fields = { project = { key = "{project}" } }`)
  работают, подстановки заменяются в строках на любой глубине.
- Окружение сервера — только то, что перечислено в `adapter_env`, плюс безопасный `PATH`.
  Серверу нужен `HOME` (`npx`, `uvx`) — добавь его явно.
- Пустой поиск не значит «нет тикета»: индекс трекера отстаёт. После обрыва ответа на
  создание без совпадения по метке запрос остаётся `unknown`, блокирует эти проблемы и
  требует проверки инженера; новый тикет «в обход» не создавай.
- Расширение проверено на синтетическом MCP-сервере; на настоящем трекере поведение надо
  подтвердить шагами 5–7 раздела 6.

## Готово, когда

- `extensions list` без ошибок; пробы 2–4 дают успех, проба 3 — «есть» у каждого раздела;
  просмотр содержит нужный проект, тип и метку `alla-request`;
- одна отправка в тестовый проект создала правильный тикет, а проба 7 находит его по метке
  (или инженеру прямо сказано, что `lookup` не настроен и дубли после обрыва он ищет сам);
- временный ключ `test` убран, токена нет ни в `mcp-tracker.toml`, ни в `config.toml`, ни в
  выводе;
- инженеру сказано: что включено, какие переменные окружения задать (имена из `adapter_env`),
  что перезапустить Qwen Code, что закоммитить (`alla-extensions/config.toml`,
  `alla-extensions/mcp-tracker.toml`), что боевой проект ещё не проверен.
