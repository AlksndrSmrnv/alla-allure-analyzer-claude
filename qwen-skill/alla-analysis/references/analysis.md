# Правила анализа

Кластер — группа похожих симптомов. TF-IDF и строгие ограничения по actual и шагам предотвращают опасные объединения, но не доказывают разные причины. Один дефект может проявляться в нескольких кластерах, а один кластер может содержать несколько причин.

Для каждого кластера установи наблюдаемый симптом, затем сопоставь сообщение, стек, шаг, логи и доступный код. Проверяй принадлежность лога запросу/тесту: время, correlation ID, операция, цепочка вызовов. Само наличие ERROR, HTTP 500 или таймаута не определяет первопричину. Не объявляй таймаут проблемой окружения без дополнительных свидетельств; ошибка в логе может быть ожидаемой для негативного теста или относиться к другому запросу.

Разделяй факт, гипотезу и следующую проверку. Если данных мало, пиши «причина не установлена», категория «неизвестно», уверенность «низкая». Не выдумывай сервисы, настройки, методы, дефекты и готовые исправления. Рекомендация должна вытекать из найденного кода или быть конкретной диагностической проверкой.

Категории: продукт, автотест, окружение, данные, неизвестно. Высокая уверенность требует согласованных прямых свидетельств; совпадение текстов, несколько одинаковых падений и сообщение модели не являются независимыми доказательствами. Проверяй отличающиеся примеры, а при противоречиях — дополнительные участники. Указывай смешанный состав в ограничениях и не распространяй локальную причину на весь кластер.

Источники содержат состояния received/absent/unavailable/truncated/skipped. Отсутствие ERROR в усечённом логе не доказывает отсутствия ошибок. Вложения сохраняются только в скачанном объёме. `context --source` может показать локальные данные, но не восстановить нескачанную часть. Для таких случаев укажи конкретно, каких данных не хватает.

Текущий checkout — дополнительное свидетельство, не гарантированно код запуска. Используй revision/commit из метаданных запуска, если он есть, и `project_revision`. Если сопоставление невозможно — «неизвестно»; если ревизии различаются — «не совпадает». Ссылки на код должны быть проверенными, с номером строки. Не исправляй тесты в рамках разбора.

В каждом JSON: короткий симптом, причина или неопределённость, категория и уверенность, 1–3 точные короткие цитаты с источниками (либо пустой список при полном отсутствии данных), ограничения, противоречия, следующее действие и сведения о версии кода. Держи текст кластера в пределах примерно 100–180 слов.

Общая сводка основывается на результатах всех кластеров. Связь кластеров оформляй как гипотезу, пока нет фактов, связывающих их с одной причиной. Статус «подтверждено» относится к наблюдаемой связи, а не к уверенной формулировке модели. Сохраняй исходные кластеры и отдельно перечисляй их ID в выводе о связи. Приоритизируй по охвату, влиянию и возможности проверки, а не только по размеру.
