# Порт серверного ядра: различия и сопровождение

Исходная база перенесена из серверного дерева `bd9dd31` (PR #197). Скилл намеренно самодостаточен: общий импорт из установленного Alla сделал бы перенос в проект автотестов невозможным. Это две поддерживаемые реализации, не обещание побайтовой идентичности.

| Область | Сервер | Проектный скилл |
|---|---|---|
| Детали ошибок | GET, когда нет message и trace; использует top-level trace | Та же обязательная дозагрузка + ограниченное обогащение частичных ошибок; учитывает statusDetails |
| Типы диагностики | Только непустые строки из statusDetails | Та же проверка в шагах, результатах и detail-fallback |
| Группировка | TF-IDF + complete linkage; настройки приложения | Тот же алгоритм, настраиваемые пороги/вес, эффективные настройки в снимке |
| Вес логов | Дефолт класса 0, но pipeline передаёт настройку приложения 0.15 | Класс и runtime по умолчанию 0.15; можно явно поставить 0 |
| Примеры | Самое длинное сообщение | Центральный пример по матрице сходства + до двух отличающихся |
| ID кластеров | Зависят от сигнатуры представителя и участников | Могут отличаться из-за другого представителя; ID действуют внутри снимка |
| Вложения | libmagic при наличии, MIME fallback | Консервативные сигнатуры + декодирование + проверка управляющих символов; неоднозначные данные пропускаются |
| Анализ | GigaChat, база знаний, HTML | Текущая модель Qwen Code, код проекта, Markdown |

При одинаковом нормализованном входе и одинаковых настройках состав групп должен совпадать. Отдельный тест `tests/test_qwen_skill_parity.py` в основном репозитории сравнивает наборы test result ID (а не ID кластеров, labels и представителей). Дозагрузка дополнительных данных, маскирование секретов и обработка вложений могут изменить входы, поэтому одинаковый launch не гарантирует одинаковую группировку двух pipeline.

Порядок обновления порта:

1. При изменении серверных triage, нормализации, логов или кластеризации проверить соответствующий файл скилла.
2. Изменения общей логики перенести в обе реализации с регрессионным примером либо явно зафиксировать здесь намеренное различие.
3. Выполнить ported-тесты скилла, серверные тесты затронутого компонента и parity-тест. Расхождение состава групп при одинаковых входах требует исправления либо изменения документированного контракта.
4. Изменения представителя не тестировать как идентичность серверу: отдельные тесты проверяют medoid, разнообразие примеров и воспроизводимость порядка.

Распознавание бинарных данных без libmagic не гарантирует полное совпадение с сервером: бинарный формат, полностью состоящий из печатных символов, неотличим от текста только по байтам. Скилл отклоняет известные сигнатуры, управляющие символы и неуверенное декодирование; такие вложения имеют `skipped` и не становятся доказательством отсутствия ошибки.
