# alla — разбор упавших прогонов Allure TestOps

После ночного прогона в TestOps десятки красных тестов. Чтобы понять, что случилось,
обычно приходится открывать каждый тест, читать стек и логи и гадать, кто виноват:
приложение, автотест или стенд.

**alla делает это за вас.** Это скилл для [Qwen CLI](https://github.com/QwenLM/qwen-code):
вы пишете номер прогона, а он отвечает, что сломалось, почему и что делать.

```text
/alla-launch 123456
```

## Что вы получаете

- **Несколько проблем вместо десятков красных тестов.** Похожие падения собраны в одну
  проблему. Каждый тест учитывается один раз, по последнему запуску: перезапуски не плодят
  дубли, а тесты, прошедшие со второй попытки, показаны отдельным списком. Отключённые в
  TestOps (muted) тесты не разбираются, только считаются.
- **Ответ, кто виноват.** У каждой проблемы есть причина и категория: приложение, автотест,
  стенд, тестовые данные или «не ясно». Причина подкреплена цитатами из логов и сообщений
  об ошибке, и скрипт проверяет, что каждая цитата действительно есть там, откуда агент её
  взял.
- **Готовые правки автотестов.** Если виноват сам тест, агент покажет diff и запишет его
  только после вашего «да». Правки, которые ослабляют тест (удалённая проверка, `@Disabled`,
  новый `sleep`), скрипт не пропускает.
- **Память команды.** Подтверждённые вами причины и рецепты сохраняются в базу знаний —
  папку `alla-kb/` в репозитории автотестов. Закоммитьте её, и в следующих прогонах скилл
  узнает такую проблему сразу, у любого, кто работает с репозиторием.
- **Безопасность.** TestOps скилл только читает. Код проекта меняется только с вашего
  согласия.

## Как выглядит результат

После разбора в терминале появляется краткий отчёт. Пример:

```text
## Разбор прогона #123456 — Nightly regression

[####------] 25 тестов: прошло 10, упало 15
15 упавших тестов -> 3 проблемы:
   🔴 требуют вашего внимания .... 1 (7 тестов)
   🟢 агент поправит сам ......... 1 (3 теста)
   🔵 стенд и данные ............. 1 (5 тестов)

### Коротко
Больше всего падений даёт ошибка приложения при создании заказа без адреса. Пять тестов
входа упали из-за недоступного auth-service — начните со стенда.

### 🔴 Требуют вашего внимания (1)

**Проблема 1** · 7 тестов
Заказ не создаётся: POST /orders отвечает 500.
   Агент считает: [ПРИЛОЖЕНИЕ] NullPointerException в OrderService, когда у заказа нет адреса доставки.
   Что делать:    Передать лог order-service команде заказов.

### 🟢 Агент может поправить сам (1)

**Проблема 2** · 3 теста
Тест ждёт код 200, а сервис отвечает 201.
   Агент считает: [АВТОТЕСТ] Контракт API изменился
   Правка:        `src/OrderTest.java:6` — ждёт вашего «да»

### 🔵 Стенд и тестовые данные (1)

**Проблема 3** · 5 тестов
Вход в систему не проходит: auth-service не отвечает.
   Агент считает: [СТЕНД] auth-service на стенде недоступен (connection refused).
   Что делать:    Проверить, что auth-service на стенде запущен.

Полный разбор: report.md
```

Как это читать:

1. **Шапка** показывает масштаб: 15 упавших тестов сводятся к 3 проблемам, и видно, сколько
   их в каждом разделе.
2. **«Коротко»** — вывод по всему прогону: что главное и с чего начать.
3. **Разделы** говорят, чья это работа:

   | Раздел | Что внутри | Что от вас нужно |
   |---|---|---|
   | 🔴 Требуют вашего внимания | Похоже на ошибку приложения, или причину не удалось определить | Посмотреть самому или передать команде приложения |
   | 🟢 Агент может поправить сам | Сломан автотест, и исправление понятно | Ответить «да» или «нет» на diff |
   | 🟡 Автотест сломан, но править вручную | Виноват тест, но агент не взялся править (написано почему) | Поправить тест |
   | 🔵 Стенд и тестовые данные | Недоступный сервис, отсутствующие данные | Проверить стенд и тестовые данные; код автотестов, скорее всего, ни при чём |

4. **Карточка проблемы**: первая строка — что случилось, простыми словами. «Агент считает» —
   причина с категорией в скобках. «Что делать» — первый шаг. «Правка» — файл и строка,
   которые агент предлагает изменить.

Подробности лежат в `report.md`: полные разборы, цитаты с указанием, из какого лога и
каких строк они взяты, все шаги, список тестов каждой проблемы и правки в виде БЫЛО/СТАЛО.

## Установка

Понадобятся Qwen CLI, Python 3.11+ и API-токен Allure TestOps.

**1. Скопируйте скилл в проект автотестов:** папку `qwen-skill/alla-launch/` — в
`<проект>/.qwen/skills/alla-launch/`.

**2. Попросите скилл установиться.** В Qwen CLI, запущенном в корне проекта:

```text
/alla-launch установи
```

Скилл сам создаст себе venv с зависимостями (1–3 минуты) и файл настроек.

**3. Впишите адрес TestOps и токен** в `.qwen/skills/alla-launch/.env`:

```text
ALLURE_ENDPOINT=https://testops.company.ru
ALLURE_TOKEN=<ваш токен>
```

Токен в чат не пишите: скилл его не спрашивает и файл `.env` не читает.

**4. Готово.** Разбирайте прогоны командой `/alla-launch 123456`.

Если установка не прошла (нет нужного Python, pip не достучался до PyPI), агент покажет, что
поправить.

> 💡 Чтобы не подтверждать каждый шаг, разрешите в Qwen CLI команду скилла — с относительным
> путём `python3 .qwen/skills/alla-launch/scripts/alla_skill.py` и с абсолютным (так её
> печатает скрипт) — и запись в `alla-reports/`. Весь `python3` не разрешайте, а
> автопринятие правок не включайте: агент сможет менять код без diff.

## Как пользоваться

Обычный разбор выглядит так.

**1. Запустите разбор.** Напишите номер прогона, вставьте ссылку на запуск или скажите
своими словами:

```text
/alla-launch 123456
```

```text
разбери прогон https://testops.company.ru/launch/123456
```

Дальше агент работает сам: выгружает прогон, разбирает каждую проблему и в конце
показывает краткий отчёт. Отвечать ему по ходу не нужно. Большой прогон займёт больше
времени: от 10 проблем агент разбирает их параллельно субагентами.

**2. Начните с 🔴.** Это проблемы, которым нужен человек. Полный разбор любой из них — в
`report.md`.

**3. Решите по правкам из 🟢.** Агент по очереди покажет diff каждой правки и спросит,
применить ли её.

```text
да
```

```text
верни правку 2
```

Тесты агент не запускает: прогоните исправленный тест сами.

**4. Поправьте агента, если он ошибся.** Назовите номер проблемы и настоящую причину.
Агент сохранит её в базу знаний проекта:

```text
в проблеме 3 причина — истёк сертификат на стенде, лечится перевыпуском
```

Если разбор верный и его стоит запомнить — «да, запомни». Если агент привязал проблему к
известной причине из базы знаний по ошибке — «эта известная проблема тут ни при чём».
Новые записи появятся в `alla-kb/`: закоммитьте их, и в следующих прогонах скилл узнает эту
проблему у всей команды.

Номер «Проблема N» в чате — тот же, что в отчёте.

## Что ещё умеет

- **Помнит прошлые разборы.** Отмечает проблемы, которые уже встречались раньше. Эта история
  хранится только на вашей машине, у коллег своя.
- **Связывает похожие проблемы.** Если у двух проблем, похоже, одна причина, отчёт это
  помечает.
- **Замечает, когда в одну проблему попали разные сбои.** Агент так и пишет и не выдаёт
  причину одного сбоя за общую.
- **Работает с многомодульными проектами.** В Java/Kotlin-проекте на Gradle или Maven база
  знаний ведётся отдельно для каждого модуля.
- **Продолжает прерванный разбор.** Повторный `/alla-launch` того же прогона в течение суток
  продолжает прерванный разбор, а не начинает заново.
- **Оценивает качество разбора.** По просьбе «проверь разбор» смотрит, как прошёл разбор и
  подтверждаются ли диагнозы данными. Результат — в папке `review/`. В ней есть сводка из
  одних чисел, без логов и имён тестов: её можно отправить разработчикам скилла.

## Настройки

Настройки задаются в `.env` скилла или переменными окружения; переменные окружения важнее
файла.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `ALLURE_ENDPOINT` | — | Адрес TestOps, без `/api` в конце (обязательно) |
| `ALLURE_TOKEN` | — | API-токен (обязательно) |
| `ALLURE_SSL_VERIFY` | `true` | Проверка TLS-сертификата TestOps. Без крайней нужды не выключайте, см. ниже |
| `ALLURE_CLUSTERING_THRESHOLD` | `0.60` | Насколько похожими должны быть падения, чтобы попасть в одну проблему. Чем ниже порог, тем больше падений объединяется |

**Корпоративный прокси с собственным сертификатом.** Отключать проверку TLS не нужно:
укажите файл с корпоративным корневым сертификатом в переменной окружения `SSL_CERT_FILE`.
В `.env` скилла эта переменная не читается. Файл заменяет встроенный список доверенных
сертификатов, поэтому в нём должны быть все нужные корневые сертификаты.
`ALLURE_SSL_VERIFY=false` — только временный обход: проверка отключается полностью, и
API-токен сможет перехватить посредник.

Полный список настроек — в [`references/setup.md`](qwen-skill/alla-launch/references/setup.md#настройки).

## Ограничения

- Прогон задаётся только номером или ссылкой: по имени запуска скилл не ищет.
- Ошибки и логи прогона уходят модели, с которой работает Qwen CLI, как есть, без
  маскирования секретов.
- Агент читает код в том виде, в каком он лежит у вас сейчас. Если прогон шёл на другой
  версии кода, строки, на которые ссылается разбор, могут не совпасть.

## Как это устроено

Python-скрипт скилла выгружает прогон из TestOps, отбирает из логов строки, связанные с
ошибкой, группирует падения и готовит для модели задания. Анализ пишет модель Qwen CLI: по
заданию и коду вашего проекта. Скрипт проверяет каждый её ответ (формат, цитаты, ссылки на
код) и собирает отчёт.

<details>
<summary>Команды скрипта (их вызывает агент, самому не нужно)</summary>

Все команды выглядят так: `python3 .qwen/skills/alla-launch/scripts/alla_skill.py <команда>`.
Первая строка вывода — `STATUS: …`, у `setup` статус печатается в конце, после вывода pip.

| Команда | Что делает |
|---|---|
| `setup [--python PATH] [-- pip-аргументы]` | Создаёт окружение скилла и `.env` из образца |
| `check` | Проверяет Python, настройки, базу знаний и доступ к TestOps |
| `prepare <ID или ссылка> [--fresh]` | Выгружает прогон и готовит задания. Неоконченный разбор моложе суток продолжает, `--fresh` начинает заново. Разбор старше суток продолжает только `next <папка>` |
| `next [папка] [--workers N \| --serial]` | Следующий шаг разбора. `--workers` — сколько субагентов (1–8), `--serial` — без них |
| `apply N --run DIR [--yes --diff ХЭШ]` | Показывает diff правки автотеста. С `--yes --diff` записывает её |
| `revert N --run DIR` | Отменяет правку, если файл после неё не трогали |
| `remember N --run DIR [--from-analysis]` | Сохраняет причину и рецепт проблемы N в `alla-kb/` из `feedback/NN.md` ([формат](qwen-skill/alla-launch/references/feedback.md)). Без этого файла ничего не сохраняет и отвечает `STATUS: fix`. С `--from-analysis` сохраняет подтверждённый разбор агента |
| `reject N <id> --run DIR` | Помечает, что запись базы знаний `<id>` не относится к проблеме N |
| `skip N --run DIR [--reason …]` | Пропускает проблему N |
| `clean [--older-than-days N] [--dry-run]` | Удаляет старые папки разборов (по умолчанию старше 14 дней) |
| `review [папка] [--no-model]` | Проверяет законченный разбор: ход, правила, качество диагнозов |
| `verify N … --run DIR` | Проверяет разборы, ничего не записывая (для субагентов) |

</details>
